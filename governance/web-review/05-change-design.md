# Level 5 — проектирование изменения ChatGPT Web

**Канонический файл:** [`05-change-design.md`](<./05-change-design.md>).
**Точка входа:** [`00-workflow.md`](<./00-workflow.md>).

Level 5 — не автономное редактирование Codex. Это работа ChatGPT Web по созданию новой candidate version на основании подтверждённых `FAIL` Levels 1–4 или `REPO FAIL`.

## Вход

```text
actual current note
+
подтверждённые FAIL / REPO FAIL
+
проверенные факты и ограничения
+
защищённый материал
```

Web не начинает содержательную правку только потому, что существует другой стилистический вариант.

## Обязательные свойства change design

Web обязан:

- связать каждое существенное изменение с подтверждённой причиной;
- исправить только подтверждённые проблемы;
- сохранить уже корректный материал;
- сохранить полезный смысл, а не обязательно старую формулировку;
- выбрать минимально достаточное изменение;
- сохранить техническую глубину, условия, причинность, ограничения и различия;
- не удалять полезную деталь только из-за длины страницы;
- при перегруженности сначала рассмотреть порядок, группировку, форму или перенос;
- соблюдать Level 1–2 и не изобретать новый устойчивый тип блока;
- не менять автоматически управляемые `NOTE-NAV-*` и `SECTION-NAV-*` вручную;
- не переписывать корректный код только ради стиля;
- соблюдать zero-trade-off защиту Level 4.

## Проза

Для исправления понятности, последовательности, полноты, смысловой нагрузки или избыточности Web формулирует exact итоговый текст до Codex.

Web не передаёт Codex выбор между materially different вариантами объяснения.

При работе с исследовательским отчётом Web использует его как evidence, но заново формулирует материал для целевого читателя. Язык отчёта не считается готовой учебной прозой.

Сокращение, объединение или перенос не должны заменять конкретную причинную модель абстрактной фразой или метафорой, если читателю снова придётся восстанавливать субъект, действие, условие, причину или следствие.

## Структура

Если проблема полностью детерминирована правилами Levels 1–2, Web может выдать `BOUNDED_STRUCTURE` с protected prose.

- Если Web задаёт exact итоговый файл/фрагмент, кандидат можно проверить primary/fresh до Codex и после исполнения подтвердить по verification contract.
- Если Web задаёт только structural postcondition, actual итоговый файл появляется после Codex и проходит применимый primary review; full-review заметка получает fresh review exact actual `Vn`.

Если содержанию требуется новый устойчивый тип блока, сначала меняется governance отдельной задачей. Codex не изобретает блок локально.

## Код

Web может:

- дать exact кодовый фрагмент;
- либо выбрать `BOUNDED_CODE` и задать интерфейс, поведение, учебную функцию, ограничения и проверки.

Codex может реализовать код внутри этого контракта. Web затем проверяет actual код, его корректность и соответствие объяснению.

## Generated regions и repository maintenance

Если изменение состава или порядка заметок требует нумерации и навигации, change design задаёт:

- section;
- точное место в смысловом маршруте;
- ожидаемое название;
- exact planned path map `old → new`;
- protected-content manifest для Web-authored прозы, кода, подписей ссылок и идентичности тематических целей;
- явный список generated regions;
- разрешённые переписывания только назначений внутренних ссылок, необходимые из-за planned path map;
- разрешение на `REPOSITORY_MAINTENANCE`.

Конкретные навигационные блоки формируют штатные scripts. `renumber_notes.py --write` может переписывать назначения ссылок и вне generated regions, но только в соответствии с approved path map; подписи ссылок, окружающая проза, код и смысловая цель связи остаются защищёнными.

## Крупная правка

Крупной считается правка с риском потери самостоятельного полезного смысла: изменение центральной модели, одновременная перестройка нескольких ключевых блоков, удаление/объединение/перенос самостоятельного аспекта.

Для неё Web ведёт временную карту:

| Исходный аспект | Действие | Итоговое место или подтверждённое основание удаления |
|---|---|---|
| ... | сохранить / переписать / перенести / объединить / удалить | ... |

Карта не добавляется в заметку.

## Выход

Level 5 создаёт bounded execution specification:

```text
Analysis-base
Candidate version
Verification contract: full-file hash or protected-content manifest
Execution mode
Allowed paths
Confirmed FAILs
Required semantic result
Exact prose/replacements or bounded postcondition
Protected material
Allowed generated regions
Allowed path/link-destination rewrite map
Task-specific checks
STOP conditions
Publication requirement
```

Level 5 не подтверждает собственный результат. Exact Web-кандидат проходит primary Levels 1–4 и применимый fresh Web review до исполнения. Candidate, который возникает только после `BOUNDED_CODE` или postcondition-only `BOUNDED_STRUCTURE`, проходит применимый primary review и fresh gate по правилам `00-workflow.md` на actual GitHub result.
