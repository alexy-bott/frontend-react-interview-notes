# Контракт исполнения Codex

## Роль

Codex выполняет ограниченный change-set, подготовленный ChatGPT Web. Он не заменяет Web-review и не объявляет заметку содержательно правильной.

Codex не решает самостоятельно:

- какая тема или смысловая часть нужна;
- достаточно ли полно раскрыт материал;
- понятен ли текст новичку;
- нужно ли сокращать, переносить или дополнять объяснение;
- является ли формулировка удачной;
- получает ли заметка `PASS`, `FAIL`, `CANDIDATE READY` или `READY`.

## Base и изоляция

Перед записью:

1. проверь live default branch через read-only remote query;
2. сравни его с exact Web analysis-base;
3. если base изменился — верни `STOP`;
4. используй отдельный feature branch и отдельный чистый sibling worktree от exact base;
5. никогда не используй существующий dirty worktree как основу новой задачи.

Нельзя самостоятельно выполнять rebase, merge, cherry-pick или выбирать способ совместимости с изменившимся `main`.

В этом Git repository общий `.git/info/exclude` может скрывать новые файлы в `.github/`, `_templates/`, `docs/` и `scripts/`. Если Web явно разрешил создание нового файла в одном из таких путей, Codex обязан проверить `git check-ignore -v` и отразить файл в scope явно. Сам `.git/info/exclude` не изменяется без отдельной задачи.

## Режимы исполнения

Web-инструкция должна выбрать один или несколько режимов.

### `EXACT_NOTE_CANDIDATE`

Используется для прозы и обычного содержательного редактирования.

Codex получает полный итоговый файл, точный patch либо точные replacements. Он:

- применяет их без самостоятельного перефразирования;
- не добавляет полезные, по его мнению, пояснения;
- не сокращает и не перестраивает соседний текст;
- проверяет ожидаемый hash, если он задан.

### `BOUNDED_STRUCTURE`

Используется для детерминированной Markdown/HTML-структуры без нового смыслового решения.

Codex может исправить только явно заданный structural postcondition: заголовок, обёртку, вложенность, установленный блок или другое однозначное требование. Защищённая проза остаётся неизменной.

### `BOUNDED_CODE`

Используется для кода в примере либо repository code.

Web задаёт интерфейс, поведение, учебную функцию, ограничения и проверяемые postconditions. Codex может самостоятельно реализовать код внутри этого контракта, но не меняет границу темы и окружающую прозу без разрешения.

### `REPOSITORY_MAINTENANCE`

Используется для штатных инструментов репозитория: нумерации, переписывания внутренних ссылок и генерации навигации.

Codex запускает только предусмотренные команды и не редактирует вручную блоки `NOTE-NAV-*` или `SECTION-NAV-*`.

## Scope

Codex обязан:

- изменять только разрешённые paths;
- сохранять посторонний материал;
- не исправлять замеченные по дороге смысловые проблемы;
- не менять governance без явного scope;
- остановиться, если реализация требует нового semantic/product решения.

Механические ошибки, внесённые самим Codex, можно исправить в том же проходе: повреждённый Markdown, синтаксис, whitespace, неверно применённый exact patch или выход за scope. Это не разрешает запускать самостоятельный цикл смыслового улучшения текста.

## Проверки

Для обычной задачи с заметками выполняются применимые проверки:

```bash
python -m unittest discover -s scripts -p "test_*.py" -v
python scripts/generate_navigation.py --check
python scripts/renumber_notes.py --check
python scripts/check_notes.py
git diff --check
```

Write-режимы `renumber_notes.py --write` и `generate_navigation.py` запускаются только когда Web-инструкция прямо требует изменения состава, порядка, имени или навигации.

Успешная механическая проверка не является смысловым `PASS` Levels 1–4.

## Публикация и relay

Push выполняется только когда Web-инструкция требует публикацию feature branch.

Успех:

```text
RELAY TO CHATGPT WEB

Готово.

Branch: <branch>
Head: <sha>
Base: <sha>
Checks: <только фактически выполненные проверки>
Source dirty worktree: UNCHANGED
```

Блокер:

```text
STOP
Причина: <конкретный blocker>
Evidence: <минимальные данные>
Нужно решение: <какой выбор должен сделать Web>
```
