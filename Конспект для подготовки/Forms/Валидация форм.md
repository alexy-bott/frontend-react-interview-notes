#### Ответ на 60 секунд

Валидация формы бывает на нескольких уровнях. HTML constraint validation даёт базовый UX: `required`, `type="email"`, `minLength`, `pattern`. Client schema validation через Zod/Yup помогает описать контракт формы, получить типы и нормальные сообщения ошибок. Server validation остаётся обязательной, потому что клиентскую проверку можно обойти, а часть правил знает только backend.

Для React Hook Form часто используют resolver: он связывает библиотеку форм со схемой. Например, `zodResolver(schema)` валидирует values по Zod-схеме и возвращает ошибки в `formState.errors`. Граница процесса: form values валидируются схемой, нормализуются в DTO, отправляются в API, а server errors возвращаются обратно в форму.

#### Ключевая схема

| Уровень | Что ловит | Ограничение |
| --- | --- | --- |
| HTML validation | пустые поля, email, min/max, pattern | базовые правила |
| Client schema | структура, типы, cross-field rules | можно обойти |
| Server validation | бизнес-правила, права, уникальность | позже по UX |
| Runtime validation API response | неожиданный backend response | нужен API boundary |

#### Развернутый ответ

HTML validation подходит для простых ограничений и базового UX: `required`, `type="email"`, `min`, `max`, `pattern`. Но кастомные UI-компоненты, сложные сообщения, зависимые поля и cross-field rules часто требуют schema/custom validation.

Схема описывает ожидаемую форму данных: email, password length, numbers, optional fields, nested objects, arrays. Zod удобен тем, что из схемы можно вывести TypeScript-тип через `z.infer`, а через resolver связать validation с React Hook Form.

Cross-field validation нужна, когда одно поле зависит от другого: confirm password, date range, at least one contact method, conditional required fields. Такие правила обычно держат в schema refinement или custom validator, чтобы они не расползались по JSX.

Backend может вернуть field errors и form-level errors. Field errors маппят на конкретные поля через `setError("email", ...)`, а общую ошибку показывают в error summary или над submit-кнопкой. Server validation остаётся источником истины для бизнес-правил, прав доступа и уникальности.

Validation mode выбирают по UX и стоимости проверки. `onSubmit` снижает шум и подходит большинству форм. `onBlur` полезен для полей, где ошибка нужна после ухода из поля. `onChange` даёт live feedback, но может раздражать и быть дороже для больших форм или async validation.

Async validation отделяют от обычной schema validation. Проверка уникальности email, промокода или доступности username требует сети, поэтому для неё нужны debounce, отмена устаревшего запроса и защита от race condition. Часто такие проверки запускают на blur или submit, а не на каждый символ.

> [!faq]+ Уточнения
> - HTML validation даёт быстрые базовые ограничения, но не покрывает сложные правила.
> - Schema validation описывает структуру формы и cross-field rules.
> - `z.infer` выводит TypeScript-тип из Zod-схемы.
> - Server errors маппят на field errors или form-level error.
> - `onSubmit`, `onBlur`, `onChange` выбирают по UX и стоимости проверки.
> - Async validation требует debounce/abort/race protection.

#### Пример

```tsx
import { zodResolver } from "@hookform/resolvers/zod";
import { useForm } from "react-hook-form";
import { z } from "zod";

const LoginSchema = z.object({
  email: z.string().email("Invalid email"),
  password: z.string().min(8, "Password must be at least 8 characters"),
});

type LoginValues = z.infer<typeof LoginSchema>;

function LoginForm() {
  const {
    register,
    handleSubmit,
    setError,
    formState: { errors },
  } = useForm<LoginValues>({
    resolver: zodResolver(LoginSchema),
    defaultValues: {
      email: "",
      password: "",
    },
  });

  const onSubmit = async (values: LoginValues) => {
    const result = await login(values);

    if (!result.ok) {
      setError("email", { message: "Email or password is incorrect" });
    }
  };

  return (
    <form onSubmit={handleSubmit(onSubmit)}>
      <input {...register("email")} />
      {errors.email && <p role="alert">{errors.email.message}</p>}

      <input type="password" {...register("password")} />
      {errors.password && <p role="alert">{errors.password.message}</p>}

      <button type="submit">Sign in</button>
    </form>
  );
}
```

#### Частые ошибки

- Считать client validation достаточной защитой.
- Дублировать разные правила в HTML, schema и backend без единого источника смысла.
- Валидировать число как строку и забывать нормализацию.
- Показывать ошибку без связи с полем.
- Запускать дорогую async validation на каждый символ.
- Не обрабатывать backend field errors.
- Использовать `z.infer`, но потом отправлять другой DTO без явного mapping.
