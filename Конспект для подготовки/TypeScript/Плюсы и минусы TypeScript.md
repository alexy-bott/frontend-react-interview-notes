#### Быстрый ответ

TypeScript добавляет к JavaScript статическую проверку типов. До запуска приложения компилятор проверяет, согласованы ли аргументы функций, свойства объектов, варианты состояний и контракты модулей. Это раньше обнаруживает часть ошибок, улучшает автодополнение и делает большие изменения безопаснее.

TypeScript особенно полезен в растущем проекте: типы связывают API между модулями, помогают находить все места, затронутые рефакторингом, и документируют допустимые состояния. Цена — настройка компилятора, поддержка типов, более высокий порог входа и иногда сложные сообщения об ошибках.

Граница TypeScript: он проверяет статическую модель кода, а не реальные данные и не бизнес-логику. Типы стираются при сборке, поэтому ответ API, значение из `localStorage` и пользовательский ввод нужно проверять в runtime.

#### Какую задачу решает TypeScript

JavaScript определяет типы значений во время выполнения. Если функция ожидает объект с полем `name`, ошибка может проявиться только на конкретном пользовательском сценарии. TypeScript строит модель допустимых значений заранее и проверяет операции над ними:

```ts
type User = {
  id: string;
  name: string;
};

function formatUser(user: User): string {
  return `${user.id}: ${user.name}`;
}

formatUser({ id: "42" });
// ошибка до запуска: отсутствует name
```

Компилятор не доказывает, что программа полностью правильна. Он исключает операции, которые противоречат объявленным или выведенным типам.

#### Что даёт проекту

**Раннее обнаружение несогласованностей.** Ошибки в именах полей, nullable-значениях, аргументах и возвращаемых типах видны во время разработки и в CI.

**Безопаснее рефакторинг.** После изменения контракта компилятор показывает места, которые нужно обновить. Это особенно ценно для общих компонентов, store, API-клиентов и библиотек.

**Точнее инструменты редактора.** Автодополнение, переход к определению, поиск использований и переименование опираются на граф типов, а не только на текст.

**Явные модели состояний.** Union и discriminated union позволяют описать допустимые варианты UI и запретить невозможные сочетания полей.

**Проверяемые контракты.** Типы связывают функции, компоненты и модули. В отличие от комментария, устаревший контракт обычно приводит к ошибке компиляции.

#### Цена и ограничения

**Типы нужно проектировать и поддерживать.** Неточная модель создаёт ложное чувство безопасности, а слишком сложная — замедляет чтение кода.

**Интеграция требует настройки.** Нужны согласованные `tsconfig`, версии TypeScript и библиотек типов, typecheck в CI, правила для generated-кода и сторонних пакетов.

**Сложная система типов увеличивает когнитивную нагрузку.** Generics, conditional и mapped types полезны, пока уменьшают дублирование. Если тип сложнее публичного API, явный контракт может быть лучше.

**Статическая проверка не покрывает runtime.** Type assertions, generics и interfaces не проверяют JSON, DOM и другие внешние значения.

**TypeScript намеренно не полностью sound.** Ради совместимости с JavaScript система допускает некоторые небезопасные случаи. Поэтому строгий конфиг и понятные границы доверия важнее самого расширения `.ts`.

#### Что происходит при сборке

TypeScript анализирует программу, сообщает ошибки и преобразует TypeScript-синтаксис в JavaScript либо только проверяет типы при `noEmit`. Большинство типов исчезает:

```ts
type User = { name: string };

function greet(user: User) {
  return `Привет, ${user.name}`;
}
```

После удаления типов остаётся обычная JavaScript-функция. Она не проверяет входной объект автоматически.

Во frontend-проектах JavaScript часто генерирует Vite, SWC, Babel или esbuild, а `tsc --noEmit` запускается отдельно для проверки типов. Успешная транспиляция не означает успешный typecheck.

#### Где TypeScript не заменяет другие проверки

| Задача | Что требуется кроме TypeScript |
| --- | --- |
| Ответ API соответствует контракту | runtime validation: guard или schema |
| Функция правильно реализует бизнес-правило | unit и integration tests |
| Интерфейс доступен с клавиатуры | accessibility-проверки |
| Код работает во всех браузерах | runtime и cross-browser tests |
| Изменение не ухудшило performance | измерения и профилирование |
| Уязвимость отсутствует | security-проверки и корректная архитектура |

#### Критерий выбора

Для долгоживущего командного приложения TypeScript обычно окупается за счёт рефакторинга и устойчивых контрактов. В маленьком одноразовом скрипте его настройка может стоить больше, чем потенциальная польза. Важны не размер файла и мода на инструмент, а срок жизни кода, количество участников, сложность моделей и цена ошибки.

#### Ключевые уточнения

- Польза TypeScript зависит от качества моделей и строгости `tsconfig`.
- Тип описывает ожидание компилятора, но не происхождение и достоверность значения.
- `any` локально отключает гарантии и может распространиться через возвращаемые значения.
- TypeScript дополняет tests и runtime validation, а не заменяет их.
- Простые и точные типы полезнее сложных вычислений, которые команда не может уверенно поддерживать.
