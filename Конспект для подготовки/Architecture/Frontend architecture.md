#### Ответ на 60 секунд

Архитектура frontend-приложения - это не выбор папок ради папок, а способ держать код понятным при росте продукта. Рабочая архитектура разделяет ответственность: UI отображает состояние, бизнес-логика описывает правила, API-слой общается с backend, state-слой управляет данными, routing связывает экраны, а shared-код не превращается в свалку.

Frontend-архитектуру описывают через границы и зависимости. Модули должны зависеть от более стабильных слоёв, а не тянуть друг друга циклически. Feature-код держат рядом: компоненты, hooks, queries, utils и тесты одной фичи находятся близко. Общие компоненты и утилиты выносятся только тогда, когда они действительно переиспользуются и имеют понятный контракт.

#### Ключевая схема

```text
app shell
-> routing
-> pages/screens
-> features
-> entities/domain
-> shared UI/lib/api
```

| Слой | За что отвечает |
| --- | --- |
| App shell | провайдеры, router, глобальная инициализация |
| Pages/screens | композиция фич на уровне маршрута |
| Features | пользовательские сценарии и actions |
| Entities/domain | доменные модели и правила |
| Shared UI | переиспользуемые визуальные компоненты |
| Shared lib/api | инфраструктура, helpers, базовый API-клиент |

#### Развернутый ответ

Качество frontend-архитектуры видно по локальности изменений. Если изменение одной фичи требует править половину приложения, значит границы модулей не помогают. Устойчивую архитектуру держат понятные зависимости, минимальная скрытая связность, тестируемость и явные контракты между слоями.

Структура папок должна отражать масштаб продукта. Для небольшого приложения достаточно простого разделения `components`, `pages`, `api`, `lib`. Для крупного продукта удобнее feature-based структура: UI, model, api, hooks и tests одной фичи лежат рядом, а не разбросаны по техническим папкам. Так проще удалить, заменить или проверить конкретный сценарий.

Dependency direction задаёт, кто от кого может зависеть. Например, shared-слой не импортирует конкретную feature, а feature не лезет во внутренности другой feature. Если это правило нарушается, появляются циклы, неожиданные side effects и сложность при рефакторинге.

Общий код выносят после появления реального повторного использования и понятного контракта. Ранний `shared` часто превращается в слишком абстрактный компонент, который сложнее менять, чем две локальные реализации. Shared должен быть стабильнее feature-кода, иначе он начинает тормозить изменения.

Бизнес-логику не прячут только в JSX. Правила сценария можно держать в доменных функциях, hooks, state-machine, query/mutation layer или service-функциях. UI-компонент тогда отвечает за отображение и связывание событий, а смысл сценария можно тестировать и менять отдельно.

> [!faq]+ Уточнения
> - Архитектура оценивается по локальности изменений, понятным границам и управляемым зависимостям.
> - Маленькому приложению не нужна тяжёлая структура, крупному продукту помогает feature-based организация.
> - Shared-слой должен иметь стабильный контракт и не знать о конкретных features.
> - Dependency direction защищает от циклов и скрытой связности.
> - Бизнес-логику выносят из JSX, когда она становится правилом сценария, а не деталями отображения.

#### Пример

```text
src/
  app/
    providers/
    router/
  pages/
    ProfilePage/
  features/
    update-profile/
      ui/
      model/
      api/
      tests/
  entities/
    user/
      model/
      api/
  shared/
    ui/
    lib/
    api/
```

Здесь фича `update-profile` может использовать `entities/user` и `shared`, но `shared` не знает о конкретной фиче.

#### Частые ошибки

- Делать технические папки, где каждая фича размазана по всему проекту.
- Выносить всё в `shared` без строгого смысла.
- Позволять feature-модулям импортировать внутренности друг друга.
- Держать API-вызовы прямо в UI-компонентах без единой политики ошибок и отмены.
- Называть архитектурой только выбор Redux, React Query или папки `components`.
