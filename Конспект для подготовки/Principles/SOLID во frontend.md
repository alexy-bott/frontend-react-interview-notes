#### Быстрый ответ

SOLID — пять принципов проектирования, которые помогают локализовать изменения, сохранять понятные контракты и уменьшать зависимость бизнес-логики от инфраструктуры. Они появились в объектно-ориентированном проектировании, но применимы не только к классам: во frontend их используют на уровне функций, компонентов, хуков, сервисов и модулей.

- **SRP:** у модуля одна связная ответственность и одна основная причина измениться.
- **OCP:** новые варианты добавляются через предусмотренную точку расширения без постоянной правки стабильного ядра.
- **LSP:** реализацию общего контракта можно заменить другой без нарушения ожидаемого поведения.
- **ISP:** потребитель зависит только от небольшого контракта, который действительно использует.
- **DIP:** высокоуровневая логика и инфраструктурные детали зависят от общего контракта, определённого потребностями сценария.

SOLID не является требованием создать интерфейс для каждой функции. Принципы полезны там, где изменение одной части затрагивает несвязанные части, реализацию трудно заменить или проверить изолированно, а общий API обещает поведение, которое его варианты не соблюдают.

#### Какую проблему решает SOLID

В связанном коде одно требование распространяет изменения по многим файлам. Например, смена API затрагивает JSX, бизнес-правила и тесты; добавление нового вида таблицы увеличивает общий компонент очередным условием; тест формы требует настоящий backend.

SOLID помогает провести границы:

```text
пользовательский сценарий -> небольшой контракт -> конкретная реализация
           |                       |
      правило продукта       HTTP, SDK, storage, UI
```

Граница считается полезной, если она делает изменение локальнее и сохраняет понятное направление зависимостей. Количество файлов, интерфейсов и слоёв само по себе качество не повышает.

#### Принципы

##### SRP: одна ответственность

Single Responsibility Principle требует, чтобы модуль отвечал перед одной группой требований, то есть имел одну основную причину для изменения. «Одна ответственность» не означает «одна функция в файле»: несколько функций могут вместе реализовывать один связный сценарий.

`LoginForm`, который одновременно отображает поля, проверяет бизнес-правила, формирует HTTP-запрос, преобразует DTO, показывает уведомления и отправляет аналитику, меняется из-за требований дизайна, backend-контракта, продукта и аналитики. DTO (Data Transfer Object) — структура данных транспортного контракта, например объект из ответа backend. Эти причины можно разделить:

- компонент отвечает за разметку и взаимодействие;
- схема или функция — за правила валидации;
- сценарий или хук — за последовательность отправки;
- API-адаптер — за HTTP и DTO;
- отдельная зависимость — за аналитику.

Разделение оправдано, когда части изменяются независимо. Если небольшой компонент и его локальная логика всегда меняются вместе, их разнос по разным слоям может только усложнить чтение.

##### OCP: расширение без постоянной правки ядра

Open/Closed Principle предлагает оставлять стабильную часть открытой для расширения и закрытой для повторяющихся изменений. Речь не о запрете редактировать существующий код, а о том, чтобы известные варианты подключались через явный контракт.

Например, таблица может отвечать за разметку строк, навигацию по страницам и состояния загрузки, а колонки и действия получать через конфигурацию. Новая предметная таблица добавит собственный набор колонок без условия `if (page === ...)` внутри общего ядра.

Точку расширения создают, когда ось изменений уже известна: несколько способов сортировки, оплаты или отображения ячейки. Универсальный API плагинов для единственного сценария нарушит простоту и YAGNI, даже если формально следует OCP.

##### LSP: поведенческая заменяемость

Liskov Substitution Principle требует, чтобы клиент общего контракта корректно работал с любой его реализацией. Совпадения методов или TypeScript-типов недостаточно: должны сохраняться значимые свойства поведения.

Реализация не должна неожиданно требовать более строгие входные данные, возвращать более слабый результат или нарушать обещанные состояния. Если общий `Button` обещает поддержку `disabled`, клавиатуры и фокуса, вариант, отрисованный как ссылка, не может молча выполнить действие в состоянии `disabled`. Возможны два честных решения: обеспечить одинаковое наблюдаемое поведение или разделить контракты `Button` и `Link`.

Структурная типизация TypeScript проверяет форму значения, но не доказывает семантику. Две реализации могут соответствовать одному `interface` и по-разному обрабатывать ошибку, отмену запроса или кеширование. Эти гарантии фиксируют в контракте и проверяют contract tests — одним набором тестов, который запускают для каждой реализации контракта.

##### ISP: контракты со стороны потребителя

Interface Segregation Principle предлагает не заставлять потребителя зависеть от данных и операций, которые ему не нужны. Контракт проектируется под роль потребителя, а не копирует самую большую доменную сущность.

`Avatar` достаточно получить `name` и `avatarUrl`; весь `User` связывает его с полями прав, настроек и API-моделью. Узкий props-контракт упрощает повторное использование и тестирование, а изменения большой модели реже затрагивают компонент.

Деление имеет границу. Десятки одноразовых интерфейсов из одного поля не помогают, если они всегда используются и меняются вместе. Цель ISP — уменьшить ненужную связанность, а не минимизировать число свойств любой ценой.

##### DIP: зависимость от политики, а не инфраструктуры

Dependency Inversion Principle разделяет высокоуровневую политику и низкоуровневые детали. Сценарий входа определяет, что ему нужна операция `login(credentials)`, а HTTP-адаптер реализует этот контракт через `fetch`, RTK Query или SDK. Такой контракт доступа к внешней системе часто называют gateway. Бизнес-сценарий не создаёт конкретный клиент внутри себя.

```text
LoginForm -> сценарий login -> AuthGateway <- HttpAuthGateway
                                    ^
                         тестовая реализация
```

Направление зависимости в исходном коде идёт к контракту сценария. Конкретная реализация подключается на внешнем уровне приложения — в composition root, то есть в месте, где собираются зависимости.

Dependency injection — способ передать реализацию через аргумент, props или context. Это не синоним DIP: можно внедрить конкретный сложный сервис без полезной инверсии, а небольшой модуль может следовать DIP без DI-контейнера.

#### Где применяется во frontend

| Ситуация | Проблема | Применение принципа |
| --- | --- | --- |
| Компонент содержит JSX, валидацию, HTTP и преобразование DTO | несвязанные требования меняют один модуль | SRP: разделить UI, сценарий, правила и API-адаптер |
| Общая таблица растёт через `isUsersPage`, `isAdmin` и другие флаги | каждый вариант изменяет стабильное ядро | OCP: передавать колонки и действия через ограниченный контракт |
| Варианты общего UI-компонента по-разному поддерживают клавиатуру и `disabled` | замена меняет наблюдаемое поведение | LSP: выровнять гарантии или разделить контракты |
| Компонент получает большой объект, но использует два поля | он зависит от чужих изменений модели | ISP: передать небольшой props-контракт или модель для отображения (view model) |
| Сценарий создаёт `new ApiClient()` внутри | инфраструктуру трудно заменить и тестировать | DIP: сценарий зависит от операции, а HTTP-клиент реализует её |
| Тест пользовательского сценария требует настоящий сервер | политика смешана с транспортом | SRP и DIP: подставить управляемую тестовую реализацию gateway, API-интеграцию проверить отдельно |

#### Пример

Сценарий входа зависит от собственного небольшого контракта:

```ts
type Credentials = {
  email: string;
  password: string;
};

type User = {
  id: string;
  name: string;
};

type AuthGateway = {
  login(credentials: Credentials): Promise<User>;
};

function createLogin(authGateway: AuthGateway) {
  return async function login(credentials: Credentials): Promise<User> {
    if (!credentials.email.includes("@")) {
      throw new Error("Email is invalid");
    }

    return authGateway.login(credentials);
  };
}
```

HTTP остаётся деталью внешней реализации:

```ts
const httpAuthGateway: AuthGateway = {
  async login(credentials) {
    const response = await fetch("/api/login", {
      method: "POST",
      headers: { "Content-Type": "application/json" },
      body: JSON.stringify(credentials),
    });

    if (!response.ok) {
      throw new Error("Login failed");
    }

    return response.json() as Promise<User>;
  },
};

const login = createLogin(httpAuthGateway);
```

В unit-тесте в `createLogin` передаётся небольшая fake-реализация без сети. Компонент может получить готовую функцию `login` через props, хук или context. Здесь SRP отделяет проверку сценария от HTTP, ISP оставляет узкий контракт, а DIP направляет зависимость к потребности сценария.

#### Границы применения

SOLID полезен как набор вопросов к изменению:

- сколько независимых требований меняет этот модуль;
- где находится стабильная часть и какая вариативность уже подтверждена;
- какие гарантии обещает общий контракт;
- какие данные и операции действительно нужны потребителю;
- может ли высокоуровневый сценарий работать с другой инфраструктурной реализацией.

Для локального компонента без повторного использования прямое решение часто лучше дополнительного слоя. Абстракция оправдана текущей сложностью, известной вариативностью или необходимостью изолированного тестирования, а не самим названием принципа.

#### Ключевые уточнения

- SOLID применяется к границам ответственности и контрактам, поэтому не требует классов.
- SRP объединяет код, который меняется по одной причине, и разделяет независимые причины изменения.
- OCP опирается на известную ось расширения и не запрещает исправлять ядро.
- LSP проверяет наблюдаемое поведение, которое TypeScript не может полностью выразить типами.
- ISP проектирует контракт от потребностей конкретного потребителя.
- DIP задаёт направление зависимостей, а dependency injection передаёт выбранную реализацию.
- Польза принципа оценивается локальностью изменений, ясностью и тестируемостью, а не количеством абстракций.
