#### Быстрый ответ

Jira — настраиваемая система учёта работы. Команда создаёт work items, связывает их с контекстом и проводит через workflow — набор статусов и переходов от появления работы до завершения. Jira показывает состояние процесса, но не определяет сам процесс и не заменяет коммуникацию.

Для разработчика качественный work item отвечает на вопросы: зачем нужна работа, какое поведение ожидается, где дизайн и API-контракт, какие зависимости и риски, кто делает следующий шаг и по каким критериям результат будет принят. Статус, assignee, связи с PR и комментарии должны отражать фактическое состояние, а не обновляться задним числом перед встречей.

Jira Cloud постепенно меняет термин `issue` на `work item`, а `project` — на `space`. Переход ещё не завершён: интерфейс и документация могут использовать новые названия, тогда как существующие JQL-запросы и API сохраняют прежние поля. Терминологию конкретного проекта проверяют в его конфигурации.

#### Что моделирует Jira

```text
work item
  -> поля и связи описывают контекст
  -> workflow ограничивает допустимые переходы
  -> board показывает выбранное представление элементов
  -> filters/JQL находят нужные срезы
```

**Work item** — единица учитываемой работы. Story, task, bug, epic и subtask являются распространёнными work types, но их набор, иерархия и смысл настраиваются. Нельзя считать, что любая Jira использует одинаковую схему.

**Workflow** — набор статусов и переходов. Статус описывает состояние, например `In Progress`; переход — допустимое действие, например `Start review`. Workflow способен требовать поля, проверять условия и запускать automation.

**Board** не хранит отдельные копии задач. Он показывает work items, выбранные filter/JQL, и раскладывает статусы по колонкам. Один work item может появляться в нескольких представлениях.

#### Work types

Командная договорённость важнее универсального словаря, но часто используют:

| Тип | Практический смысл |
| --- | --- |
| Story | пользовательское или продуктовое поведение с самостоятельной ценностью |
| Task | техническая, организационная или продуктовая работа, которую не оформляют как story |
| Bug | расхождение фактического и ожидаемого поведения |
| Epic | крупная область результата, объединяющая несколько элементов |
| Subtask | часть родительского work item без самостоятельного продуктового контекста |

Story не обязана иметь формулировку «Как пользователь, я хочу...», а task не является автоматически «техническим долгом». Тип нужен для удобного процесса, полей, отчётов и workflow, а не ради подгонки любой работы под шаблон.

#### Содержание work item

Минимально полезная карточка содержит:

- краткий Summary, по которому элемент можно найти;
- проблему, цель или наблюдаемый симптом;
- границы: что входит и что намеренно не входит;
- acceptance criteria с проверяемым поведением;
- ссылки на дизайн, API/OpenAPI, решение и связанные work items;
- зависимости и известные риски;
- сведения об окружении и данных, если они нужны для воспроизведения;
- требования к rollout, analytics или migration, если они меняют реализацию.

Не каждый пункт обязателен для мелкой задачи. Карточка должна хранить тот контекст, без которого следующий участник будет заново угадывать решение.

#### Frontend-задача

Для пользовательской функции обычно проверяют:

| Область | Какие вопросы закрыть |
| --- | --- |
| UI states | loading, empty, error, success, partial data, disabled и retry |
| Input | validation, paste/autofill, keyboard, локализация и длинные значения |
| API | schema, errors, authorization, pagination и cache invalidation |
| Layout | mobile/desktop, переполнение, zoom и browser support |
| Accessibility | семантика, accessible name, focus, клавиатура и объявление ошибок |
| Delivery | feature flag, analytics, migration, SSR и rollback при необходимости |
| Verification | acceptance criteria, tests и способ ручной проверки |

Перечень адаптируют к задаче. Например, у изменения build configuration нет UI states, но есть влияние на окружения, source maps, caching и pipeline.

#### Acceptance criteria

Acceptance criteria описывают наблюдаемое поведение, а не внутренние шаги реализации:

```text
Given пользователь открыл форму профиля
When вводит email неверного формата и нажимает Save
Then запрос не отправляется
And ошибка связана с полем email
And после исправления значения форма отправляется один раз
```

Формат Given/When/Then необязателен. Важно, чтобы критерии были однозначно проверяемыми, учитывали существенные негативные сценарии и не диктовали случайную реализацию вроде имени внутреннего hook.

Acceptance criteria конкретного work item не заменяют общую Definition of Done команды: code review, tests, сборку и другие постоянные требования качества.

#### Качественный bug report

Bug должен позволять отличить дефект от неизвестного ожидания и воспроизвести проблему:

```text
Summary: форма профиля отправляет email неверного формата после paste

Environment:
production, Chrome 140, пользователь с подтверждённым аккаунтом

Preconditions:
открыта страница Profile settings

Steps:
1. Вставить "test@" в поле Email.
2. Нажать Save.

Actual:
отправляется PATCH /profile, server возвращает 422.

Expected:
запрос не отправляется, около поля появляется связанное с ним сообщение.

Evidence:
request ID, screenshot/video, console error без tokens и персональных данных
```

Версия приложения, browser/OS, роль пользователя и feature flags добавляются только когда могут влиять на воспроизведение. Секреты, полные токены и лишние персональные данные в Jira не помещают.

#### Workflow и реальный статус

Названия статусов различаются, но они должны отвечать на вопрос, что сейчас происходит:

```text
To Do -> In Progress -> Review -> QA/Verification -> Done
                    \-> Blocked -> In Progress
```

`Blocked` полезен, когда работа действительно не может двигаться. Комментарий фиксирует причину, проверенные варианты, владельца следующего шага и влияние на срок или Sprint Goal.

Открытый PR не обязательно означает `Done`: CI может падать, review не завершён, rollout не выполнен. С другой стороны, workflow не должен требовать бессмысленных переходов, которые никто не использует. Статусы отражают наблюдаемые этапы команды.

#### Декомпозиция и связи

Работу делят, когда части можно независимо проверить, выпустить или поручить разным участникам. Хорошие границы:

- исследование неизвестного API и последующая реализация;
- backend contract и frontend integration;
- базовый пользовательский поток и отдельно согласованное расширение;
- миграция данных/конфигурации и изменение приложения.

Не следует создавать subtask на каждую строку работы только ради отчётности. Если UI, API adapter и tests образуют один небольшой проверяемый результат, один work item с локальным планом может быть понятнее.

Links делают зависимости машинно видимыми: `blocks`, `is blocked by`, `duplicates`, `relates to`, parent/child. Ссылка в тексте без типа связи хуже показывает, что именно должно произойти раньше.

#### Оценка

Story points, часы и другие estimates являются полями и договорённостями команды, а не гарантией Jira или обязательным правилом Scrum.

Оценка учитывает объём, сложность, неопределённость и риск. Если задача неясна, число не исправляет проблему: сначала уточняют требования, проводят spike или явно добавляют диапазон/риск.

Изменение оценки после появления новых знаний не является автоматической ошибкой разработчика. Важно сохранить причину изменения и использовать данные для будущего планирования, а не превращать estimate в персональный KPI.

#### JQL

JQL (Jira Query Language) ищет work items по полям, операторам, ключевым словам и функциям. Примеры используют существующие поля JQL; из-за перехода терминологии UI может уже говорить `space/work item`, а запрос — всё ещё `project/issue`.

Свои незавершённые задачи:

```jql
project = WEB
AND assignee = currentUser()
AND resolution = Unresolved
ORDER BY priority DESC, updated DESC
```

Заблокированные элементы активного Sprint:

```jql
project = WEB
AND sprint in openSprints()
AND status = Blocked
ORDER BY priority DESC
```

Обновлённые за последние семь дней bugs компонента:

```jql
project = WEB
AND issuetype = Bug
AND component = Checkout
AND updated >= -7d
ORDER BY updated DESC
```

Конкретные поля и значения узнают через autocomplete Jira: `status = Blocked` не сработает, если команда использует другое имя или локализацию.

#### Jira и коммуникация

Карточка сохраняет устойчивый контекст, но не заменяет быстрый разговор при неоднозначности. После разговора решение, изменение scope и следующий шаг возвращают в Jira, чтобы информация не осталась только у участников созвона.

Полезный комментарий кратко отвечает:

```text
Что изменилось?
Что проверено?
Что мешает или какой риск появился?
Кто и что делает дальше?
```

Не нужно дублировать в комментариях данные, уже очевидные из автоматической связи с PR или истории статусов.

#### Ключевые уточнения

- Jira хранит work items и workflow команды, но не определяет автоматически Scrum, качество или реальный способ работы.
- Work types, поля, иерархия и статусы настраиваются; значение Story, Task и Done проверяют по договорённости конкретной команды.
- Status отражает фактический этап, а комментарий к blocker называет причину, влияние и следующий шаг.
- Acceptance criteria проверяют поведение конкретной задачи; Definition of Done задаёт общий уровень готовности Increment.
- Story points и часы поддерживают планирование, но не являются точной гарантией срока и не подходят для персонального KPI.
- JQL сохраняет существующие имена полей во время перехода Jira от `issue/project` к `work item/space`.
