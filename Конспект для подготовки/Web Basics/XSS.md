#### Быстрый ответ

XSS (Cross-Site Scripting, межсайтовый скриптинг) — уязвимость, при которой данные атакующего становятся исполняемым кодом внутри origin доверенного приложения. Скрипт получает права страницы: читает доступный DOM и хранилища, отправляет запросы текущей сессии, подменяет интерфейс и выводит доступные данные наружу.

Основная защита — сохранять данные данными. Обычный текст выводят через безопасную привязку данных фреймворка или `textContent`, значения кодируют для конкретного контекста вывода, динамические URL проверяют по protocol, а разрешённый пользовательский HTML пропускают через поддерживаемый sanitizer со списком допустимых элементов и атрибутов.

CSP, Trusted Types и `HttpOnly` cookie ограничивают вероятность или последствия атаки, но не заменяют безопасные точки вывода (sinks). XSS внутри origin уже обходит многие предположения о доверии к собственному frontend.

#### Модель источник → преобразование → точка интерпретации

```text
недоверенный источник данных
  -> преобразования в приложении
  -> опасная точка интерпретации данных как кода
  -> code execution in trusted origin
```

**Источник (source)** — не только поле формы. Недоверенными могут быть query/hash URL, ответ API, CMS, WebSocket-сообщение, имя файла, `postMessage`, `localStorage` и сторонняя интеграция.

**Преобразование (transform)** — декодирование, рендеринг Markdown, шаблон, конкатенация HTML или извлечение части объекта. Данные могут стать опасными после нескольких безопасно выглядящих шагов.

**Точка интерпретации (sink)** — API, который воспринимает строку как HTML, JavaScript, CSS или URL. Защита выбирается по конкретному sink, а не только по месту первоначального ввода.

#### Stored, reflected и DOM XSS

| Вид | Как вредоносные данные попадают к жертве |
| --- | --- |
| Stored XSS | сохраняется в базе/CMS и позже показывается пользователям |
| Reflected XSS | приходят в запросе и сразу отражаются в серверном ответе |
| DOM-based XSS | клиентский JavaScript переносит данные из источника в опасный DOM sink |

Классификации могут пересекаться. Сохранённое значение из API способно вызвать DOM XSS, если React-компонент передаст его в `innerHTML`. Важнее найти фактическую цепочку от источника до sink, чем спорить о единственном названии.

#### Контекст вывода

Один универсальный `escape()` не защищает все контексты:

| Контекст | Безопасная основа |
| --- | --- |
| HTML text | framework escaping или `textContent` |
| HTML attribute | framework binding и отсутствие конкатенации markup |
| URL | разбор через `URL`, список разрешённых protocols/origins |
| Исходный код JavaScript | не вставлять данные в исполняемый скрипт; безопасная сериализация |
| CSS | не строить stylesheet из произвольной строки |
| Разрешённый HTML | sanitizer со списком допустимых тегов, атрибутов и URL protocols |

HTML escaping превращает `<` в текстовое представление и подходит для текстового контекста HTML. Оно не делает строку безопасным JavaScript-кодом или URL. Сначала выбирают безопасный API, затем применяют контекстное кодирование там, где оно действительно нужно.

#### Опасные sinks

К DOM XSS часто приводят:

- `innerHTML`, `outerHTML`, `insertAdjacentHTML()`;
- `document.write()`;
- `eval()`, `new Function()` и строка в timer;
- динамическое создание встроенного обработчика события;
- небезопасный `srcdoc` у `iframe`;
- URL со схемой `javascript:` в исполняемом контексте;
- third-party widget API, принимающий raw HTML.

```js
// Строка интерпретируется как HTML.
content.innerHTML = userComment;

// Строка остаётся текстом.
content.textContent = userComment;
```

Удаление `<script>` через регулярное выражение не является sanitization. Исполнение возможно через множество тегов, атрибутов, URL-схем, SVG/MathML и особенностей разбора HTML. Используют библиотеку, которая разбирает HTML и поддерживает актуальную модель браузера.

#### React

React экранирует строковые значения в JSX:

```tsx
function Comment({ text }: { text: string }) {
  return <p>{text}</p>;
}
```

Значение становится текстовым DOM-узлом, а не разметкой. Это защищает конкретный sink, но не все действия приложения.

`dangerouslySetInnerHTML` обходит escaping:

```tsx
function Article({ html }: { html: string }) {
  return <article dangerouslySetInnerHTML={{ __html: html }} />;
}
```

Если продукт действительно принимает rich text, HTML санитизируют до этого компонента и централизуют использование опасного API. Например, DOMPurify является специализированным sanitizer; конфигурация определяет допустимые tags, attributes и URL protocols.

React также не проверяет бизнес-безопасность URL. Значение для `href`, `src`, redirect или `window.location` разбирают через `URL` и ограничивают допустимые protocols и origins.

Markdown сам по себе не гарантирует безопасность. Renderer может разрешать raw HTML, links, images или plugins, которые создают опасный output. Его режим и sanitizer являются частью security contract.

#### SSR и сериализация данных

HTML, созданный на сервере, может получить XSS до запуска React. Особый риск — вставка JSON прямо внутрь `<script>`:

```html
<script>
  window.__DATA__ = USER_CONTROLLED_JSON;
</script>
```

Обычный `JSON.stringify` не обязан безопасно закрыть контекст HTML-скрипта: последовательность `</script>` способна завершить элемент. Сериализатор фреймворка должен экранировать значимые для HTML символы или передавать данные отдельным безопасным способом.

Нельзя собирать SSR markup строковой конкатенацией и считать последующую hydration защитой. Уязвимый HTML уже обработан браузером до hydration.

#### Санитизация, валидация и encoding

**Валидация** проверяет, соответствует ли input бизнес-формату. Она уменьшает неожиданные значения, но не знает все будущие output contexts.

**Кодирование/экранирование (encoding/escaping)** не даёт данным закрыть текущий синтаксический контекст. Способ зависит от контекста HTML, атрибута, URL, JavaScript или CSS.

**Санитизация** разбирает разрешённый HTML и удаляет опасные элементы, attributes и protocols. Она нужна только когда markup является функцией продукта.

Хранить исходный HTML или уже sanitized version — отдельное архитектурное решение. При изменении sanitizer старые данные иногда нужно обработать заново, поэтому версия policy и исходное значение могут храниться раздельно с ограниченным доступом.

#### CSP

Content Security Policy ограничивает источники ресурсов и способы выполнения скриптов. Строгая политика использует nonce или hash вместо широкого `unsafe-inline`, запрещает `eval` и может применять `strict-dynamic` согласно архитектуре загрузки.

CSP является defense in depth:

- может заблокировать внедрённый встроенный скрипт;
- ограничивает отправку данных через некоторые resource types;
- создаёт violation reports для поиска проблем;
- не исправляет подмену DOM, утечку через разрешённый origin или опасную логику доверенного скрипта.

Политику сначала проверяют через `Content-Security-Policy-Report-Only`, анализируют нарушения, затем включают блокирующий режим. Случайное добавление `unsafe-inline` ради совместимости способно убрать основную защиту скриптов.

#### Trusted Types

Trusted Types позволяют потребовать, чтобы опасные DOM sinks принимали не обычную строку, а значение, созданное зарегистрированной policy. Это помогает централизовать sanitization и обнаружить прямые вызовы `innerHTML`.

Механизм особенно полезен большому приложению с устаревшими опасными sinks, но поддержку браузеров и интеграцию библиотек проверяют отдельно. Trusted Types не определяет, какая политика sanitization безопасна; эту логику всё равно проектирует команда.

#### `HttpOnly` и последствия атаки

`HttpOnly` cookie нельзя прочитать через JavaScript, поэтому атакующий не всегда сможет вынести токен сессии на своё устройство. Но скрипт внутри приложения способен:

- отправлять same-origin requests с cookie;
- читать доступные API responses;
- менять данные пользователя;
- подменить форму входа или платёжный UI;
- читать Web Storage и IndexedDB.

Поэтому `HttpOnly` ограничивает один путь кражи, а устранение XSS остаётся обязательным.

#### Проверка

1. Найти все HTML/JS/URL sinks статическим поиском и lint rules.
2. Проследить источники из URL, API, CMS, хранилищ и сообщений.
3. Проверить framework escape boundaries и wrappers над sanitizer.
4. Запретить или централизовать `dangerouslySetInnerHTML`/`innerHTML`.
5. Добавить CSP Report-Only и анализировать violations.
6. Тестировать вредоносные данные в разных контекстах, не ограничиваясь `<script>alert(1)</script>`.
7. Обновлять sanitizer и сторонние скрипты как зависимости, влияющие на безопасность.

#### Ключевые уточнения

- XSS возникает при переходе данных в исполняемый sink; само наличие пользовательского ввода ещё не определяет уязвимость.
- Экранирование зависит от контекста вывода, а sanitizer нужен только для HTML, который продукт намеренно разрешает.
- React защищает текстовую привязку в JSX, но `dangerouslySetInnerHTML`, URL, SSR и сторонние скрипты остаются отдельными границами.
- CSP и Trusted Types ограничивают выполнение и опасные sinks, но не заменяют корректную обработку данных.
- `HttpOnly` уменьшает возможность украсть cookie, но XSS всё ещё действует с правами открытой страницы.
