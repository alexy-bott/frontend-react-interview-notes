#### Быстрый ответ

SSE (Server-Sent Events, серверные события) — стандарт для непрерывной передачи текстовых событий от сервера к браузеру по одному HTTP-соединению. Клиент создаёт `EventSource`, сервер отвечает с `Content-Type: text/event-stream` и отправляет блоки с полями `event`, `data`, `id` и `retry`.

SSE подходит для уведомлений, прогресса, логов и live feed, когда основной поток идёт сервер → клиент. Действия пользователя при этом отправляются обычными HTTP-запросами. Для активного двустороннего обмена и бинарных сообщений чаще выбирают WebSocket.

Браузер автоматически переподключает `EventSource`; `id` и `Last-Event-ID` позволяют серверу продолжить поток. Но история, удаление дубликатов, новый снимок состояния после слишком долгого разрыва, аутентификация и настройка proxy остаются ответственностью приложения.

#### Как работает поток

```text
new EventSource("/events")
  -> HTTP-запрос
  -> 200 OK + Content-Type: text/event-stream
  -> ответ остаётся открытым
  -> сервер периодически дописывает события и отправляет порции данных
  -> браузер разбирает поток и создаёт MessageEvent
```

SSE использует обычную семантику HTTP-ответа, но не завершает body после одного сообщения. Это отличает его от polling, где клиент создаёт новый запрос по расписанию, и от long polling, где запрос завершается при событии, после чего клиент открывает следующий.

#### Формат `text/event-stream`

Одно событие заканчивается пустой строкой:

```text
event: build.updated
id: 1042
retry: 3000
data: {"buildId":"build-7","status":"done"}

```

Поля имеют определённый смысл:

- `event` — имя события; без него вызывается обычный обработчик `message`;
- `data` — строка данных; несколько последовательных `data:` объединяются через перевод строки;
- `id` — обновляет идентификатор последнего события у `EventSource`;
- `retry` — рекомендуемая браузеру задержка перед reconnect в миллисекундах;
- строка, начинающаяся с `:`, является comment и может служить heartbeat.

Полезная нагрузка (payload) остаётся строкой. JSON нужно разобрать и проверить runtime-схемой. SSE не предоставляет бинарные сообщения; кодирование binary data в base64 увеличивает размер и часто означает, что выбран не лучший транспорт.

#### Client API

```ts
const source = new EventSource("/api/build-events");

source.addEventListener("build.updated", (event) => {
  const message = parseBuildEvent(event.data);
  updateBuildCache(message);
});

source.addEventListener("open", () => {
  setConnectionState("live");
});

source.addEventListener("error", () => {
  setConnectionState("reconnecting");
});

function stopUpdates() {
  source.close();
}
```

`error` не всегда означает окончательное закрытие: стандартный `EventSource` обычно переходит к повторному подключению. Для намеренной остановки вызывают `close()`, иначе соединение и обработчики останутся активными после ухода с экрана.

В React соединение создают в effect или отдельном менеджере транспорта и закрывают в cleanup. Один экран не должен случайно открывать новое соединение при каждом render.

#### Восстановление после разрыва

Когда событие содержит `id`, браузер запоминает его. При reconnect он передаёт последнее значение серверу в `Last-Event-ID`. Чтобы это действительно восстановило данные, сервер должен хранить события или уметь построить продолжение после указанного курсора.

```text
клиент получил событие 1042
  -> connection оборвалось
  -> reconnect с Last-Event-ID: 1042
  -> сервер отдаёт 1043, 1044, ...
```

Если сохранённая история начинается с 1100, продолжение невозможно. Сервер должен вернуть сигнал для нового снимка состояния либо закрыть поток так, чтобы клиент отдельно запросил актуальное состояние.

Повторная доставка возможна: сервер и клиент могут по-разному понимать, успело ли событие обработаться до разрыва. Обработчики делают идемпотентными или удаляют дубликаты по `id`. SSE сам по себе не гарантирует однократную обработку (exactly-once processing).

#### Authentication и CORS

Стандартный `EventSource` constructor не позволяет добавить произвольный `Authorization` header. Для same-origin приложения удобно использовать session cookie. Для cross-origin cookie создают:

```ts
const source = new EventSource("https://api.example.com/events", {
  withCredentials: true,
});
```

Сервер должен разрешить точный origin, credentials и правильно настроить cookie. `Access-Control-Allow-Origin: *` нельзя сочетать с ответом, доступным с credentials.

Bearer token в query string прост в реализации, но URL попадает в логи сервера/proxy, monitoring и инструменты истории. Если этот вариант неизбежен, используют короткоживущий одноразовый ticket, а не основной access token. Альтернатива — читать потоковый ответ через `fetch`, где можно добавить заголовок, но разбор и reconnect тогда реализует приложение, а не `EventSource`.

Аутентификация при открытии потока не отменяет авторизацию конкретной подписки. Сервер не должен принимать произвольный channel/user ID только потому, что клиент успешно вошёл в сессию.

#### Server и инфраструктура

Для корректного потока нужны как минимум:

```http
HTTP/1.1 200 OK
Content-Type: text/event-stream
Cache-Control: no-cache
Connection: keep-alive
```

Точное сочетание заголовков зависит от версии HTTP и proxy. Критично не название каждого заголовка, а отсутствие буферизации: reverse proxy или middleware не должен накапливать события в большом буфере, иначе клиент увидит их пачкой с задержкой.

Сервер после каждого события отправляет накопленный output, периодически посылает heartbeat-комментарий для неактивного соединения и освобождает подписку, timer и database cursor при разрыве. На уровне платформы проверяют idle timeouts, максимальную длительность ответа и лимиты одновременных соединений.

При HTTP/1.x браузеры имеют небольшой лимит параллельных соединений к одному origin, и несколько вкладок с SSE могут его исчерпать. В HTTP/2 число потоков согласуется отдельно и обычно выше, но инфраструктурный лимит всё равно существует. Полезно разделять одно соединение между несколькими типами событий вместо отдельного `EventSource` на каждый виджет.

#### Согласованность и backpressure

SSE удобно сочетать со снимком состояния:

1. Получить текущее состояние через HTTP.
2. Открыть поток с cursor/revision снимка.
3. Применять новые события по порядку.
4. При пропуске запросить новый снимок.

Если сервер генерирует события быстрее, чем браузер и UI их обрабатывают, очередь растёт. Для прогресса достаточно последнего значения; audit events терять нельзя. Поэтому сервер может объединять события, которые допустимо отбросить, ограничивать буфер и закрывать соединение с медленным клиентом, требуя восстановиться по курсору.

В UI высокочастотные события не обязательно рендерят по одному. State и кеш обновляют пакетно или с ограниченной частотой, сохраняя при этом корректный курсор обработки.

#### SSE и WebSocket

| Критерий | SSE | WebSocket |
| --- | --- | --- |
| Направление | сервер → клиент | оба направления |
| Модель транспорта | потоковый HTTP-ответ | отдельный двусторонний протокол после handshake |
| Data | text | text и binary |
| Повторное подключение в браузере | встроено | реализует приложение |
| Resume primitive | `id` / `Last-Event-ID` | определяется application protocol |
| Пользовательские заголовки запроса | нет в стандартном `EventSource` | нет в браузерном конструкторе `WebSocket` |
| Типичные задачи | logs, progress, notifications | chat, collaboration, interactive realtime |

#### Ключевые уточнения

- SSE — один поток сервер → клиент, а не серия polling-запросов.
- Автоматический reconnect не восстанавливает историю без event IDs и сохранения событий на сервере.
- `Last-Event-ID` даёт cursor, но exactly-once обработку приложение строит само.
- `EventSource` не принимает custom `Authorization` header; способ authentication выбирают отдельно.
- Буферизация в proxy и idle timeout могут превратить рабочий локально поток в задержанный или постоянно рвущийся production flow.
- Клиент закрывает неиспользуемый `EventSource`, иначе остаются ресурсы соединения и подписки.

#### Когда SSE подходит

- прогресс длительной серверной задачи;
- live logs и build output;
- notifications для открытого приложения;
- изменения статуса заказа;
- dashboard updates средней частоты;
- live feed, где команды клиента продолжают идти через HTTP.

Для offline push, когда страница закрыта, SSE не подходит: браузер не держит соединение страницы постоянно. Такой сценарий относится к Push API и Service Worker.
