#### Быстрый ответ

REST (Representational State Transfer) — архитектурный стиль распределённых систем. Он разделяет клиент и сервер, требует взаимодействия без хранения состояния диалога на сервере (stateless), допускает кеширование, использует единый интерфейс ресурсов и позволяет размещать посредников между клиентом и сервером. HTTP хорошо реализует эти ограничения, но REST не равен формуле «JSON по HTTP».

В практическом REST API ресурс имеет устойчивый URI, клиент получает или отправляет его представление, а смысл операции задают HTTP-метод, статус и заголовки. Например, `GET /users/42` получает представление пользователя, а `PUT /users/42/preferences` заменяет известное состояние настроек.

Не каждый удобный HTTP API полностью соответствует REST. API без гипермедиа (hypermedia) часто точнее назвать ориентированным на ресурсы (resource-oriented) или REST-like. Это не делает его автоматически плохим: важно честно понимать контракт и не приписывать ему свойства, которых нет.

#### Ограничения REST

| Ограничение | Смысл |
| --- | --- |
| Client–server | интерфейс клиента отделён от хранения и бизнес-логики сервера |
| Stateless | каждый запрос содержит контекст, необходимый для его обработки |
| Cacheable | ответ явно допускает или запрещает повторное использование |
| Uniform interface | ресурсы и сообщения подчиняются единой общей модели |
| Layered system | клиент может не знать, отвечает origin, gateway, proxy или cache |
| Code on demand | сервер при необходимости передаёт исполняемый код; ограничение необязательное |

Эти ограничения работают вместе. URL вида `/users/42` и JSON сами по себе ещё не делают систему RESTful, если сообщения не самодостаточны, кэширование игнорируется, а каждое действие имеет собственный несогласованный протокол.

#### Единый интерфейс

В исходном описании REST uniform interface включает четыре идеи.

**Идентификация ресурсов.** Ресурс имеет идентификатор, обычно URI. Ресурс — концепция вроде «пользователь 42» или «текущая коллекция заказов», а не конкретная JSON-строка.

**Изменение через представления.** Клиент получает представление ресурса и отправляет новое представление или инструкцию изменения. JSON — распространённый формат, но REST не ограничен JSON.

**Самоописывающиеся сообщения.** Метод, media type, status code, cache headers и другие метаданные дают достаточно информации, чтобы понять обработку сообщения без скрытого отдельного протокола.

**Hypermedia as the Engine of Application State (HATEOAS).** Ответ содержит ссылки и доступные переходы, через которые клиент узнаёт следующие действия. Например, оплаченный заказ уже не предлагает ссылку `cancel`.

Многие production API используют ресурсы, HTTP-семантику и stateless-запросы, но маршруты следующих операций заранее зашиты в клиент. Они сохраняют полезные REST-принципы, хотя не выполняют HATEOAS в строгом смысле.

#### Что означает stateless

Stateless означает отсутствие скрытого диалогового состояния между запросами. Сервер не должен требовать, чтобы конкретный клиент сначала выполнил «шаг 1» на том же соединении, если этот контекст нельзя восстановить из нового запроса.

Сервер при этом хранит состояние ресурсов: пользователей, заказы, права и результаты операций. Это не противоречит REST. Различие проходит между resource state, принадлежащим системе, и client session state, необходимым только для продолжения разговора с одним клиентом.

Authentication credentials передаются или определяются для каждого запроса. Bearer token хорошо вписывается в эту модель. Серверная cookie-session, где короткий ID ссылается на скрытое состояние сессии, широко используется в HTTP-приложениях, но в строгой оценке ослабляет REST stateless constraint. Безопасность и удобство авторизации важнее попытки формально назвать любой API REST.

Stateless упрощает балансировку: следующий запрос может обработать другой экземпляр сервиса, если общее ресурсное состояние доступно. Цена — необходимый контекст повторяется в запросах, а многошаговую операцию приходится моделировать явным ресурсом или workflow state.

#### Ресурсы, методы и команды

Ресурсные URI обычно называют существительные:

```http
GET    /users/42
GET    /users/42/orders
POST   /orders
PUT    /users/42/preferences
PATCH  /orders/73
DELETE /sessions/current
```

Семантика методов остаётся стандартной: `GET` безопасен, `PUT` и `DELETE` идемпотентны, `POST` передаёт данные ресурсу на обработку, а свойства `PATCH` зависят от patch-документа.

Не каждую доменную операцию удобно выразить простым CRUD. Отмену заказа можно представить созданием ресурса отмены:

```http
POST /orders/73/cancellations
```

или командным endpoint:

```http
POST /orders/73/cancel
```

Первый вариант лучше вписывается в ресурсную модель и даёт операции собственный status и idempotency contract. Второй иногда проще и честнее отражает доменную команду. Выбор оценивают по понятности, повторяемости, аудиту и жизненному циклу операции, а не по запрету глаголов любой ценой.

#### Представления и content negotiation

Ресурс и его представление не равны. Один ресурс может иметь JSON, HTML или другое представление. Клиент сообщает предпочтение через `Accept`, а сервер описывает тело через `Content-Type`:

```http
GET /reports/42
Accept: application/json
```

```http
HTTP/1.1 200 OK
Content-Type: application/json
ETag: "report-12"
```

`ETag` относится к версии конкретного представления. С `If-None-Match` он позволяет проверить кэш, а с `If-Match` — не перезаписать конкурентное изменение незаметно.

#### Коллекции и ошибки

Коллекция проектируется как отдельный ресурс:

```http
GET /orders?status=paid&sort=-createdAt&cursor=eyJpZCI6NzN9
```

Контракт задаёт допустимые filters, стабильную сортировку, pagination, форму следующего cursor и поведение при невалидных параметрах. Все параметры, меняющие набор данных, входят в cache key frontend-клиента.

Статус передаёт общий результат, а структурированное тело — конкретную проблему. `404` описывает отсутствие ресурса, `409` — конфликт текущего состояния, `412` — невыполненную HTTP-precondition, `422` — распознанное, но невыполнимое содержание согласно контракту API.

Возвращать `200 OK` с `{ "success": false }` для любой ошибки невыгодно: кэш, мониторинг и универсальный API-клиент теряют стандартную семантику ответа.

#### Кэширование и слои

REST требует явно обозначать кэшируемость ответа. HTTP предоставляет `Cache-Control`, validators и conditional requests. Кэш может находиться в браузере, Service Worker, CDN, reverse proxy или API gateway.

Layered system позволяет добавлять эти узлы без изменения клиентского контракта. Но чувствительные и пользовательские ответы требуют правильных `private`, `no-store`, `Vary` и cache key; иначе общий слой способен отдать данные не тому пользователю.

#### REST, RPC и GraphQL

| Подход | Когда естественен |
| --- | --- |
| REST-like HTTP API | ресурсы, стандартная HTTP-семантика, кэш и зрелая инфраструктура |
| RPC | операции естественно являются командами или вычислениями |
| GraphQL | клиентам нужны разные формы связанного графа данных через единый schema-контракт |

Это не шкала качества. REST удобен, когда модель ресурсов и HTTP дают полезные свойства. Большое число специальных UI-агрегаций может привести к множеству запросов или специализированным endpoints; RPC или GraphQL иногда выражают такую систему яснее.

#### Что важно frontend-разработчику

Frontend опирается на предсказуемый контракт: URI, методы, статус, форму ответа, pagination и error model. На этой основе query library строит cache keys, invalidation, retries и optimistic updates.

Клиент всё равно валидирует внешние данные во время выполнения. OpenAPI и TypeScript уменьшают расхождения на этапе разработки, но ответ сервера может принадлежать другой версии, пройти через старый cache или нарушить контракт из-за ошибки.

#### Ключевые уточнения

- REST является набором архитектурных ограничений, а не синонимом JSON, HTTP или CRUD-маршрутов.
- Stateless запрещает скрытую зависимость от предыдущего взаимодействия, но не хранение состояния ресурсов на сервере.
- URI идентифицирует ресурс, а JSON является одним из возможных его представлений.
- Uniform interface включает не только методы HTTP, но и самодостаточные сообщения и hypermedia; API без HATEOAS обычно является REST-like.
- Ресурсная модель полезна пока делает контракт понятнее; доменную команду не следует искусственно маскировать, если RPC-форма точнее задачи.
