#### Быстрый ответ

HTTPS — обмен HTTP-сообщениями через соединение, защищённое TLS. TLS шифрует данные, обнаруживает их подмену и позволяет браузеру проверить, что сертификат действителен для запрошенного домена. Обычный HTTP этих свойств не даёт: участник сети может читать и изменять трафик.

HTTPS защищает канал передачи, а не само приложение. XSS, CSRF, слабая авторизация и уязвимый сервер остаются возможными. Сертификат также не доказывает, что сайт добросовестен: он подтверждает связь ключа с доменным именем через доверенную цепочку сертификатов.

Для production используют HTTPS на всём пути, перенаправляют HTTP на HTTPS, устраняют mixed content, ставят cookie с `Secure` и только после проверки инфраструктуры включают HSTS. Многие возможности браузера доступны только в secure context, которым обычно является HTTPS-страница.

#### Что даёт TLS

| Свойство | Что защищает |
| --- | --- |
| Конфиденциальность | содержимое запроса и ответа нельзя прочитать как открытый текст по пути |
| Целостность | изменение защищённых данных обнаруживается |
| Аутентификация сервера | браузер проверяет сертификат, домен, срок действия и доверенную цепочку |

Во время TLS handshake клиент и сервер согласуют параметры соединения, сервер предъявляет сертификат, а стороны получают сеансовые ключи. После этого HTTP-сообщения защищаются более быстрым симметричным шифрованием.

Для HTTP/1.1 и HTTP/2 TLS обычно работает поверх TCP. HTTP/3 использует QUIC поверх UDP и интегрирует TLS 1.3 в установление соединения. Поэтому формула «HTTPS — HTTP поверх TLS поверх TCP» полезна для HTTP/1.1 и HTTP/2, но не является универсальной для HTTP/3.

#### Что видно за пределами защищённого канала

TLS защищает HTTP path, query string, headers и body. Однако наблюдатель сети всё ещё видит IP-адреса, объём трафика, время и длительность соединений. Домен также может быть виден через обычный DNS или параметры установления TLS; DoH и Encrypted Client Hello уменьшают часть этой утечки, но не скрывают сам факт соединения с IP-адресом.

Если TLS завершается на CDN или reverse proxy, защищённый участок от пользователя заканчивается там. Соединение от proxy до origin-сервера должно быть защищено и настроено отдельно; значок замка в браузере не описывает внутреннюю сеть инфраструктуры.

#### Сертификат и доверие

Сертификат связывает публичный ключ с доменными именами и подписывается центром сертификации (CA), которому доверяет браузер или операционная система. Браузер проверяет:

- входит ли запрошенный домен в сертификат;
- не истёк ли срок действия;
- строится ли цепочка до доверенного корневого сертификата;
- не нарушены ли ограничения сертификата и политики браузера.

Self-signed certificate подписан самим владельцем и по умолчанию не входит в доверенную цепочку. Он подходит для контролируемой локальной среды после явной настройки доверия, но публичный production-сайт использует сертификат доверенного CA и автоматическое продление.

#### Перенаправление и HSTS

Обычный redirect с `http://` на `https://` улучшает навигацию, но самый первый HTTP-запрос ещё не защищён. Сетевой атакующий способен перехватить его и не дать пользователю перейти на HTTPS.

HSTS (`Strict-Transport-Security`) запоминает правило обращаться к домену только по HTTPS. После получения политики браузер самостоятельно заменяет HTTP на HTTPS до отправки сетевого запроса:

```http
Strict-Transport-Security: max-age=31536000; includeSubDomains
```

Браузер учитывает HSTS только из защищённого HTTPS-ответа. HSTS preload позволяет встроить правило в список браузера и защитить первое посещение, но требует отдельной регистрации и строгой готовности всех заявленных доменов.

`includeSubDomains` распространяет правило на поддомены. Если какой-либо из них не поддерживает HTTPS, он станет недоступен. Поэтому HSTS сначала проверяют с небольшим `max-age`, затем постепенно увеличивают срок и только после аудита рассматривают `includeSubDomains` и preload.

#### Mixed content

Mixed content возникает, когда HTTPS-документ запрашивает подресурс по HTTP. Такой ресурс можно подменить на сетевом пути и через него повлиять на защищённую страницу.

Браузеры блокируют наиболее опасный активный контент, включая HTTP-скрипты, стили, `iframe` и `fetch`. Некоторые типы пассивного контента браузер может автоматически обновить до HTTPS или заблокировать по собственным правилам. Надёжное решение — использовать HTTPS URL для API, CDN, изображений, шрифтов и всех остальных ресурсов.

#### Secure context и cookie

Многие powerful features браузера доступны только в secure context, чтобы сетевой атакующий не мог подменить код, который получает доступ к чувствительным возможностям устройства. Конкретная доступность зависит от API и браузера; `http://localhost` в ряде случаев считается потенциально доверенной локальной средой.

Cookie с атрибутом `Secure` отправляется только по защищённому соединению. Этот атрибут не шифрует значение отдельно и не заменяет `HttpOnly` или `SameSite`: каждый из них решает другую задачу.

#### Порядок внедрения и диагностика

```text
сертификат и автоматическое продление
  -> HTTPS на приложении, proxy и CDN
  -> один redirect на итоговый HTTPS URL
  -> устранение mixed content
  -> Secure cookies
  -> постепенное включение HSTS
```

При ошибке проверяют сертификат и его цепочку, системное время, имя домена, DNS, TLS-настройки proxy/CDN и вкладки Security и Network в DevTools. Заблокированные HTTP-ресурсы отображаются как mixed content в консоли.

#### Ключевые уточнения

- TLS защищает конфиденциальность и целостность канала и проверяет сертификат сервера, но не исправляет уязвимости приложения.
- HTTP path, query, headers и body шифруются, а IP-адрес, время и объём трафика полностью не скрываются.
- Redirect переводит пользователя на HTTPS после HTTP-запроса, а уже известная HSTS-политика заставляет браузер использовать HTTPS до обращения к сети.
- `Secure`, `HttpOnly` и `SameSite` являются независимыми атрибутами cookie и не заменяют друг друга.
- Формула с TCP зависит от версии: HTTP/2 обычно использует TLS поверх TCP, а HTTP/3 — QUIC с интегрированным TLS 1.3.
