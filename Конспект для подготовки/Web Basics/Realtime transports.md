#### Быстрый ответ

Транспорт для обновлений в реальном времени (realtime transport) — способ доставлять клиенту изменения вскоре после их появления на сервере. Выбор начинается не с WebSocket, а с требований: кто инициирует сообщения, насколько важна задержка, как часто идут события и что должно произойти после обрыва.

Для редких обновлений достаточно повторного HTTP-запроса или polling — периодического опроса сервера. Для преимущественного потока сервер → клиент подходит SSE. WebSocket нужен при активном двустороннем обмене с низкой задержкой. Long polling остаётся запасным вариантом, когда долгоживущее соединение недоступно или инфраструктура уже построена вокруг HTTP-запросов.

Сам транспорт не гарантирует согласованность состояния. Решение для production также определяет формат сообщений, аутентификацию, порядок и повторную доставку, повторное подключение (reconnect) с увеличением задержки между попытками (backoff), восстановление снимка состояния (snapshot), управление перегрузкой потока (backpressure) и синхронизацию с клиентским кешем.

#### Как выбрать транспорт

| Подход | Модель | Подходящие сценарии | Основная цена |
| --- | --- | --- | --- |
| Повторный HTTP-запрос | запрос → ответ по действию пользователя | CRUD, обновление после mutation, запрос при focus | данные меняются только после нового запроса |
| Polling | периодические запросы клиента | статус редкой фоновой задачи, несложный dashboard | пустые запросы и задержка до следующего интервала |
| Long polling | сервер держит запрос до события или timeout | запасной HTTP-вариант, редкие события с меньшей задержкой | повторное открытие запросов, сложные timeouts и масштабирование |
| SSE | одно HTTP-соединение сервер → клиент | уведомления, прогресс, логи, live feed | нет встроенного двустороннего канала и бинарных сообщений |
| WebSocket | постоянный двусторонний канал | чат, совместное редактирование, multiplayer, частые команды и события | собственный протокол сообщений и сложный жизненный цикл |

Realtime здесь означает свойство пользовательского сценария, а не строгую гарантию мгновенной доставки. Сеть, фоновая вкладка, перегрузка сервера и повторное подключение всегда добавляют задержку и разрывы.

#### Сначала определить требования

Перед выбором транспорта отвечают на вопросы:

1. Данные идут только от сервера или оба участника часто отправляют сообщения?
2. Допустима задержка в несколько секунд или событие нужно показывать почти сразу?
3. Что важнее: каждое событие или только последнее актуальное состояние?
4. Можно ли восстановить состояние обычным HTTP-снимком?
5. Нужно ли отправлять binary data?
6. Сколько одновременно открытых вкладок, пользователей и подписок ожидается?
7. Какие proxies, load balancers и платформенные ограничения проходят соединения?

Например, dashboard с обновлением раз в минуту не становится лучше от WebSocket: polling проще наблюдать, кешировать и эксплуатировать. Для совместного редактора задержка и двусторонний поток критичны, поэтому постоянный канал оправдан.

#### Snapshot и события

Надёжная модель часто сочетает два канала:

```text
HTTP-снимок: полное состояние на момент S
  -> realtime-события после S
  -> локальное применение событий
  -> при пропуске или reconnect новый снимок
```

Снимок состояния (snapshot) — полное состояние ресурса. Событие (event) — сообщение об изменении после этого состояния. Если строить UI только из событий, новая вкладка не знает историю, а пропущенное событие навсегда искажает состояние.

Если порядок важен, событие должно содержать возрастающий sequence number, revision, event ID или другой курсор. Клиент замечает пропуск и запрашивает новый снимок либо диапазон пропущенных событий. Timestamp сам по себе слабее порядкового номера: часы могут расходиться, а несколько событий могут иметь одинаковое время.

#### Message protocol

WebSocket и SSE доставляют bytes/text, но не определяют бизнес-формат. Его проектирует приложение:

```json
{
  "type": "order.updated",
  "version": 2,
  "eventId": "evt-1042",
  "resourceId": "order-42",
  "revision": 8,
  "payload": { "status": "paid" }
}
```

Полезные поля зависят от задачи:

- `type` выбирает обработчик;
- `version` позволяет развивать schema;
- `eventId` помогает deduplication и resume;
- `resourceId` связывает событие с сущностью в кеше;
- `revision` не даёт старому событию перезаписать новое состояние;
- correlation ID связывает команду с ответом или ошибкой.

Полезная нагрузка сообщения (payload) является внешними данными и проверяется runtime-схемой. TypeScript type не валидирует JSON, пришедший по сети.

#### Гарантии доставки и порядок

Нельзя обещать однократную доставку (exactly-once delivery) только выбором WebSocket или SSE. Обрыв может произойти после выполнения операции, но до получения подтверждения; после reconnect клиент не знает, нужно ли повторять команду.

На практике проектируют:

- **at-most-once** — событие может потеряться, но не повторяется;
- **at-least-once** — событие повторяют до подтверждения, поэтому клиент должен удалять дубликаты;
- idempotency — повтор command с тем же ключом не создаёт вторую операцию;
- ordering scope — порядок определён глобально, по channel или только по resource.

Даже если транспорт сохраняет порядок frames внутри одного живого соединения, порядок между повторными подключениями, несколькими экземплярами сервера и разными каналами требует прикладного протокола.

#### Reconnect и восстановление

Reconnect — состояние, а не один `setTimeout`:

```text
disconnected
  -> connecting
  -> authenticating
  -> восстановление подписок и курсора
  -> connected
```

Повторные попытки делают с экспоненциальным увеличением задержки (exponential backoff) и jitter — случайным разбросом этой задержки. Без jitter тысячи клиентов после сбоя одновременно обращаются к восстановившемуся серверу, создавая шторм повторных подключений.

После соединения клиент повторно проходит аутентификацию, восстанавливает подписки и передаёт курсор последнего подтверждённого события. Если сервер уже удалил историю или обнаружен пропуск, клиент получает новый снимок состояния.

Browser может заморозить background tab, device может потерять сеть без немедленного `close`, а deployment может завершить все connections. Поэтому UI различает `connecting`, `live`, `reconnecting`, `stale` и `offline`, если эта разница влияет на решение пользователя.

#### Backpressure

Backpressure — ситуация, когда производитель сообщений создаёт их быстрее, чем потребитель успевает обработать. Без контроля растут очереди, потребление памяти и задержка, после чего «realtime» показывает давно устаревшие события.

Стратегия зависит от семантики:

- не терять финансовые события и замедлить производителя или потребителя;
- объединить несколько progress updates в последнее значение;
- ограничить клиентскую очередь и запросить снимок после переполнения;
- throttle rendering, но продолжить аккумулировать доменные изменения;
- разорвать перегруженное соединение и восстановиться по курсору.

У классического браузерного API `WebSocket` нет полноценного входного механизма backpressure. Для исходящей очереди доступен `bufferedAmount`, но это только число байтов, ожидающих отправки. Протокол SSE также должен учитывать медленного клиента.

#### Интеграция с frontend state

Транспортный слой не должен знать о компонентах. Он разбирает и проверяет сообщение, а затем обновляет кеш серверного состояния или отправляет доменное событие:

```ts
socket.addEventListener("message", (event) => {
  const message = parseRealtimeMessage(event.data);

  if (message.type === "order.updated") {
    store.dispatch(ordersApi.util.invalidateTags([
      { type: "Order", id: message.resourceId },
    ]));
  }
});
```

Инвалидация подходит, когда событие только сообщает об изменении. Точечное обновление кеша быстрее, если payload полный, проверен, имеет revision и совпадает с фильтрами запроса. Для высокочастотного потока не следует обновлять React state на каждый исходный tick: данные агрегируют и публикуют с частотой, которую способен отрисовать UI.

#### Authentication и безопасность

Долгое соединение не отменяет срок жизни session. Server проверяет authentication при открытии, authorization для каждой subscription/command и реакцию на истечение credential.

Соединение с cookie-аутентификацией требует защиты от cross-site использования. Для WebSocket сервер проверяет `Origin`, потому что браузерная установка WebSocket-соединения не использует CORS preflight как `fetch`. Для SSE действуют правила HTTP/CORS, а стандартный `EventSource` имеет ограничения на пользовательские заголовки.

Сообщения ограничивают по размеру и частоте, payload валидируют, а ошибки не раскрывают секреты. `wss://` и HTTPS защищают транспорт, но не заменяют авторизацию внутри протокола.

#### Ключевые уточнения

- WebSocket — не синоним realtime: polling или SSE могут точнее соответствовать задаче.
- Снимок задаёт полное состояние, события доставляют изменения; вместе они позволяют восстановиться после разрыва.
- Transport не предоставляет автоматически exactly-once delivery, business ordering и idempotency.
- Backoff снижает частоту повторных подключений, а jitter распределяет попытки клиентов во времени.
- Backpressure решают с учётом смысла данных: некоторые события нельзя терять, другие можно объединять.
- Realtime-событие обычно обновляет кеш или хранилище; компоненты читают уже согласованное состояние.

#### Примеры выбора

| Сценарий | Обоснованный вариант |
| --- | --- |
| Обновить список после сохранения формы | mutation + инвалидация HTTP-кеша |
| Проверять статус импорта каждые 10 секунд | polling с остановкой после terminal status |
| Показывать лог deployment | SSE + event ID + новый снимок при пропуске |
| Чат с отправкой, typing и delivery status | WebSocket + подтверждения сообщений |
| Live price ticker | WebSocket/SSE + sequence + aggregation перед render |
| Редкие уведомления только при открытой странице | SSE или умеренный polling в зависимости от инфраструктуры |
