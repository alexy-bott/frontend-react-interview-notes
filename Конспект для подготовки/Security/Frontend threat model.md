#### Быстрый ответ

Threat model, или модель угроз, описывает: что система защищает, кто и через какие точки может атаковать, где проходят границы доверия, каков возможный ущерб и какой слой его снижает. Для frontend активами являются не только tokens, но и персональные данные, доступные действия, файлы, API-ответы, история форм, логи и данные аналитики.

Браузер пользователя нельзя считать доверенной средой: пользователь управляет DevTools, запросами, storage и исполняемым клиентом. Скрытая кнопка, route guard и TypeScript улучшают UX, но сервер всё равно проверяет аутентификацию, полномочия, владение ресурсом, tenant и бизнес-инварианты.

Frontend отвечает за собственный слой: безопасно выводит недоверенные данные, ограничивает third-party code, не раскрывает лишние данные и секреты, корректно проектирует session/CSRF flow и не отправляет PII в logs. Защита проверяется тестами, security headers, review и наблюдаемостью, а оставшийся риск фиксируется явно.

#### Модель анализа

```text
актив -> источник угрозы -> точка входа -> граница доверия
      -> сценарий атаки -> ущерб -> контроль -> проверка -> остаточный риск
```

| Шаг | Вопрос |
| --- | --- |
| Актив | Что потеряет ценность при чтении, изменении или недоступности? |
| Атакующий | Какие возможности у анонимного, обычного, привилегированного пользователя или поставщика? |
| Точка входа | URL, form, API, WebSocket, upload, `postMessage`, dependency? |
| Граница доверия | Где данные переходят между browser, API, CDN, iframe, CI или vendor? |
| Угроза | Как именно нарушается конфиденциальность, целостность или доступность? |
| Контроль | Какой слой предотвращает, ограничивает или обнаруживает сценарий? |
| Проверка | Каким test, header, log или alert подтверждается контроль? |

STRIDE можно использовать как подсказку категорий: подмена личности, изменение данных, отказ от авторства, раскрытие информации, отказ в обслуживании и повышение полномочий. Метод не заменяет конкретный сценарий и оценку ущерба.

#### Активы и границы доверия

Frontend обрабатывает данные в DOM, памяти JavaScript, cookies, Web Storage, IndexedDB, Cache Storage, network requests, source maps, error reports и analytics. Нужно определить срок жизни, получателей и допустимость каждого места.

Источники за границей доверия:

- URL, query и fragment;
- API, WebSocket и CMS, даже если они принадлежат компании;
- `localStorage` и IndexedDB, которые мог изменить другой код origin;
- `postMessage` из другого browsing context;
- загруженные файлы и пользовательский HTML/Markdown;
- npm dependencies, CDN и third-party scripts;
- service worker и ранее закешированный frontend bundle.

«Пришло с нашего backend» не означает «можно вставить как HTML». Доверие зависит от операции: JSON-текст безопасно отрисовывается как текст, но становится XSS-риском в `innerHTML` без sanitization.

#### Разделение ответственности

| Риск | Frontend | Server/инфраструктура |
| --- | --- | --- |
| Доступ к проекту | скрывает недоступное действие, не запрашивает лишнее | проверяет session, permission, tenant и resource ownership |
| XSS | использует безопасные DOM API, sanitization, избегает опасных sinks | задаёт CSP/Trusted Types по архитектуре, валидирует stored content |
| CSRF | передаёт token/header по протоколу | проверяет token и `Origin`, задаёт cookie attributes |
| Утечка PII | минимизирует DOM, storage и telemetry payload | минимизирует API response и доступ к данным |
| Supply chain | ограничивает dependencies и сторонние scripts | защищает CI, registry, artifact и deployment |

Defense in depth означает независимые уровни. React escaping снижает риск текстового XSS, но не защищает `dangerouslySetInnerHTML` и скомпрометированный script. CSP ограничивает выполнение кода, но не исправляет небезопасный sink. `HttpOnly` скрывает cookie от JavaScript, но XSS-код всё ещё может действовать в открытой сессии.

#### Пример: удаление проекта

```text
Актив:
- проект и его данные

Атакующие сценарии:
- обычный пользователь подставляет чужой projectId
- вредный сайт инициирует cookie-auth request
- XSS выполняет действие в текущей сессии

Контроли:
- server проверяет session, permission, tenant и project ownership
- state-changing request проходит CSRF-защиту
- UI показывает подтверждение и не раскрывает закрытые поля
- audit log фиксирует actor, projectId, result и request correlation id

Проверка:
- authorization integration tests
- CSRF tests
- XSS/CSP checks
- alert на аномальные массовые удаления
```

Confirmation dialog защищает от случайного действия, а не от обхода полномочий. Audit log помогает расследовать событие, но не предотвращает его; для критического риска нужен также alert и возможность остановки/восстановления.

#### Приоритизация

Список всех теоретических атак бесполезен без приоритета. Оценивают вероятность, достижимость, стоимость атаки, масштаб данных, полномочия и обратимость ущерба. Сначала закрывают сценарии с высоким impact и реалистичным путём, затем принимают, переносят или дополнительно контролируют остаточный риск.

Модель пересматривают при новых trust boundaries: OAuth provider, iframe, payment SDK, upload, service worker, новый API, admin flow или изменение CI/CD. Это часть проектирования, а не разовая таблица перед релизом.

#### Ключевые уточнения

- Клиентский код и состояние браузера контролируются пользователем и не являются серверной security boundary.
- Недоверенность данных определяется источником и способом использования, а не только доменом.
- Каждый контроль связывается с конкретной угрозой и способом проверки.
- UX-проверка, предотвращение, ограничение ущерба, обнаружение и восстановление — разные функции защиты.
- Defense in depth сохраняет независимые уровни, но не оправдывает слабость основного контроля.
- Модель угроз обновляется вместе с архитектурой и реальными инцидентами.
