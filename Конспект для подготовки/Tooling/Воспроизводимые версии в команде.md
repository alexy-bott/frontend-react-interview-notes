#### Ответ на 60 секунд

Чтобы у всех разработчиков и CI были одинаковые версии зависимостей, недостаточно написать версии в `package.json`. Нужны: один package manager, один lock-файл, зафиксированная версия package manager, понятная версия Node, воспроизводимая install-команда и CI/Docker, которые используют те же правила.

Практический набор: коммитить lock-файл, не смешивать npm/yarn/pnpm, указать `packageManager` в `package.json`, указать Node через `engines`, `.nvmrc`, `.node-version` или Docker image, использовать `npm ci` / `yarn install --immutable` / `pnpm install --frozen-lockfile` в CI, не коммитить `node_modules`, не удалять lock без причины.

Lock-файл фиксирует точное dependency tree, а frozen install заставляет установку упасть, если `package.json` и lock расходятся. Так команда быстрее ловит случайные изменения зависимостей и избегает ситуации “у меня локально работает, а у тебя нет”.

#### Ключевая схема

| Что фиксируем | Чем фиксируем |
| --- | --- |
| Версию Node | `.nvmrc`, `.node-version`, `engines`, Docker image |
| Package manager | `packageManager`, README, CI commands |
| Dependency tree | lock-файл |
| Install в CI | `npm ci`, `yarn install --immutable`, `pnpm install --frozen-lockfile` |
| Registry/auth | `.npmrc` + env/CI variables |
| Обновления | Renovate/Dependabot, review lock diff, tests |
| Runtime image | Dockerfile с конкретным Node/base image |

#### Развернутый ответ

**`package.json` задаёт диапазоны, lock-файл фиксирует результат.**
Если в manifest стоит `^1.2.3`, package manager может выбрать совместимую версию в диапазоне. Lock-файл записывает конкретную выбранную версию и транзитивное дерево. Поэтому без lock-файла две установки в разные дни могут отличаться.

**Один проект - один package manager.**
npm, Yarn и pnpm по-разному строят lock-файлы и `node_modules`. Если часть команды запускает npm, а часть pnpm, можно получить разные dependency trees, разные peer warnings и разные ошибки resolution. В проекте должны быть один lock-файл, одна команда установки и один package manager в документации/CI.

**Frozen install нужен именно для проверки дисциплины.**
`npm ci` ставит зависимости по lock-файлу и падает, если lock не соответствует `package.json`. Аналоги: `yarn install --immutable`, `pnpm install --frozen-lockfile`. Это важно для merge requests: если разработчик изменил dependency в `package.json`, но забыл обновить lock, CI должен упасть.

**Версия Node тоже часть воспроизводимости.**
Даже с одинаковыми пакетами разные версии Node/npm могут иначе обрабатывать package exports, ESM/CJS, postinstall scripts, optional dependencies и native bindings. Поэтому версию Node фиксируют через `.nvmrc`/`.node-version`, `engines`, Volta/asdf или Docker image. В CI лучше использовать явный Node image/version, а не “что стоит на runner”.

**Docker и CI должны повторять локальные правила.**
Если локально проект использует pnpm, а Dockerfile запускает `npm install`, воспроизводимость сломана. Если в Docker сначала копируют `package.json` и lock, затем делают frozen install, cache работает лучше и dependency layer меняется только при изменении manifest/lock.

**Обновления зависимостей должны быть управляемыми.**
Renovate/Dependabot полезны, когда MR показывает, что изменилось. Но даже patch/minor updates требуют проверок: install, typecheck, tests, build, bundle budget. Lock diff не игнорируют: он показывает реальные изменения транзитивных пакетов.

#### Где применяется во frontend

| Ситуация | Что проверить |
| --- | --- |
| У одного разработчика проект не стартует | Node version, package manager, lock, clean install |
| CI падает на install | `package.json` и lock расходятся |
| После merge изменился bundle | обновились транзитивные зависимости или разные lock-файлы |
| Docker build отличается от локального | install command, Node image, lock copy order |
| Peer dependency warning | версии React/testing/UI-kit и package manager resolution |
| Private package не ставится | `.npmrc`, registry, CI token |
| Security update | lock diff, tests, build, bundle budget |

#### Если уточнили

> - **Как сделать, чтобы версии пакетов были одинаковые?** Коммитить lock-файл и использовать frozen install в CI. Для локальной команды дополнительно фиксировать package manager и Node version.
> - **Что важнее: `engines` или lock?** Это разные уровни. `engines` описывает Node/package manager constraints, lock фиксирует dependency tree.
> - **Почему `npm install` может изменить lock?** Это команда разработки: она может пересчитать dependency tree, если manifest и lock расходятся или добавляется пакет.
> - **Почему нельзя коммитить `node_modules`?** Это сгенерированная директория, зависящая от платформы и package manager. Коммитят manifest + lock, а установку повторяют.
> - **Что делать при конфликте lock-файла?** Разрешить конфликт через package manager, затем выполнить clean install, tests/build и посмотреть итоговый diff.

#### Пример policy для проекта

```json
{
  "packageManager": "pnpm@9.15.0",
  "engines": {
    "node": ">=20 <23"
  },
  "scripts": {
    "install:ci": "pnpm install --frozen-lockfile",
    "typecheck": "tsc --noEmit",
    "build": "vite build"
  }
}
```

```text
# .node-version
20.18.0
```

Такой набор не гарантирует магически одинаковую среду, но задаёт правила: какая версия Node ожидается, какой package manager использовать и какая команда должна проверять lock.

#### Практический чеклист

| Нужно | Почему |
| --- | --- |
| Один lock-файл | одно dependency tree |
| `packageManager` | одинаковый manager/version |
| `engines` или Node version file | меньше расхождений Node |
| frozen install в CI | lock и manifest не расходятся |
| явный Node image в Docker/CI | runner не выбирает случайную версию |
| clean install при странных ошибках | убрать локальный state |
| review lock diff | видеть реальные dependency changes |

#### Частые ошибки

- Коммитить несколько lock-файлов.
- Использовать `npm install` в CI там, где нужен frozen install.
- Обновлять `package.json` без lock-файла.
- Не фиксировать Node version.
- Менять package manager без обновления README, CI и Dockerfile.
- Игнорировать peer dependency warnings.
- Удалять lock-файл при конфликте вместо корректного разрешения.
