#### Быстрый ответ

Realtime-экран получает изменения без ручного обновления страницы. Его проектирование начинается с требований к направлению, частоте и допустимой задержке данных: для редких обновлений достаточно polling, для одностороннего потока от сервера подходит Server-Sent Events (SSE), а для постоянного двустороннего обмена - WebSocket.

Надёжная модель обычно сочетает начальный снимок данных (snapshot) по HTTP и последующие события. Клиент загружает согласованное состояние, применяет новые события к query cache или запрашивает данные заново, а после разрыва соединения восстанавливает подписку и проверяет, не пропущены ли изменения.

#### Ключевая схема

```text
HTTP snapshot
-> открытие канала и подписка
-> получение события
-> проверка формата, версии и id
-> обновление кеша | invalidation и refetch
-> разрыв соединения
-> reconnect с задержкой
-> восстановление с cursor/id | новый snapshot
```

| Транспорт | Направление | Когда выбирать | Существенное ограничение |
| --- | --- | --- | --- |
| Polling | request/response по расписанию | обновления редкие, допустима задержка | лишние запросы и задержка до следующего интервала |
| SSE | server -> client | уведомления, логи, статусы задач | клиент не отправляет сообщения по тому же потоку |
| WebSocket | client <-> server | чат, совместное редактирование, частые команды | нужен собственный протокол, reconnect и контроль потока |

#### Базовая модель

Snapshot - полный согласованный срез данных на определённый момент. Событие - сообщение об изменении после этого момента, например `order.updated`. Только поток событий не гарантирует, что новый клиент знает исходное состояние, а только snapshot быстро устаревает. Их сочетание даёт базу и последующие изменения.

Событие должно иметь понятный контракт. Обычно в нём есть тип, идентификатор события, версия протокола и payload. Идентификатор позволяет не применять дубликат дважды и может помочь запросить изменения после последнего обработанного события. Версия сообщает клиенту, умеет ли он интерпретировать сообщение.

Доставка сообщения и обновление интерфейса - разные этапы. Transport получает строку или бинарные данные, API-слой разбирает и проверяет внешний payload, слой данных обновляет кеш или объявляет его устаревшим, а React выполняет render из нового состояния. Компоненту не нужно напрямую управлять DOM после каждого сообщения.

#### Развернутый ответ

**Выбор транспорта.** Polling проще развернуть и наблюдать; query-библиотека может останавливать его для скрытой вкладки и повторять запросы после возвращения. SSE использует обычный HTTP-поток и `EventSource`, поддерживает автоматическое переподключение и идентификаторы событий. WebSocket создаёт постоянный двусторонний канал, но приложение само определяет типы сообщений, подтверждения, повторные отправки и восстановление подписок.

**Начальная синхронизация.** Между получением snapshot и открытием канала может возникнуть окно, в котором данные изменятся. Полностью закрыть его можно только при поддержке backend: snapshot содержит cursor или revision, а подписка запрашивает события после этой позиции. Если такого протокола нет, практичный вариант - открыть канал и повторно получить snapshot либо выполнить refetch после подключения, принимая возможный дополнительный запрос.

**Обновление кеша.** Полное событие с проверенным объектом позволяет точечно изменить сущность в query cache. Сигнал вида `order.changed` не содержит достаточно данных, поэтому безопаснее сделать invalidation и refetch. Точечное обновление быстрее, но обязано учитывать списки с разными фильтрами и сортировкой; invalidation проще поддерживать.

**Порядок и дубликаты.** WebSocket сохраняет порядок кадров внутри одного соединения, но после reconnect приложение всё равно должно определить, какие события подтверждены, пропущены или повторены. Для операций, чувствительных к порядку, backend выдаёт возрастающую revision, sequence или cursor. Клиент сравнивает её с последней применённой позицией и при разрыве последовательности запрашивает восстановление.

**Reconnect.** Немедленные повторные подключения множества клиентов могут перегрузить сервис. Используют экспоненциальную задержку (exponential backoff) с небольшим случайным отклонением (jitter), чтобы клиенты не повторяли попытку одновременно. После reconnect восстанавливают auth и подписки, а затем подтверждают актуальность данных.

**Высокая частота событий.** Если сообщения приходят быстрее, чем интерфейс успевает их обрабатывать, растут очередь, память и число render. Это давление потока данных называют backpressure. В браузерном API `WebSocket` нет встроенного управления backpressure, поэтому приложение ограничивает собственный буфер, объединяет события, обновляет UI с заданной частотой или переходит на протокол, где сервер умеет замедлять отправку.

**Жизненный цикл.** Соединение открывают только при нужной сессии и подписке, закрывают при logout и смене пользователя, а обработчики удаляют при завершении владельца соединения. Вкладка в background может замедлять timers или надолго терять сеть, поэтому возвращение в visible-состояние является поводом проверить свежесть snapshot.

#### Пример

Событие, содержащее только идентификатор изменённой сущности, не пытается воспроизвести серверное состояние на клиенте:

```ts
type OrderChangedEvent = {
  type: "order.changed";
  eventId: string;
  orderId: string;
};

function applyRealtimeEvent(event: OrderChangedEvent) {
  queryClient.invalidateQueries({ queryKey: ["order", event.orderId] });
  queryClient.invalidateQueries({ queryKey: ["orders"] });
}
```

До вызова функции входящее JSON-сообщение должно быть разобрано и проверено как внешние данные. Invalidation подходит здесь потому, что событие не содержит нового заказа; cache получит актуальное состояние обычным API-запросом.

#### Ключевые уточнения

- Realtime описывает требование к свежести интерфейса, а WebSocket - только один из транспортов. Для редких обновлений polling может быть проще и дешевле.
- Reconnect восстанавливает соединение, но не доказывает, что данные актуальны. Нужен cursor, журнал событий или повторный snapshot.
- Сетевой порядок внутри соединения не заменяет прикладные id, revision и правила обработки дубликатов после reconnect.
- Точечное обновление кеша возможно только при достаточном и проверенном payload. Событие-уведомление обычно приводит к invalidation.
- Throttle и batching уменьшают частоту обновления UI, но требуют определить, какие промежуточные события можно безопасно объединить или отбросить.
