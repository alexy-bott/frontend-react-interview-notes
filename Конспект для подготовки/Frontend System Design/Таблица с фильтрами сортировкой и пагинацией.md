#### Ответ на 60 секунд

Таблица с фильтрами, сортировкой и пагинацией проектируется вокруг API-контракта и состояния страницы. Если данных много, frontend не должен загружать всё и фильтровать в браузере. Клиент хранит `page/cursor`, `limit`, `sort`, `filters`, `search` в URL или route state, отправляет их на backend, а server state хранит в query/cache layer с полным cache key.

Нужно сразу описать UI states: первая загрузка, refetch, empty result, error, disabled actions, selected rows, bulk actions, optimistic updates, access denied. Для больших таблиц важны debounce search, cancellation устаревших запросов, stable sorting, virtualization, сохранение selected rows и понятная политика cache invalidation после mutations.

Главная мысль: таблица - это не просто `<table>`. Это связка URL state, API query params, cache key, отображения состояний, доступности, производительности и тестов.

#### Ключевая схема

```text
URL params
-> query args
-> API request
-> server state cache
-> table view model
-> UI states and actions
```

| Часть | Что решить |
| --- | --- |
| Pagination | page/offset или cursor |
| Sorting | поля, направление, stable tie-breaker |
| Filters | формат query params, пустые значения |
| Search | debounce, abort, min length |
| Cache key | endpoint + page/cursor + sort + filters + search |
| Selection | local state или URL/store для bulk actions |
| Performance | virtualization, memoized columns, Map/Set |

#### Развернутый ответ

Первый выбор - server-side или client-side обработка. Если список маленький и полностью загружается один раз, client-side filter/sort может быть нормальным. Если данных много, есть права доступа, поиск, сортировка по backend-полям или pagination, обработка должна быть на сервере.

URL state нужен для deep link и восстановимости. Если пользователь выбрал `status=active`, `sort=-createdAt`, `page=3`, ссылка должна открыть тот же вид. Локальное состояние подходит для временных UI-деталей вроде открытого dropdown, но параметры результата лучше держать в URL.

Query/cache layer должен получать все параметры, влияющие на результат. Если `filter` не входит в query key, UI может показать закешированные данные от другого фильтра. После mutation нужно решить, что делать: invalidation списка, точечное обновление строки, optimistic update или refetch.

Selection требует отдельной модели. Если пользователь выбирает rows на текущей странице, достаточно локального `Set`. Если selection должен жить между страницами, фильтрами или route changes, нужна более явная политика: selected ids, clear on filter change, select all matching query или только visible rows.

Performance зависит от размера данных и частоты обновлений. Для больших таблиц используют virtualization, memoized columns, `Set` для selected ids, `Map` для lookup по id, debounce search и отмену запросов. Сортировка/фильтрация на каждый render без memoization может тормозить даже при средних данных.

#### Где применяется во frontend

| Ситуация в проекте | Что проектируется | Конкретное решение |
| --- | --- | --- |
| Пользователь делится ссылкой на отфильтрованную таблицу | состояние результата должно переживать reload | хранить filters/sort/page в URL query params |
| Search input быстро меняется | старые ответы могут прийти позже новых | debounce + AbortController/query cancellation |
| Выбрано 100 rows для bulk action | `includes` в каждой строке станет дорогим | хранить selected ids в `Set` |
| После удаления строки таблица показывает старые данные | cache устарел после mutation | invalidation query или точечное удаление из cache |
| Таблица содержит 20 000 строк | DOM и render становятся тяжёлыми | server pagination и/или virtualization |
| Сортировка по `createdAt` даёт прыгающие элементы | несколько строк имеют одинаковую дату | добавить stable tie-breaker: `createdAt desc, id desc` |

> [!faq]+ Уточнения
> - Для больших данных filter/sort/pagination обычно server-side.
> - URL state подходит для filters/sort/page/search.
> - Cache key должен включать все query params.
> - Offset pagination удобна для numbered pages, cursor - для infinite scroll и изменяемых данных.
> - Selection across pages требует отдельного product decision.
> - Virtualization не заменяет pagination; она уменьшает DOM/render cost.

#### Пример

```tsx
function UsersPage() {
  const [params, setParams] = useSearchParams();

  const queryArgs = {
    page: Number(params.get("page") ?? 1),
    sort: params.get("sort") ?? "-createdAt",
    status: params.get("status") ?? "all",
    search: params.get("search") ?? "",
  };

  const usersQuery = useUsersQuery(queryArgs);
  const selectedIds = useMemo(() => new Set<string>(), []);

  return (
    <UsersTable
      rows={usersQuery.data?.items ?? []}
      loading={usersQuery.isLoading}
      refetching={usersQuery.isFetching}
      selectedIds={selectedIds}
      onChangeParams={setParams}
    />
  );
}
```

#### Частые ошибки

- Хранить filters/page только локально и терять deep link.
- Не включать sort/filter/search в cache key.
- Делать `selectedIds.includes(id)` для каждой строки большого списка.
- Сортировать state-array мутацией через `items.sort()`.
- Не сбрасывать page при изменении filters/search.
- Не различать initial loading и background refetch.
- Не проектировать empty state отдельно от error state.
