#### Быстрый ответ

Strategy («Стратегия») - поведенческий паттерн, который представляет несколько взаимозаменяемых способов решения одной задачи через общий контракт. Основной код получает выбранную функцию или объект и вызывает его, не зная деталей конкретного алгоритма.

Во frontend стратегия подходит для действительно изменяемого поведения: правил сортировки и валидации, расчёта цены, способа авторизации или реализации аналитики. Она полезна, когда варианты имеют одинаковый смысл, выбираются во время выполнения и развиваются независимо. Для одного короткого условия обычный `if` понятнее отдельной абстракции.

#### Ключевая схема

```text
входные данные
-> выбор стратегии
-> общий контракт
-> конкретный алгоритм
-> результат ожидаемой формы
```

| Часть | Роль |
| --- | --- |
| Контекст (context) | код, которому нужен результат, но не детали алгоритма |
| Контракт стратегии | одинаковые входные данные, результат и правила ошибок |
| Конкретная стратегия | один вариант алгоритма |
| Выбор стратегии | решение по config, props, типу сценария или данным |

#### Базовая модель

Без Strategy основной код часто содержит растущую развилку:

```text
если тип A -> выполнить алгоритм A
если тип B -> выполнить алгоритм B
если тип C -> выполнить алгоритм C
```

Паттерн выносит алгоритмы за пределы контекста. Контекст вызывает, например, `calculate(input)`, а конкретная реализация определяет способ расчёта. Новый вариант можно добавить отдельной реализацией, если общий контракт по-прежнему описывает все варианты без специальных исключений.

Во frontend Strategy обычно является функцией, объектом с одним методом или зависимостью сервиса. Классы не обязательны: важна взаимозаменяемость поведения, а не синтаксис реализации.

#### Развернутый ответ

**Контракт.** Стратегии должны получать данные одного смыслового уровня и возвращать сопоставимый результат. Если одна сортировка меняет исходный массив, другая создаёт копию, а третья требует дополнительный сетевой запрос, они формально похожи по имени, но имеют разные побочные эффекты и плохо взаимозаменяемы.

**Выбор.** Стратегию можно передать через props или dependency injection либо выбрать из словаря по проверенному ключу. Сам выбор остаётся явной бизнес-развилкой; Strategy не устраняет условия полностью, а отделяет выбор варианта от его реализации.

**Расширение.** Паттерн упрощает добавление вариантов, когда стабильная часть сценария уже выделена. Например, форма одинаково управляет полями и submit, но получает разные правила валидации. Если каждый вариант требует другой структуры UI и другого жизненного цикла, общий context становится искусственным и стратегии уже не решают задачу.

**Тестирование.** Алгоритмы проверяются отдельно обычными unit-тестами. Контекст можно протестировать с простой fake-стратегией, чтобы проверить, какие данные он передаёт и как использует результат. Это уменьшает необходимость воспроизводить все варианты в тестах компонента.

#### Где применяется во frontend

| Сценарий | Изменяемое поведение | Почему подходит Strategy |
| --- | --- | --- |
| Таблица | comparator для имени, даты или приоритета | все варианты определяют порядок тех же строк |
| Форма | правила валидации для разных сценариев | form state и отображение ошибок остаются общими |
| Checkout | расчёт комиссии по тарифу или стране | алгоритмы возвращают цену по одному контракту |
| Analytics | отправка события в разные providers | приложение вызывает единый `track`, не знает API SDK |
| Auth | password, OAuth или SSO | варианты запускают разный flow, но возвращают согласованный auth result |

Strategy не нужна только потому, что функция передаётся через props. Callback `onClick` сообщает о событии владельцу компонента; стратегией он становится, когда представляет один из взаимозаменяемых алгоритмов, которые использует сам context.

#### Пример

Таблица принимает comparator - стратегию определения порядка двух пользователей:

```ts
type Compare<T> = (left: T, right: T) => number;

const compareUsersByName: Compare<User> = (left, right) =>
  left.name.localeCompare(right.name);

const compareUsersByCreatedAt: Compare<User> = (left, right) =>
  right.createdAt.localeCompare(left.createdAt);

function sortUsers(users: readonly User[], compare: Compare<User>): User[] {
  return [...users].sort(compare);
}
```

`sortUsers` отвечает за копирование и запуск сортировки, а стратегия - только за сравнение двух элементов. Одинаковый контракт позволяет заменить правило без изменения функции-контекста.

#### Ключевые уточнения

- Strategy отделяет выбор алгоритма от его выполнения, но сам выбор варианта всё равно должен находиться в понятном месте.
- Общая сигнатура недостаточна: взаимозаменяемые стратегии должны иметь согласованные побочные эффекты, ошибки и семантику результата.
- Обычная функция или callback может реализовать Strategy; отдельная иерархия классов для этого не требуется.
- Простое и стабильное условие не нуждается в паттерне. Абстракция оправдана изменяемым семейством вариантов, а не желанием убрать любой `if`.
