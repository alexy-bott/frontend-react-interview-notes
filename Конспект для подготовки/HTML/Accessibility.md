#### Ответ на 60 секунд

Accessibility, или доступность, - это подход к разработке интерфейсов, при котором сайтом или приложением могут пользоваться люди с разными возможностями: с нарушениями зрения, слуха, моторики, когнитивными особенностями, а также пользователи клавиатуры, скринридеров, увеличения масштаба или нестабильного устройства ввода. Это не отдельная “фича”, а часть качества интерфейса.

На практике доступность обеспечивается семантической HTML-разметкой, правильными ролями и `aria-*` там, где семантики не хватает, видимым focus state, навигацией с клавиатуры, достаточным контрастом, текстовыми альтернативами для изображений и корректной связью `label` с полями формы. Доступная реализация улучшает не только жизнь пользователей с assistive technologies, но и общий UX: интерфейс становится понятнее, предсказуемее и устойчивее.

#### Ключевая схема

| Область | Что проверить |
| --- | --- |
| Семантика | правильные HTML-элементы вместо лишних `div` |
| Клавиатура | `Tab`, `Enter`, `Space`, `Esc`, видимый фокус |
| Формы | `label`, текст ошибки, `aria-describedby` |
| Медиа | осмысленный `alt`, captions, transcript |
| Визуальная часть | контраст, масштабирование, не только цвет |
| ARIA | использовать как дополнение, а не замену HTML |

#### Развернутый ответ

WCAG описывает доступность через четыре принципа: интерфейс должен быть воспринимаемым, управляемым, понятным и надёжным для разных пользователей и технологий. На практике это превращается в конкретные решения: текстовые альтернативы, keyboard navigation, контраст, понятные ошибки, предсказуемое поведение и совместимость со screen readers.

Клавиатурная доступность означает, что пользователь может пройти по интерактивным элементам через `Tab`, активировать действия через `Enter` или `Space`, закрыть модальное окно через `Esc`, видеть текущий фокус и не застревать в focus trap. Для custom-компонентов это приходится проектировать явно, поэтому нативные элементы часто надёжнее.

ARIA нужна, когда HTML-семантики не хватает: например, для сложного combobox, tabs, dialog или live region. Но `aria-*` не добавляет поведение само по себе. `role="button"` не сделает `div` кнопкой полностью: нужно добавить фокус, keyboard handlers, disabled state и доступное имя.

Визуальные сигналы должны иметь не только цвет. Ошибка в форме должна быть текстом, связана с полем через `aria-describedby` и заметна screen reader. Контраст, масштабирование, отсутствие критичного текста внутри изображения и нормальные focus states напрямую влияют на возможность пользоваться интерфейсом.

> [!faq]+ Уточнения
> - WCAG удобно помнить через POUR: perceivable, operable, understandable, robust.
> - Нативный HTML обычно даёт роль, фокус и keyboard behavior без ручной сборки.
> - `aria-*` описывает смысл и состояние, но не реализует интерактивное поведение.
> - Focus state нельзя удалять без полноценной замены через `:focus-visible`.
> - Цвет не должен быть единственным способом показать ошибку, статус или выбор.

#### Пример

```html
<form>
  <label for="email">Email</label>
  <input
    id="email"
    name="email"
    type="email"
    autocomplete="email"
    aria-describedby="email-error"
  />

  <p id="email-error" role="alert">
    Введите корректный email.
  </p>

  <button type="submit">Отправить</button>
</form>
```

Здесь поле связано с label, ошибка связана с полем через `aria-describedby`, а кнопка является настоящей кнопкой, доступной с клавиатуры.

#### Частые ошибки

- Делать кликабельный `div` вместо `button` или `a`.
- Убирать `outline` без полноценной замены через `:focus-visible`.
- Писать `alt="image"` вместо осмысленного описания изображения.
- Использовать ARIA там, где достаточно нативного HTML.
- Делать модальное окно без управления фокусом и закрытия по `Esc`.
