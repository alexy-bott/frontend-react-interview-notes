#### Быстрый ответ

Frontend performance (производительность интерфейса) - это скорость, отзывчивость и визуальная стабильность приложения с точки зрения реального пользователя. Оптимизация начинается с измерения конкретного сценария, поиска узкого места и проверки результата, а не с применения списка советов.

Текущие Core Web Vitals: LCP измеряет появление главного контента, INP - задержку взаимодействий, CLS - неожиданные сдвиги layout. Ориентиры категории good: LCP не более `2.5 s`, INP не более `200 ms`, CLS не более `0.1` на 75-м перцентиле посещений отдельно для мобильных и настольных устройств.

Причины различаются. LCP зависит от TTFB, обнаружения и загрузки главного ресурса и рендеринга. INP ухудшается из-за занятого основного потока, долгих задач, тяжёлых обработчиков и обновлений интерфейса. CLS создают элементы без зарезервированного места, поздние вставки и нестабильная загрузка шрифтов.

Исправление выбирают по измеренной причине, затем сравнивают результат в лабораторных условиях и проверяют полевые данные через RUM. Локальный Lighthouse помогает диагностике, но не заменяет данные реальных пользователей.

#### Ключевая схема

```text
выбрать пользовательский сценарий
→ проверить полевые данные и воспроизвести проблему в лаборатории
→ разложить задержку по этапам
→ найти основное узкое место
→ внести одно направленное изменение
→ сравнить метрики и побочные эффекты
→ установить бюджет производительности и мониторинг регрессии
```

| Симптом | Основные участки проверки |
| --- | --- |
| Главный контент появляется поздно | TTFB, критический путь, LCP-ресурс, клиентский рендеринг |
| Интерфейс поздно реагирует | задержка ввода, обработчик, render, layout, paint |
| Контент прыгает | размеры медиа, шрифты, баннеры, поздние вставки в DOM |
| Долго загружается JavaScript | состав bundle, chunks, кэш, сжатие |
| Страница тормозит после работы | обработчики, renders, layout thrashing, рост памяти |

#### Базовая модель загрузки

Пользователь ждёт не один «frontend». Итоговая задержка складывается из последовательных и параллельных этапов:

```text
навигация
→ DNS / соединение / TLS
→ ответ сервера и TTFB
→ разбор HTML и обнаружение ресурсов
→ CSS, fonts, images, JavaScript
→ style / layout / paint
→ hydration или клиентская инициализация
→ готовность к устойчивому взаимодействию
```

Оптимизация одного этапа полезна только в пределах его вклада в критический путь. Например, уменьшение JavaScript не исправит LCP, если сервер отвечает четыре секунды. Быстрый TTFB не спасёт страницу, если LCP-изображение обнаруживается только после выполнения большого клиентского bundle.

Waterfall показывает сетевые зависимости во времени: когда ресурс был обнаружен, чего ждал и конкурировал ли с более важными загрузками. Профиль Performance показывает работу основного потока и этапы рендеринга. Эти представления отвечают на разные части одной проблемы.

#### Полевые и лабораторные данные

Полевые данные собираются у реальных пользователей. Они включают разные устройства, сети, состояние кэша, географию и действия. RUM, или Real User Monitoring, связывает метрику со страницей, версией приложения и контекстом сессии.

Лабораторное измерение запускает управляемый сценарий в DevTools, Lighthouse или автоматическом тесте. Оно удобно для повторения и поиска причины: сетевой waterfall, CPU-профиль, долгие задачи, сдвиги layout и покрытие bundle.

INP требует реальных взаимодействий и является прежде всего полевой метрикой. Lighthouse без пользовательского ввода использует TBT как лабораторный индикатор занятости основного потока, но TBT не равен INP.

Рабочий процесс использует оба источника: полевые данные показывают реальную проблему, лаборатория помогает её воспроизвести и объяснить, а полевые данные после релиза подтверждают эффект.

#### LCP

Largest Contentful Paint оценивает, когда в viewport (области просмотра) отрисован крупнейший подходящий элемент основного контента. Это может быть изображение, постер видео или текстовый блок.

Полезно разложить LCP на четыре части:

1. TTFB - время до первого байта документа.
2. Resource load delay - задержка до начала загрузки LCP-ресурса.
3. Resource load duration - длительность загрузки ресурса.
4. Element render delay - ожидание от готовности ресурса до отрисовки элемента.

Такое разложение определяет направление исправления. Высокий TTFB ведёт к backend, CDN и кэшированию. Позднее обнаружение изображения - к HTML, preload или приоритету. Долгая загрузка - к формату, размеру и сети. Задержка отрисовки - к блокирующему CSS и JavaScript, клиентскому рендерингу или занятости основного потока.

LCP-изображение обычно не загружают лениво. Ему задают корректный URL в исходном HTML, размеры и при необходимости `fetchpriority="high"`; `preload` добавляют, если ресурс действительно критичен и иначе обнаруживается поздно.

#### INP

Interaction to Next Paint оценивает отзывчивость по взаимодействиям пользователя. Задержка взаимодействия состоит из:

```text
задержка до начала обработки
→ выполнение обработчиков события
→ задержка подготовки следующего кадра
```

Задержка ввода растёт, если событие пришло во время долгой задачи. Время обработки увеличивают тяжёлый обработчик, JavaScript-вычисление или обновление большого дерева. Задержка представления включает оставшийся рендеринг: стили, layout и paint.

Поэтому debounce не является универсальным исправлением INP. Он может сократить частоту необязательных вызовов, но не уменьшит стоимость одного тяжёлого render. Диагностика должна показать, какая часть взаимодействия занимает время.

Типичные исправления:

- удалить или отложить некритичный JavaScript;
- разделить длинную работу на короткие задачи с передачей управления браузеру;
- перенести чистое CPU-вычисление в Web Worker;
- уменьшить область обновления DOM или React-дерева;
- виртуализировать действительно большой список;
- устранить повторные принудительные пересчёты layout;
- давать визуальную обратную связь до необязательной тяжёлой работы.

#### CLS

Cumulative Layout Shift измеряет неожиданные перемещения видимого контента. Проблема важна не только визуально: пользователь может нажать не на тот элемент, если кнопка сместилась в момент взаимодействия.

Основные причины:

- у изображения, видео или iframe не зарезервированы размеры;
- баннер или сообщение вставляется над существующим контентом;
- системный и загружаемый шрифты имеют сильно разные метрики;
- placeholder не соответствует размеру загруженного компонента;
- анимация меняет свойства layout вместо `transform`, обрабатываемого на этапе compositing.

Для медиа задают `width`/`height` или `aspect-ratio`. Для динамического блока заранее резервируют место либо вставляют его в область, где сдвиг ожидаем пользователем. Шрифты оптимизируют сочетанием `font-display`, preload только нужных файлов, подмножеств символов и близких метрик запасного шрифта.

#### JavaScript и bundle

Стоимость JavaScript состоит не только из байтов по сети. Файл нужно скачать, распаковать, разобрать, скомпилировать и выполнить. На слабом мобильном процессоре даже небольшой сжатый bundle может надолго занять основной поток.

Основные рычаги:

- удалить неиспользуемый код и тяжёлые зависимости;
- разделить bundle по маршрутам и редко используемым возможностям;
- не загружать один пакет в нескольких несовместимых версиях;
- использовать tree shaking в production и проверять его анализатором bundle;
- надолго кэшировать assets с хэшем содержимого в имени;
- не дробить код на настолько мелкие chunks, что растут число запросов и сетевые накладные расходы;
- контролировать сторонние скрипты отдельно от собственного приложения.

Динамический импорт полезен, когда модуль не нужен для первого сценария. Если вынесенный chunk всегда требуется сразу после загрузки, разделение может только добавить сетевую зависимость.

#### Рендеринг и основной поток

Изменение DOM или CSS может вызвать style calculation, layout, paint и compositing. Стоимость зависит от свойства и размера затронутого дерева.

Для анимации обычно выбирают `transform` и `opacity`, потому что браузер часто может обновить их на этапе compositing без нового layout. Это не абсолютная гарантия: создание слоёв потребляет память, а сложный paint или слишком много слоёв тоже ухудшают производительность.

Чередование чтения layout и записи в DOM создаёт layout thrashing. Чтения группируют до записей, а визуальные обновления объединяют через `requestAnimationFrame`.

`content-visibility: auto` может пропустить рендеринг далёкого содержимого вне области просмотра. Виртуализация полезна для больших списков, но усложняет управление focus, измерение высоты и доступность; её не применяют к десяти простым строкам без измеренной проблемы.

#### Images, fonts и network

Изображение должно соответствовать реальному размеру отображения. `srcset` и `sizes` позволяют браузеру выбрать вариант под viewport и плотность пикселей. AVIF или WebP уменьшают передаваемый объём, если качество и поддержка подходят проекту.

Ленивую загрузку применяют к медиа вне области просмотра, но не к главному LCP-ресурсу. Явные размеры одновременно уменьшают CLS.

HTTP-кэширование с хэшем содержимого позволяет долго хранить неизменяемые assets. HTML обычно требует более осторожной политики, чтобы новая версия могла сослаться на новые файлы с хэшами.

`preconnect` заранее создаёт соединение с важным внешним origin. `preload` сообщает о конкретном критичном ресурсе. Обе подсказки конкурируют за сеть, поэтому их добавляют после анализа waterfall, а не для каждого файла.

#### Пример диагностики

Симптом: главное изображение карточки товара появляется через `4.2 s`, а сжатый bundle весит `900 KB`.

1. Полевые данные подтверждают плохой LCP на мобильных устройствах.
2. Waterfall показывает TTFB `500 ms`, но изображение начинает загружаться только после клиентского запроса и выполнения входного bundle.
3. Главная причина - позднее обнаружение LCP-ресурса, а не только размер картинки.
4. Данные товара и URL изображения переносят в HTML, созданный на сервере; изображению задают размеры и высокий приоритет.
5. Редко используемый редактор выносят через динамический импорт, уменьшая работу основного потока до первого paint.
6. Лабораторное измерение подтверждает ранний старт загрузки и меньшую задержку отрисовки.
7. RUM после развёртывания проверяет LCP и одновременно INP/CLS, чтобы улучшение не создало новую регрессию.

Пример важен порядком рассуждения: сначала измеренная причинная цепочка, затем конкретные изменения. Простое сжатие изображения уменьшило бы время загрузки, но не устранило бы несколько секунд ожидания до начала запроса.

#### Бюджеты производительности

Разовое ускорение легко потерять. Бюджет превращает ожидание в проверяемое ограничение: максимальный начальный JavaScript, размер критичного изображения, число сторонних запросов, LCP/CLS в синтетическом тесте или допустимая доля долгих задач.

Бюджет должен соответствовать пользовательскому сценарию и устройствам аудитории. Один общий лимит для всех маршрутов может скрыть проблему тяжёлого checkout или, наоборот, мешать оправданно тяжёлому маршруту редактора.

В CI удобно ловить крупную регрессию bundle и лабораторных метрик. Полевой мониторинг нужен для изменений backend, CDN, устройств и реального поведения, которые не воспроизводятся одной сборкой.

#### Границы и компромиссы

- SSR может ускорить появление HTML, но не гарантирует быстрый LCP при высоком TTFB и не убирает стоимость hydration.
- Code splitting уменьшает начальный bundle, но добавляет chunks и возможные сетевые ожидания позже.
- Preload ускоряет один ресурс, отнимая пропускную способность у других.
- Кэш ускоряет повторный визит, но требует корректного версионирования и инвалидации.
- Виртуализация уменьшает DOM, но усложняет пользовательский опыт и доступность.
- Мемоизация экономит повторное вычисление, но сама потребляет память и время сравнения.

Оптимизация считается успешной, когда улучшает целевой пользовательский сценарий без неприемлемой цены в корректности, доступности, поддерживаемости и других метриках.

#### Ключевые уточнения

- Core Web Vitals являются полевыми метриками; лабораторное измерение помогает объяснить причину, но не воспроизводит всех пользователей.
- LCP, INP и CLS измеряют разные стороны пользовательского опыта и требуют разных исправлений.
- Передаваемый размер не равен полной стоимости JavaScript: важны разбор, компиляция и выполнение.
- `async`, rAF, debounce и code splitting меняют планирование работы, но не делают тяжёлую работу бесплатной.
- Resource hints являются подсказками о приоритете, а не гарантией и не универсальным ускорением.
- Способ оптимизации выбирают после определения узкого места и проверяют измерением до и после.
- Оптимизацию закрепляют бюджетом, CI-проверкой и RUM, иначе регрессия незаметно вернётся.
