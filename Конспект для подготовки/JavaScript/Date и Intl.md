#### Быстрый ответ

`Date` хранит одну временную метку (`timestamp`) - число миллисекунд от начала эпохи Unix. Сам объект не хранит часовой пояс: локальные getters и форматтеры интерпретируют метку в часовом поясе среды, а UTC-методы - в UTC.

`Date` изменяем, имеет ограниченный диапазон и не различает предметные типы «момент времени», «календарная дата» и «локальное время». Для API временную метку передают как строку ISO 8601 с `Z` или смещением либо как число от эпохи Unix по явному контракту. Значение только с датой часто лучше хранить строкой `YYYY-MM-DD`.

`Intl.DateTimeFormat`, `Intl.NumberFormat`, `Intl.RelativeTimeFormat` и `Intl.Collator` выполняют форматирование и сравнение с учётом локали. Формат отображения не используют как формат хранения и не разбирают обратно без отдельного parser.

#### Ключевая схема

```text
момент времени / timestamp
→ Date хранит миллисекунды
→ форматтер применяет timeZone и locale
→ строка для пользователя
```

| Предметное значение | Подход |
| --- | --- |
| Момент события | ISO-строка со смещением или `Z`, либо число от эпохи Unix |
| День рождения без времени | строка только с датой или отдельный предметный тип |
| Локальное время встречи | дата + время + часовой пояс IANA |
| Отображение | `Intl.DateTimeFormat` |
| Длительность | отдельное число с единицей или предметная модель, но не Date |

#### Временная метка и часовой пояс

```js
const date = new Date("2026-07-27T12:00:00Z");

date.getTime();     // миллисекунды timestamp
date.toISOString(); // ISO-строка в UTC
date.getHours();    // интерпретация в локальном часовом поясе
date.getUTCHours(); // интерпретация в UTC
```

Одна временная метка форматируется по-разному в Москве, Берлине и Нью-Йорке, но обозначает один момент времени.

```js
new Intl.DateTimeFormat("ru-RU", {
  dateStyle: "long",
  timeStyle: "short",
  timeZone: "Europe/Moscow",
}).format(date);
```

Явный `timeZone` делает отображение независимым от настройки устройства. Если его нет, используется локальный часовой пояс среды выполнения.

#### Создание и разбор

Надёжный сетевой формат содержит часовой пояс или смещение:

```js
new Date("2026-07-27T12:00:00Z");
new Date("2026-07-27T15:00:00+03:00");
```

Обе строки описывают один момент времени.

Строки нестандартного формата вроде `"07/08/2026"` неоднозначны и зависят от реализации и локали. Их не передают в `Date.parse` без собственного parser.

Числовой конструктор использует номера месяцев от `0` до `11`:

```js
new Date(2026, 0, 1); // 1 января в локальном часовом поясе
```

Это частый источник ошибки на единицу. Для API-строк и календарных форм обычно используют единый преобразователь или библиотеку вместо разбросанных вызовов конструктора.

`new Date(invalidValue)` создаёт невалидный `Date`; `getTime()` возвращает `NaN`:

```js
const date = new Date("invalid");
Number.isNaN(date.getTime()); // true
```

#### Календарная дата и момент времени

`"2026-07-27"` обозначает календарную дату, но превращение в Date добавляет семантику часового пояса. При форматировании в зоне западнее UTC день может стать предыдущим.

Если предметная область говорит «день рождения 27 июля» без момента суток, хранить его как момент времени обычно неверно. Строка только с датой или отдельная структура `{ year, month, day }` лучше сохраняет смысл.

Если предметная область говорит «создано в конкретный момент», хранится временная метка, которая форматируется в часовом поясе пользователя.

#### Mutability

```js
const date = new Date();
date.setDate(date.getDate() + 1); // изменяет тот же объект
```

Для неизменяемого обновления копируют временную метку:

```js
const next = new Date(date.getTime());
next.setDate(next.getDate() + 1);
```

Поверхностная копия объекта с Date сохраняет ссылку на тот же экземпляр Date. `structuredClone` создаёт отдельный Date с той же временной меткой.

#### Календарный день и 24 часа

Добавить один календарный день в локальном времени и прибавить `24 * 60 * 60 * 1000` миллисекунд - не всегда одно и то же из-за переходов на летнее или зимнее время (DST).

```js
const tomorrowSameLocalTime = new Date(date);
tomorrowSameLocalTime.setDate(tomorrowSameLocalTime.getDate() + 1);

const exactly24HoursLater = new Date(date.getTime() + 86_400_000);
```

Первый вариант выражает календарную операцию в локальном часовом поясе, второй - длительность ровно 24 часа. На границе перехода DST локальное время на часах может различаться.

Рабочий календарь также включает праздники, рабочие дни и часовой пояс организации; методы Date не знают эти правила.

#### `Intl.DateTimeFormat`

```js
const formatter = new Intl.DateTimeFormat("ru-RU", {
  dateStyle: "medium",
  timeStyle: "short",
  timeZone: "Europe/Moscow",
});

formatter.format(date);
```

Formatter можно переиспользовать для списка, чтобы не создавать его на каждый row render.

`formatToParts()` возвращает структурированные части, если UI нужен собственный layout:

```js
formatter.formatToParts(date);
```

Не следует разбирать готовую строку отображения обратно: порядок, знаки пунктуации и цифры зависят от локали.

#### Другие `Intl` API

```js
new Intl.NumberFormat("ru-RU", {
  style: "currency",
  currency: "RUB",
}).format(1234.5);

new Intl.RelativeTimeFormat("ru", {
  numeric: "auto",
}).format(-1, "day"); // "вчера"

new Intl.Collator("ru", {
  sensitivity: "base",
}).compare("Е", "ё");
```

Pluralization выражают через `Intl.PluralRules`, а не проверкой последней цифры: правила языка сложнее и зависят от целого значения.

`locale` и `timeZone` должны быть частью контекста UI. Жёсткая нарезка ISO-строки подходит для хранения или отладки, но не для пользовательского отображения.

#### Контракт API

Для момента времени:

```json
{ "createdAt": "2026-07-27T12:00:00.000Z" }
```

Для календарной даты без времени:

```json
{ "birthday": "1990-07-27" }
```

Для запланированного локального события может потребоваться:

```json
{
  "localDateTime": "2026-10-25T10:00:00",
  "timeZone": "Europe/Berlin"
}
```

Смещение показывает разницу с UTC в одном конкретном моменте, а часовой пояс IANA содержит правила будущих переходов DST. Выбор определяется предметной областью.

#### Где применяется во frontend

- Преобразователь API различает момент времени, календарную дату и длительность вместо одного типа Date для всего.
- Часовой пояс пользователя форматирует временную метку через `Intl.DateTimeFormat`.
- Календарная арифметика учитывает DST и предметные правила.
- Обратный отсчёт использует разницу временных меток, а для измерения внутри сессии - монотонный таймер.
- Форматтер таблицы переиспользуется, а строка отображения не используется как ключ данных.

#### Ключевые уточнения

- Date хранит временную метку, а часовой пояс появляется при разборе, форматировании и календарных операциях.
- Локальные getters зависят от окружения; UTC-getters интерпретируют значение в UTC.
- Строки даты нестандартного формата разбираются ненадёжно.
- Date изменяем, поэтому общий объект может измениться неожиданно для другого потребителя.
- Календарный день не всегда равен длительности 24 часа из-за DST.
- Календарную дату без времени не нужно без причины превращать в момент времени.
- Intl форматирует по `locale` и `timeZone`, но результат отображения не является стабильным форматом хранения.
