#### Быстрый ответ

State в React - это память компонента, которая сохраняется между renders и влияет на возвращаемый UI. Setter из `useState` не изменяет значение в текущем render, а запрашивает следующий render с новым snapshot. State обновляют неизменяемо: вместо изменения существующего объекта или массива создают новое значение.

У каждого состояния должен быть понятный владелец и единый источник истины. Данные хранят как можно ближе к компонентам, которым они нужны; при совместном использовании поднимают к ближайшему общему родителю. Значение, которое полностью вычисляется из props или другого state, обычно вычисляют во время render, а не дублируют в отдельном state. Context передаёт значение через дерево, но сам по себе не является хранилищем.

#### Ключевая схема

| Данные | Подходящее место |
| --- | --- |
| Локальное состояние кнопки, dropdown или модального окна | `useState` внутри ближайшего компонента |
| Связанные переходы сложного локального состояния | `useReducer` |
| Общие данные нескольких соседних компонентов | ближайший общий родитель |
| Значение нужно глубоко в поддереве | state у владельца + Context для передачи |
| Фильтр должен сохраняться в URL и открываться по ссылке | URL search params |
| Данные сервера с cache, retry и invalidation | query cache, например RTK Query |
| Глобальное клиентское состояние с независимыми подписчиками | внешний store, если локального владельца недостаточно |
| Значение полностью вычисляется из props/state | обычная переменная или `useMemo` для дорогого вычисления |

#### Базовая модель

`useState` возвращает snapshot для конкретного render и setter. При вызове setter React ставит обновление в очередь. Следующий вызов компонента получает новое значение, но обработчик из предыдущего render продолжает видеть прежний snapshot.

State принадлежит позиции компонента в React tree. Пока на этой позиции сохраняются тип компонента и его идентичность, React сохраняет state. Удаление компонента, смена его типа или `key` уничтожает прежний state.

При выборе структуры полезно проверить пять свойств:

1. связанные значения обновляются согласованно;
2. state не допускает противоречивых комбинаций;
3. вычисляемые значения не дублируются;
4. одна и та же сущность не хранится в нескольких копиях;
5. структура не вложена глубже, чем требуется для обновлений.

#### Развернутый ответ

##### Что действительно нужно хранить в state

В state хранится минимальный набор данных, который меняется со временем и нужен для следующего render. Например, для поиска достаточно хранить `query`; отфильтрованный список можно получить из `products` и `query`.

Производное значение (derived value) не становится state только потому, что у него есть отдельное имя. `useMemo` также не превращает его в state: Hook лишь кеширует результат вычисления между renders и нужен только при подтверждённой стоимости или для стабильной ссылки.

Копирование prop в state оправдано, если prop задаёт только начальное значение, а дальнейшие изменения родителя намеренно игнорируются. Тогда это явно отражают названием вроде `initialValue` или `defaultValue`. В остальных случаях копия легко рассинхронизируется с prop.

##### Как избегать противоречий и дублирования

Несколько boolean-полей могут описывать невозможное состояние, например одновременно `isLoading` и `isSuccess`. Один статус `"idle" | "loading" | "success" | "error"` задаёт допустимые варианты явно.

Если список хранится в `items`, выбранную сущность обычно представляют через `selectedId`, а не второй копией объекта `selectedItem`. После изменения объекта в списке выбранное значение вычислится по идентификатору и не останется устаревшим.

Объекты и массивы state считаются неизменяемыми snapshots. Изменение существующего объекта через присваивание поля не сообщает React о новом значении и меняет данные, на которые могут ссылаться предыдущие renders. Обновление создаёт новый объект или массив с нужными изменениями.

##### Colocation и lifting state up

Совместное размещение состояния (state colocation) означает, что владелец находится рядом с местом использования. Это уменьшает область обновления и количество компонентов, которым нужно знать о данных.

Поднятие состояния (lifting state up) применяется, когда два или больше компонентов должны читать и изменять одно значение. State переносится к их ближайшему общему родителю, а вниз передаются значение и обработчики. Поднимать его сразу в корень приложения не требуется.

Context решает передачу данных через несколько уровней, но значение всё равно хранится в state, reducer или внешнем store. Выбор между Context и store зависит не от слова «глобальный», а от частоты обновлений, необходимых selectors, инструментов отладки и границ владения.

##### UI state, URL state и server state

Локальный UI state описывает состояние интерфейса: открыта ли панель, какой tab выбран, что введено в несохранённое поле. URL state нужен, когда состояние должно пережить перезагрузку, поддерживать back/forward и передаваться ссылкой.

Server state является локальным представлением удалённых данных. Для него нужны cache, повторные запросы, дедупликация, invalidation и обработка устаревших данных. Эти задачи обычно решает query-библиотека, а не произвольный глобальный `useState`.

#### Пример

В state хранится только поисковая строка. Видимый список вычисляется при каждом render из текущих `products` и `query`.

```tsx
import { useState } from "react";

type Product = { id: string; title: string };

export default function ProductList({ products }: { products: Product[] }) {
  const [query, setQuery] = useState("");
  const normalizedQuery = query.trim().toLowerCase();

  const visibleProducts = products.filter(product =>
    product.title.toLowerCase().includes(normalizedQuery)
  );

  return (
    <section>
      <label>
        Search
        <input
          value={query}
          onChange={event => setQuery(event.target.value)}
        />
      </label>

      <ul>
        {visibleProducts.map(product => (
          <li key={product.id}>{product.title}</li>
        ))}
      </ul>
    </section>
  );
}
```

Отдельный `useState` для `visibleProducts` потребовал бы синхронизировать его и с `products`, и с `query`. Прямое вычисление не создаёт второй источник истины. Если фильтрация действительно станет дорогой, её стоимость сначала измеряют, а затем при необходимости оборачивают в `useMemo`.

#### Где применяется во frontend

| Ситуация | Решение | Причина |
| --- | --- | --- |
| Открытие dropdown | локальный state | значение нужно небольшому поддереву |
| Два поля управляют одним preview | state у общего родителя | оба компонента используют один источник истины |
| Фильтр каталога должен быть shareable | URL search params | состояние восстанавливается по ссылке и истории браузера |
| Auth user нужен всему приложению | auth state + Context или store | один владелец и много удалённых потребителей |
| Список заказов загружается с backend | query cache | нужны cache, retry и invalidation |
| Сложный wizard имеет допустимые переходы | reducer или state machine | переходы и невозможные состояния выражены явно |

#### Ключевые уточнения

- State является snapshot конкретного render; setter планирует следующее значение, а не изменяет текущую переменную.
- Context передаёт значение, но хранение и обновление остаются ответственностью state, reducer или store.
- Derived value вычисляется из уже существующих данных и не требует отдельной синхронизации через Effect.
- Копия prop в state допустима только как намеренно независимое начальное значение.
- Место хранения выбирают по владельцу, времени жизни и способу использования данных, а не по размеру приложения.
