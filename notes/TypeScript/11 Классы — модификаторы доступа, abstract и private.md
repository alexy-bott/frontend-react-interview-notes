# Классы — модификаторы доступа, abstract и private

## Быстрый ответ

TypeScript расширяет JavaScript-классы статическими контрактами: типами полей и методов, `public`, `protected`, `private`, `readonly`, abstract-классами и проверкой `implements`. Большая часть этих конструкций помогает компилятору, но не добавляет runtime-защиту после сборки.

`public` доступен везде, `protected` — внутри класса и наследников, TypeScript `private` — только внутри самого класса. Нативное JavaScript-поле `#private` действительно закрыто в runtime. `abstract` запрещает создавать экземпляр базового класса и требует от наследников реализовать абстрактные члены.

Классы уместны, когда модели нужны состояние, поведение, инварианты и identity экземпляра. Для простого контракта данных чаще достаточно object type или interface: они не создают runtime-код и не требуют наследования.

## Что TypeScript добавляет к JavaScript-классу

```ts
abstract class Storage {
  constructor(protected readonly key: string) {}

  abstract read(): string | null;

  clear(): void {
    localStorage.removeItem(this.key);
  }
}
```

- `abstract class` нельзя создать через `new`;
- `protected key` доступен классу и наследникам;
- `readonly` запрещает переприсвоить поле после инициализации;
- `abstract read()` задаёт обязательный контракт для наследника;
- параметр конструктора с модификатором одновременно объявляет и инициализирует поле — это parameter property.

## Модификаторы доступа

| Модификатор | Где доступен | Runtime-защита |
| --- | --- | --- |
| `public` | везде | нет ограничения |
| `protected` | класс и наследники | нет |
| `private` | только объявивший класс | нет после удаления типов |
| `#field` | только тело класса | да, механизм JavaScript |

TypeScript `private` влияет и на совместимость: классы с private/protected-членами совместимы не только по форме, а с учётом происхождения этих членов. Это одно из исключений из обычной структурной модели TypeScript.

Нативное `#private` выбирают, если скрытие должно соблюдаться при выполнении. TypeScript `private` достаточно, когда задача — защитить архитектурную границу во время разработки.

## `implements` и `extends`

`extends` наследует реализацию и контракт базового класса. `implements` только проверяет, что экземпляр класса соответствует interface; методы автоматически не добавляются:

```ts
interface Disposable {
  dispose(): void;
}

class Subscription implements Disposable {
  dispose(): void {
    console.log("unsubscribe");
  }
}
```

`implements` также не меняет типы членов класса. Если interface допускает `name?: string`, класс всё равно должен сам явно решить, является ли его поле необязательным.

## Когда класс не нужен

Для DTO, props, API-response и конфигураций обычно нужны только данные. Их проще описывать через `type` или `interface`. Класс оправдан, если он действительно владеет поведением и поддерживает инварианты, например управляет подпиской, кэшем, состоянием редактора или объектом доменной модели.

Наследование увеличивает связанность. Во frontend-коде композиция функций, hooks и небольших объектов часто проще, особенно для UI. Но это критерий архитектуры, а не запрет на классы.

## Ключевые уточнения

- `readonly` запрещает переприсваивание поля, но не делает вложенный объект глубоко неизменяемым.
- `private` TypeScript и `#private` JavaScript решают похожую задачу на разных этапах.
- `abstract` существует в типовой модели и компилируется в обычный JavaScript-класс; запрет `new` проверяет TypeScript.
- `implements` проверяет instance side класса и не копирует реализацию.
- Класс одновременно существует как runtime-значение конструктора и как тип его экземпляров.
- Для простой формы данных interface не хуже класса: выбор зависит от необходимости поведения и runtime-экземпляров.
