## Быстрый ответ

Declaration file `.d.ts` описывает типовую форму JavaScript API, которое существует в runtime. Такой файл участвует в typecheck, но не создаёт JavaScript и не реализует поведение.

Декларации нужны для пакета без встроенных типов, глобального скрипта, расширения `Window`, module augmentation и публикации собственной библиотеки. Ключевое требование: описание должно соответствовать реальному runtime API. Если `.d.ts` обещает несуществующий метод, TypeScript пропустит вызов, а приложение упадёт.

Готовый пакет сначала проверяют на bundled types и `@types/*`. Собственную декларацию пишут, когда подходящих типов нет или проект действительно расширяет существующий контракт.

## Откуда TypeScript получает декларации

TypeScript знает стандартные JavaScript и DOM API из файлов `lib.*.d.ts`. Типы сторонних библиотек обычно приходят из одного из источников:

1. пакет публикует `.d.ts` вместе с JavaScript;
2. отдельный пакет `@types/name` поставляет декларации DefinitelyTyped;
3. приложение содержит локальный `.d.ts` для собственного или старого (legacy) API.

Версии JavaScript-пакета и его деклараций должны быть совместимы. Отдельный `@types/*`, рассчитанный на другой major API, способен описывать методы, которых фактически нет.

## Описать глобальное значение

Если внешний `<script>` создаёт глобальную переменную, TypeScript можно сообщить её форму:

```ts
declare const APP_VERSION: string;

declare function trackPageView(path: string): void;
```

`declare` означает: «значение уже будет в runtime, здесь находится только его описание». Этот код не создаёт `APP_VERSION` и `trackPageView`.

## Расширить `Window`

```ts
export {};

declare global {
  interface Window {
    analytics?: {
      track(
        event: string,
        payload?: Record<string, unknown>
      ): void;
    };
  }
}
```

`export {}` делает файл модулем, после чего `declare global` явно открывает глобальную область для augmentation. Optional-поле отражает реальность: внешний скрипт может ещё не загрузиться.

Глобальные расширения влияют на весь проект, поэтому имена держат под устойчивым namespace вроде `window.analytics`, а не добавляют множество несвязанных глобалей.

## Описать модуль без типов

```ts
declare module "legacy-format" {
  export type FormatOptions = {
    locale?: string;
  };

  export function formatDate(
    value: Date,
    options?: FormatOptions
  ): string;
}
```

Декларация должна повторять реальный способ импорта и форму exports. CommonJS, ESM, callable export и global library требуют разных шаблонов `.d.ts`.

Пустая декларация скрывает ошибку отсутствующих типов, но фактически превращает весь пакет в `any`:

```ts
declare module "untyped-package";
```

Это допустимый временный мост, но не полноценная типизация.

## Расширение модуля (module augmentation)

Module augmentation дополняет существующую декларацию пакета или локального модуля:

```ts
import "./router";

declare module "./router" {
  interface RouteMeta {
    requiresAuth?: boolean;
  }
}
```

TypeScript объединяет interface с исходным `RouteMeta`. При этом augmentation описывает уже существующий runtime-контракт; он не добавляет реализацию. Если приложение не установило соответствующее поле или plugin, декларация снова окажется ложной.

## Декларации собственной библиотеки

Для TypeScript-библиотеки `tsc` может сгенерировать типовой API:

```json
{
  "compilerOptions": {
    "declaration": true,
    "emitDeclarationOnly": true,
    "declarationMap": true,
    "outDir": "dist/types"
  }
}
```

Пакет указывает entry деклараций через поле `types` либо через корректно настроенные package exports. Публикуется только тот API, который потребитель может реально импортировать из JavaScript output.

Генерация `.d.ts` выявляет утечки внутренних типов: если exported function использует непубликуемый контракт, публичная декларация может стать неудобной или невозможной для потребителя.

## Как проверить качество декларации

- импорт и export syntax совпадают с JavaScript-пакетом;
- необязательные, nullable-поля и варианты перегрузки отражают реальное поведение;
- runtime-значения не объявлены только потому, что так удобнее типизировать;
- пакет и `@types` совместимы по версии;
- минимальный пример использования пакета проходит typecheck и запускается;
- публичные declarations не содержат ненужного `any` и внутренних путей проекта.

## Ключевые уточнения

- `.d.ts` описывает существующий код и сам не создаёт runtime-значений.
- `declare` является обещанием компилятору; TypeScript не проверяет его истинность при запуске.
- Declaration merging и module augmentation дополняют типовую модель, но реализацию нужно добавить отдельно.
- Пустой `declare module` временно снимает ошибку ценой `any` для всего API.
- `skipLibCheck` может скрыть конфликт сторонних declarations, но не исправляет несоответствие типов и runtime.
- При публикации библиотеки JavaScript, `.d.ts`, package exports и версии должны обновляться согласованно.
