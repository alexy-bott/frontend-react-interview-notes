# Доступность диалогов, выпадающих элементов и оверлеев

## Быстрый ответ

Overlay — перекрывающий слой поверх основного интерфейса, но его доступное поведение определяется не внешним видом, а конкретным паттерном. Модальное диалоговое окно (modal dialog) блокирует взаимодействие с фоном и удерживает фокус внутри; menu предлагает набор действий с навигацией стрелками; popover обычно остаётся немодальным; tooltip показывает короткую подсказку и не содержит интерактивных элементов.

Для modal dialog нужны доступное имя, начальный фокус внутри, ограничение `Tab` рамками окна, `Esc`, недоступный для взаимодействия фон и возврат фокуса после закрытия. Menu, listbox и combobox имеют другие роли и keyboard-модели, поэтому универсальный «dropdown» нельзя сделать одним набором ARIA-атрибутов.

Portal меняет место узла в DOM и помогает вывести слой из `overflow` или локального stacking context, но не реализует семантику и focus management. Radix UI предоставляет готовое поведение, однако приложение по-прежнему отвечает за title, description, выбранный паттерн, стили фокуса и корректную композицию через `asChild`.

## Карта темы

Слово «dropdown» описывает внешний вид, а не роль. Перед реализацией нужно определить содержимое и взаимодействие:

| Паттерн | Назначение | Фокус и клавиатура |
| --- | --- | --- |
| Modal dialog | отдельная задача, временно блокирующая страницу | фокус внутри, `Tab` цикличен, `Esc` закрывает |
| Non-modal dialog | вспомогательное окно при доступном фоне | фокус может перейти наружу по понятному правилу |
| Menu | набор команд или действий | при открытии фокус переносится на `menuitem`; стрелки перемещают фокус, `Enter` активирует item или открывает submenu, `Space` используется опционально по правилам конкретного item, `Esc` закрывает, `Tab` выводит фокус наружу и закрывает menu |
| Listbox/select | выбор значения из списка | активный и выбранный вариант, стрелки и typeahead |
| Combobox | input и связанный список вариантов | ввод текста, раскрытие и навигация по options |
| Popover | дополнительный немодальный контент | модель зависит от содержимого; focus trap обычно отсутствует |
| Tooltip | короткое неинтерактивное описание | появляется от hover и keyboard focus, сам фокус не получает |

Typeahead — переход к элементу по набираемым символам. Tab stop — позиция компонента в последовательной навигации клавишей `Tab`. Полные клавиши и роли берутся из APG-паттерна выбранного компонента.

Обычное меню навигации сайта часто лучше строить из ссылок и disclosure-кнопки, а не из ARIA `menu`. Роль `menu` предполагает поведение, похожее на меню приложения, и меняет ожидания keyboard-пользователя.

## Modal dialog

Модальность должна совпадать визуально, семантически и функционально. Если фон затемнён, но на него всё ещё можно перейти клавишей `Tab` или скринридером, пользователь попадает в скрытый контекст. Если указано `aria-modal="true"`, а код не блокирует фон, ARIA обещает поведение, которого нет.

Полный цикл dialog:

1. Trigger, то есть элемент открытия, открывает окно и запоминается для последующего возврата фокуса.
2. Dialog получает роль `dialog` или `alertdialog` и доступное имя через видимый title.
3. Фокус переносится на подходящий узел внутри.
4. Фон становится inert, то есть недоступным для фокуса и взаимодействия, а `Tab`/`Shift+Tab` остаются внутри.
5. `Esc` и явная кнопка закрытия завершают взаимодействие; закрытие по фону зависит от продукта и риска действия.
6. Фокус возвращается на элемент открытия или другой логичный элемент, если первый исчез.

`alertdialog` используют для короткого срочного сообщения, которое требует ответа. Обычная форма в modal остаётся `dialog`, даже если в ней есть валидация.

Начальный фокус выбирается по содержимому. В большом текстовом dialog можно сфокусировать заголовок с `tabindex="-1"`; в подтверждении разрушительного действия — безопасную кнопку отмены; в короткой форме — первое подходящее поле. Простое правило «всегда первый фокусируемый элемент» не учитывает смысл действия.

Нативный `<dialog>` при открытии через `showModal()` попадает в верхний слой браузера (top layer) и получает модальное поведение, но разработчик всё равно задаёт имя, содержимое, способ закрытия и проверяет возврат фокуса в целевых браузерах. Для составных приложений часто используют проверенный готовый компонент, который унифицирует эти детали.

## Menu, popover и tooltip

Menu содержит команды. Фокус обычно находится на одном элементе, стрелки перемещают его между элементами, disabled item не активируется. `Esc` закрывает menu и возвращает фокус к элементу или контексту, из которого menu был открыт, например к menu button или parent `menuitem`. Произвольная форма внутри `menu` нарушает этот паттерн; для фильтра с полями больше подходит popover или dialog.

Popover — общий контейнер дополнительного содержимого. Если он немодальный, пользователь может перейти фокусом на остальную страницу, поэтому focus trap ему обычно не нужен. При открытии простого информационного popover автоматический перенос фокуса тоже может быть лишним; при наличии формы решение зависит от ожидаемого сценария.

Нативный HTML `popover` — отдельный механизм показа слоя, а не готовая семантическая роль. `popover="auto"` выводит элемент в top layer, поддерживает light dismiss и close requests, но не превращает содержимое в modal dialog и не реализует клавиатурную модель `menu`, `listbox` или другого widget. Семантика и клавиши по-прежнему выбираются по содержимому.

Tooltip даёт краткое описание trigger. В APG этот pattern пока отмечен как work in progress; его базовая модель предполагает появление подсказки при hover или клавиатурном фокусе, закрытие по `Esc` и сохранение фокуса на trigger. Сам tooltip не получает фокус и не содержит интерактивных элементов. Слой с кнопкой или ссылкой требует другого паттерна, например popover или dialog.

## Portal и слои

Portal позволяет отрисовать React-поддерево в другом DOM-контейнере, обычно рядом с `body`, сохраняя при этом React context и всплытие React events по дереву компонентов. Это помогает избежать обрезания через `overflow: hidden` и части проблем со stacking context.

Portal не решает автоматически:

- доступное имя и роль;
- начальный и возвращаемый фокус;
- inert-фон и focus trap;
- закрытие по `Esc` и внешнему взаимодействию;
- scroll lock;
- порядок нескольких перекрывающих слоёв.

Внешнее взаимодействие (outside interaction) включает событие указателя или перевод фокуса за пределы слоя. Его обработка должна учитывать вложенные overlays: date picker внутри dialog не должен восприниматься родительским dialog как случайный внешний клик.

## Radix UI и `asChild`

Radix управляет большей частью ролей, клавиш и фокуса, если сохраняется ожидаемая структура primitives. Приложение добавляет содержательный `Title`, при необходимости `Description`, визуальный индикатор фокуса и проверяет продуктовый сценарий.

`asChild` передаёт поведенческие props и `ref` единственному дочернему элементу вместо создания стандартного DOM-узла. Пользовательский компонент должен пробросить все полученные props на итоговый DOM-элемент и принять переданный `ref`. В React 19 `ref` можно принимать как обычный prop; для совместимости с React 18 обычно используют `forwardRef`. Если оставить только `onClick` и `className`, можно потерять обработчики клавиатуры, ARIA-атрибуты и другие props Radix.

## Пример

```tsx
<Dialog.Root>
  <Dialog.Trigger asChild>
    <Button>Редактировать профиль</Button>
  </Dialog.Trigger>

  <Dialog.Portal>
    <Dialog.Overlay className="overlay" />
    <Dialog.Content className="dialog-content">
      <Dialog.Title>Профиль</Dialog.Title>
      <Dialog.Description>
        Измените данные и сохраните форму.
      </Dialog.Description>

      <ProfileForm />

      <Dialog.Close asChild>
        <Button type="button" variant="secondary">Отмена</Button>
      </Dialog.Close>
    </Dialog.Content>
  </Dialog.Portal>
</Dialog.Root>
```

Здесь Radix связывает dialog с title и description и управляет фокусом модального окна. Дизайн-системный `Button` обязан передать DOM-кнопке полученные props и `ref`. Для подтверждения удаления лучше рассмотреть `AlertDialog`, у которого паттерн и выбор безопасного начального действия соответствуют подтверждению риска.

## Проверка

1. Определить семантический паттерн по содержимому, а не по слову «dropdown» в дизайне.
2. Пройти открытие, внутреннюю навигацию, `Esc`, закрытие и возврат фокуса только клавиатурой.
3. Проверить роль, доступное имя, описание и состояния в дереве доступности.
4. Проверить вложенный popover/select, внешнее взаимодействие, прокрутку и несколько уровней overlays.
5. Проверить увеличение масштаба, мобильную видимую область и длинное содержимое: кнопка закрытия и важные элементы управления должны оставаться достижимыми.

## Где применяется во frontend

- При выборе overlay-компонента: сначала определяется реальный паттерн — modal dialog, menu, listbox, combobox, popover или tooltip — и только затем его внешний вид.
- При modal dialog: нужно согласовать модальность визуально, через accessibility semantics и фактическое блокирование взаимодействия с фоном.
- При native HTML popover: браузер может обеспечить top layer, light dismiss и close requests, но семантику widget и его клавиатурную модель приложение выбирает отдельно.
- При React Portal: перенос DOM-узла решает задачу слоя, но не добавляет роль, focus trap, возврат фокуса и `Esc`.
- При Radix UI: primitives дают базовые роли, клавиатуру и focus management, а приложение отвечает за содержательные title/description и корректную композицию.
- При `asChild`: дизайн-системный компонент должен сохранить все переданные props и `ref`, иначе часть поведения primitive потеряется.

## Ключевые уточнения

- Overlay описывает слой, а dialog, menu, listbox, popover и tooltip задают разные доступные контракты.
- Modal dialog делает фон недоступным и удерживает фокус; немодальный popover обычно этого не делает.
- `aria-modal` сообщает модальность, но поведение фокуса и фона реализуется отдельно.
- Portal меняет DOM-расположение, сохраняя React-связи, и сам по себе не добавляет accessibility.
- Tooltip содержит только неинтерактивную подсказку; элементы управления требуют popover или dialog.
- Radix primitive остаётся доступным только при сохранении структуры, props, `ref` и содержательных подписей.
