## Быстрый ответ

Проектирование frontend-фичи - это перевод пользовательского сценария и ограничений продукта в согласованную техническую модель: данные и API-контракты, состояние, интерфейсные состояния, права доступа, обработку ошибок, производительность и тестирование. Сначала уточняют, кто и в каких условиях выполняет сценарий, затем определяют источники данных и владельцев состояния, описывают основной поток и сбои и только после этого выбирают библиотеки и конкретные реализации.

Результатом должен быть не перечень технологий, а объяснимое решение. Из него понятно, откуда берутся данные, что происходит после каждого действия пользователя, как интерфейс ведёт себя при загрузке и ошибке, где проходят границы ответственности и какие компромиссы приняты.

## Ключевая схема

```text
сценарий и ограничения
-> данные и API-контракты
-> владельцы состояния
-> основной поток и состояния интерфейса
-> ошибки, доступ и восстановление
-> производительность и доступность
-> тестирование и наблюдаемость
```

| Этап | Что нужно выяснить | Какое решение должно появиться |
| --- | --- | --- |
| Сценарий | кто, что и зачем делает | границы фичи и критерий успеха |
| Ограничения | объём данных, устройства, сеть, роли, SSR, SEO | требования, влияющие на архитектуру |
| Данные | сущности, свежесть, источники, формат ответа | API-контракты и преобразование данных |
| Состояние | кому принадлежат данные и как долго они живут | local, form, URL, server или global state |
| Интерфейс | какие состояния увидит пользователь | loading, empty, error, pending, success |
| Качество | что может стать медленным, недоступным или нестабильным | измерения, защита, тесты и мониторинг |

## Базовая модель

Проектирование начинается с пользовательского сценария, а не с компонента. Например, формулировка «показать таблицу пользователей» недостаточна. Нужно знать, кто видит таблицу, сколько в ней данных, можно ли делиться настроенным видом, какие действия доступны, требуются ли массовые операции и насколько свежими должны быть данные.

После уточнения сценария определяют владельца каждого состояния:

- **локальное состояние (local state)** принадлежит конкретной части интерфейса: открыт ли dropdown, какая вкладка выбрана внутри компонента;
- **состояние формы (form state)** содержит вводимые значения, признаки изменения полей и ошибки;
- **состояние URL (URL state)** описывает представление страницы, которое должно переживать reload и открываться по ссылке: фильтры, сортировка, страница;
- **серверное состояние (server state)** - данные с backend, у которых есть загрузка, кеш, актуальность и повторное получение;
- **глобальное клиентское состояние (global client state)** нужно нескольким независимым частям приложения, например для темы интерфейса или текущего workspace.

Такое разделение предотвращает появление одного общего store, где смешаны временные детали интерфейса, данные форм и копии серверных ответов.

## Развернутый ответ

**Данные и контракты.** Для каждого запроса важно определить входные параметры, форму ответа, ошибки и правила свежести. DTO - объект в формате внешнего API; модель интерфейса может иметь другую форму. Преобразование на границе API позволяет не распространять особенности backend по компонентам.

**Основной поток.** Полезно пройти сценарий от первого открытия до результата: что запускает загрузку, что видит пользователь, какое действие отправляет запрос, можно ли повторить действие и что происходит после успеха. Затем тот же поток разбирают для медленной сети, пустых данных, ошибки, конфликта и недостатка прав.

**Изменения данных.** Пессимистическое обновление ждёт подтверждения сервера и только затем меняет интерфейс. Оптимистическое обновление сразу показывает ожидаемый результат, а при ошибке откатывает его. Второй вариант ускоряет обратную связь, но требует надёжного rollback и подходит только тогда, когда операция предсказуема и её несложно отменить в UI.

**Границы и компромиссы.** Хранение фильтров в URL усложняет сериализацию, но даёт deep link и восстановление после reload. Точечное обновление query cache экономит запрос, но сложнее полной invalidation. Универсальный компонент уменьшает повторение только до тех пор, пока его API остаётся понятнее нескольких специализированных реализаций.

**Проверяемость решения.** Архитектура должна позволять проверить ключевую бизнес-логику отдельно от деталей рендера, а пользовательский сценарий - интеграционным или E2E-тестом. Для production-сбоев заранее определяют наблюдаемые сигналы: ошибки запросов, время ответа, долю неуспешных действий и контекст, достаточный для воспроизведения.

## Пример

Для экрана заказов рассуждение может выглядеть так:

1. Менеджер ищет заказы, меняет статус и отправляет ссылку на отфильтрованный список коллеге.
2. Фильтры, сортировка и страница хранятся в URL; открытая строка - в локальном состоянии; список заказов - в query cache.
3. Backend выполняет фильтрацию и пагинацию, потому что весь набор велик и доступ зависит от прав пользователя.
4. Первая загрузка, фоновое обновление, пустой результат, ошибка и сохранение статуса отображаются как разные состояния.
5. Изменение статуса ждёт ответ сервера: конфликт возможен, если заказ уже изменил другой менеджер.
6. Интеграционный тест проверяет поиск и изменение статуса, а E2E-тест - доступ по сохранённой ссылке и запрет действия без нужного permission.

Этот пример не задаёт единственную архитектуру. Он показывает порядок, в котором требования приводят к решениям и позволяют объяснить каждый выбор.

## Ключевые уточнения

- Выбор библиотеки следует из модели данных и ограничений. Само упоминание Redux, RTK Query или React Hook Form не объясняет архитектуру фичи.
- Серверное состояние не становится клиентским только потому, что отображается на клиенте. Его источник истины находится на сервере, поэтому для него важны кеш, свежесть и синхронизация.
- Состояния `loading`, `empty`, `error` и `refetching` описывают разные ситуации и требуют разного поведения интерфейса.
- Производительность проектируют от измеримых условий: объёма данных, частоты обновлений, стоимости render и сети. Мемоизация без выявленного узкого места не является архитектурным решением.
- Frontend-проверка прав управляет интерфейсом, но не защищает ресурс. Сервер обязан самостоятельно проверять авторизацию каждого запроса.
