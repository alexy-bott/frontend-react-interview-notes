## Быстрый ответ

Таблица с фильтрами, сортировкой и пагинацией проектируется как представление серверной коллекции, а не только как набор строк. Сначала определяют объём и изменчивость данных, затем согласуют формат query-параметров с backend, выбирают владельца состояния страницы и включают все параметры результата в ключ кеша.

Для большого набора backend обычно фильтрует, сортирует и разбивает данные на страницы, а frontend хранит восстанавливаемые параметры в URL, загружает соответствующий срез и отдельно показывает первую загрузку, фоновое обновление, пустой результат и ошибку. Дополнительно проектируют защиту от устаревших ответов, выбор строк, доступность таблицы и поведение после изменения данных.

## Ключевая схема

```text
URL-параметры
-> нормализованные параметры запроса
-> API и ключ кеша
-> страница данных + метаданные пагинации
-> модель строк и состояния интерфейса
-> действия пользователя
-> обновление или invalidation кеша
```

| Решение | Основной вопрос |
| --- | --- |
| Обработка данных | весь набор помещается на клиенте или операции выполняет backend? |
| Пагинация | нужен номер страницы или последовательное продолжение списка? |
| URL | какие параметры должны переживать reload и передаваться ссылкой? |
| Кеш | какие параметры определяют конкретный результат запроса? |
| Выбор строк | действует ли выбор только на видимой странице или на всём результате? |
| Производительность | ограничивает ли работу сеть, вычисления React или число DOM-узлов? |

## Базовая модель

**Клиентская обработка** подходит, когда весь набор уже загружен, остаётся небольшим и пользователь имеет право получить все строки. Frontend может отфильтровать и отсортировать массив без дополнительных запросов.

**Серверная обработка** нужна, когда набор велик, часто изменяется, доступ ограничен или сортировка и поиск зависят от данных backend. Frontend передаёт `search`, `filters`, `sort` и параметры страницы, а сервер возвращает только нужный срез.

Есть две распространённые модели пагинации:

- **offset pagination** запрашивает позицию или номер страницы, например `page=3&limit=20`; удобна для перехода к конкретной странице, но при вставках и удалениях между запросами строки могут смещаться;
- **cursor pagination** передаёт непрозрачный указатель на продолжение, например `after=eyJpZCI6...`; лучше переносит изменяющиеся данные и подходит для infinite scroll, но обычно не позволяет сразу открыть произвольную страницу.

Параметры результата удобно хранить в URL, если пользователь должен восстановить вид после reload, использовать кнопки Back/Forward или поделиться ссылкой. Открытый dropdown и состояние hover остаются локальными: они не описывают сам результат.

## Развернутый ответ

**Контракт запроса.** Frontend и backend согласуют допустимые поля сортировки, формат нескольких фильтров, пустые значения и метаданные ответа. Для устойчивой сортировки нужен дополнительный уникальный критерий: если несколько записей имеют одинаковый `createdAt`, порядок можно определить как `createdAt desc, id desc`.

**Ключ кеша.** Все параметры, меняющие результат, должны участвовать в query key: ресурс, страница или cursor, размер страницы, сортировка, фильтры и поиск. Иначе разные представления будут считаться одним запросом и пользователь увидит данные от прежних параметров.

**Смена параметров.** При изменении фильтра или поиска номер страницы обычно возвращают к первой: прежняя третья страница может не существовать в новом результате. Быстрый ввод поиска создаёт несколько запросов. Debounce уменьшает их количество, а отмена или механизм query-библиотеки не позволяет позднему ответу для старого текста заменить новый результат.

**Выбор строк.** Для выбора видимых строк достаточно `Set` с идентификаторами. Выбор между страницами требует продуктового контракта: сохраняется ли он после смены фильтра, означает ли «выбрать все» видимые строки или все записи, подходящие под запрос, и как отразить исключения. Для действия над всем результатом безопаснее отправлять на backend сам фильтр и список исключённых id, а не пытаться загрузить все id в браузер.

**Изменения и кеш.** После удаления или редактирования строки можно точечно изменить кеш либо объявить запрос устаревшим (invalidate) и загрузить его заново. Точечное обновление экономит сеть, но должно корректно учитывать все закешированные страницы и фильтры. Invalidation проще и надёжнее, но создаёт дополнительный запрос.

**Производительность.** Серверная пагинация уменьшает объём передаваемых данных, а виртуализация оставляет в DOM только видимую часть длинного списка. Это разные оптимизации: небольшая страница может не требовать виртуализации, а infinite scroll может использовать и cursor pagination, и виртуализацию. Сначала измеряют, где возникает задержка.

**Доступность.** Для табличных данных используют семантическую таблицу с понятными заголовками. Состояние сортировки сообщают через `aria-sort`, интерактивные элементы доступны с клавиатуры, а изменение результата не должно неожиданно переносить focus. Если макет является списком карточек, не стоит применять табличную семантику только из-за визуальной сетки.

## Пример

Нормализация URL отделяет строковые параметры браузера от аргументов API:

```ts
type UsersQuery = {
  page: number;
  limit: number;
  sort: "createdAt" | "name";
  direction: "asc" | "desc";
  status?: "active" | "blocked";
  search: string;
};

function readUsersQuery(params: URLSearchParams): UsersQuery {
  return {
    page: Math.max(1, Number(params.get("page")) || 1),
    limit: 20,
    sort: params.get("sort") === "name" ? "name" : "createdAt",
    direction: params.get("direction") === "asc" ? "asc" : "desc",
    status:
      params.get("status") === "active" || params.get("status") === "blocked"
        ? (params.get("status") as "active" | "blocked")
        : undefined,
    search: params.get("search")?.trim() ?? "",
  };
}

const query = readUsersQuery(new URLSearchParams(location.search));
const queryKey = ["users", query];
```

Объект `query` содержит все параметры, влияющие на ответ, поэтому может быть аргументом API и частью ключа кеша. В реальном приложении запись параметров обратно в URL должна использовать те же значения по умолчанию, чтобы адрес не менялся между эквивалентными состояниями.

## Ключевые уточнения

- URL хранит состояние представления, а не сами строки. Данные остаются серверным состоянием и загружаются по параметрам URL.
- Debounce сокращает частоту запуска поиска, но сам по себе не гарантирует правильный порядок ответов. Нужна отмена устаревшего запроса или библиотека, которая не применит его результат к новому ключу.
- `Set` ускоряет проверку выбранного id, но не определяет продуктовую семантику выбора между страницами.
- Стабильный порядок требует явного дополнительного критерия сортировки; полагаться на случайный порядок записей с одинаковым значением нельзя.
- Виртуализация уменьшает число элементов в DOM, а пагинация уменьшает объём получаемых данных. Одна не заменяет другую автоматически.
