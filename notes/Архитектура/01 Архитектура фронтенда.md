## Быстрый ответ

Frontend-архитектура определяет границы модулей, владельцев данных, направление зависимостей и общие правила, которые позволяют приложению меняться без каскада случайных правок. Она охватывает не только папки: UI composition, state и data flow, API boundary, routing, обработку ошибок, performance, security, testing и delivery.

Хорошее решение соответствует масштабу продукта и команды. Связанный код одной feature расположен рядом, взаимодействие проходит через узкие public contracts, а более стабильные нижние модули не зависят от конкретных пользовательских сценариев. Качество видно по локальности изменения и возможности объяснить, какой модуль владеет каждым состоянием и правилом.

## Ключевая схема

```text
product scenarios и quality requirements
-> module boundaries и ownership
-> dependency direction и public contracts
-> data/state flow
-> runtime и delivery boundaries
-> tests, monitoring и controlled evolution
```

| Область | Архитектурный вопрос |
| --- | --- |
| Модули | какой бизнес-смысл и ответственность собраны вместе? |
| Зависимости | кто может импортировать и вызывать кого? |
| Данные | где источник истины и кто меняет состояние? |
| Интеграции | где проверяется и преобразуется внешний контракт? |
| Runtime | где ошибки, async work и ресурсы получают lifecycle? |
| Качество | как измеряются performance, reliability и regressions? |

## Базовая модель

Архитектура начинается с границ изменения. Если правка checkout требует менять общий UI kit, auth store и несвязанные pages, модули отражают технические детали хуже, чем бизнес-сценарии. Feature-based organization собирает UI, model, API и tests одного сценария рядом и уменьшает область поиска.

Модуль скрывает внутренности и экспортирует public API. Dependency rule не позволяет нижнему стабильному слою импортировать верхний конкретный сценарий. Это предотвращает cycles и ситуацию, когда shared button знает о checkout или profile.

State ownership дополняет файловые границы. Server state остаётся в query/cache layer, URL state - в router, form draft - в form owner, локальная видимость - у ближайшего компонента. Один смысл имеет один источник истины; остальные уровни получают значение или производят данные из него.

## Развернутый ответ

**Масштаб.** Небольшому приложению достаточно нескольких понятных модулей. Многоуровневая методология окупается, когда features и команды растут, а независимые изменения начинают конфликтовать. Архитектура сложнее проблемы создаёт ceremony без пользы.

**Связность и cohesion.** Высокая внутренняя связность (cohesion) означает, что содержимое модуля меняется по одной причине. Низкая внешняя связанность означает, что детали одного модуля не протекают в другие. Повтор двух локальных строк иногда дешевле преждевременного shared abstraction с десятком режимов.

**Бизнес-логика.** JSX связывает state с представлением, но правила цены, permissions, переходов workflow и преобразования данных должны иметь тестируемый контракт. Это может быть pure function, reducer, state machine, service или feature model; отдельный class layer не обязателен.

**Cross-cutting concerns.** Auth, telemetry, error mapping и configuration нужны многим modules. Их подключают через app composition и инфраструктурные interfaces, не заставляя feature знать конкретный SDK. Так provider можно заменить и централизованно применить privacy/security policy.

**Эволюция.** Архитектурное правило фиксируют вместе с причиной и проверяют review, lint boundary rules или tests. Когда контекст изменился, правило пересматривают. Диаграмма без соответствия реальным imports и runtime flow быстро становится недостоверной.

## Пример

```text
src/
  app/             # bootstrap, providers, router
  pages/           # route composition
  features/
    update-profile/
      ui/
      model/
      api/
      index.ts     # public contract
  entities/
    user/
  shared/
    ui/
    api/
    lib/
```

`update-profile` использует публичные контракты `entities/user` и `shared/api`. `shared` не импортирует feature, а другая feature не обращается к внутреннему store через deep import. Конкретная схема может отличаться; важны ownership и проверяемое направление зависимостей.

## Ключевые уточнения

- Структура папок является следствием границ, а не самостоятельной целью архитектуры.
- Локальность изменения проверяется реальным сценарием: сколько modules и contracts затрагивает новая бизнес-правка.
- Shared-код должен быть стабильнее consumers; повторное использование без устойчивого контракта ещё не требует общего abstraction.
- Один источник истины не означает один глобальный store: разные виды состояния имеют разных естественных owners.
- Архитектура включает production behavior и delivery, поэтому error handling, observability и rollback не являются внешними деталями.
