## Быстрый ответ

Обновление запускает рендер (`render`): React вызывает компоненты и получает от них новое описание интерфейса. Во время рендера React сопоставляет возвращаемые описания с тем, что уже смонтировано. Это сопоставление называется reconciliation.

По умолчанию React связывает новое описание с уже смонтированным компонентом или DOM-узлом, когда совпадают тип и место среди соседей. В списке React может сохранить эту связь при изменении порядка: при том же типе стабильный `key` позволяет узнать ту же сущность на новом месте. Пока связь сохраняется, React сохраняет связанный state и может повторно использовать смонтированную часть интерфейса. Если связь теряется — например, изменился тип или `key`, — React размонтирует прежнее поддерево и монтирует новое с начальным state.

Рендер только подготавливает необходимые изменения. Живой DOM React обновляет позже, во время commit.

## Карта темы

| Уровень | Совместное условие | Результат |
| --- | --- | --- |
| Идентичность / state | `key` не задан: тот же тип остаётся на той же позиции среди детей одного родителя | React сохраняет прежнюю идентичность и связанный state |
| Идентичность / state | `key` не задан: после перестановки или вставки типы на прежних позициях совпадают, но данные переместились | идентичность и state остаются у позиций, а не следуют за данными; поэтому state может перейти к другой записи |
| Идентичность / state | среди детей того же родителя совпадают `key` и тип, даже если элемент переставлен | React сохраняет идентичность сущности и её state на новой позиции |
| Идентичность / state | родитель изменился, тип изменился или изменился `key` | это новая идентичность: прежнее поддерево размонтируется, новое монтируется с начальным state |
| DOM | новое описание DOM-элемента связано с прежним DOM-узлом и DOM-тип тот же | React повторно использует прежний DOM-узел и применяет к нему нужные изменения |
| DOM | связь нового описания с прежним DOM-узлом потеряна (даже при том же DOM-типе) или DOM-тип изменился | прежний DOM-узел и его поддерево заменяются новым DOM-поддеревом |

## Базовая модель

JSX создаёт React elements - обычные объекты с описанием типа элемента, props и дочернего содержимого. При обновлении React вызывает компоненты и получает следующее описание интерфейса. По мере обхода дерева React сопоставляет возвращённые элементы с существующими узлами и вызывает вложенные компоненты. Эти действия чередуются внутри render phase, а не выполняются двумя отдельными проходами.

React не решает общую задачу поиска математически минимальной разницы между произвольными деревьями. Для интерфейсов используется предсказуемая модель идентичности:

1. позиция определяет, с каким прежним соседом сравнивается элемент;
2. тип показывает, можно ли сохранить прежний компонент или DOM-узел;
3. `key` уточняет идентичность среди соседей, особенно в списках.

Результатом render phase является подготовленная работа. Во время commit React вставляет, удаляет и обновляет DOM-узлы. Сам факт render компонента не означает, что соответствующий DOM обязательно изменится.

## Развернутый ответ

### Сопоставление DOM-элементов

Если на той же позиции остаётся, например, `<button>`, React сохраняет существующий DOM-узел и вычисляет, какие атрибуты, обработчики или текст нужно обновить. Изменения применяются в commit phase.

Если `<button>` заменяется на `<a>`, тип DOM-элемента меняется. React создаёт новый узел и удаляет прежний вместе с относящимся к нему поддеревом. Сохранить state дочерних компонентов через такую замену нельзя, потому что изменилась идентичность корня поддерева.

### Сопоставление компонентов и сохранение state

React хранит state не внутри вызова функции компонента, а связывает его с позицией компонента в render tree. Если на этой позиции остаётся тот же тип компонента, state сохраняется, даже когда изменились props или условие в коде записано в другой ветке.

Если на той же позиции появляется другой тип компонента, прежняя идентичность исчезает и связанный с ней state уничтожается. Поэтому компонент не следует объявлять внутри другого компонента: при каждом render создаётся новый объект функции, React видит другой тип и сбрасывает вложенный state.

### Списки и `key`

В списке одной позиции недостаточно: элементы могут перемещаться, добавляться и удаляться. `key` позволяет сопоставить соседние элементы по сущности, а не только по индексу. Стабильный `key={user.id}` помогает сохранить state конкретной строки после сортировки. Индекс массива связывает state с позицией и поэтому опасен в изменяемом списке.

`key` не обязан быть глобально уникальным - уникальность требуется только среди соседей, а для одной сущности значение должно оставаться стабильным между renders. Индекс безопасен лишь для действительно неизменяемого списка; `Math.random()` создаёт новую идентичность на каждом render и приводит к remount. `key` является специальным полем React и не попадает в props: нужный идентификатор передают отдельно.

`key` также можно использовать вне `map`, если нужно явно различить компоненты на одной позиции или осознанно сбросить state. Подробные правила выбора разобраны в отдельной заметке [key](<./key.md>).

### Reconciliation, Fiber и React 18

Внутреннее Fiber-дерево позволяет React хранить текущую версию интерфейса и подготавливаемую версию. В React 18 render, использующий concurrent-возможности, может быть приостановлен, продолжен или отброшен. React не применяет частично подготовленные DOM-изменения: mutation происходит после завершения нужной работы в commit phase.

Не каждый render в React 18 автоматически прерываемый. Без concurrent-функции обычное обновление может выполняться синхронно, как в предыдущих версиях. Поэтому Fiber объясняет возможность планирования, но не означает, что React всегда отдаёт управление браузеру посередине любого render.

## Пример

Пример показывает, как `key` меняет идентичность компонента на той же позиции.

```tsx
import { useState } from "react";

function Editor({ userId }: { userId: string }) {
  const [draft, setDraft] = useState("");

  return (
    <label>
      Draft for {userId}
      <input value={draft} onChange={event => setDraft(event.target.value)} />
    </label>
  );
}

export default function Profile({ userId }: { userId: string }) {
  return <Editor key={userId} userId={userId} />;
}
```

Пока `userId` не меняется, React сохраняет идентичность `Editor` и его `draft`. После изменения `userId` меняется `key`, поэтому прежний `Editor` размонтируется, новый монтируется с пустым state. Без `key` тот же `Editor` на той же позиции сохранил бы прежний `draft`, несмотря на новые props.

## Где применяется во frontend

| Ситуация | Как работает идентичность | Практическое следствие |
| --- | --- | --- |
| Переключение пользователя в форме | новый `key={userId}` создаёт новый экземпляр | черновик предыдущего пользователя сбрасывается |
| Сортировка редактируемой таблицы | стабильный `row.id` следует за записью | локальный state остаётся у правильной строки |
| Замена `<Form />` на `<Success />` | тип на позиции меняется | state формы уничтожается |
| Новый объект props у того же компонента | тип и позиция сохраняются | state остаётся, хотя компонент может снова выполниться |
| Concurrent-обновление React 18 | React может отбросить незавершённую render work | побочные эффекты нельзя выполнять во время render |

## Ключевые уточнения

- Reconciliation происходит во время render phase; commit применяет подготовленный результат к host-среде, например DOM.
- State сохраняется у того же типа компонента на той же позиции с той же идентичностью, а не у конкретной строки JSX.
- `key` участвует в идентичности среди соседей и может намеренно сбросить state вне списка.
- `key` должен быть стабильным и уникальным среди соседей; он не передаётся компоненту как обычный prop.
- React вычисляет необходимые DOM-операции, но не обещает математически минимальное решение для произвольных деревьев.
- Возможность прервать render относится к concurrent-обновлениям, а не ко всем renders React 18.
