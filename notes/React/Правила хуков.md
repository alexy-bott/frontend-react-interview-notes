## Быстрый ответ

У Hooks два базовых правила React 18. Во-первых, их вызывают только на верхнем уровне, до условных `return`: не внутри `if`, циклов, вложенных функций, event handlers или `try/catch`. Во-вторых, Hooks вызывают только из function components и custom Hooks. Так React получает одинаковый порядок вызовов на каждом render и связывает каждый `useState`, `useRef` или Effect с правильными внутренними данными.

Dependencies Effects, `useMemo` и `useCallback` должны отражать все reactive values, которые читаются внутри callback. Их не выбирают вручную ради желаемой частоты запуска: они следуют из кода. `eslint-plugin-react-hooks` проверяет порядок вызовов и полноту dependencies. Cleanup нужен тем Effects, которые создают ресурс или подписку; Effect без внешней синхронизации часто вообще не требуется.

## Ключевая схема

| Требование | Причина |
| --- | --- |
| Hooks на верхнем уровне | порядок вызовов остаётся одинаковым между renders |
| Hooks до условного `return` | ранний выход не пропускает часть Hook-цепочки |
| Hooks только в React-функциях | React управляет их state и lifecycle |
| Custom Hook начинается с `use` | линтер и React tooling распознают Hook-контракт |
| Все reactive values указаны в dependencies | callback получает актуальные props, state и локальные значения |
| Setup и cleanup симметричны | повторная синхронизация не оставляет старый ресурс |

## Базовая модель

При каждом render JavaScript заново выполняет функцию компонента. Имена локальных переменных вроде `count` или `isOpen` существуют только внутри этого выполнения и не передаются React как идентификаторы Hooks. Вызов `useState` сообщает React тип операции, но не имя переменной, в которую разработчик запишет результат.

Поэтому React связывает данные Hooks с компонентом и порядком вызовов. Упрощённо можно представить, что Fiber текущего компонента хранит цепочку Hook-записей, а во время render React последовательно перемещается по ней:

```text
первый useState  -> первая Hook-запись
второй useState  -> вторая Hook-запись
useEffect        -> третья Hook-запись
```

На следующем render тот же порядок позволяет вернуть каждому вызову прежний state, ref или Effect. Позиция здесь является учебной моделью публичного правила; код приложения не должен обращаться к внутренней Hook-цепочке Fiber.

Если на одном render второй Hook был `useState`, а на другом из-за условия он не вызвался, следующим вторым вызовом станет `useEffect`. React потеряет соответствие: данные, сохранённые для одной Hook-позиции, будут прочитаны другим вызовом. Поэтому проблема находится не в самом `if`, а в изменении последовательности Hooks между renders.

```text
render 1: useState -> useState -> useEffect
render 2: useState ->            useEffect
                              ^ позиции сдвинулись
```

Поэтому условие переносится не вокруг Hook, а внутрь его callback или результата:

```tsx
useEffect(() => {
  if (!enabled) return;

  const connection = connect();
  return () => connection.disconnect();
}, [enabled]);
```

`useEffect` вызывается на каждом render в одной позиции, но внешний ресурс создаётся только при `enabled === true`.

### Почему Hooks вызывают только из React-функций

Во время render React знает, какой Fiber сейчас вычисляется, и может связать очередной Hook с этим компонентом. Event handler, timer или обычный callback выполняется позже, когда render уже завершён. В этот момент нельзя создать новый `useState` или зарегистрировать Hook в середине существующей цепочки; handler может только вызвать ранее полученный setter или `dispatch`.

Custom Hook разрешён, потому что он синхронно вызывается во время render компонента. Его внутренние Hooks становятся частью той же последовательности. Custom Hook не получает отдельный скрытый компонент и не создаёт общий state между вызовами.

Обычная helper-функция, случайно вызванная во время render, не заменяет Custom Hook. Префикс `use` объявляет Hook-контракт для разработчика, линтера и React tooling: функция может вызывать Hooks и сама должна вызываться по их правилам.

Dependency array решает другую задачу и не определяет позицию Hook. Порядок вызовов помогает React найти Effect, а dependencies показывают, нужно ли после текущего commit заменить прежнюю синхронизацию новой. Callback замыкает значения конкретного render, поэтому пропущенная dependency оставляет ему устаревший snapshot.

## Развернутый ответ

### Где разрешено вызывать Hooks

Hook вызывается на верхнем уровне function component или custom Hook. Вызов внутри обычной utility-функции не поддерживается, даже если эта функция запускается во время render. Event handler может вызывать setter, полученный от Hook, но не сам `useState` или `useContext`.

Custom Hook получает префикс `use` и подчиняется тем же правилам. Обычная функция без Hooks не должна называться `useSomething`, потому что такое имя сообщает линтеру и читателю, что внутри действует Hook-контракт.

### Как определяются dependencies

Reactive values - props, state и значения, объявленные непосредственно в теле компонента. Если Effect или memo callback читает такое значение, оно указывается в dependency array. React сравнивает каждый dependency с предыдущим через `Object.is`.

Значение, объявленное вне компонента, не является reactive для конкретного render и обычно не требует dependency. Setter из `useState` и объект ref имеют стабильную идентичность; линтер позволяет их не указывать. Ручное удаление обычного prop или state из массива создаёт stale closure - callback продолжает использовать значения render, в котором он был создан.

Если dependency меняется слишком часто, исправляют источник нестабильности или структуру Effect. Возможные решения: перенести объект внутрь Effect, использовать updater-функцию, разделить разные процессы синхронизации или вынести действие пользователя в event handler. Удаление dependency без изменения кода не исправляет модель.

### Когда нужен cleanup

Cleanup возвращается, если setup создал то, что нужно остановить или отменить: подписку, timer, observer, соединение, imperative widget или запрос с `AbortController`. React вызывает cleanup перед новым setup с изменившимися dependencies и при unmount.

Effect, который только устанавливает `document.title`, может не требовать cleanup. Требование «каждый Effect обязан вернуть функцию» неверно; важна симметрия конкретной внешней синхронизации.

### Strict Mode и чистота

В React 18 Strict Mode в development выполняет дополнительный цикл `setup -> cleanup -> setup` при первом mount. Проверка показывает, полностью ли cleanup отменяет setup. Код не должен скрывать повторный запуск через ref-флаг: это оставляет исходную проблему при реальном повторном появлении компонента.

Updater-функции state также должны быть чистыми, потому что Strict Mode может вызывать их дополнительно в development для обнаружения побочных эффектов.

## Версии

Правила выше относятся к обычным Hooks React 18. В React 19 API `use` имеет отдельные разрешения для условий и циклов, но его нельзя переносить на `useState`, `useEffect` и остальные Hooks. Это исключение рассматривается только в версионном материале [React 18 и 19](<./React 18 и 19.md>).

## Пример

Custom Hook всегда вызывает `useState` и `useEffect` в одном порядке, а условие находится внутри Effect.

```tsx
import { useEffect, useState } from "react";

function useNow(enabled: boolean) {
  const [now, setNow] = useState(() => Date.now());

  useEffect(() => {
    if (!enabled) return;

    const intervalId = window.setInterval(() => {
      setNow(Date.now());
    }, 1000);

    return () => window.clearInterval(intervalId);
  }, [enabled]);

  return now;
}

export default function Clock({ enabled }: { enabled: boolean }) {
  const now = useNow(enabled);

  return <time>{new Date(now).toLocaleTimeString("ru-RU")}</time>;
}
```

При `enabled === false` Hook не нарушает порядок: Effect всё равно зарегистрирован, но setup не создаёт interval. При переключении с `true` на `false` React сначала вызывает cleanup прежнего Effect и останавливает timer.

## Где применяется во frontend

| Ситуация | Правило в коде | Результат |
| --- | --- | --- |
| Подписка зависит от `roomId` | `roomId` остаётся в dependencies | старое соединение закрывается, новое использует актуальную комнату |
| Interval изменяет счётчик | updater `setCount(value => value + 1)` | callback не зависит от устаревшего `count` |
| Effect создаёт объект из props | объект создаётся внутри Effect | dependency описывается примитивными входами, а не новой ссылкой каждого render |
| POST отправляется по клику | запрос остаётся в event handler | повторный Effect не отправляет действие пользователя снова |
| Custom Hook подписывается на browser API | setup и cleanup находятся рядом | каждый экземпляр корректно управляет своей подпиской |

## Ключевые уточнения

- **Порядок вызовов:** React связывает все Hooks компонента с позициями вызовов, потому что имена локальных переменных не входят в Hook API. Поэтому последовательность остаётся одинаковой между renders.
- **Место вызова:** event handler использует ранее полученный setter или `dispatch`, но не вызывает новый Hook. Custom Hook, напротив, выполняется во время render и добавляет свои вызовы в ту же последовательность.
- **Effects:** dependencies описывают прочитанные reactive values, а не желаемое расписание. Cleanup возвращается для созданного ресурса, но не требуется каждому Effect формально.
- **Версия:** особый контракт `use` из React 19 не меняет правила `useState`, `useEffect` и остальных Hooks React 18.
