## Быстрый ответ

Мемоизация в React - это оптимизация, при которой React сохраняет результат вычисления или ссылку и повторно использует их, пока связанные данные не изменились. За счёт этого React может пропустить часть повторной работы во время следующих renders. Мемоизация влияет только на производительность: логика приложения должна оставаться правильной и без неё.

В React 18 для ручной мемоизации используются три основных инструмента. `React.memo` позволяет пропустить render дочернего компонента при прежних props. `useMemo` сохраняет результат вычисления между renders. `useCallback` возвращает прежнюю ссылку на функцию, пока её зависимости не изменились. Props и зависимости по умолчанию сравниваются через `Object.is`, поэтому новый объект, массив или функция считаются новым значением даже при одинаковом содержимом.

Мемоизацию добавляют после измерения конкретной проблемы: дорогого вычисления или часто повторяющегося render тяжёлого компонента с прежними props. `memo`, `useMemo` и `useCallback` тоже выполняют сравнения и хранят значения, поэтому лёгкую работу часто выгоднее повторить. Если задержку создаёт слишком большой DOM или широкое обновление state и context, мемоизация не устраняет исходную причину.

## Ключевая схема

| Инструмент | Что сравнивает | Результат при равенстве |
| --- | --- | --- |
| `React.memo(Component)` | предыдущие и новые props | может пропустить повторный вызов дочернего компонента |
| `useMemo(calculate, deps)` | значения в списке зависимостей | возвращает сохранённый результат, не вызывая `calculate` |
| `useCallback(fn, deps)` | значения в списке зависимостей | возвращает прежнюю ссылку на функцию |

-> точечно добавить memo / useMemo / useCallback
-> повторно измерить production-сборку

## Базовая модель

По умолчанию render родителя приводит к render его дочерних компонентов. Это нормальное поведение: React вызывает компоненты, получает новое описание интерфейса, сравнивает его с предыдущим и в commit phase применяет к DOM только необходимые изменения. Поэтому вызов компонента ещё не означает изменение DOM и обычно не является проблемой, пока сам render остаётся дешёвым.

Мемоизация добавляет проверку перед повторной работой. По умолчанию React сравнивает предыдущие и новые props либо зависимости через `Object.is`. Примитивы обычно сравниваются по значению: `Object.is(5, 5)` возвращает `true`. Для объектов, массивов и функций важна ссылка: два отдельно созданных объекта `{}` считаются разными, хотя выглядят одинаково.

Из этого следует связь между тремя инструментами. `React.memo` не сможет пропустить дочерний компонент, если родитель при каждом render передаёт новый объект или callback (функцию обратного вызова). `useMemo` может сохранить ссылку на вычисленный объект, а `useCallback` - ссылку на функцию. Эти Hooks полезны только тогда, когда стабильная ссылка позволяет избежать конкретной повторной работы.

Список зависимостей определяет срок жизни сохранённого значения. Если хотя бы одна зависимость изменилась по `Object.is`, React пересчитает `useMemo` или вернёт новую функцию из `useCallback`. Все реактивные значения - props, state и переменные, объявленные внутри компонента и прочитанные в вычислении, - должны присутствовать в зависимостях. Иначе функция может работать с устаревшими данными из [замыкания](<../JavaScript/Замыкание.md>).

## Развернутый ответ

### `React.memo`

`memo(Component)` возвращает новую версию компонента с проверкой props. Когда родитель рендерится, React сравнивает каждый новый prop с предыдущим через `Object.is`. Если все props равны, React обычно может пропустить повторный render этого компонента.

Мемоизация касается только props, полученных от родителя. Изменение собственного state или context, который читает компонент, всё равно запускает render. `memo` также не является поведенческой гарантией: код должен работать правильно и без него.

Объекты, массивы и функции часто мешают этой оптимизации, потому что литерал или функция внутри родителя создают новую ссылку при каждом render. Сначала стоит упростить props компонента и передавать только необходимые данные. `useMemo` и `useCallback` добавляют тогда, когда сохранить ссылку действительно нужно для измеримой оптимизации.

У `memo` есть второй аргумент `arePropsEqual`, позволяющий написать собственное сравнение. Он нужен редко: функция должна сравнить каждый prop, включая callbacks, и быть быстрее самого render. Глубокое сравнение неизвестной структуры способно оказаться дороже компонента и заблокировать интерфейс.

### `useMemo`

`useMemo(calculateValue, dependencies)` вызывает чистую функцию вычисления на первоначальном render. При следующих renders React возвращает сохранённый результат, пока все зависимости равны предыдущим по `Object.is`. Если зависимость изменилась, вычисление запускается заново.

Первый типичный случай - действительно дорогой расчёт: фильтрация, сортировка, группировка или построение индекса по большой коллекции. Дешёвое выражение вроде `price * quantity` обычно не нуждается в `useMemo`.

Второй случай - стабильная ссылка на вычисленный объект или массив, который передаётся в `React.memo`-компонент либо используется как зависимость другого Hook. Здесь ценность может быть не в стоимости вычисления, а в том, что ссылка остаётся прежней.

`useMemo` не предотвращает render текущего компонента и не должен использоваться для хранения данных, необходимых для корректной логики. React сохраняет результат как оптимизацию и может удалить его по технической причине, после чего выполнит расчёт заново. Данные, влияющие на отображение, хранят в state; изменяемое значение, которое не должно запускать render, - в ref. Условия сброса сохранённого результата описаны в [документации `useMemo` для React 18](https://18.react.dev/reference/react/useMemo).

### `useCallback`

`useCallback(fn, dependencies)` возвращает прежнюю функцию, пока зависимости не изменились. Он не ускоряет тело функции и не предотвращает создание новой функции в JavaScript: функция из текущего render всё равно создаётся, но React может проигнорировать её и вернуть сохранённую ссылку.

Основной случай - callback передаётся как prop в компонент, обёрнутый в `memo`. Без `useCallback` новая ссылка сделает prop изменившимся, поэтому дочерний компонент не сможет пропустить render. Второй случай - функция является зависимостью другого Hook, и изменение ссылки запускает повторный Effect или пересчёт.

Если функция нужна только внутри Effect, часто проще объявить её прямо внутри Effect, а не оборачивать в `useCallback`. Это уменьшает количество зависимостей и делает причину повторного запуска понятнее. Все прочитанные внутри callback реактивные значения - props, state и переменные из тела компонента - должны оставаться в его списке зависимостей.

### Что проверить до мемоизации

Сначала нужно проверить причину лишней работы. Локальный UI-state не стоит поднимать выше, чем требуется: чем выше расположен state, тем большее поддерево затрагивает его обновление. Render должен оставаться чистым, а Effects не должны без необходимости обновлять state цепочкой.

[Context](<./Context.md>) лучше разделять по назначению и частоте обновлений. Если один provider передаёт большой объект и создаёт новую ссылку при каждом render, все компоненты, читающие этот context, получают обновление. `memo` не может остановить такое обновление: он сравнивает props, а не значение context внутри компонента.

Для длинного списка основной стоимостью могут быть тысячи компонентов и DOM-узлов. Виртуализация (virtualization) оставляет в интерфейсе только видимую часть списка и тем самым уменьшает объём работы. `memo` решает другую задачу: позволяет не вызывать повторно уже существующие элементы, если их props не изменились.

## Версии и совместимость

Основной материал этой карточки относится к React 18 без React Compiler: используются ручные `memo`, `useMemo` и `useCallback`.

[React Compiler](<./React Compiler.md>) - отдельный инструмент этапа сборки (build time), а не часть кода React 18, выполняющегося в браузере (runtime). Он анализирует компоненты и Hooks во время сборки и может автоматически добавить мемоизацию там, где это безопасно. Compiler поддерживает React 18, но для версий ниже React 19 требуется отдельная настройка, описанная в [официальной инструкции по установке](https://react.dev/learn/react-compiler/installation). Поэтому его поведение не входит в основную модель этой карточки.

## Пример

Пример показывает совместную работу трёх инструментов в длинном списке. Такая оптимизация оправдана после измерения: для десятка простых элементов она, скорее всего, не нужна. `console.log` используется для наблюдения за вызовами `TodoItem`; в development с включённым Strict Mode дополнительные проверочные вызовы могут добавить повторные сообщения.

```tsx
import { memo, useCallback, useMemo, useState } from "react";

type Todo = {
  id: string;
  title: string;
};

const TodoItem = memo(function TodoItem({
  todo,
  selected,
  onToggle,
}: {
  todo: Todo;
  selected: boolean;
  onToggle: (id: string) => void;
}) {
  console.log("TodoItem render", todo.id);

  return (
    <li>
      <label>
        <input
          type="checkbox"
          checked={selected}
          onChange={() => onToggle(todo.id)}
        />
        {todo.title}
      </label>
    </li>
  );
});

export function TodoList({ todos }: { todos: Todo[] }) {
  const [query, setQuery] = useState("");
  const [selectedId, setSelectedId] = useState<string | null>(null);

  const visibleTodos = useMemo(() => {
    const normalizedQuery = query.trim().toLowerCase();

    return todos.filter((todo) =>
      todo.title.toLowerCase().includes(normalizedQuery),
    );
  }, [todos, query]);

  const handleToggle = useCallback((id: string) => {
    setSelectedId((currentId) => (currentId === id ? null : id));
  }, []);

  return (
    <>
      <label>
        Search:
        <input value={query} onChange={(event) => setQuery(event.target.value)} />
      </label>
      <ul>
        {visibleTodos.map((todo) => (
          <TodoItem
            key={todo.id}
            todo={todo}
            selected={selectedId === todo.id}
            onToggle={handleToggle}
          />
        ))}
      </ul>
    </>
  );
}
```

`useMemo` повторно фильтрует список только при изменении `todos` или `query`. `useCallback` возвращает прежнюю ссылку `handleToggle`, потому что callback использует стабильный setter и функциональное обновление state: следующее значение вычисляется из `currentId`, переданного React.

При изменении `selectedId` родитель рендерится снова, но `useMemo` возвращает прежний массив `visibleTodos`, а `useCallback` - прежнюю функцию `handleToggle`. Объекты `todo` также сохраняют ссылки. Поэтому у большинства `TodoItem` все props остаются прежними, и `memo` позволяет пропустить их render. Повторно вызываются только элементы, у которых изменился prop `selected`.

Если родитель `TodoList` при каждом render создаёт новые объекты `todo`, `memo` увидит новые props и не сможет пропустить элементы. Сам массив `visibleTodos` не передаётся в `TodoItem`, поэтому изменение ссылки на массив не мешает сравнению отдельных элементов; важны ссылки на объекты `todo` внутри него.

Пример предполагает неизменяемое обновление `todos`: при изменении списка родитель передаёт новый массив, а изменившийся элемент получает новый объект. Если изменить существующий массив на месте и сохранить прежнюю ссылку, `useMemo` не увидит изменения зависимости и может вернуть устаревший результат фильтрации.

## Ключевые уточнения

### Границы инструментов

- **`React.memo` сравнивает props, но не блокирует собственный state и context.** Компонент с равными props всё равно рендерится, если изменился его state или используемое значение context.
- **`useMemo` сохраняет результат вычисления, но не предотвращает render компонента.** Функция компонента уже выполняется, после чего Hook решает вернуть прежний результат или пересчитать его.
- **`useCallback` сохраняет итоговую ссылку, но не предотвращает создание функции.** React может проигнорировать новую функцию текущего render и вернуть сохранённую, если зависимости прежние.
- **Сохранённые значения этих API не являются хранилищем данных приложения.** Код должен оставаться корректным, даже если React повторит render или удалит результат мемоизации.

### Ссылки и зависимости

- **Объект, массив и функция сравниваются по ссылке.** Новый литерал считается новым prop или зависимостью, даже если его содержимое совпадает с предыдущим.
- **Список зависимостей должен содержать все реактивные значения.** Пропущенная зависимость может оставить callback или вычисление с устаревшими props и state.
- **`key` определяет идентичность, а не мемоизацию.** Смена `key` создаёт новую сущность и сбрасывает state поддерева; стабильный `key` сам по себе не запрещает render.

### Стратегия оптимизации

- **Профилирование выполняют до и после изменения.** Измерять нужно production-сборку и конкретное медленное взаимодействие, а не количество `console.log` в development Strict Mode.
- **Виртуализация и мемоизация решают разные задачи.** Первая уменьшает количество одновременно созданных элементов, вторая пытается не повторять работу для уже существующих.
- **React Compiler не исправляет широкое состояние, тяжёлые Effects и слишком большой DOM.** Автоматическая мемоизация не заменяет архитектурные и алгоритмические оптимизации.
