## Быстрый ответ

`key` - служебное значение, которое помогает React различать соседние элементы между renders. В списке React использует позицию и `key`, чтобы понять, какой новый элемент соответствует прежней сущности после добавления, удаления или перемещения. От этого зависит сохранение экземпляра компонента, локального state и связанного DOM.

Хороший `key` уникален среди соседей и стабилен на протяжении жизни сущности. Обычно это `id` из данных. Индекс массива описывает позицию, поэтому при сортировке, вставке или удалении state может оказаться у другой строки. `Math.random()` и создание UUID во время render дают новый `key` каждый раз, из-за чего React пересоздаёт компоненты и DOM. Осознанная смена `key` полезна, когда состояние компонента действительно нужно сбросить.

## Ключевая схема

| Свойство `key` | Что означает |
| --- | --- |
| Уникален среди соседей | одинаковый `key` можно использовать в другом независимом списке |
| Стабилен между renders | одна сущность получает один `key` на протяжении своей жизни |
| Получен из данных | `todo.id`, `user.id`, `message.id` |
| Создан вместе с записью | локальный UUID генерируется при добавлении данных, а не во время render |
| Не передаётся как prop | нужный идентификатор передают отдельно, например `userId={user.id}` |
| Изменение `key` | прежний экземпляр размонтируется, новый монтируется с новым state |

## Базовая модель

Без явного `key` React сопоставляет соседние элементы прежде всего по их позиции. Для статичного набора этого может быть достаточно. В изменяемом списке позиция и сущность расходятся: после вставки первая запись может стать второй, хотя сама запись не изменилась.

`key` добавляет к позиции устойчивую идентичность. React может связать запись с прежним компонентом, даже если она переместилась. При совпавших типе и `key` React сохраняет экземпляр и его state. При новом `key` прежняя идентичность больше не подходит, поэтому React монтирует новый экземпляр.

`key` нужен самому React и не входит в `props`. Если компоненту требуется тот же идентификатор для запроса или обработчика, его нужно передать отдельным prop.

## Развернутый ответ

### Откуда брать `key`

Для серверных данных обычно используется идентификатор записи: `id`, `slug` или другой стабильный первичный ключ. Для данных, создаваемых локально, идентификатор следует создать один раз в момент добавления записи и сохранить вместе с ней. Например, `crypto.randomUUID()` подходит при создании новой заметки, но не внутри `map` во время render.

Значение `key` не обязано быть числом и не обязано быть уникальным во всём приложении. React требует уникальности только среди элементов одного массива или одной группы соседей.

### Почему индекс может связать state не с той записью

Представим редактируемую таблицу, где каждая строка хранит локальный черновик. Если первая запись удалена, все следующие индексы уменьшаются. При `key={index}` React сопоставляет прежнюю строку с новой записью на той же позиции и может сохранить там прежний локальный state или DOM-состояние input.

Индекс допустим, когда элементы не имеют стабильных идентификаторов и список гарантированно не сортируется, не фильтруется, не получает вставок в середину и не содержит состояния, которое должно следовать за сущностью. Это узкое условие, поэтому идентификатор из данных обычно надёжнее.

### Почему случайный `key` приводит к remount

`Math.random()`, `Date.now()` или новый UUID внутри render возвращают другое значение при каждом вызове компонента. Старые и новые keys не совпадают, поэтому React удаляет прежние экземпляры и создаёт новые. Это сбрасывает state и пользовательский ввод, снимает focus, повторно запускает Effects и создаёт лишнюю DOM-работу.

### `key` вне списка

React позволяет использовать `key` для явного различения компонентов на одной позиции. Например, редактор профиля можно связать с `userId`. При переключении пользователя новый `key` гарантирует новый экземпляр формы без черновика предыдущего пользователя.

Это не средство «обновить компонент посильнее». Смена `key` оправдана только тогда, когда по смыслу появляется другая сущность и прежнее локальное состояние не должно сохраняться.

## Пример

В списке `todo.id` сохраняет идентичность записи, а в форме `userId` намеренно сбрасывает локальный state при смене пользователя.

```tsx
import { useState } from "react";

type Todo = { id: string; title: string };

function TodoList({ todos }: { todos: Todo[] }) {
  return (
    <ul>
      {todos.map(todo => (
        <li key={todo.id}>{todo.title}</li>
      ))}
    </ul>
  );
}

function Editor() {
  const [draft, setDraft] = useState("");

  return (
    <label>
      Draft
      <input value={draft} onChange={event => setDraft(event.target.value)} />
    </label>
  );
}

function UserEditor({ userId }: { userId: string }) {
  return <Editor key={userId} />;
}
```

После сортировки `todos` каждая строка сохраняет связь со своим `id`. После изменения `userId` React монтирует новый `Editor`, поэтому `draft` снова становится пустой строкой.

Если `map` должен вернуть несколько соседних узлов без дополнительного DOM-контейнера, используется полная форма Fragment:

```tsx
import { Fragment } from "react";

type Todo = { id: string; title: string };

function TodoDescriptions({ todos }: { todos: Todo[] }) {
  return (
    <dl>
      {todos.map(todo => (
        <Fragment key={todo.id}>
          <dt>{todo.title}</dt>
          <dd>{todo.id}</dd>
        </Fragment>
      ))}
    </dl>
  );
}
```

Короткая запись `<>...</>` не принимает `key`.

## Где применяется во frontend

| Ситуация | Подходящий `key` | Почему |
| --- | --- | --- |
| Редактируемая таблица | `row.id` | state и DOM строки следуют за записью при сортировке |
| Drag-and-drop список | `item.id` | перемещение не создаёт новую идентичность элемента |
| Чат | `message.id` | новые сообщения не меняют идентичность старых |
| Локально созданные заметки | UUID, сохранённый при создании записи | значение остаётся стабильным между renders |
| Сброс формы при смене пользователя | `key={userId}` на форме | новая сущность получает новый локальный state |

## Ключевые уточнения

- `key` различает элементы только среди соседей; глобальная уникальность не требуется.
- Идентификатор создаётся вместе с данными, а не во время render компонента.
- Индекс безопасен только при действительно неизменяемом порядке и отсутствии state, связанного с сущностью.
- `key` не доступен как `props.key`; нужное значение передаётся отдельным prop.
- Смена `key` означает remount, поэтому её используют для осознанного сброса, а не как обычную оптимизацию.
