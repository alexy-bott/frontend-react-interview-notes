## Быстрый ответ

React обновляет интерфейс в несколько этапов: сначала получает запрос на обновление, затем выполняет render, после этого применяет изменения во время commit, а браузер при необходимости отрисовывает результат. Ниже описан обычный клиентский цикл React DOM 18 с `createRoot`. Если страница уже содержит HTML, созданный на сервере, React подключается к нему через `hydrateRoot`; этот процесс называется [hydration](<./Hydration.md>).

Первоначальный render запускается вызовом `root.render(<App />)`. Последующие обновления планируются после вызова setter-а state, изменения используемого context или обновления данных внешней подписки. Новые props не возникают самостоятельно: дочерний компонент получает их во время render родителя, поэтому их изменение является следствием обновления выше по дереву.

Во время render phase React вызывает компоненты с текущими props, state и context и получает React elements - объектные описания будущего UI. В рамках reconciliation React сопоставляет новый результат с текущим деревом и определяет, какие элементы нужно сохранить, добавить, изменить или удалить. Реальный DOM на этой фазе не меняется.

Во время commit phase React применяет подготовленные DOM-изменения, синхронизирует refs и запускает `useLayoutEffect`. После commit браузер получает возможность при необходимости пересчитать стили и расположение элементов, а затем выполнить paint. `useEffect` выполняется после commit: обычно браузер сначала показывает обновлённый кадр, но для некоторых обновлений из пользовательского события Effect может запуститься раньше.

Главное различие: вызов компонента, изменение DOM и browser paint - это три разные операции. Компонент может выполниться повторно, даже если менять DOM в результате не потребуется.

## Ключевая схема

```text
первоначальный запуск или запланированное обновление
-> render phase
   -> вызвать компоненты
   -> выполнить reconciliation
   -> определить необходимые изменения
-> commit phase
   -> применить DOM-изменения
   -> синхронизировать refs
   -> выполнить useLayoutEffect
-> после commit возможны две операции:
   - браузер при необходимости выполняет layout и paint
   - React выполняет useEffect
   относительный порядок paint и useEffect зависит от причины обновления
```

| Понятие | Что означает |
| --- | --- |
| Запуск (trigger) | первоначальный запуск или обновление, из-за которого React планирует работу |
| React element | объектное описание элемента UI, обычно созданное из JSX |
| Render phase | вызов компонентов и вычисление следующего UI |
| Reconciliation | сопоставление нового результата с текущим деревом внутри render phase |
| Commit phase | непрерываемое применение подготовленных изменений к DOM |
| Browser paint | отрисовка браузером изменившихся пикселей страницы |

## Базовая модель

Компонент React не возвращает DOM-узел и не изменяет страницу напрямую. Он возвращает JSX, из которого создаются React elements. Каждый такой объект описывает тип элемента, его props и дочерние элементы. React использует эти описания, чтобы понять, каким должен стать интерфейс.

На первоначальном render React создаёт необходимые DOM-узлы, но ещё не добавляет их в документ. Во время commit phase React вставляет подготовленные узлы в DOM-дерево. При последующих renders React сопоставляет новый результат с текущим деревом, вычисляет необходимые изменения и применяет их во время commit.

При сопоставлении важны позиция, тип и `key`. Тот же тип в той же позиции обычно сохраняет локальный state. Другой тип означает новое поддерево и сброс прежнего state. Среди соседних элементов `key` позволяет React понять, какие сущности сохранились после вставки, удаления или перестановки.

Термин Virtual DOM обычно используют как общее название объектного представления UI в памяти. Это не отдельная фаза и не полная копия браузерного DOM. Практически важнее понимать последовательность render/reconciliation → commit и различать результат компонента от реальных DOM-изменений.

## Развернутый ответ

### 1. Что запускает обновление

Первоначальный клиентский render запускается вызовом `createRoot(container).render(<App />)`. После него setter из `useState` или `dispatch` из `useReducer` ставит обновление в очередь. React 18 может объединить несколько обновлений в один render через [automatic batching](<./Batching.md>).

React отслеживает, какие компоненты читают context, и обновляет их при изменении значения provider. Внешнее хранилище подключается через подписку. Hook `useSyncExternalStore` получает функцию `getSnapshot`, которая возвращает snapshot - неизменяемый снимок нужной компоненту части хранилища. Когда подписка сообщает об изменении, React повторно вызывает `getSnapshot` и запускает render, если новое значение отличается от предыдущего по `Object.is`.

Props являются входными данными компонента, а не самостоятельным React API для запуска обновления. Сначала обновляется и рендерится родитель, после чего его потомки получают props из нового результата. По умолчанию render родителя приводит к вызову вложенных компонентов, даже если их props равны предыдущим.

### 2. Render и reconciliation

Render означает вызов функции компонента. React передаёт ей актуальные props, а Hooks возвращают state и context для текущего render. Полученный JSX описывает следующую версию интерфейса.

Код render должен быть чистым: одинаковые входные данные должны давать одинаковый JSX, а компонент не должен во время вычисления изменять DOM, внешние объекты или запускать запросы. В development-режиме React 18 Strict Mode дополнительно вызывает тела компонентов и некоторые переданные React чистые функции, включая инициализатор начального state и updater-функцию, переданную setter-у. Он также выполняет дополнительный цикл setup → cleanup → setup для Effects, чтобы обнаружить отсутствующую очистку. В production эти дополнительные проверки не выполняются.

Reconciliation происходит во время render phase. React сопоставляет новые элементы с текущим внутренним деревом и использует эвристики вместо универсального сравнения любых деревьев. Главные признаки идентичности - позиция, тип и `key`. Результатом этой фазы становится перечень работы, которую нужно выполнить во время commit.

### 3. Commit и отрисовка браузером

Если render phase успешно завершилась, React переходит к commit. Эта фаза не прерывается: React применяет подготовленные вставки, удаления и изменения DOM, синхронизирует [refs](<./useRef.md>), привязанные к элементам, и запускает `useLayoutEffect`. Если новый результат не требует изменения конкретного DOM-узла, React не трогает его, даже если соответствующий компонент был вызван повторно.

`useLayoutEffect` выполняется после DOM-изменений, но до того, как браузер сможет показать обновлённый кадр. Поэтому в нём можно измерить layout - геометрию элементов - и синхронно скорректировать интерфейс, но тяжёлая работа задержит paint.

После commit браузер получает возможность при необходимости пересчитать стили и layout, а затем нарисовать изменившиеся пиксели во время paint. React запускает setup-функцию `useEffect` после commit. Для обновления, не вызванного пользовательским взаимодействием, React обычно позволяет браузеру сначала выполнить paint. Для клика или другого взаимодействия Effect может выполниться до paint, поэтому его нельзя считать операцией, которая гарантированно происходит после показа кадра. Такое поведение зафиксировано в [документации `useEffect` для React 18](https://18.react.dev/reference/react/useEffect).

### 4. Внутренняя модель: Fiber и concurrent rendering

[Fiber](<./Fiber.md>) - внутренняя архитектура reconciler, части React, которая выполняет reconciliation. Каждый fiber представляет компонент или другой узел React-дерева и хранит связи с соседними узлами, state и информацию о запланированной работе. React сохраняет уже показанное текущее дерево (current tree), пока готовит рабочее дерево следующей версии (work-in-progress tree). Пользователь не видит рабочее дерево до commit.

Такое устройство позволяет React назначать обновлениям приоритеты и во время concurrent render периодически уступать основной поток браузеру для более срочной работы. React не переносит render в отдельный поток. В React 18 concurrent rendering используется возможностями вроде [transitions](<./useTransition и useDeferredValue.md>) и [Suspense](<./Suspense и lazy.md>), что отдельно описано в [анонсе React 18](https://react.dev/blog/2022/03/29/react-v18).

Прерываемость не означает, что любой render автоматически выполняется маленькими фрагментами. Обычное срочное обновление может пройти синхронно от начала до конца. Fiber даёт React возможность приостановить, продолжить или отбросить concurrent render, но не делает тяжёлые вычисления бесплатными.

### 5. Когда React может пропустить работу

Если setter получает state, равный текущему значению по `Object.is`, React обычно пропускает обновление компонента и его потомков. В некоторых случаях React всё же может вызвать компонент перед тем, как отбросить результат, поэтому код render в любом случае должен оставаться чистым.

Повторный вызов компонента также не означает обязательного изменения DOM. Reconciliation может показать, что итоговые DOM-свойства не изменились. Это экономит DOM-операции, хотя стоимость выполнения компонента уже была понесена.

`React.memo` позволяет пропустить render дочернего компонента, если родитель рендерится. По умолчанию React сравнивает каждый новый prop с предыдущим через `Object.is`; вместо этого можно передать собственную функцию `arePropsEqual`. Новые объекты и функции имеют другие ссылки и не проходят стандартное сравнение. Собственное обновление state или используемого context всё равно приводит к render, а мемоизация остаётся оптимизацией, а не гарантией.

## Версии и совместимость

Основная модель этой карточки рассчитана на клиентское приложение с React 18 и `createRoot`. Для страницы с HTML, подготовленным на сервере, начальной точкой будет `hydrateRoot`; SSR и hydration разбираются отдельно. Подробный механизм Fiber и различия между версиями вынесены в [карточку Fiber](<./Fiber.md>) и [разбор версий](<./React 18 и 19.md>).

## Пример

Пример показывает, что повторный render компонента не обязательно приводит к изменению всех созданных им DOM-узлов. `console.log` здесь нужен только для наблюдения за вызовами компонентов; в development с включённым Strict Mode дополнительные проверочные вызовы могут добавить повторные сообщения.

```tsx
import { useState } from "react";

function Result({ value }: { value: number }) {
  console.log("Result render");
  return <p>Result: {value}</p>;
}

export function Calculator() {
  const [count, setCount] = useState(0);
  const [query, setQuery] = useState("");

  console.log("Calculator render");

  return (
    <>
      <label>
        Query:
        <input value={query} onChange={(event) => setQuery(event.target.value)} />
      </label>
      <p>Query: {query}</p>
      <button type="button" onClick={() => setCount((value) => value + 1)}>
        Increment
      </button>
      <Result value={count * 2} />
    </>
  );
}
```

При вводе текста `setQuery` ставит обновление `Calculator` в очередь. React повторно вызывает `Calculator`, а затем `Result`, потому что по умолчанию компоненты-потомки рендерятся вместе с родителем. Во время commit изменится текст `Query`, но существующий DOM-узел `<p>`, созданный из результата `Result`, останется прежним, поскольку его тип и текстовое содержимое не изменились.

При нажатии `Increment` изменяется `count`, поэтому новый prop `value` доходит до `Result`, и React обновляет его текст во время commit. Если измерения покажут, что повторный вызов тяжёлого дочернего компонента создаёт проблему, его можно точечно оптимизировать через [мемоизацию](<./Мемоизация.md>).

## Где применяется во frontend

| Ситуация | Что происходит | Практический вывод |
| --- | --- | --- |
| Строки списка содержат `<input>` | React связывает state с позицией, типом и `key` | использовать стабильный идентификатор данных, чтобы state не перешёл к другой строке |
| Ввод обновляет тяжёлый список | срочное обновление input конкурирует с дорогим render результатов | уменьшить вычисления, использовать виртуализацию (virtualization) для показа только видимых строк и при необходимости [transition](<./useTransition и useDeferredValue.md>) |
| Context или store обновляет большой экран | компоненты, которые читают изменившийся context или подписаны на изменившуюся часть store, получают обновление | разделять context и подписывать компонент только на необходимые данные |
| Интерфейс тормозит после действия | задержка может находиться в render, commit, layout или browser paint | измерять этапы через [React DevTools Profiler](<../Performance/React performance profiling.md>) и браузерный Performance panel |
| Страница получила HTML с сервера | [hydration](<./Hydration.md>) связывает существующий HTML с клиентским React-деревом | первоначальный результат клиента должен соответствовать серверному, иначе возникает несоответствие при hydration |

## Ключевые уточнения

### Запуск обновления и render

- **Новые props дочерний компонент получает во время render родителя.** Поэтому источник появления новых props находится выше по дереву, а не внутри дочернего компонента.
- **Дочерний компонент может рендериться независимо от новых props.** Причиной может быть его собственный state, изменившийся context или обновление внешней подписки.
- **React обычно пропускает обновление при прежнем значении state.** Если setter получает значение, равное текущему по `Object.is`, компонент и его потомки не требуют нового результата. При этом компонент всё ещё может быть вызван по другой причине, например из-за render родителя или изменения context.
- **Вызов компонента и изменение DOM - разные операции.** Render вычисляет следующее описание UI. Если reconciliation не находит различий в DOM-свойствах, commit не меняет соответствующие узлы, хотя стоимость выполнения компонента уже была понесена.

### Reconciliation и идентичность

- **Reconciliation выполняется внутри render phase и учитывает идентичность элементов.** React сопоставляет элементы по позиции, типу и `key`, после чего подготавливает работу для commit. Индекс массива подходит для статичного списка, но после вставки, удаления или перестановки может связать локальный state, фокус или введённое значение с неправильной строкой.

### Concurrent rendering, Strict Mode и Effects

- **В React 18 прерываемыми могут быть concurrent-обновления.** Обычный срочный render может выполняться синхронно от начала до конца, поэтому тяжёлый JavaScript по-прежнему способен заблокировать основной поток браузера (main thread).
- **Дополнительные проверки React 18 Strict Mode относятся к режиму разработки.** Повторные вызовы компонентов и чистых функций помогают находить нечистые вычисления, а дополнительный цикл setup → cleanup → setup для Effects - отсутствующую очистку. Эти проверки не описывают обычное production-поведение.
- **`useEffect` выполняется после commit, но не всегда после browser paint.** Для обновления из пользовательского взаимодействия React может выполнить Effect до того, как браузер покажет кадр.

### Мемоизация

- **`React.memo` по умолчанию сравнивает props через `Object.is`.** Собственный state и используемый context по-прежнему могут запустить render, а правила пользовательского сравнения `arePropsEqual` подробнее разобраны в карточке [о мемоизации](<./Мемоизация.md>).
