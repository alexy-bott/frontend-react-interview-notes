## Быстрый ответ

Пакетная обработка обновлений (batching) - это объединение нескольких запросов на изменение state перед следующим render. React сначала собирает обновления в очередь, затем вычисляет итоговое состояние и обычно выполняет один render затронутой части дерева вместо render после каждого setter. При этом переменная state внутри текущего обработчика не меняется: она остаётся снимком того render, в котором был создан обработчик.

В React 18 при использовании `createRoot` или `hydrateRoot` automatic batching работает не только в React event handlers, но и в callbacks `Promise`, `setTimeout`, native events и других источников. Если следующее значение зависит от предыдущего обновления в очереди, используется updater-функция: `setCount(count => count + 1)`. `flushSync` позволяет принудительно обновить DOM синхронно, но нужен редко, главным образом для интеграции с browser API или сторонним imperative-кодом.

## Ключевая схема

| Действие | Что попадает в очередь | Результат |
| --- | --- | --- |
| `setCount(count + 1)` | заменить state вычисленным значением | несколько вызовов из одного snapshot могут дать одинаковое значение |
| `setCount(count => count + 1)` | вычислить значение из предыдущего элемента очереди | несколько updater-функций применяются последовательно |
| Несколько setters в одном callback | несколько обновлений | React 18 с новым root обычно объединяет их в один render |
| Два отдельных пользовательских события | независимые очереди | каждый клик обрабатывается отдельно |
| `flushSync(() => setState(...))` | синхронная обработка обновления | DOM обновлён к следующей строке после `flushSync` |

## Базовая модель

Каждый render получает собственный снимок state. Вызов setter не изменяет переменную внутри уже выполняющегося кода, а добавляет обновление в очередь React. После завершения текущего обработчика React обрабатывает очередь, вычисляет следующий state и запускает render.

Setter принимает два разных вида аргумента:

1. **Значение:** React ставит в очередь замену state уже вычисленным значением.
2. **Updater-функцию:** React передаст ей актуальный промежуточный state из очереди и использует возвращённое значение дальше.

Batching сокращает промежуточные renders и не позволяет интерфейсу показать частично применённый набор связанных обновлений. Он не делает setter синхронным и не объединяет все обновления приложения навсегда в один batch.

## Развернутый ответ

### Почему три `setCount(count + 1)` дают `+1`

В обработчике, созданном при `count === 0`, выражение `count + 1` каждый раз вычисляется как `1`. В очередь попадают три замены на одно и то же значение. Итоговый state равен `1`.

В записи `setCount(value => value + 1)` React ставит в очередь функцию. При обработке очереди первая функция получает `0` и возвращает `1`, вторая получает `1` и возвращает `2`, третья получает `2` и возвращает `3`.

Updater-функция особенно нужна, когда новое значение зависит от предыдущего state и до следующего render может быть поставлено несколько обновлений. Если новое значение полностью определяется данными текущего события, передавать обычное значение допустимо.

### Что изменилось в React 18

До React 18 React автоматически объединял прежде всего обновления внутри собственных event handlers. Обновления из `setTimeout`, `Promise.then` или native event handler могли приводить к отдельным renders.

В React 18 расширенный automatic batching включается для root, созданного через `createRoot` или `hydrateRoot`. Обновления внутри одного callback группируются независимо от его источника. Legacy API `ReactDOM.render` сохранял прежнее поведение для постепенной миграции. Это условие прямо указано в [руководстве по обновлению до React 18](https://react.dev/blog/2022/03/08/react-18-upgrade-guide#automatic-batching).

React обрабатывает отдельные намеренные пользовательские события, например два клика, независимо. Также не следует рассчитывать, что обновления из несвязанных callbacks обязательно попадут в один batch: границы определяет планирование React и источник работы, а не только близость строк в коде.

### Когда нужен `flushSync`

`flushSync` из `react-dom` заставляет React синхронно обработать обновления внутри callback и применить изменения к DOM до выполнения следующей строки. Это может понадобиться, когда browser API или сторонняя библиотека сразу после callback читает DOM. Пример - подготовка разметки перед открытием системного диалога печати.

Это крайний инструмент. `flushSync` может ухудшить производительность, обработать часть ожидающей работы и заставить Suspense снова показать fallback. В обычном React-коде читать новое состояние через DOM сразу после setter обычно не требуется.

### Batching и transitions решают разные задачи

Batching группирует обновления, чтобы избежать лишних промежуточных renders. Transition помечает обновление как несрочное и позволяет React 18 подготовить его с использованием concurrent rendering. Несколько обновлений могут одновременно быть объединены в batch и иметь transition-приоритет; одно не отменяет другое.

## Пример

Пример показывает разницу между заменой state готовым значением и последовательными updater-функциями.

```tsx
import { useState } from "react";

export default function Counter() {
  const [count, setCount] = useState(0);

  function incrementOnce() {
    setCount(count + 1);
    setCount(count + 1);
    setCount(count + 1);
  }

  function incrementThreeTimes() {
    setCount(value => value + 1);
    setCount(value => value + 1);
    setCount(value => value + 1);
  }

  return (
    <div>
      <p>Count: {count}</p>
      <button onClick={incrementOnce}>Add one</button>
      <button onClick={incrementThreeTimes}>Add three</button>
    </div>
  );
}
```

Первый обработчик увеличивает значение на `1`, потому что все три выражения используют один snapshot `count`. Второй увеличивает его на `3`, потому что каждая updater-функция получает результат предыдущей. В обоих случаях React обрабатывает очередь после завершения обработчика и не показывает промежуточные значения `1` и `2` отдельными commits.

## Где применяется во frontend

| Ситуация | Что важно |
| --- | --- |
| Несколько связанных полей state меняются в одном действии | React 18 обычно объединяет обновления и не показывает промежуточное состояние UI |
| Счётчик получает несколько изменений до render | updater-функция вычисляет каждое значение из предыдущего элемента очереди |
| Обновление приходит из `Promise` или `setTimeout` | automatic batching требует React 18 и нового root API |
| Browser API должен немедленно прочитать изменённый DOM | `flushSync` допустим как крайняя мера интеграции |
| Фильтрация большого списка не должна блокировать ввод | используется transition; batching сам по себе не задаёт приоритет |

## Ключевые уточнения

- Batching объединяет обработку запросов на state, но не изменяет snapshot внутри текущего обработчика.
- Updater-функция нужна, когда новое значение зависит от предыдущего значения в очереди.
- React 18 расширяет automatic batching для root, созданного новым client API; одного обновления версии пакета при сохранении `ReactDOM.render` недостаточно.
- Отдельные пользовательские события обрабатываются независимо, поэтому два клика не превращаются в один общий batch.
- `flushSync` обеспечивает синхронный DOM commit для интеграции, но не является способом «ускорить» React.
