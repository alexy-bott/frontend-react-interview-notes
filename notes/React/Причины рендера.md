## Быстрый ответ

React вызывает компонент при первоначальном render и при обновлении, затрагивающем этот участок дерева. Обновление может быть запрошено собственным state компонента, state его предка, изменением используемого context или новым снимком данных внешнего хранилища. Когда родитель рендерится, React по умолчанию рекурсивно вызывает его дочерние компоненты, поэтому дочерний компонент может выполниться даже с прежними props.

Новые props не являются самостоятельным источником render: дочерний компонент получает их во время render родителя. Изменение `key` тоже не является обычной причиной повторного render - React считает элемент другой сущностью, удаляет прежний экземпляр и монтирует новый. Вызов компонента не означает обязательное изменение DOM: во время commit React применяет только необходимые изменения.

## Ключевая схема

| Источник | Как компонент попадает в render |
| --- | --- |
| Первоначальный запуск | `root.render(...)` начинает построение дерева |
| Собственный state | setter из `useState` или `dispatch` из `useReducer` запрашивает обновление |
| State предка | React рендерит обновившегося предка и по умолчанию проходит его потомков |
| Context | потребитель рендерится, если используемое значение context изменилось по `Object.is` |
| Внешнее хранилище | подписка сообщает об изменении, а новый snapshot отличается по `Object.is` |
| Новые props | передаются во время render родителя, а не запускают его сами |
| Новый `key` | создаёт новую идентичность: прежний экземпляр размонтируется, новый монтируется |

## Базовая модель

Render начинается с запроса обновления в определённой точке дерева. React вызывает соответствующий компонент, получает следующее описание интерфейса и рекурсивно обрабатывает его потомков. По умолчанию render родителя приводит к render дочерних компонентов независимо от того, изменились ли их props.

React может пропустить часть работы. Например, `React.memo` по умолчанию сравнивает каждый prop с предыдущим значением через `Object.is` и обычно пропускает render дочернего компонента, если props не изменились. Это не блокирует обновление собственного state или используемого context. Мемоизация является оптимизацией, а не новой моделью обновления.

После render React выполняет commit только там, где результат требует изменения DOM. Поэтому полезно различать три события:

1. обновление было запрошено;
2. функция компонента была вызвана;
3. DOM действительно изменился.

Они связаны, но не равнозначны.

## Развернутый ответ

### Собственный state

Setter из `useState` и `dispatch` из `useReducer` ставят обновление в очередь. Значение state внутри уже выполняющегося обработчика не меняется: оно остаётся снимком текущего render. React применит очередь при следующем render.

Если следующее значение совпадает с предыдущим по `Object.is`, React может пропустить обновление компонента и его потомков. Поэтому сам факт вызова setter не следует описывать как гарантию видимого render или изменения DOM.

### Render родителя и props

Когда React вызывает родительский компонент, он обрабатывает возвращённых потомков. Обычный дочерний компонент при этом также вызывается, даже если получил те же значения props. Новые props появляются как результат нового вычисления родителя; они не приходят в дочерний компонент отдельным каналом и не запускают родителя.

`React.memo` может сократить эту работу. По умолчанию он сравнивает каждый prop через `Object.is`. Новый объект, массив или функция не равны прежним по ссылке, поэтому могут помешать пропуску render. Однако стабилизировать каждое значение через `useMemo` или `useCallback` не нужно: сначала следует подтвердить проблему измерением.

### Context

Компонент, который читает context через `useContext`, подписан на значение ближайшего Provider. React сравнивает предыдущее и новое значение через `Object.is`. Для объекта это означает сравнение ссылки, для примитива - сравнение самого значения.

Изменение context обновляет его потребителей даже при использовании `React.memo`. Если один Provider хранит большой объект с несвязанными данными, изменение одного поля может затронуть всех потребителей этого объекта. В таком случае помогает разделение context по смыслу или стабилизация значения, когда его содержимое действительно не изменилось.

### Внешнее хранилище

`useSyncExternalStore` получает данные через `getSnapshot`. После уведомления подписки React повторно вызывает `getSnapshot` и рендерит компонент, если snapshot отличается по `Object.is`. Snapshot должен быть неизменяемым: при отсутствии изменений возвращается прежнее значение, а при изменении - новое.

Библиотеки состояния могут добавлять selectors и собственные функции сравнения. Тогда причину render нужно искать не только в React, но и в договорённости конкретной библиотеки: какой фрагмент store выбран и как сравниваются предыдущий и новый результаты selector.

### `key` и remount

`key` участвует в сопоставлении элементов между renders. Если на той же позиции появился другой `key`, React не обновляет прежний экземпляр компонента, а заменяет его новым. Локальный state и DOM-состояние прежнего поддерева сбрасываются, Effects проходят cleanup, после чего новый экземпляр монтируется заново.

Это полезно для осознанного сброса формы, но случайно меняющийся `key` создаёт лишние монтирования и потерю пользовательского ввода.

## Пример

Пример разделяет render родителя, пропуск по `React.memo` и независимое обновление через context.

```tsx
import { createContext, memo, useContext, useState } from "react";

const ThemeContext = createContext("light");

const SaveButton = memo(function SaveButton() {
  const theme = useContext(ThemeContext);
  console.log("SaveButton render");

  return <button className={theme}>Save</button>;
});

export default function App() {
  const [count, setCount] = useState(0);
  const [theme, setTheme] = useState("light");

  return (
    <ThemeContext.Provider value={theme}>
      <p>Count: {count}</p>
      <button onClick={() => setCount(c => c + 1)}>Increment</button>
      <button onClick={() => setTheme(t => t === "light" ? "dark" : "light")}>
        Toggle theme
      </button>
      <SaveButton />
    </ThemeContext.Provider>
  );
}
```

При изменении `count` компонент `App` рендерится, но `SaveButton` обычно пропускается благодаря `memo`: его props отсутствуют, а значение context осталось прежним. При изменении `theme` `SaveButton` рендерится независимо от `memo`, потому что используемый context получил новое значение. В development-режиме Strict Mode сообщения в консоли могут появляться дополнительно; это не production-поведение.

## Где применяется во frontend

| Симптом | Возможная причина | Что проверить |
| --- | --- | --- |
| Тяжёлый дочерний компонент выполняется вместе с родителем | обычное рекурсивное поведение render | React DevTools Profiler, стоимость компонента и изменение его props |
| Все потребители context обновляются одновременно | Provider передал новое значение | состав объекта `value`, `Object.is`, границы отдельных contexts |
| Компонент с selector обновляется слишком часто | selector возвращает новое значение или сравнение слишком широкое | выбранные данные и правила equality конкретной библиотеки |
| Форма неожиданно сбрасывается | изменился `key` или тип компонента | стабильность идентичности между renders |
| Render есть, а DOM визуально не изменился | следующий JSX совпал с предыдущим | отделить вызов компонента от commit и browser paint |

## Ключевые уточнения

- Render родителя по умолчанию включает обработку его потомков; изменение props не является отдельным событием, запускающим этот процесс.
- `React.memo` учитывает props, но собственный state и используемый context по-прежнему могут обновить компонент.
- Context сравнивается через `Object.is`; выражение «изменилась ссылка» точно только для объектов и функций.
- Новый `key` создаёт новый экземпляр компонента и сбрасывает его локальный state.
- Оптимизировать render следует после измерения: сам по себе вызов компонента не доказывает проблему производительности.
