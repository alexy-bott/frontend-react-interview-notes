## Быстрый ответ

SemVer - это схема версионирования `MAJOR.MINOR.PATCH`. `PATCH` обычно означает исправления без изменения API, `MINOR` - новые обратно совместимые возможности, `MAJOR` - breaking changes. В `package.json` версии часто указывают не точно, а диапазоном.

`^1.2.3` означает `>=1.2.3 <2.0.0`, `~1.2.3` — `>=1.2.3 <1.3.0`, exact `1.2.3` не задаёт range. Для `0.x` caret уже: `^0.2.3` не переходит на `0.3.0`, а `^0.0.3` не переходит на `0.0.4`, потому что слева от первой ненулевой части compatibility boundary меняется.

Диапазон в `package.json` говорит, какие версии допустимы, а lock-файл фиксирует конкретно выбранные версии. Поэтому для воспроизводимости важны оба файла: manifest описывает правила, lock фиксирует результат.

## Ключевая схема

| Запись | Идея | Пример допустимого обновления |
| --- | --- | --- |
| `1.2.3` | точная версия | только `1.2.3` |
| `^1.2.3` | compatible с тем же major | `1.3.0`, `1.9.9` |
| `~1.2.3` | patch внутри minor | `1.2.4`, `1.2.9` |
| `>=1.2.3` | нижняя граница | любая версия выше, если подходит |
| `*` / `latest` | почти без ограничения | риск неожиданных обновлений |
| pre-release | `1.2.3-beta.1` | отдельная осторожность при matching |
| lock-файл | выбранная версия | конкретное дерево зависимостей |

## Базовая модель

SemVer — договор publisher и consumer о public API. Range выражает допустимые releases, resolver выбирает concrete version, lock сохраняет выбор. Ни prefix, ни слово patch не гарантируют фактическую совместимость, если package нарушил contract или consumer зависел от undocumented behavior.

## Развернутый ответ

**Версия пакета и диапазон версии - не одно и то же.**
Когда в `package.json` написано `^1.2.3`, это не означает “всегда будет установлена ровно `1.2.3`”. Это означает “можно установить совместимую версию в рамках диапазона”. Какая версия реально установлена, видно в lock-файле.

**SemVer помогает, но не гарантирует отсутствие проблем.**
Идея SemVer держится на дисциплине авторов пакета. Если библиотека ошибочно выпустила breaking change в minor или patch, формально диапазон разрешит обновление, а проект может сломаться. Поэтому в рабочих проектах обновления зависимостей проверяют тестами, typecheck, build и иногда ручным smoke-тестом.

**`^` удобен, но требует lock-файла.**
В приложениях часто используют caret ranges, чтобы получать patch/minor исправления. Но без lock-файла две установки в разные дни могут выбрать разные версии. Lock-файл удерживает конкретный dependency tree, а обновление происходит только когда lock пересоздали или обновили зависимость.

**Транзитивные зависимости тоже важны.**
Проект может напрямую зависеть от `A`, а `A` зависит от `B`. Даже если `A` не изменился, обновление `B` в допустимом диапазоне может повлиять на итоговое дерево, если lock отсутствует или обновлён.

**Exact versions не всегда лучше.**
Точные версии уменьшают случайные обновления на уровне manifest, но не решают весь dependency tree без lock-файла. В библиотеках слишком жёсткие версии могут мешать потребителям, а в приложениях exact versions часто используют только осознанно, например для проблемного пакета.

Pre-release (`2.0.0-beta.1`) имеет меньший precedence, чем final `2.0.0`, и обычный range не обязан подхватывать pre-release без явного включения соответствующей линии. Pre-release используют осознанно: API и upgrade path ещё могут меняться.

## Практическое применение

| Ситуация | Как semver влияет |
| --- | --- |
| Обновление React/Next/Vite | major обычно требует reading migration guide |
| Баг после install | возможно изменилось дерево зависимостей |
| Renovate/Dependabot MR | нужно понимать major/minor/patch риск |
| Shared package | слишком широкий диапазон может сломать потребителей |
| Security fix | нужно обновить lock и проверить transitive dependency |
| CI отличается от локального окружения | проверить lock, package manager и Node version |

## Пример

```json
{
  "dependencies": {
    "react": "^19.0.0",
    "date-fns": "~4.1.0",
    "some-risky-lib": "2.3.4"
  }
}
```

Как читать:

- `react` может обновиться внутри major `19`, если lock будет обновлён.
- `date-fns` ограничен patch-обновлениями внутри `4.1`.
- `some-risky-lib` зафиксирован точной версией на уровне manifest.

## Ключевые уточнения

- `^` закрепляет левую ненулевую часть, поэтому ranges `1.x`, `0.2.x` и `0.0.3` ведут себя по-разному.
- SemVer применяется к public API package; toolchain/config/output могут иметь дополнительные migration risks.
- Dist-tag `latest` — registry pointer, а не version range и не гарантия стабильности.
- Lock фиксирует выбранную transitive graph; manifest range определяет будущие допустимые updates.
- Major читают вместе с migration guide, minor/patch всё равно проходят install, typecheck, tests и production build.
- Security update может потребовать overrides/resolutions и lock-only change, но temporary override затем сопровождают и удаляют.
