# Главный поток, долгие задачи и отзывчивость

## Быстрый ответ

Main thread — основной поток процесса рендеринга. На нём выполняется большая часть JavaScript страницы, обработчики событий, разбор HTML, расчёт стилей, layout и подготовка команд рисования. Пока поток занят одной синхронной задачей, он не может начать следующий обработчик или подготовить новый кадр.

Long task в Long Tasks API — задача на основном потоке длительностью более 50 мс. Порог помогает диагностике, но пользовательская задержка может складываться и из нескольких меньших задач. Для отзывчивости уменьшают объём JavaScript и рендеринга, дробят допускающую паузы работу, виртуализируют большие списки и переносят подходящие процессорные вычисления в Web Worker.

Метрика INP (Interaction to Next Paint) измеряет время от действия пользователя до следующего кадра с визуальным результатом. Задержка может возникнуть до запуска обработчика, во время его выполнения или после него на расчёте стилей, layout и paint. Поэтому быстрый обработчик ещё не гарантирует быстрый интерфейс.

## Что выполняется на main thread

```text
задачи с JavaScript
обработчики событий
разбор HTML
расчёт стилей и layout
часть конвейера рендеринга
координация кадра
```

Сетевой запрос во время ожидания не занимает основной поток. Но разбор большого JSON, callback-функция завершившегося `fetch` и обновление DOM снова выполняются на нём.

`async/await` меняет способ планирования продолжения функции, но не переносит CPU-работу в другой поток. То же относится к Promise и timers.

## Задачи и выполнение до завершения

Event loop берёт задачу и выполняет её до завершения — это свойство называют run-to-completion. Браузер не прерывает произвольную JavaScript-функцию посередине, чтобы обработать клик или нарисовать кадр.

```js
button.addEventListener("click", () => {
  const startedAt = performance.now();

  while (performance.now() - startedAt < 200) {
    // синхронная работа
  }

  status.textContent = "Готово";
});
```

Изменение `textContent` попадёт на экран только после завершения обработчика и последующей работы рендеринга. В течение этих 200 мс другие взаимодействия ждут.

После задачи выполняются все накопившиеся microtasks — продолжения вроде обработчиков Promise из отдельной очереди. Браузер обрабатывает эту очередь перед следующей обычной задачей и обычно перед подготовкой кадра, поэтому длинная цепочка callback-функций Promise тоже способна отложить рендеринг.

## Из чего складывается INP

Interaction to Next Paint делит задержку взаимодействия на три части:

1. **Задержка ввода (input delay)** — от действия пользователя до начала обработчиков. Причина часто в уже выполняющейся работе на основном потоке.
2. **Время обработки (processing duration)** — длительность обработчиков данного взаимодействия.
3. **Задержка отображения (presentation delay)** — от завершения обработчиков до кадра с результатом, включая расчёт стилей, layout и paint.

```text
user input
  -> input delay
  -> event handlers
  -> presentation delay
  -> next paint
```

INP учитывает клики, касания и ввод с клавиатуры в течение посещения страницы. Это полевая метрика общей отзывчивости, а не только время одного выбранного обработчика.

## Почему появляется long task

- загрузился и выполняется большой JavaScript-бандл;
- обработчик синхронно фильтрует или сортирует большой набор;
- `JSON.parse` обрабатывает крупный ответ;
- React рассчитывает большое дерево или синхронно выполняет дорогой commit;
- DOM слишком велик, поэтому style/layout занимают много времени;
- повторяющийся timer запускает тяжёлую работу в момент взаимодействия;
- одна callback-функция последовательно выполняет критичную и некритичную работу.

Проблема зависит от устройства. Задача, быстрая на компьютере разработчика, может стать long task на слабом телефоне.

## Сначала уменьшить работу

Дробление не уменьшает общий объём вычислений и добавляет накладные расходы. Сначала убирают ненужную работу:

- сокращают JavaScript для первоначальной загрузки через разделение бандла (code splitting) и отложенную загрузку (lazy loading);
- не пересчитывают производные данные без изменения входных значений;
- уменьшают DOM и виртуализируют большие списки;
- оставляют в обработчике только работу, необходимую для следующего кадра;
- устраняют layout thrashing;
- выбирают подходящую частоту валидации и сетевых обновлений.

Затем измеряют оставшееся узкое место и выбирают способ планирования.

## Как отдать управление браузеру

Если алгоритм можно разделить, его части запускают как разные задачи event loop. В примере `processItem()` обозначает обработку одного элемента:

```js
function yieldToMain() {
  if (globalThis.scheduler?.yield) {
    return globalThis.scheduler.yield();
  }

  return new Promise(resolve => setTimeout(resolve, 0));
}

async function processItems(items, chunkSize = 500) {
  for (let index = 0; index < items.length; index += chunkSize) {
    const chunk = items.slice(index, index + chunkSize);

    for (const item of chunk) {
      processItem(item);
    }

    await yieldToMain();
  }
}
```

`scheduler.yield()` специально предназначен для временной передачи управления браузеру и ставит продолжение функции в новую приоритетную задачу. API пока поддерживается не всеми распространёнными браузерами, поэтому пример использует `setTimeout` как fallback. Оба варианта дают браузеру возможность обработать ввод и подготовить кадр между частями. Размер порции (`chunk`) подбирают измерением, а не фиксируют универсально.

```js
await Promise.resolve();
```

Такой `await` продолжает функцию в microtask и обычно не даёт браузеру перейти к следующему кадру. Чтобы действительно отдать управление браузеру, нужна граница новой задачи или подходящий API планирования.

## `requestAnimationFrame` и работа в период простоя

`requestAnimationFrame` синхронизирует визуальное обновление с подготовкой кадра. Он не предназначен для тяжёлых вычислений: длинная callback-функция сама задержит кадр.

`requestIdleCallback` подходит только для некритичной работы, которую можно отложить и при необходимости разделить. У занятой страницы свободное время может долго не появляться, а поддержка и поведение API различаются между браузерами.

## Когда нужен Web Worker

Worker подходит для независимых процессорных задач: разбора и преобразования больших данных, поиска, сложных вычислений и обработки изображений. Он освобождает основной поток, но имеет цену:

- запуск worker;
- передача сообщений;
- структурированное клонирование либо передача владения через Transferable objects;
- отдельная обработка ошибок;
- отсутствие прямого доступа к DOM.

Маленькое вычисление переносить невыгодно, если обмен данными дороже самой работы.

## React 18 и main thread

Concurrent rendering в React 18 позволяет планировать и прерывать часть вычислений render phase, а `useTransition` помечает обновление как некритичное. Но JavaScript всё равно выполняется на основном потоке, а commit phase, в которой React применяет изменения к DOM, остаётся синхронной. Тяжёлый цикл внутри компонента React не переносится в Worker.

Практические источники задержки: рендеринг тысяч строк, дорогие селекторы состояния, синхронная валидация при каждом вводе символа, большой commit и нестабильные props, из-за которых мемоизация не пропускает вычисления. Решение выбирают после измерения в React Profiler и панели Performance браузера.

## Как диагностировать

1. Воспроизвести конкретное медленное взаимодействие.
2. Записать профиль Performance с искусственным замедлением CPU, близким к устройствам пользователей.
3. Разделить задержку ввода, выполнение JavaScript и задержку отображения.
4. Найти long tasks, Evaluate Script, layout и paint.
5. Проверить дерево вызовов (Call tree) и представление Bottom-up, которое группирует суммарную стоимость функций.
6. Изменить одно узкое место и повторить измерение.

Полевой INP, собранный на устройствах реальных пользователей, показывает масштаб проблемы, а локальная запись Performance помогает найти причину. Одно не заменяет другое.

## Ключевые уточнения

- Ожидание сети не занимает основной поток, но разбор ответа и обновление DOM снова выполняются на нём.
- Promise и `async/await` меняют планирование продолжения, но не переносят процессорную работу в другой поток.
- `await Promise.resolve()` создаёт microtask; браузер обычно не готовит новый кадр между microtasks одной контрольной точки.
- Long task определяется порогом 50 мс, а INP учитывает весь путь от ввода до кадра и может ухудшиться из-за нескольких меньших задержек.
- Concurrent rendering React 18 планирует часть render phase, но не отменяет стоимость JavaScript, DOM и синхронной commit phase.
