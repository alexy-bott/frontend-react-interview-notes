## Быстрый ответ

Утечка памяти (memory leak) возникает, когда данные больше не нужны приложению, но остаются достижимыми по цепочке ссылок от корневых объектов, или GC roots. Сборщик мусора не знает бизнес-смысл «модалка закрыта» и не освобождает достижимый объект.

Частые причины во frontend: listeners и подписки без очистки, интервальные timers, observers, незавершённые очереди, кэши без ограничения размера, замыкания с большими данными и отделённые DOM-узлы (detached DOM nodes) — узлы, удалённые из документа, но удерживаемые JavaScript-ссылкой.

Утечку подтверждают повторяемым сценарием. Выполняют действие несколько раз, запускают сборку мусора, сравнивают снимки JavaScript-кучи (heap snapshots) и ищут объекты, количество или удерживаемый размер (retained size) которых продолжает расти. Один большой снимок или временный рост памяти ещё не доказывает утечку.

## Как сборщик мусора принимает решение

Сборщик мусора начинает с корневых ссылок — GC roots. К ним относятся глобальные объекты, активные кадры стека вызовов и внутренние ссылки среды. Всё, до чего можно дойти по графу ссылок, считается живым.

```text
Window / активный стек / внутренние roots
              ↓
listener → замыкание → состояние компонента → большой массив
```

Пока `window` хранит listener, замыкание и захваченный массив достижимы. Удаление DOM-элемента не разрывает эту цепочку автоматически.

Цикл сам по себе не является утечкой:

```js
const first = {};
const second = {};

first.second = second;
second.first = first;
```

Если внешних ссылок на оба объекта больше нет, сборщик мусора, обходящий граф достижимости, может освободить весь цикл.

## Утечка, избыточное удержание и частые выделения памяти

| Проблема | Как выглядит |
| --- | --- |
| Утечка памяти (memory leak) | объём живых объектов растёт после повторения одного сценария |
| Избыточное удержание (memory bloat) | приложение стабильно удерживает больше памяти, чем нужно |
| Частые выделения (allocation churn) | код создаёт много временных объектов и провоцирует частую сборку мусора |

У пользователя симптомы могут быть похожи: постепенное замедление, паузы, закрытие вкладки на слабом устройстве. Но исправления различаются. При утечке разрывают цепочку удерживающих ссылок, при избыточном объёме уменьшают постоянную модель данных, а при частых выделениях сокращают создание временных объектов.

## Типичные цепочки удерживающих ссылок

**Event listeners.** Глобальный объект живёт дольше экрана и удерживает обработчик вместе с его замыканием.

**Подписки.** Store, WebSocket, EventSource или шина событий хранит callback-функцию до явной отписки.

**Timers.** `setInterval` продолжает ссылаться на callback-функцию; повторно запланированный `setTimeout` создаёт похожий долгоживущий цикл.

**Observers.** `ResizeObserver`, `IntersectionObserver` и `MutationObserver` нужно отключать, когда наблюдение больше не требуется.

**Кэши и коллекции.** `Map` и массив хранят сильные ссылки, которые препятствуют сборке объекта. Если нет политики удаления, кэш растёт вместе с числом просмотренных сущностей.

**Замыкания.** Функция может захватить большой объект ради одного маленького поля и жить дольше ожидаемого.

## Отделённые DOM-узлы

Отделённый узел удалён из DOM-дерева документа, но всё ещё достижим из JavaScript или другого DOM-узла:

```js
const detached = document.querySelector(".modal");

detached.remove();
globalModalHistory.push(detached);
```

Ссылка на одного потомка способна удерживать всё отделённое поддерево через DOM-связи. В Heap Snapshot ищут detached elements, затем в разделе Retainers просматривают путь удерживающих ссылок от root до узла.

Не каждый отделённый узел является ошибкой: библиотека может временно хранить элемент для повторной вставки. Утечка подтверждается только ожидаемым жизненным циклом объекта и ростом после повторений.

## Очистка как часть жизненного цикла

```js
function mountModal(modal) {
  const controller = new AbortController();

  window.addEventListener(
    "keydown",
    event => {
      if (event.key === "Escape") {
        modal.close();
      }
    },
    { signal: controller.signal },
  );

  return () => {
    controller.abort();
    modal.remove();
  };
}
```

Функция очистки должна вызываться при каждом пути ухода: кнопке закрытия, Escape, смене маршрута и unmount. Полезно иметь одну идемпотентную функцию очистки, повторный вызов которой не ломает состояние.

AbortController также можно использовать для группы listeners и API, поддерживающих `signal`. Отмена `fetch` полезна для жизненного цикла и прекращения лишней работы, хотя завершившийся запрос обычно сам освобождает связанные callback-функции.

## React Effects

Effect, который создаёт внешнюю подписку, должен вернуть симметричную функцию очистки:

```tsx
useEffect(() => {
  const unsubscribe = store.subscribe(handleChange);

  return unsubscribe;
}, [store]);
```

В development-режиме React Strict Mode выполняет дополнительный цикл setup → cleanup → setup. Он помогает обнаружить Effect, который не отменяет сделанное при setup. В production этого дополнительного цикла нет.

Не каждый вызов обновления state после unmount является утечкой памяти. Важен вопрос, продолжает ли внешняя система удерживать callback-функцию и связанные данные.

## `Map`, `WeakMap` и кэш

`WeakMap` хранит ключи-объекты по слабым ссылкам: наличие ключа только в WeakMap не мешает сборке мусора. Это удобно для метаданных, срок жизни которых совпадает со сроком жизни объекта или DOM-узла.

`WeakMap` не подходит для строковых ID, не позволяет перечислять содержимое как обычный кэш и не мешает другим ссылкам удерживать значение. Для прикладного кэша чаще нужна явная политика: срок жизни (TTL), ограничение размера, вытеснение старых записей, инвалидация и очистка при выходе пользователя.

`WeakRef` и `FinalizationRegistry` не используют как основной механизм очистки: момент сборки мусора не гарантирован, а программа не должна зависеть от своевременного вызова финализатора.

## Сценарий диагностики

1. Открыть страницу в стабильном начальном состоянии.
2. Выполнить сборку мусора из DevTools и снять исходный Heap Snapshot.
3. Повторить подозрительный сценарий 10–20 раз.
4. Вернуться в начальное состояние интерфейса и снова выполнить сборку мусора.
5. Снять второй snapshot и открыть представление Comparison.
6. Найти растущие типы объектов, detached nodes и retained size.
7. Открыть Retainers и пройти путь ссылок до root.
8. Исправить владельца ссылки и повторить тот же сценарий.

Консоль DevTools сама может удерживать недавно просмотренные объекты. Во время измерения не сохраняют подозрительные значения в глобальные переменные и очищают лишние ссылки из консоли.

## Инструменты DevTools

| Инструмент | Что показывает |
| --- | --- |
| Chrome Task Manager | общее потребление памяти и объём живой JavaScript-кучи |
| Performance monitor | изменение кучи, числа DOM-узлов и listeners во времени |
| Heap Snapshot | граф достижимых объектов в конкретный момент |
| Comparison view | разницу между snapshots |
| Allocation instrumentation | где создаются объекты, которые продолжают жить |
| Detached elements profile | удалённые DOM-узлы, удерживаемые ссылками |

**Shallow size**, или поверхностный размер, — память самого объекта. **Retained size**, или удерживаемый размер, — объём, который потенциально освободится, если объект и уникально удерживаемые им зависимости станут недостижимы. Большой retained size помогает найти объект-владелец, а не только самую большую строку или массив.

## Ключевые уточнения

- Сборщик мусора освобождает недостижимое, а не «больше не нужное бизнесу».
- Циклическая ссылка без пути от root собирается нормально.
- Повторяемый рост живых объектов после сборки мусора указывает на проблему точнее, чем общий размер одного снимка.
- Отделённый DOM-узел подтверждает утечку только тогда, когда по жизненному циклу он уже должен быть освобождён.
- Snapshot показывает, что осталось в памяти, а путь удерживающих ссылок объясняет почему; `WeakMap` помогает лишь там, где срок жизни данных связан с ключом-объектом.
