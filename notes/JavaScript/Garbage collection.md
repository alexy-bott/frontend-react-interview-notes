## Быстрый ответ

Garbage collection (сборка мусора) - автоматическое освобождение памяти, занятой значениями, которые больше недостижимы для программы. Базовая учебная модель начинается с корней (`roots`): сборщик проходит по сильным ссылкам и помечает всё, до чего можно добраться; остальная память становится кандидатом на освобождение.

Утечка памяти в JavaScript возникает не потому, что GC «забыл» объект, а потому, что ненужный приложению объект всё ещё достижим. Его может удерживать растущий кэш, глобальная переменная, активный таймер, подписка, observer, обработчик события или отсоединённый DOM-узел, сохранённый в JavaScript.

Цикл ссылок сам по себе не является утечкой. Если весь цикл недостижим от корней, современный сборщик мусора может удалить его целиком.

Момент сборки не гарантирован. Нельзя строить бизнес-логику на времени освобождения объекта, принудительно запускать GC в обычном браузерном коде или использовать `FinalizationRegistry` как обязательную очистку.

## Ключевая схема

```text
корни (roots)
→ пройти по сильным ссылкам
→ достижимые значения остаются живы
→ недостижимые значения можно освободить
```

| Понятие | Значение |
| --- | --- |
| Root (корень) | стартовая точка, известная движку или браузеру |
| Достижимое значение | значение, доступное из корней по цепочке сильных ссылок |
| Недостижимое значение | значение, которое программа больше не может получить обычным путём |
| Утечка памяти | ненужное значение остаётся достижимым |
| Retainer | объект или механизм, удерживающий ссылку |
| Слабая ссылка | связь, которая сама по себе не сохраняет объект живым |

## Что считается достижимым

К корням относятся значения, от которых движок и браузер должны продолжать выполнение: глобальное окружение, активные контексты выполнения и стек вызовов, а также ссылки, удерживаемые браузерными механизмами для текущей работы.

От корней сборщик идёт по свойствам объектов, элементам коллекций, лексическим окружениям функций и другим сильным связям. Пока существует хотя бы один такой путь, объект считается достижимым независимо от того, нужен ли он приложению.

```js
let user = { profile: { name: "Ann" } };
const profile = user.profile;

user = null;
```

Объект `user` может стать недостижимым, но `profile` остаётся живым из-за отдельной переменной. Присваивание `null` разрывает только одну связь и не «удаляет объект из памяти» напрямую.

## Почему циклы собираются

```js
let first = {};
let second = {};

first.other = second;
second.other = first;

first = null;
second = null;
```

Два объекта продолжают ссылаться друг на друга, но путь от корней к ним исчез. При модели mark-and-sweep (пометка и очистка) они не будут помечены и могут быть освобождены.

Простой подсчёт ссылок без дополнительного анализа действительно не справился бы с таким циклом. Современные JavaScript-движки используют трассирующую сборку мусора, поэтому правило «любая циклическая ссылка создаёт утечку» неверно.

## Как работают реальные сборщики

Mark-and-sweep - полезная базовая модель, но не полное описание V8, SpiderMonkey или JavaScriptCore. Реальные движки делят объекты по поколениям, выполняют работу частями, используют параллельные и конкурентные этапы и перемещают объекты для уменьшения фрагментации памяти.

Эти оптимизации решают две задачи: уменьшить общий расход памяти и не создавать слишком длинные паузы основного потока. Конкретный алгоритм, момент запуска и стоимость прохода зависят от движка, объёма памяти и поведения программы.

Для frontend-разработчика устойчивый инвариант проще: недостижимая память может быть освобождена, а достижимая - нет. Код должен своевременно разрывать ссылки, жизненный цикл которых завершён.

## Что такое утечка памяти

GC понимает достижимость, но не намерение разработчика. Если закрытый экран всё ещё хранится в массиве истории приложения, он технически доступен и не является мусором для движка, хотя приложению больше не нужен.

Типичные источники удержания:

| Источник | Что удерживает | Как завершить жизненный цикл |
| --- | --- | --- |
| `setInterval` | callback и его замыкание | `clearInterval` |
| обработчик события на живом объекте | обработчик и захваченные значения | `removeEventListener` или `AbortSignal` |
| observer | callback и наблюдаемые сущности | `disconnect()` или `unobserve()` |
| подписка | callback компонента | вызов `unsubscribe` |
| `Map` или массив кэша | ключи, значения, история | лимит, TTL, LRU или явное удаление |
| detached DOM node | поддерево DOM | убрать сохраняющую JavaScript-ссылку |
| незавершённая асинхронная работа | callbacks и связанное состояние | отмена, завершение или удаление ссылки |

Замыкание не является утечкой само по себе. Оно удерживает значения из лексического окружения, которые нужны сохраняемой функции. Проблема возникает, когда сама функция живёт дольше ожидаемого и вместе с окружением удерживает большие данные.

## Listener: когда есть утечка, а когда нет

Сам цикл «DOM-узел → обработчик → замыкание → DOM-узел» может быть собран, если вся группа недостижима. Утечка появляется, когда живой внешний объект продолжает удерживать один из элементов группы.

Например, `window` живёт вместе со страницей. Listener на `window` удерживает callback, а callback - захваченные данные закрытого экрана:

```js
function mountDashboard() {
  const rows = new Array(100_000).fill("data");

  function onResize() {
    console.log(rows.length);
  }

  window.addEventListener("resize", onResize);

  return () => {
    window.removeEventListener("resize", onResize);
  };
}
```

Если функцию очистки не вызвать, глобальный `window` продолжит удерживать `onResize` и `rows`. Если обработчик находится только на полностью недостижимом локальном элементе, одно отсутствие `removeEventListener` ещё не доказывает утечку.

## Timers, observers и подписки

Активный `setInterval` зарегистрирован в браузерной среде. Пока интервал не отменён, среда должна уметь вызвать callback, поэтому захваченное им окружение остаётся достижимым.

`MutationObserver`, `ResizeObserver`, обработчик WebSocket, подписка на store и похожие API имеют собственный жизненный цикл. Для них нужно знать симметричную операцию завершения: `disconnect`, `close`, `unsubscribe`, `abort` или функцию очистки библиотеки.

Одноразовый `setTimeout` обычно освобождает callback после выполнения, но большая задержка всё равно удерживает замыкание до запуска или отмены.

## Cache и коллекции

Обычные `Map`, `Set`, массив и объект держат сильные ссылки. Кэш без лимита может расти бесконечно даже при полностью исправном GC.

`WeakMap` подходит, когда запись должна существовать ровно пока доступен объект-ключ и полный список записей не нужен. Он не решает кэш по строковому URL, ограничение памяти, TTL или LRU: для таких требований нужна явная политика вытеснения.

Слабая ссылка не означает немедленное удаление. Она только не добавляет сильный путь достижимости; момент фактической сборки выбирает движок.

## `WeakRef` и `FinalizationRegistry`

`WeakRef` позволяет попытаться получить объект, не удерживая его сильной ссылкой. `FinalizationRegistry` позволяет зарегистрировать необязательный callback после сборки целевого объекта.

Оба API зависят от недетерминированного GC. Callback может выполниться намного позже или не успеть выполниться до закрытия страницы. Их нельзя использовать для сохранения данных, обязательного закрытия соединения или корректности бизнес-операции.

Основную очистку выполняют явно. Weak API применяют для вспомогательных кэшей и диагностических сценариев, где отсутствие или задержка callback не ломает программу.

## Как искать утечку

Диагностика начинается с воспроизводимого сценария, например десять раз открыть и закрыть модальное окно или перейти между маршрутами.

1. Записать исходное состояние после стабилизации страницы.
2. Несколько раз повторить сценарий создания и удаления сущности.
3. Дать приложению завершить задачи и при диагностике инициировать GC через DevTools.
4. Сравнить снимки heap или временную шкалу выделения памяти.
5. Найти объекты, количество которых растёт, и изучить путь удержания до корня.
6. Исправить конкретный жизненный цикл и повторить тот же сценарий.

`Shallow size` показывает память самого объекта. `Retained size` оценивает память, которая могла бы освободиться вместе с ним. `Detached DOM tree` указывает на удалённое из документа поддерево, которое всё ещё удерживается JavaScript-ссылкой.

Один высокий снимок памяти не доказывает утечку: кэш, JIT и отложенный GC могут увеличивать heap законно. Признак утечки - устойчивый рост после повторяемого сценария и невозможность освободить ненужные объекты.

## Где применяется во frontend

- Очистка компонента отменяет обработчики, интервалы, observers и подписки, принадлежащие его жизненному циклу.
- API-клиент отменяет устаревшие запросы, чтобы их callbacks и промежуточные данные не жили дольше необходимого.
- Кэш получает лимит или политику вытеснения вместо надежды на автоматический GC.
- `WeakMap` связывает метаданные с DOM-узлом или объектом без продления его жизни.
- DevTools Memory показывает путь удержания, который объясняет реальную причину утечки.

## Ключевые уточнения

- GC освобождает недостижимые значения, а не всё, что разработчик считает ненужным.
- Присваивание `null` разрывает одну ссылку, но не гарантирует немедленную сборку объекта.
- Циклическая ссылка не является утечкой, если весь цикл недостижим.
- Обработчик на недостижимом объекте может быть собран вместе с ним; важен путь от живого корня.
- Замыкание становится проблемой только при неожиданно долгом жизненном цикле сохраняемой функции.
- Weak-коллекции не дают гарантий о моменте удаления и не заменяют управляемый кэш.
- `FinalizationRegistry` не подходит для обязательной очистки.
