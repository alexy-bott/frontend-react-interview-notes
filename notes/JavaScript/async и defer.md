## Быстрый ответ

`async` и `defer` управляют моментом выполнения внешнего классического скрипта относительно разбора HTML. Оба позволяют скачивать файл параллельно с разбором документа, но выполняют его по-разному.

`defer` ждёт окончания парсинга HTML, сохраняет порядок скриптов в документе и выполняется до `DOMContentLoaded`. Поэтому он подходит для основного приложения и файлов, которые зависят друг от друга.

`async` выполняет скрипт сразу после загрузки: если HTML-парсер ещё работает, выполнение временно остановит разбор документа. Порядок нескольких `async`-скриптов определяется скоростью загрузки, а `DOMContentLoaded` их не ждёт. Это вариант для независимой аналитики, рекламы и виджетов.

`<script type="module">` имеет отдельную модель: браузер загружает весь граф импортов, а выполнение без `async` по умолчанию отложено до разбора документа. Атрибут `defer` модульному скрипту не нужен и не меняет его поведение.

## Ключевая схема

```text
классический скрипт без атрибутов:
разбор HTML → остановка → загрузка → выполнение → продолжение разбора

классический скрипт с defer:
разбор HTML + загрузка → окончание разбора → выполнение по порядку → DOMContentLoaded

классический скрипт с async:
разбор HTML + загрузка → выполнение сразу после готовности → продолжение разбора

модуль без async:
разбор HTML + загрузка графа зависимостей → выполнение → DOMContentLoaded
```

| Вариант | Загрузка | Момент выполнения | Порядок документа | `DOMContentLoaded` ждёт |
| --- | --- | --- | --- | --- |
| классический без атрибутов | парсер ждёт файл | сразу в месте `<script>` | да | выполнение уже завершено |
| классический `defer` | параллельно с HTML | после разбора HTML | да | да |
| классический `async` | параллельно с HTML | сразу после загрузки | нет | нет |
| модуль без `async` | граф параллельно с HTML | после разбора HTML и готовности графа | да | да |
| модуль с `async` | граф параллельно с HTML | сразу после готовности графа | нет | нет |

## Почему обычный script блокирует HTML-парсер

HTML-парсер строит DOM последовательно. Встретив обычный классический `<script>` в документе, он должен допустить, что код немедленно прочитает или изменит уже построенную часть DOM, вызовет `document.write()` или повлияет на дальнейший разбор. Поэтому браузер скачивает и выполняет скрипт до продолжения парсинга.

```html
<p id="before">Уже существует</p>
<script src="/app.js"></script>
<p id="after">Ещё не разобран во время app.js</p>
```

Во время выполнения `app.js` первый элемент уже находится в DOM, а второй обычно ещё не создан парсером. Это предсказуемая модель, но сетевое ожидание и выполнение задерживают построение страницы.

## `defer`

`defer` применяется к внешнему классическому скрипту с `src`. Скачивание идёт параллельно с HTML, но выполнение начинается после завершения разбора документа. Скрипт видит построенный DOM без обязательного размещения тега в конце `body`.

Несколько скриптов с `defer` выполняются в порядке документа, даже если второй файл загрузился раньше первого:

```html
<script defer src="/vendor.js"></script>
<script defer src="/app.js"></script>
```

`app.js` выполнится после `vendor.js`. Событие `DOMContentLoaded` будет создано после выполнения всех скриптов с `defer`, поэтому обработчик внутри такого файла успеет подписаться на него.

`defer` не переносит код с основного потока. Большой bundle по-прежнему нужно разобрать, скомпилировать и выполнить; меняется момент работы и устраняется сетевое блокирование HTML-парсера.

## `async`

`async` подходит скрипту, который не зависит от DOM, соседних скриптов и порядка инициализации приложения. Браузер начинает загрузку параллельно, а затем выполняет файл при первой возможности после его готовности.

```html
<script async src="/analytics.js"></script>
<script async src="/ads.js"></script>
```

Если `ads.js` загрузился первым, он может выполниться раньше `analytics.js`, независимо от порядка тегов. Такой скрипт может выполниться как до, так и после `DOMContentLoaded`.

Когда `async`-скрипт готов во время разбора HTML, его JavaScript всё равно выполняется в основном потоке и на это время останавливает парсер. Поэтому `async` не гарантирует, что сторонний код не повлияет на отзывчивость и рендеринг страницы.

## Модульные скрипты

Модуль подключают через `type="module"`:

```html
<script type="module" src="/app.js"></script>
```

Браузер загружает не только `app.js`, но и найденный по статическим `import` граф зависимостей. После готовности граф связывается и выполняется. Без `async` модульный скрипт ведёт себя как отложенный: не блокирует HTML-парсер во время сетевой загрузки и выполняется после разбора документа до `DOMContentLoaded`.

Атрибут `defer` у модульного скрипта не меняет поведение, потому что выполнение уже отложено по умолчанию. `async` меняет модель: модуль и его зависимости выполняются сразу после готовности, без сохранения порядка относительно других `async`-скриптов.

Модульный скрипт может дольше ждать зависимость глубоко в графе. Поэтому момент его выполнения определяется готовностью всего графа, а не только размером файла в `src`.

## Встроенные и динамически добавленные скрипты

Для обычного встроенного классического скрипта без `src` параллельно скачивать нечего, поэтому `async` и `defer` не дают описанного эффекта:

```html
<script>
  initialize();
</script>
```

Такой код выполняется в месте тега и блокирует парсер на время своей работы.

Скрипт, созданный через DOM API, не считается вставленным HTML-парсером. Внешние классические скрипты, добавленные динамически, по умолчанию ведут себя как `async`. Если нескольким файлам нужен порядок, его задают явно: например, устанавливают `script.async = false` до добавления в документ или загружают следующую зависимость после предыдущей.

```js
const script = document.createElement("script");
script.src = "/widget.js";
script.async = true;
document.head.append(script);
```

## `DOMContentLoaded` и `load`

`DOMContentLoaded` означает, что HTML разобран, а скрипты с `defer` и модульные скрипты без `async` выполнены. Событие не ждёт обычные изображения и `async`-скрипты.

`window.load` происходит позже, когда загружены зависимые ресурсы документа, включая изображения и скрипты. Для запуска приложения обычно не нужно ждать `load`: скрипт с `defer` или модульный скрипт уже получает готовый DOM.

Если код подключается поздно и хочет слушать `DOMContentLoaded`, сначала проверяют `document.readyState`, иначе событие могло уже произойти.

## Практический выбор

| Сценарий | Подход | Причина |
| --- | --- | --- |
| Основной классический bundle | `defer` | DOM готов, порядок предсказуем |
| Несколько зависимых классических скриптов | `defer` | сохраняется порядок документа |
| Независимая аналитика | `async` | не нужно ждать основной код |
| Современное ESM-приложение | `type="module"` | модульный граф и отложенное выполнение по умолчанию |
| Независимый ESM-виджет | модуль с `async` | выполняется сразу после готовности графа |
| Критичный маленький встроенный код | inline осознанно | нет сетевого ожидания, но выполнение блокирует парсер |

## Ключевые уточнения

- `async` и `defer` разделяют сетевую загрузку и выполнение классического скрипта, но не убирают стоимость JavaScript в основном потоке.
- `defer` сохраняет порядок и задерживает `DOMContentLoaded`; `async` не гарантирует порядок и не задерживает это событие.
- `async`-скрипт при готовности может временно остановить HTML-парсер своим выполнением.
- `defer` имеет смысл для внешнего классического скрипта; модульный скрипт уже отложен по умолчанию.
- `type="module"` ждёт загрузки графа статических зависимостей, а не только входного файла.
- Динамически добавленные классические скрипты имеют другую модель и по умолчанию выполняются асинхронно.
- Выбор атрибута не заменяет уменьшение bundle, code splitting и контроль сторонних скриптов.
