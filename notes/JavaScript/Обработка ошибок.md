## Быстрый ответ

`throw` прерывает обычное выполнение и передаёт ошибку вверх по текущему синхронному стеку вызовов до ближайшего `catch`. Если обработчика нет, ошибка достигает среды выполнения и считается необработанной.

`try...catch` перехватывает ошибки, возникшие во время выполнения блока `try`. Он не охватывает callback, который будет запущен позже в отдельной задаче. Отклонение Promise попадёт в `catch`, только если этот Promise ожидается через `await` внутри `try`; без `await` цепочке нужен собственный `.catch()` или обработчик выше.

`finally` выполняется после `try`/`catch` независимо от результата и подходит для освобождения ресурсов. `return` или `throw` внутри `finally` опасен: он может заменить исходный результат или ошибку.

На уровне приложения ошибки классифицируют, добавляют контекст, показывают пользователю понятное состояние и отправляют диагностику. Catch без восстановления, преобразования или логирования только скрывает дефект.

## Ключевая схема

```text
операция
├─ ожидаемый результат → продолжить сценарий
└─ throw / rejected Promise
   → ближайшая граница обработки
   ├─ восстановить
   ├─ преобразовать и throw дальше
   └─ показать резервное состояние + записать диагностику
```

| Механизм | Что перехватывает |
| --- | --- |
| `try...catch` | синхронный `throw` во время выполнения `try` |
| `try...catch` + `await` | отклонение ожидаемого Promise |
| `.catch()` | отклонение конкретной цепочки Promise |
| `window.error` | необработанные ошибки скрипта на уровне страницы |
| `unhandledrejection` | отклонение Promise без своевременного обработчика |

Глобальные события помогают наблюдаемости, но приходят слишком поздно для обычной локальной бизнес-обработки.

## `throw` и распространение ошибки

В JavaScript через `throw` можно передать любое значение, но обычно используют объект `Error` или класс-наследник:

```js
function parsePort(value) {
  const port = Number(value);

  if (!Number.isInteger(port) || port < 1 || port > 65535) {
    throw new RangeError("Port must be an integer from 1 to 65535");
  }

  return port;
}
```

`Error` содержит `name`, `message` и обычно `stack` со стеком вызовов. Строка или обычный объект не дают единообразной информации о месте ошибки и хуже обрабатываются системами логирования.

Когда функция вызывает другую функцию, необработанный `throw` завершает текущий вызов и передаётся вызывающей функции:

```js
function loadConfig(raw) {
  return normalizeConfig(JSON.parse(raw));
}

try {
  loadConfig("not json");
} catch (error) {
  console.error(error);
}
```

`JSON.parse` бросает `SyntaxError`; `loadConfig` не перехватывает его, поэтому управление переходит в внешний `catch`.

## Область действия `try...catch`

`catch` работает только для кода, который успел выполниться внутри `try` до выхода из этого блока.

```js
try {
  setTimeout(() => {
    throw new Error("later");
  }, 0);
} catch (error) {
  // Не выполнится.
}
```

Callback таймера запустится позже, в другой задаче, когда исходный `try` уже завершён. Обработчик помещают внутрь callback либо оборачивают API в Promise и обрабатывают его цепочку.

```js
setTimeout(() => {
  try {
    riskyOperation();
  } catch (error) {
    reportError(error);
  }
}, 0);
```

Это не означает запуск нового потока: callback всё ещё выполняется в основном потоке, но в другом вызове и с новым стеком.

## Promise и `async/await`

`await` превращает отклонение ожидаемого Promise в `throw` внутри `async`-функции, поэтому его перехватывает окружающий `try...catch`:

```js
async function loadUser() {
  try {
    const response = await fetch("/api/user");

    if (!response.ok) {
      throw new Error(`HTTP ${response.status}`);
    }

    return await response.json();
  } catch (error) {
    showLoadError(error);
    return null;
  }
}
```

Без `await` блок `try` завершится раньше, а отклонение останется внутри цепочки Promise:

```js
async function incorrect() {
  try {
    return Promise.reject(new Error("failed"));
  } catch (error) {
    // Этот catch не обработает rejection.
  }
}
```

Если ошибку должен перехватить локальный `catch`, Promise необходимо ожидать через `await`:

```js
async function correct() {
  try {
    return await Promise.reject(new Error("failed"));
  } catch (error) {
    return "fallback";
  }
}
```

Вызывающий код в обоих случаях может обработать возвращённый Promise. Разница важна для локальных `catch` и `finally` внутри самой функции.

## `finally`

`finally` выполняется при обычном результате, throw и большинстве выходов через `return`:

```js
const controller = new AbortController();
const timerId = setTimeout(() => controller.abort(), 5000);

try {
  return await fetch(url, { signal: controller.signal });
} finally {
  clearTimeout(timerId);
}
```

Очистка ресурсов не должна скрывать основной результат. Этот код вернёт `2`, а исходный `return 1` будет потерян:

```js
function example() {
  try {
    return 1;
  } finally {
    return 2;
  }
}
```

Если очистка сама может завершиться ошибкой, нужно заранее определить поведение: сохранить исходную ошибку, добавить ошибку очистки как `cause`, объединить ошибки или хотя бы не заменить молча более важную причину.

## Типы стандартных ошибок

| Error | Типичная причина |
| --- | --- |
| `SyntaxError` | невалидный синтаксис или JSON |
| `ReferenceError` | имя не найдено или переменная находится в TDZ |
| `TypeError` | операция неприменима к значению |
| `RangeError` | значение за допустимым диапазоном |
| `URIError` | некорректная последовательность в функции обработки URI |
| `AggregateError` | несколько причин, например отказ всех входов `Promise.any` |
| `DOMException` | ошибка Web API, например `AbortError` |

Тип ошибки помогает вызывающему коду принять решение. Однако `instanceof` может быть ненадёжным между разными средами выполнения, например между страницей и `iframe` или Worker. В публичный контракт ошибки поэтому часто добавляют стабильное поле `code`.

## Пользовательские классы ошибок

```js
class ApiError extends Error {
  constructor(message, { status, body, cause } = {}) {
    super(message, { cause });
    this.name = "ApiError";
    this.status = status;
    this.body = body;
  }
}
```

`cause` сохраняет исходную техническую ошибку при добавлении контекста:

```js
try {
  return JSON.parse(raw);
} catch (error) {
  throw new Error("Cannot parse application config", {
    cause: error,
  });
}
```

Новая ошибка объясняет сбой на уровне текущей функции, а `cause` сохраняет первопричину. Простая замена на `throw new Error("failed")` без `cause` уничтожила бы важный контекст.

## Ожидаемый результат или исключение

Не каждое отрицательное состояние является исключением. Пользователь ввёл неверный email или поиск не нашёл результатов - это ожидаемая ветка интерфейса, которую часто удобнее вернуть как данные.

```ts
type ValidationResult =
  | { ok: true; value: Email }
  | { ok: false; message: string };
```

`throw` удобен, когда текущий уровень не может продолжить обычный сценарий: сеть недоступна, нарушено обязательное условие или парсер получил некорректный формат. Возвращаемый результат удобнее, когда вызывающий код обязан разобрать несколько ожидаемых исходов.

Критерий выбора - контракт функции, а не правило «исключения только для редких ошибок». Один уровень API должен одинаково представлять одинаковые ситуации.

## Границы обработки

Ошибка должна обрабатываться на уровне, который знает, что делать дальше. Низкоуровневая функция обычно не знает, какой UI показать, а компонент не должен разбирать детали TCP или JSON parser.

```text
низкоуровневый API
→ добавить status/body/cause
→ прикладной слой решает, повторить запрос или преобразовать ошибку
→ интерфейс показывает состояние ошибки и доступное действие
→ система мониторинга получает технический контекст
```

Catch считается полезным, если он:

- восстанавливает сценарий;
- переводит ошибку в контракт текущего слоя;
- добавляет контекст и перебрасывает дальше;
- освобождает ресурсы;
- сообщает ошибку наблюдаемости, не дублируя одно событие на каждом уровне.

Пустой `catch` создаёт ложное ощущение успеха и усложняет диагностику.

## Ошибки UI и React

React Error Boundary перехватывает ошибки рендеринга и методов жизненного цикла дочернего дерева и показывает резервный интерфейс. Он не является общим `catch` для обработчиков событий, таймеров, серверных обработчиков и произвольного асинхронного кода.

Ошибки загрузки обычно хранятся в состоянии библиотеки для серверных данных или компонента и отображаются отдельной веткой интерфейса. Необработанное отклонение Promise не превращается автоматически в ошибку рендеринга, которую поймает Error Boundary.

Для диагностики в production полезны маршрут, версия релиза, действие пользователя, идентификатор запроса и source maps. В телеметрию нельзя отправлять секреты, токены и лишние персональные данные.

## Ключевые уточнения

- `throw` распространяется по текущему стеку вызовов, а не по лексической вложенности функций.
- `try...catch` не охватывает callback будущей задачи только потому, что он был зарегистрирован внутри `try`.
- Локальный `try...catch` перехватывает отклонение Promise, если соответствующий Promise ожидается через `await` внутри него.
- `finally` подходит для очистки ресурсов, но его `return` или `throw` может заменить исходный результат.
- Объект `Error` сохраняет единый контракт и стек вызовов лучше, чем строка.
- `catch` должен восстановить сценарий, преобразовать или дополнить ошибку либо осознанно сообщить о ней, а не скрыть её.
- Error Boundary и глобальные обработчики имеют ограниченную область и не заменяют локальную обработку.
