## Быстрый ответ

Event loop (цикл событий) - механизм браузера, который определяет, когда выполнять JavaScript-задачи, микрозадачи, обработчики событий и обновление интерфейса. Сам движок JavaScript выполняет код, а браузер как среда выполнения предоставляет таймеры, DOM, сеть, очереди задач и рендеринг страницы.

Для обычной задачи действует такая причинная модель: браузер выбирает готовую `task`, JavaScript выполняет её до конца, затем происходит полная очистка очереди микрозадач. Начальный скрипт, callback таймера и обработчик пользовательского события выполняются как задачи. Обработчики `then`/`catch`/`finally`, продолжение после `await` и `queueMicrotask` выполняются как микрозадачи.

Обновление интерфейса не является обязательным «третьим шагом» каждой итерации. Когда возникает rendering opportunity, актуальный HTML Standard ставит отдельную задачу обновления rendering. Event loop выполнит её после предыдущей задачи и её микрозадач, когда выберет эту задачу среди готовых.

Очередь микрозадач очищается полностью, включая новые микрозадачи, добавленные во время этой очистки. Поэтому `Promise.then` после текущего скрипта обычно выполняется раньше `setTimeout(..., 0)`. Бесконечная цепочка микрозадач не даст циклу событий перейти к следующей задаче и обновлению интерфейса. Асинхронный API меняет расписание работы, но не переносит тяжёлый JavaScript с основного потока.

## Карта темы

```text
обычная task
-> выполнить JavaScript до опустошения стека вызовов
-> выполнить все накопившиеся микрозадачи
-> выбрать следующую готовую task

rendering opportunity
-> поставить task обновления rendering
-> при выборе этой task вызвать rAF и обновить интерфейс
```

| Источник | Тип продолжения | Пример |
| --- | --- | --- |
| Начальный скрипт | задача | выполнение подключённого `<script>` |
| Таймер после истечения задержки | задача | `setTimeout`, `setInterval` |
| Пользовательское событие | задача | обработчик `click` или `keydown` |
| Реакция Promise | микрозадача | `then`, `catch`, `finally` |
| Продолжение `async`-функции | микрозадача | код после `await` |
| Явная микрозадача | микрозадача | `queueMicrotask` |
| Наблюдение за изменениями DOM | этап микрозадач | callback `MutationObserver` |

## Базовая модель

Движок JavaScript выполняет инструкции и управляет стеком вызовов. Браузер предоставляет DOM, таймеры, сетевые API, рендеринг и event loop. Когда алгоритм браузерного API требует отложить callback, он ставит задачу или микрозадачу по правилам этого API и не запускает её посреди уже выполняющейся функции. Не каждый callback и не каждое DOM-событие образуют новую задачу: некоторые события dispatch-ятся внутри уже выполняющейся задачи, а `dispatchEvent()` вызывает обработчики синхронно.

Задача выполняется по правилу run-to-completion: начавшийся JavaScript-код выполняется до конца и не прерывается другой JavaScript-задачей. Пока стек вызовов занят, основной поток не может запустить следующий обработчик события или обновить страницу.

После задачи браузер выполняет microtask checkpoint - этап полной очистки очереди микрозадач. Каждая микрозадача может добавить следующую, поэтому этап закончится только после опустошения очереди. Rendering opportunity отслеживается отдельно: при её наступлении браузер ставит задачу обновления rendering, которую event loop затем может выбрать среди готовых задач. Поэтому новый кадр не обязан появляться после каждой обычной задачи.

## Развернутый ответ

### Где находится event loop

Event loop не является синтаксической возможностью языка и не «живёт внутри Promise». Он принадлежит среде, в которой выполняется JavaScript. Окно браузера, Worker и Node.js имеют собственные циклы событий: общая идея похожа, но очереди, этапы и источники задач различаются. Эта карточка описывает основной поток браузерной страницы.

HTML Standard определяет циклы событий и несколько источников задач (`task sources`). В спецификации нет одной общей «очереди макрозадач» для всех событий. Термин macrotask распространён в учебных материалах как противопоставление microtask, но стандарт использует слово `task`. Браузер выбирает готовую задачу из подходящей очереди по правилам своей среды выполнения.

### Регистрация callback и выполнение task

`setTimeout(callback, 0)` устанавливает минимальную задержку, после которой задача таймера может стать готовой. Это не обещание немедленного выполнения: сначала должны завершиться текущая задача и все микрозадачи, а браузер также может выбрать другие готовые задачи.

События от пользовательского ввода, например `click`, доставляются через задачи источника user interaction. Внутри такой задачи браузер синхронно вызывает подходящие обработчики на этапах capture, target и bubble. Но программный `dispatchEvent()` выполняет dispatch и обработчики в текущем стеке вызовов, не создавая новую задачу. Эти этапы объяснены в [DOM events](<./DOM events.md>).

### Microtask checkpoint

Изменение состояния Promise и запуск его обработчика - разные события. Даже если Promise уже выполнен (`fulfilled`), обработчик из `then` не вызывается синхронно: для него создаётся отдельная микрозадача.

`await` использует ту же модель. `async`-функция возвращает Promise и приостанавливает только собственное выполнение. Когда ожидаемый Promise меняет состояние, продолжение функции попадает в очередь микрозадач. Само ожидание не блокирует выполнение остального JavaScript.

Микрозадачи позволяют завершить связанную работу до следующего внешнего события. Но длинная или бесконечная цепочка создаёт starvation, то есть не отдаёт управление таймерам, пользовательскому вводу и рендерингу.

### Rendering opportunity

Когда возникает rendering opportunity, браузер ставит задачу обновления rendering. При выполнении этой задачи он вызывает подходящие callbacks `requestAnimationFrame`, затем выполняет предусмотренные стандартом шаги обновления интерфейса, включая обновление стилей и layout. Paint, compositing и внутренние оптимизации зависят от движка, а принудительный layout может произойти раньше, если код прочитает геометрию сразу после изменения стилей.

`requestAnimationFrame` синхронизирует callback с подготовкой кадра, но сам callback всё равно выполняется в основном потоке. Тяжёлое вычисление внутри него задержит отрисовку.

### Long tasks и параллельность

Promise, таймер и `queueMicrotask` не переносят вычисления на другой поток. Если callback выполняет большой цикл, основной поток остаётся занят. Разбиение работы на задачи даёт браузеру возможность обработать пользовательский ввод и обновить интерфейс между порциями. Web Worker действительно выполняет JavaScript в другом потоке со своим event loop, но не имеет прямого доступа к DOM.

Разбиение тоже имеет стоимость: нужно хранить промежуточное состояние, выбирать размер порции и учитывать изменение данных между задачами. Поэтому сначала находят конкретную долгую задачу (`long task`) в панели Performance, а затем выбирают способ оптимизации.

## Пример

```js
console.log("A");

setTimeout(() => console.log("timeout"), 0);

Promise.resolve().then(() => {
  console.log("promise");
  queueMicrotask(() => console.log("nested microtask"));
});

console.log("B");
```

Результат:

```text
A
B
promise
nested microtask
timeout
```

Начальный скрипт является текущей задачей. Он выводит `A` и `B`, таймер регистрирует будущую задачу, а `then` - микрозадачу. После скрипта выполняется обработчик `then`, затем добавленная им микрозадача. Только после опустошения очереди микрозадач event loop может выбрать задачу таймера.

```js
async function run() {
  console.log("1");
  await null;
  console.log("3");
}

run();
console.log("2");
```

`run()` синхронно выводит `1` и возвращает Promise. Продолжение после `await` становится микрозадачей, поэтому итоговый порядок: `1`, `2`, `3`.

## Где применяется во frontend

| Наблюдение | Причина в модели | Что проверять |
| --- | --- | --- |
| `then` выполняется раньше таймера | микрозадачи выполняются до следующей задачи | порядок регистрации и тип очереди |
| Обработчик клика запаздывает | основной поток занят долгой задачей или микрозадачами | панель Performance, Long Tasks, INP |
| DOM изменён, но кадр не появился | JavaScript или микрозадачи ещё не отдали поток рендерингу | длительность задачи и цепочки микрозадач |
| `requestAnimationFrame` пропускает кадры | callback или предыдущая работа слишком тяжёлые | длительность кадра и принудительный layout |
| Вычисление блокирует интерфейс | асинхронное расписание не создаёт параллельности | разбиение на части или Web Worker |

## Ключевые уточнения

- Event loop принадлежит среде выполнения; ECMAScript сам по себе не определяет DOM-задачи и рендеринг.
- Начальный скрипт и обработчик события являются задачами, а не отдельным этапом перед запуском event loop.
- «Macrotask» - учебный термин; HTML Standard оперирует tasks, task queues и task sources.
- Очередь микрозадач очищается до конца, поэтому рекурсивные микрозадачи могут задержать пользовательский ввод и рендеринг.
- Схема «task → microtasks → render» полезна как причинное упрощение, но актуальный стандарт ставит обновление rendering как отдельную задачу.
- Пользовательское событие обычно приходит через задачу, но программный `dispatchEvent()` вызывает обработчики синхронно.
- Браузер не обязан рисовать после каждой обычной задачи, а `requestAnimationFrame` не переносит тяжёлый код с основного потока.
