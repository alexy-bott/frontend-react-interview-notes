## Быстрый ответ

`fetch` - браузерный Web API для выполнения сетевых запросов. Вызов возвращает `Promise<Response>`: объект `Response` содержит HTTP-статус, заголовки и поток тела ответа.

Promise от `fetch` отклоняется, если запрос не удалось выполнить, например из-за сетевой ошибки, блокировки CORS или отмены. Статусы `404` и `500` означают, что HTTP-ответ получен, поэтому сами по себе не отклоняют Promise. Их проверяют через `response.ok` или `response.status`.

Получение `Response` ещё не означает, что тело полностью загружено и корректно. Тело читают отдельно через `json()`, `text()`, `blob()` или потоковый API, после чего внешние данные при необходимости проверяют во время выполнения. TypeScript описывает ожидаемую форму данных, но не проверяет фактический JSON с сервера.

## Ключевая схема

```text
создать Request
→ выполнить fetch
→ получить статус и заголовки Response
→ проверить HTTP-статус
→ прочитать тело
→ проверить формат и структуру данных
→ вернуть результат или нормализованную ошибку
```

| Этап | Что может пойти не так |
| --- | --- |
| Создание и отправка запроса | некорректный URL или настройки, CORS, сеть, отмена |
| Проверка ответа | HTTP-статус `4xx` или `5xx` |
| Чтение тела | обрыв соединения, повторное чтение, ошибка потока |
| Парсинг | тело не соответствует заявленному формату |
| Проверка данных | JSON имеет неожиданную структуру |
| Бизнес-логика | сервер сообщает предметную ошибку внутри корректного ответа |

## Что делает `fetch`

`fetch(input, init)` принимает URL или объект `Request` и необязательные настройки. Браузер формирует запрос, применяет правила безопасности и HTTP, а Promise выполняется объектом `Response`, когда доступны статус и заголовки. Тело ответа в этот момент может ещё поступать по сети.

```js
const response = await fetch("/api/users/42", {
  method: "GET",
  headers: {
    Accept: "application/json",
  },
});

if (!response.ok) {
  throw new Error(`HTTP ${response.status}`);
}

const user = await response.json();
```

`response.ok` равен `true` для статусов от `200` до `299`. Проверка нужна до возврата результата прикладному коду, но тело ошибки часто стоит прочитать: backend может передать машинный код, сообщение и ошибки отдельных полей.

## Настройки запроса

| Поле | Назначение |
| --- | --- |
| `method` | HTTP-метод; по умолчанию `GET` |
| `headers` | заголовки запроса, например `Accept` и `Content-Type` |
| `body` | тело запроса; `fetch` не разрешает его для `GET` и `HEAD` |
| `credentials` | правила отправки cookie и данных HTTP-аутентификации |
| `signal` | отмена через `AbortSignal` |
| `cache` | взаимодействие с HTTP-кэшем браузера |
| `redirect` | обработка перенаправлений; по умолчанию `follow` |

`Accept` сообщает, какой формат ответа ожидает клиент. `Content-Type` описывает формат отправляемого тела. Для JSON тело сериализуют, а заголовок задают явно:

```js
await fetch("/api/users", {
  method: "POST",
  headers: {
    Accept: "application/json",
    "Content-Type": "application/json",
  },
  body: JSON.stringify({ name: "Ann" }),
});
```

Для `FormData` `Content-Type` вручную обычно не задают: браузер сам сформирует `multipart/form-data` с нужным `boundary`, то есть строкой-разделителем частей тела.

## Ошибки разных уровней

У сетевого запроса нет единственного вида ошибки. Разделение уровней помогает показать правильное состояние интерфейса и решить, можно ли повторить запрос.

| Уровень | Пример | Как обрабатывать |
| --- | --- | --- |
| Выполнение запроса | сеть недоступна, CORS, отмена | `catch`, отдельное состояние сети или отмены |
| HTTP | `401`, `404`, `422`, `500` | проверить `status`, прочитать тело ошибки |
| Формат | ожидался JSON, пришёл HTML | сообщить об ошибке протокола или парсинга |
| Контракт данных | в JSON отсутствует обязательное поле | проверка данных во время выполнения |
| Бизнес-правило | промокод истёк, лимит исчерпан | предметная ошибка для конкретного сценария |

`401 Unauthorized` обычно означает, что требуется аутентификация или обновление сессии. `403 Forbidden` означает, что сервер распознал запрос, но не разрешает действие. Логику обновления токена централизуют в API-слое и защищают от одновременного запуска нескольких refresh-запросов.

## Тело `Response`

Тело ответа представлено `ReadableStream`. Методы `json()`, `text()`, `blob()` и `arrayBuffer()` полностью читают этот поток и возвращают Promise с результатом. После чтения `response.bodyUsed` становится `true`, а повторная попытка прочитать то же тело завершается ошибкой.

Если действительно нужны две независимые ветви чтения, `response.clone()` вызывают до первого чтения. Клонирование разделяет поток на две ветви, но не является бесплатным: непрочитанные данные одной ветви могут накапливаться в памяти. В обычном API-слое тело лучше прочитать один раз и передать дальше уже разобранное значение.

Пустые ответы, включая распространённый `204 No Content`, нельзя безусловно разбирать через `response.json()`. Ошибка парсинга возможна и при статусе `2xx`, если тело пустое или содержит невалидный JSON.

## Проверка внешних данных

Аннотация `Promise<User>` существует только во время проверки TypeScript-кода. Во время выполнения браузер получает обычные данные, поэтому generic-параметр или `as User` не доказывают соответствие ответа типу `User`.

Надёжная вспомогательная функция принимает результат как `unknown`, а затем передаёт его функции проверки:

```ts
class ApiError extends Error {
  constructor(
    public status: number,
    public body: unknown,
  ) {
    super(`HTTP ${status}`);
  }
}

async function readBody(response: Response): Promise<unknown> {
  if (response.status === 204) {
    return undefined;
  }

  const contentType = response.headers.get("content-type") ?? "";
  return contentType.includes("application/json")
    ? response.json()
    : response.text();
}

async function fetchJson<T>(
  url: string,
  parse: (value: unknown) => T,
  options: RequestInit = {},
): Promise<T> {
  const response = await fetch(url, {
    ...options,
    headers: {
      Accept: "application/json",
      ...options.headers,
    },
  });

  const body = await readBody(response);

  if (!response.ok) {
    throw new ApiError(response.status, body);
  }

  return parse(body);
}
```

`parse` может быть type guard (функцией уточнения типа), валидатором схемы или функцией ручной проверки. Внутреннему стабильному API иногда достаточно проверить несколько критичных полей; данные из внешнего или нестабильного источника требуют более строгой схемы.

## Отмена, повторы и устаревшие ответы

Запрос отменяют через `AbortSignal`, если его результат больше не нужен: пользователь изменил поисковую строку, перешёл на другой маршрут или компонент завершил работу. Механизм подробно разобран в [AbortController](<./AbortController.md>).

Повторять запрос можно не всегда. `GET`, `HEAD`, `PUT` и `DELETE` определены как идемпотентные методы: несколько одинаковых запросов должны иметь тот же ожидаемый эффект, что и один. `POST` обычно не идемпотентен, поэтому автоматический повтор может создать дубликат; для него нужен дополнительный контракт API, например idempotency key.

Количество повторов ограничивают, а задержку между ними постепенно увеличивают (`backoff`). Ответ `400` обычно не станет успешным от повторения, а `429` или временный `5xx` иногда имеет смысл повторить с учётом `Retry-After`.

## Credentials и CORS

По умолчанию `fetch` отправляет credentials, например cookie, только для запросов к тому же origin (источнику). `credentials: "include"` разрешает их и для cross-origin-запроса к другому источнику, но сервер должен явно разрешить такой CORS-сценарий: вернуть конкретный `Access-Control-Allow-Origin` и `Access-Control-Allow-Credentials: true`.

`fetch` не обходит CORS. CORS - браузерный механизм, определяющий, может ли JavaScript прочитать ответ от другого origin. Настройка `credentials` тоже не заменяет аутентификацию: она только управляет отправкой cookie и других учётных данных, а способ авторизации определяется контрактом приложения.

## Где применяется во frontend

- Тонкий HTTP-клиент централизует базовый URL, заголовки, чтение тела и нормализацию ошибок, чтобы компоненты не повторяли протокольную логику.
- Проверка данных во время выполнения ставится на границе с backend, чтобы некорректные внешние данные не распространялись как доверенные TypeScript-типы.
- `AbortSignal` останавливает работу, результат которой устарел, и не даёт старому ответу перезаписать новое состояние UI.
- Библиотеки для серверного состояния, например RTK Query или TanStack Query, добавляют к запросам кэш, дедупликацию, повторы, инвалидацию и синхронизацию состояний.

## Границы `fetch`

`fetch` выполняет запрос и предоставляет низкоуровневые объекты `Request` и `Response`. Сам по себе он не определяет:

- какие HTTP-статусы считать ошибкой приложения;
- как валидировать JSON;
- как кэшировать серверные данные и обновлять интерфейс;
- когда повторять или дедуплицировать запросы;
- как обновлять access token (токен доступа);
- как отменить уже выполненное изменение на backend.

Эти правила реализуют API-клиент, библиотека для серверного состояния и контракт с backend.

## Ключевые уточнения

- `fetch` относится к Web API среды выполнения, а не к языку ECMAScript.
- HTTP-ответ со статусом `4xx` или `5xx` обычно успешно выполняет `Promise<Response>`; его статус проверяет приложение.
- `Response` может быть получен до полной загрузки тела; чтение тела является отдельной асинхронной операцией.
- Тело ответа читается один раз, если заранее не создан `response.clone()`.
- Generic-параметр TypeScript не заменяет проверку ответа во время выполнения.
- Таймаут через один `Promise.race` не останавливает запрос; для реальной отмены нужен `AbortSignal`.
- Автоматический повтор зависит от метода, вида ошибки и идемпотентности операции.
