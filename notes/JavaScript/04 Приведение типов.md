## Быстрый ответ

Приведение типов - преобразование значения из одного JavaScript-типа в другой. Явное преобразование видно в коде: `Number(value)`, `String(value)`, `Boolean(value)`. Неявное преобразование запускает сам оператор или синтаксический контекст, например `if (value)`, `"total: " + value` или `value == 0`.

У каждого контекста свой алгоритм. Логическое условие преобразует значение к типу `boolean`, арифметика - к числовому типу `Number` или `BigInt`, шаблонная строка - к строке. Если операция получает объект, то сначала пытается получить из него примитив через `Symbol.toPrimitive`, `valueOf()` или `toString()`.

Само приведение типов не является ошибкой: это часть языка. Риск появляется, когда цепочка преобразований неочевидна читателю. На границах приложения данные формы, URL и API лучше преобразовывать явно и отдельно проверять.

## Ключевая схема

```text
оператор или API определяет ожидаемый тип
→ если значение уже подходит, использовать его
→ иначе применить соответствующую абстрактную операцию спецификации
→ для объекта сначала получить примитив
→ выполнить операцию над преобразованным значением
```

| Контекст | Преобразование | Пример |
| --- | --- | --- |
| `if`, `!`, `&&`, `||` | ToBoolean | `if (value)` |
| унарный `+`, `-`, `*`, `/` | ToNumeric | `+input` |
| шаблонная строка | ToString | `` `${value}` `` |
| бинарный `+` | приведение к примитивам, затем конкатенация или сложение | `1 + "2"` |
| нестрогое равенство | Abstract Equality | `value == null` |
| ключ свойства | ToPropertyKey | `object[key]` |

## Явное преобразование

```js
String(42);        // "42"
Number("42");     // 42
Boolean("hello"); // true
BigInt("42");     // 42n
```

Явный вызов показывает намерение, но не гарантирует допустимый результат. `Number("")` возвращает `0`, `Number("text")` - `NaN`, а `Boolean("false")` - `true`, потому что строка непустая.

```js
const raw = form.elements.age.value;
const age = Number(raw);

if (raw.trim() === "" || !Number.isInteger(age) || age < 0) {
  showAgeError();
}
```

Здесь отдельно определена семантика пустого поля, затем выполнено преобразование и проверен предметный диапазон. Один `Number(raw)` не отвечает на вопрос, допустимо ли исходное значение.

## Truthy и falsy

В boolean-контексте falsy являются:

- `false`;
- `0` и `-0`;
- `0n`;
- `NaN`;
- пустая строка `""`;
- `null`;
- `undefined`.

Остальные обычные значения являются truthy, то есть считаются истинными в логическом контексте. В частности, пустой массив, пустой объект и объект-обёртка для `false` являются truthy:

```js
Boolean([]);                 // true
Boolean({});                 // true
Boolean(new Boolean(false)); // true
```

Проверка `if (!value)` объединяет все falsy-значения. Это правильно только тогда, когда `0`, `false` и `""` действительно означают отсутствие. Для данных API такая проверка часто теряет допустимые значения.

```js
if (value == null) {
  // только null или undefined
}
```

Это один из немногих осознанных сценариев `==`: алгоритм отдельно считает `null` и `undefined` равными друг другу, но не другим обычным значениям.

## Преобразование к числу

| Значение | `Number(value)` |
| --- | --- |
| `undefined` | `NaN` |
| `null` | `0` |
| `true` / `false` | `1` / `0` |
| `""` или строка из пробелов | `0` |
| строка с корректной записью числа | соответствующее число |
| строка, которую нельзя целиком преобразовать в число | `NaN` |
| `BigInt` | соответствующий `Number`; большое значение может потерять точность |
| `Symbol()` | `TypeError` |

Унарный `+` обычно выполняет такое же числовое преобразование, но не принимает `BigInt`:

```js
+"42"; // 42
+1n;   // TypeError
```

`parseInt` и `parseFloat` разбирают начало строки и могут игнорировать хвост, поэтому это не полная замена `Number`:

```js
Number("12px");        // NaN
Number.parseInt("12px", 10); // 12
```

Выбор зависит от контракта: для CSS-подобной строки допустим разбор префикса, для поля «целое число» лишний хвост обычно является ошибкой.

## Бинарный `+`

Оператор `+` выполняет и сложение, и конкатенацию. Сначала операнды преобразуются к примитивам. Если после этого хотя бы один операнд является строкой, оба преобразуются к строкам; иначе выполняется числовое сложение.

```js
1 + 2;       // 3
1 + "2";     // "12"
"1" + 2 + 3; // "123"
1 + 2 + "3"; // "33"
```

Вычисление идёт слева направо. В третьем примере первая операция уже создаёт строку, поэтому следующая продолжает конкатенацию.

Смешивать `BigInt` и `Number` в арифметике нельзя без явного преобразования:

```js
1n + 1; // TypeError
```

Это защищает от неявной потери точности, но разработчик должен сам решить, какой числовой тип подходит задаче.

## Объект в примитив

Если оператору нужен примитив, а передан объект, запускается преобразование ToPrimitive.

Упрощённый порядок для обычного объекта:

1. Если определён `Symbol.toPrimitive`, вызвать его с подсказкой `hint`.
2. Для подсказки `"number"` или `"default"` обычно попробовать `valueOf()`, затем `toString()`.
3. Для подсказки `"string"` попробовать `toString()`, затем `valueOf()`.
4. Если ни один метод не вернул примитив, выбросить `TypeError`.

Аргумент `hint` сообщает предпочтительный результат: `"string"`, `"number"` или `"default"`. Он не обязывает пользовательский метод вернуть конкретный тип, но результат обязан быть примитивом.

```js
const money = {
  amount: 100,

  [Symbol.toPrimitive](hint) {
    return hint === "string"
      ? `${this.amount} RUB`
      : this.amount;
  },
};

String(money); // "100 RUB"
+money;        // 100
```

В прикладной модели магическое числовое поведение объекта может ухудшить читаемость. Часто понятнее явные методы `money.format()` и `money.toNumber()`. `Symbol.toPrimitive` оправдан, когда такая семантика стабильна и ожидаема для типа.

## Почему `[] == false`

Этот пример показывает несколько последовательных правил, а не одно «странное сравнение»:

```text
[] == false
→ [] преобразуется к примитиву: ""
→ false преобразуется к Number: 0
→ "" преобразуется к Number: 0
→ 0 == 0
→ true
```

При `===` преобразования нет, поэтому `[] === false` сразу возвращает `false` из-за разных типов.

## Логические операторы возвращают значения

`&&` и `||` проверяют, является ли операнд truthy или falsy, но возвращают исходное значение, а не обязательно `boolean`:

```js
"user" && 42; // 42
"" || "fallback"; // "fallback"
```

`||` выбирает резервное значение для любого falsy-значения. `??` выбирает его только для `null` и `undefined`:

```js
0 || 10; // 10
0 ?? 10; // 0
```

Для числовой настройки, где `0` допустим, nullish coalescing точнее выражает намерение.

## Где применяется во frontend

- Значения `<input>` приходят строками даже для многих числовых сценариев и требуют явного разбора.
- `URLSearchParams.get()` возвращает строку или `null`, поэтому отсутствие и пустая строка различаются.
- API может законно вернуть `0`, `false` или `""`; общая falsy-проверка не должна превращать их в отсутствие.
- Условный рендеринг в React через `items.length && ...` способен вывести `0`; сравнение `items.length > 0` однозначнее.
- Значения `data-*` в `dataset` являются строками и не получают автоматическую предметную типизацию.

## Ключевые уточнения

- Способ приведения типов определяется конкретным оператором; одного универсального алгоритма «привести типы» нет.
- Явное преобразование не заменяет проверку формата и бизнес-ограничений.
- Пустые массив и объект truthy, потому что все обычные объекты truthy.
- Бинарный `+` после ToPrimitive выбирает между строковой конкатенацией и числовым сложением.
- `&&` и `||` возвращают один из исходных операндов, а не нормализованное логическое значение.
- ToPrimitive сначала даёт объекту возможность определить своё представление, но в результате обязан получить примитив.
- На внешних границах лучше явно разделять отсутствие, преобразование, проверку и использование значения.
