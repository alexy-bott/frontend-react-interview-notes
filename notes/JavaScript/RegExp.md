## Быстрый ответ

`RegExp` описывает шаблон поиска в строке. Литерал `/pattern/flags` удобен для статического шаблона, а `new RegExp(string, flags)` - для динамически построенного.

Регулярные выражения используют для поиска, извлечения, замены и проверки формата. Для проверки всей строки шаблон закрепляют якорями `^` и `$`, иначе совпадение в любой части строки может дать ложный успех.

Флаги меняют семантику: `g` ищет все совпадения и использует изменяемый `lastIndex`, `i` игнорирует регистр, `m` меняет поведение якорей по строкам, `s` разрешает точке захватывать переводы строк, `u` и `v` включают Unicode-семантику, а `y` требует совпадения точно с позиции `lastIndex`.

Регулярное выражение не заменяет parser сложного языка и не должно строиться из пользовательского ввода без экранирования. Неудачный шаблон способен вызвать катастрофический возврат (`catastrophic backtracking`) и заблокировать main thread.

## Ключевая схема

| Задача | API |
| --- | --- |
| Есть ли совпадение | `regex.test(text)` |
| Первое совпадение и группы | `regex.exec(text)` / `text.match(regex)` |
| Все совпадения с группами | `text.matchAll(regexWithG)` |
| Замена | `text.replace` / `replaceAll` |
| Разделение | `text.split(regex)` |

```js
const pattern = /^(?<name>[a-z]+)-(?<id>\d+)$/i;
const match = pattern.exec("user-42");

match?.groups?.name; // "user"
match?.groups?.id;   // "42"
```

## Литерал и конструктор

```js
const staticPattern = /user-\d+/i;

const prefix = "user";
const dynamicPattern = new RegExp(`${prefix}-\\d+`, "i");
```

В конструкторе строка проходит два уровня экранирования: сначала правила JavaScript-строки, затем parser регулярного выражения. Для `\d` в итоговом шаблоне нужно написать `"\\d"` в обычной строке.

Если в шаблон вставляется произвольный текст, метасимволы регулярного выражения должны быть экранированы. Иначе `.` или `*` изменит смысл шаблона, а сложный ввод может создать риск для производительности и безопасности.

## Основные элементы шаблона

| Синтаксис | Значение |
| --- | --- |
| `.` | любой символ по правилам флагов |
| `\d`, `\w`, `\s` | сокращённые классы символов |
| `[a-z]`, `[^0-9]` | набор / отрицание набора |
| `*`, `+`, `?`, `{m,n}` | quantifiers |
| `^`, `$` | anchors |
| `(pattern)` | захватывающая группа |
| `(?:pattern)` | незахватывающая группа |
| `(?<name>pattern)` | именованная захватывающая группа |
| `a|b` | alternative |
| `(?=...)`, `(?!...)` | positive/negative lookahead |
| `(?<=...)`, `(?<!...)` | positive/negative lookbehind |

Сокращение `\w` традиционно не означает «любая Unicode-буква». Для категорий Unicode используют property escapes с флагом `u` или `v`:

```js
/^\p{L}+$/u.test("Привет"); // true
```

## Проверка формата и якоря

```js
/\d{4}/.test("id=1234; extra"); // true
/^\d{4}$/.test("id=1234; extra"); // false
```

Первый шаблон отвечает на вопрос «есть ли где-то четыре цифры». Второй проверяет, что вся строка состоит ровно из четырёх цифр.

Frontend-валидация не должна пытаться полностью доказать корректность email, телефона или URL для бизнес-правил одним огромным регулярным выражением. Формат, нормализация, предметные ограничения и проверка на сервере являются разными уровнями.

Для URL применяют `new URL`, для сложной грамматики - parser, а для email часто достаточно разумной проверки формата и подтверждения адреса.

## Группы и извлечение

```js
const pattern = /^(?<year>\d{4})-(?<month>\d{2})-(?<day>\d{2})$/;
const match = pattern.exec("2026-07-27");

if (match) {
  console.log(match.groups.year); // "2026"
}
```

Regex проверяет форму, но не календарную корректность: `2026-99-99` также совпадёт. После извлечения values проверяют domain constraints.

Незахватывающую группу `(?:...)` используют, когда группировка нужна для приоритета или квантификатора, но само значение извлекать не требуется. Это уменьшает число позиционных групп и делает контракт стабильнее.

## `g`, `lastIndex` и состояние

Регулярное выражение с `g` или `y` хранит изменяемый `lastIndex`:

```js
const pattern = /a/g;

pattern.test("a"); // true, lastIndex = 1
pattern.test("a"); // false, поиск начинается с 1
```

Переиспользование одного регулярного выражения с флагом `g` при проверке может чередовать результаты. Для одиночной проверки убирают `g`, создают новый экземпляр или осознанно сбрасывают `lastIndex`.

`matchAll` требует регулярное выражение с флагом `g` и возвращает итератор всех совпадений, сохраняя группы:

```js
const matches = [...text.matchAll(/(?<id>\d+)/g)];
```

## Replacement

```js
"Ada Lovelace".replace(
  /(?<first>\w+) (?<last>\w+)/,
  "$<last>, $<first>",
);
// "Lovelace, Ada"
```

Function replacer удобнее для вычисляемой и безопасной логики:

```js
text.replace(/\d+/g, (value) => String(Number(value) + 1));
```

Replacement не является HTML sanitizer. Regex не понимает DOM parsing contexts и не должен использоваться для удаления опасных tags/attributes из untrusted HTML.

## Unicode

Без Unicode-семантики точка и квантификаторы могут работать с кодовыми единицами UTF-16 и разделять суррогатную пару. Флаги `u` и `v` улучшают работу с кодовыми точками и свойствами Unicode.

Даже Unicode-выражение обычно оперирует кодовыми точками, а не графемными кластерами. Для пользовательских символов с комбинируемыми знаками и последовательностей emoji применяют `Intl.Segmenter`.

Флаг `i` не заменяет полноценный поиск с учётом локали. Для сортировки и сравнения отображаемого текста используют `Intl.Collator` и нормализацию по правилам предметной области.

## Катастрофический возврат

Шаблон с неоднозначными вложенными квантификаторами может проверять огромное число вариантов:

```js
/^(a+)+$/.test("aaaaaaaaaaaaaaaaaaaa!");
```

На строке без совпадения время способно резко вырасти и заблокировать main thread. Это особенно опасно для шаблонов над длинным пользовательским текстом.

Защита:

- упрощать неоднозначные nested quantifiers;
- ограничивать длину входной строки;
- использовать anchors и более конкретные classes;
- тестировать худший случай без совпадения;
- выбирать parser или движок с линейным временем для сложных шаблонов над недоверенным вводом.

## Где применяется во frontend

- Извлечение части строго известного identifier format.
- Простая проверка формата до валидации на сервере.
- Поиск и замена в редакторе с контролем длины ввода и происхождения шаблона.
- Разбор log line или generated route segment с устойчивой grammar.
- Unicode property escapes для категорий символов, но работу с графемами передают `Intl.Segmenter`.

## Ключевые уточнения

- Без якорей регулярное выражение ищет подстроку; проверка всей строки требует явно закреплённого шаблона.
- Constructor имеет двойной уровень escaping.
- Флаги `g` и `y` делают RegExp объектом с изменяемым состоянием через `lastIndex`.
- Захватывающая группа извлекает данные, а незахватывающая только группирует шаблон.
- Совпадение формата не доказывает соответствие предметным правилам.
- Кодовая точка Unicode и графема являются разными уровнями.
- Регулярное выражение не является HTML-parser или средством очистки опасного ввода.
- Худший случай backtracking нужно проверять на длинной строке без совпадения.
