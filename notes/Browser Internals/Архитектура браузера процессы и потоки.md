## Быстрый ответ

Современный браузер обычно разделяет работу между несколькими процессами. На примере Chromium: основной процесс браузера (browser process) управляет его интерфейсом, навигацией и привилегированными операциями; процессы рендеринга (renderer processes) обрабатывают содержимое сайтов; отдельные процессы или сервисы отвечают за сеть, GPU и вспомогательные задачи.

Внутри процесса находятся потоки. В процессе рендеринга основной поток (main thread) разбирает HTML, строит DOM, выполняет большую часть JavaScript, рассчитывает стили и раскладку (layout). Поток композитора и потоки растеризации помогают подготовить и собрать кадр, а Web Workers выполняют JavaScript на рабочих потоках.

Разделение даёт изоляцию, безопасность и устойчивость: сбой одной вкладки не обязан останавливать весь браузер. Цена — дополнительная память и обмен данными между процессами через IPC. Конкретная архитектура является деталью реализации браузера, а не требованием веб-стандартов.

## Процесс и поток

**Процесс** получает от операционной системы собственное адресное пространство памяти и набор разрешений. Другой процесс не может напрямую читать эту память; для обмена используется межпроцессное взаимодействие — IPC (Inter-Process Communication).

**Поток** выполняет инструкции внутри процесса. Потоки одного процесса разделяют его память, поэтому обмениваться данными им проще, но ошибка синхронизации может затронуть общий процесс.

```text
Browser process
  ├─ UI и навигация
  ├─ привилегированные операции
  └─ координация других процессов через IPC

Renderer process
  ├─ main thread
  ├─ compositor thread
  ├─ raster threads
  └─ worker threads при использовании Workers
```

## Основные процессы Chromium

| Процесс или сервис | Основная ответственность |
| --- | --- |
| Основной процесс браузера | адресная строка, вкладки, навигация, разрешения, координация |
| Процесс рендеринга | DOM, CSS, JavaScript и содержимое сайта |
| Сетевой сервис | DNS, соединения, HTTP, кэш и загрузка ресурсов |
| GPU-процесс | команды GPU, компоновка слоёв и изоляция графической работы |
| Вспомогательные процессы | аудио, декодирование и другие изолируемые сервисы |

Границы могут меняться между версиями и платформами: сервис способен работать в отдельном процессе или внутри другого. Для frontend-разработчика важна не точная таблица процессов конкретной версии Chrome, а разделение привилегированного кода браузера и процесса рендеринга. Последний работает в sandbox — изолированной среде с ограниченными правами.

## Что происходит в процессе рендеринга

Процесс рендеринга получает поток HTML после подтверждения навигации (navigation commit) и превращает его в интерактивную страницу.

**Основной поток (main thread)** выполняет основную работу документа:

- разбирает HTML и строит DOM;
- разбирает CSS и участвует в построении CSSOM;
- выполняет JavaScript страницы;
- рассчитывает стили и раскладку;
- создаёт список команд рисования (paint records);
- обрабатывает значительную часть событий пользователя.

**Поток композитора (compositor thread)** собирает информацию о слоях, может обрабатывать некоторые прокрутки и анимации без нового выполнения JavaScript на основном потоке и отправляет задачи на растеризацию.

**Потоки растеризации (raster threads)** превращают команды рисования для частей слоёв в пиксели — растровые фрагменты (tiles). **GPU-процесс** помогает отобразить и скомпоновать готовые поверхности.

Эта схема объясняет, почему `transform` иногда продолжает анимироваться при занятом main thread, но обычный JavaScript-обработчик клика ждёт освобождения основного потока.

## Site Isolation и процессы рендеринга

Упрощение «одна вкладка — один процесс» неточно. Chromium старается изолировать сайты, поэтому `iframe` с другого сайта может получить отдельный процесс рендеринга. При нехватке ресурсов браузер также способен переиспользовать процессы.

Site Isolation усиливает защиту: данные разных сайтов разделены не только Same-Origin Policy на уровне логики, но и границами процессов. Это особенно важно против атак, пытающихся прочитать чужую память.

Frontend-код не должен зависеть от того, находятся ли два документа в одном процессе. Разрешённое взаимодействие определяется Web API, политикой одного источника (same-origin policy) и sandbox, а не физическим размещением.

## Основной поток и Workers

`async/await`, Promise и таймеры не создают новый поток. Их callback-функции продолжат выполняться на основном потоке, когда соответствующая задача попадёт в очередь.

Web Worker действительно выполняет JavaScript на рабочем потоке. Он не имеет прямого доступа к DOM и обменивается данными с документом через сообщения. Поэтому Worker подходит для ресурсоёмких процессорных вычислений, но не для непосредственного обновления интерфейса.

## Зачем браузеру несколько процессов

**Устойчивость.** Сбой процесса рендеринга одной страницы можно изолировать от других вкладок и интерфейса браузера.

**Безопасность.** Процесс рендеринга работает в sandbox с ограниченными правами, а доступ к сети и файлам проходит через более привилегированные компоненты.

**Отзывчивость.** Сеть, GPU и часть рендеринга могут работать параллельно с main thread страницы.

**Цена.** У процессов отдельная память, поэтому копируются общие структуры и растут накладные расходы на IPC. Браузер балансирует изоляцию и расход ресурсов.

## Ключевые уточнения

- Процесс имеет отдельную память; потоки внутри процесса разделяют память.
- Конкретная схема процессов Chromium является реализацией этого браузера, а не стандартом для Firefox и Safari; одна вкладка также не обязана соответствовать одному процессу.
- Процесс рендеринга работает в sandbox, поэтому привилегированные операции проходят через контролируемое межпроцессное взаимодействие.
- Promise и `async/await` продолжают процессорную работу на основном потоке, а Web Worker действительно выполняет JavaScript на рабочем потоке.
- Поток композитора способен обработать только часть визуальных изменений без основного потока и не делает произвольный UI-код параллельным.
