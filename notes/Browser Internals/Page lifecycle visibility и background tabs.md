## Быстрый ответ

Жизненный цикл страницы описывает, что происходит с вкладкой, когда она видима, скрыта, заморожена, выгружена или восстановлена из back/forward cache (BFCache). Эти состояния важно различать: скрытая страница ещё выполняет JavaScript, замороженная временно не выполняет задачи, а выгруженная прекращает существование.

Браузер экономит ресурсы фоновых вкладок: приостанавливает `requestAnimationFrame`, ограничивает таймеры и в некоторых случаях может заморозить или удалить страницу из памяти. Поэтому приложение не должно считать `setInterval` точными часами или ожидать, что перед закрытием обязательно выполнится завершающая callback-функция.

Основной практический сигнал — событие `visibilitychange`. При скрытии страницы останавливают необязательные обновления и сохраняют важное состояние, а при возвращении сравнивают текущее время с последней синхронизацией, запрашивают актуальные данные и возобновляют работу.

## Какие состояния нужно различать

| Состояние | Что означает | Что может делать приложение |
| --- | --- | --- |
| Visible | содержимое вкладки хотя бы частично видно | выполнять анимации и обычные фоновые обновления |
| Hidden | вкладка не видна пользователю | JavaScript ещё работает, но браузер может ограничивать ресурсы |
| Frozen | выполнение приостанавливаемых задач остановлено | код страницы не получает время выполнения до возобновления |
| Terminated | страница выгружена | её JavaScript больше не выполняется |
| Discarded | браузер удалил скрытую страницу из памяти | при возвращении произойдёт новая загрузка |

Состояния `visible` и `hidden` определены Page Visibility API. Более подробная модель `active`, `passive`, `frozen`, `terminated` и `discarded` используется Page Lifecycle API и зависит от браузера. Это полезная модель поведения, но не единый кроссбраузерный автомат состояний.

Фокус и видимость — разные признаки. Окно может быть видимым, но не иметь фокуса клавиатуры, например когда пользователь работает во втором окне рядом. Для решения «показывать ли анимацию» обычно важна видимость; для решения «куда направлять ввод» — фокус.

## Почему фоновые таймеры ненадёжны

Событийный цикл не обещает выполнить callback-функцию таймера ровно через заданную задержку. Задержка задаёт минимальное время, после которого задача может попасть в очередь. В скрытой вкладке браузер дополнительно ограничивает частоту таймеров и распределяет процессорное время между страницами.

`requestAnimationFrame` связан с подготовкой видимого кадра и в скрытой вкладке обычно не вызывается. Это экономит CPU и заряд батареи, но означает, что прошедшее время нельзя считать количеством выполненных кадров или срабатываний interval.

При возвращении не нужно запускать каждое пропущенное срабатывание. Надёжнее хранить абсолютное время последнего обновления, запросить текущее состояние и продолжить работу от него. В примере `fetchFreshData()` обозначает прикладной запрос актуальных данных:

```js
const REFRESH_INTERVAL = 30_000;
let lastUpdatedAt = 0;
let timeoutId;
let isRefreshing = false;

function scheduleNextRefresh(delay) {
  window.clearTimeout(timeoutId);
  timeoutId = window.setTimeout(refreshAndSchedule, delay);
}

async function refreshAndSchedule() {
  if (isRefreshing) {
    return;
  }

  isRefreshing = true;

  try {
    await fetchFreshData();
    lastUpdatedAt = Date.now();
  } catch (error) {
    console.error("Polling failed", error);
  } finally {
    isRefreshing = false;
  }

  if (!document.hidden) {
    scheduleNextRefresh(REFRESH_INTERVAL);
  }
}

function stopPolling() {
  window.clearTimeout(timeoutId);
  timeoutId = undefined;
}

document.addEventListener("visibilitychange", async () => {
  if (document.hidden) {
    stopPolling();
    return;
  }

  if (Date.now() - lastUpdatedAt >= REFRESH_INTERVAL) {
    await refreshAndSchedule();
  } else {
    scheduleNextRefresh(
      REFRESH_INTERVAL - (Date.now() - lastUpdatedAt),
    );
  }
});

void refreshAndSchedule();
```

Следующий запрос планируется только после завершения предыдущего, поэтому медленный ответ не создаёт несколько одновременно выполняющихся обновлений.

## Что делать при скрытии и возвращении

Реакция зависит от продукта, а не только от API:

| Сценарий | При `hidden` | При `visible` |
| --- | --- | --- |
| Периодические запросы (polling) | остановить необязательные запросы | проверить давность данных и обновить их |
| Анимация или canvas | остановить собственный цикл, если он есть | продолжить от текущего времени, а не от номера кадра |
| Видео и аудио | сохранить факт воспроизведения; пауза зависит от пользовательского сценария | не запускать автоматически то, что пользователь уже остановил |
| Dashboard с WebSocket | не перерисовывать каждое невидимое изменение | получить актуальный снимок данных или повторно синхронизироваться, если события могли потеряться |
| Авторизация | не ждать точного срабатывания таймера истечения | заново проверить срок токена перед запросом |
| Редактор | сохранить черновик локально | сверить локальную и серверную версии |

Скрытие вкладки само по себе не означает, что нужно закрыть любой WebSocket или EventSource. Для чата может быть важна доставка сообщений, а для графика котировок достаточно повторной синхронизации. Решение зависит от стоимости соединения, допустимости пропуска событий и серверной модели восстановления.

## Сохранение состояния перед уходом

Переход в `hidden` — последний сигнал, который во многих мобильных сценариях удаётся наблюдать надёжнее, чем выгрузку страницы. В этот момент можно синхронно сохранить небольшой черновик в локальное хранилище или отправить небольшую аналитическую запись через `navigator.sendBeacon()`.

`sendBeacon()` просит браузер отправить данные асинхронно, не удерживая страницу открытой. Он подходит для небольших POST-сообщений, но не гарантирует выполнение критичной бизнес-операции и не заменяет обычный запрос с обработкой ответа.

`beforeunload` следует добавлять только когда есть несохранённые пользовательские данные и действительно нужно показать системное предупреждение. Событие может не выполниться, не позволяет задать произвольный текст диалога и способно ухудшить работу BFCache. Для автоматического сохранения оно не является основной точкой жизненного цикла.

Событие `unload` ещё менее надёжно и не подходит для критичной логики. Страница может быть завершена операционной системой или удалена браузером без возможности выполнить финальный JavaScript.

## BFCache и обычный HTTP-кэш

Back/forward cache (BFCache) хранит целое состояние страницы для быстрого перехода назад и вперёд: JavaScript-кучу, DOM и позицию прокрутки. Это не то же самое, что HTTP-кэш, который хранит отдельные ответы ресурсов.

При восстановлении из BFCache браузер не выполняет обычную загрузку документа заново. Событие `pageshow` получает `event.persisted === true`, а существующие объекты и listeners продолжают жить:

```js
window.addEventListener("pageshow", event => {
  if (event.persisted) {
    void refreshSession();
    void fetchFreshData();
  }
});
```

На `pageshow` проверяют данные, срок сессии и состояние соединений. Не нужно безусловно инициализировать всё приложение повторно: listener, созданный до помещения в BFCache, уже существует.

`pagehide` сообщает, что страница покидает экран, а `event.persisted` показывает, рассчитывает ли браузер сохранить её в BFCache. Это подходящее место для освобождения ресурсов, которые могут помешать сохранению или должны быть восстановлены позже. Однако событие тоже не гарантировано при аварийном завершении процесса.

## Заморозка и удаление страницы из памяти

При заморозке браузер приостанавливает выполнение большинства задач страницы. Promise или timer не «пропадает», но callback-функция не выполнится, пока среда не получит возможность продолжить работу. Серверное время и сетевое состояние при этом продолжают меняться, поэтому после возврата нужна проверка актуальности.

В Chromium события `freeze` и `resume` позволяют дополнительно подготовиться к заморозке и возвращению. В обработчике `freeze` освобождают ресурсы, которые могут конфликтовать с другими вкладками или BFCache: соединения IndexedDB, BroadcastChannel, WebRTC, WebSocket, сетевой polling и Web Locks. Эти рекомендации относятся к модели [Page Lifecycle API в Chromium](https://developer.chrome.com/docs/web-platform/page-lifecycle-api); события используют как дополнительное улучшение, а не как единственную кроссбраузерную основу.

Скрытая вкладка может быть удалена из памяти (discarded) без отдельной callback-функции. При следующем открытии документ загрузится заново. В Chromium `document.wasDiscarded` позволяет после загрузки узнать, что предыдущий экземпляр страницы был удалён. Восстановление всё равно должно опираться на сохранённые данные, а не на обязательность этого свойства.

## Основная модель восстановления

После любого длительного отсутствия приложение должно исходить из того, что окружающий мир изменился:

1. Определить, сколько реального времени прошло.
2. Проверить авторизацию и доступность соединения.
3. Получить актуальный снимок данных или разницу с известной версией.
4. Восстановить только нужные подписки и циклы.
5. Не дублировать listeners, timers и запросы.
6. Показать пользователю конфликт, если локальный черновик расходится с серверным состоянием.

Эта модель работает и после `visibilitychange`, и после BFCache, и после полной перезагрузки. Отличается только объём сохранённого в памяти состояния.

## Ключевые уточнения

- Видимость, фокус и заморозка — разные состояния: скрытая страница ещё может выполнять JavaScript, а замороженная не запускает приостанавливаемые задачи.
- Timer задаёт минимальную задержку; после возвращения приложение сверяется с фактическим временем и актуальными данными вместо воспроизведения пропущенных интервалов.
- BFCache сохраняет живое состояние страницы, а HTTP-кэш — отдельные ответы ресурсов.
- Переход в `hidden` подходит для раннего сохранения лучше, чем ненадёжная попытка выполнить критичную работу в `beforeunload` или `unload`.
- Заморозка и удаление страницы из памяти зависят от браузера и могут не дать завершающего события, поэтому восстановление опирается на заранее сохранённое состояние.
