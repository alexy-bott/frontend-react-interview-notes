## Быстрый ответ

Rendering pipeline, или конвейер рендеринга, — этапы, через которые браузер превращает DOM, CSS и визуальные изменения в пиксели: вычисляет стили, определяет размеры и положение элементов на этапе layout, создаёт команды рисования на этапе paint, растеризует их и собирает слои на этапе composite.

Reflow обычно называют повторный layout — пересчёт размеров и позиций. Repaint означает повторное создание команд рисования без обязательного изменения геометрии. Composite, или компоновка, собирает уже подготовленные слои в итоговый кадр.

Не каждое изменение проходит все этапы. Геометрическое свойство может потребовать layout, затем paint и composite; `color` часто не требует layout; `transform` и `opacity` у уже выделенного слоя иногда обрабатываются на потоке композитора. Это возможности оптимизации, а не безусловные гарантии для любого элемента и браузера.

## От DOM и CSSOM к кадру

После parsing документа браузер имеет DOM и CSSOM. Для видимого содержимого он строит внутренние структуры рендеринга и выполняет работу примерно так:

```text
DOM + CSSOM
   ↓
style calculation
   ↓
layout
   ↓
paint records
   ↓
rasterization
   ↓
composite
   ↓
displayed frame
```

Названия и внутренние структуры различаются между движками, но модель объясняет стоимость изменений.

## Расчёт стилей

Браузер сопоставляет элементы с CSS-селекторами, применяет каскад и наследование, затем вычисляет итоговые значения свойств. Изменение класса родителя способно сделать неактуальными стили большого поддерева, даже если JavaScript изменил одну строку.

Само изменение DOM не всегда сразу запускает синхронный расчёт. Браузер может отложить работу и объединить несколько изменений перед следующим кадром. Но чтение актуальной геометрии способно заставить его выполнить накопленные расчёты немедленно.

## Layout и reflow

Layout определяет размеры и координаты блоков элементов. Изменение `width`, `height`, `padding`, шрифта, содержимого или доступной ширины может повлиять на соседей и потомков.

```js
card.style.width = "480px";

const height = card.offsetHeight;
```

Перед возвратом `offsetHeight` браузеру нужна актуальная геометрия. Если предыдущая запись сделала данные layout неактуальными, чтение может вызвать принудительный синхронный пересчёт (forced synchronous layout).

Layout thrashing — многократный лишний пересчёт раскладки — возникает, когда код чередует изменения DOM и чтение геометрии:

```js
for (const item of items) {
  item.style.width = `${containerWidth}px`;
  console.log(item.offsetHeight);
}
```

Вместо одного общего расчёта браузер вынужден постоянно догонять изменения. Чтения группируют отдельно от записей, а работу распределяют по кадрам только если это действительно нужно.

## Paint и растеризация

Paint определяет, что и в каком порядке нужно нарисовать: фон, текст, границы, тени и другие визуальные части. Результатом являются команды рисования, а не сразу пиксели экрана.

Растеризация (rasterization) превращает эти команды в пиксели для частей слоёв. Работа может выполняться на отдельных потоках и использовать GPU, но это не делает дорогой paint бесплатным. Большая перерисовываемая область, размытие, сложные тени и фильтры увеличивают стоимость.

## Слои и composite

Для некоторых элементов браузер создаёт отдельные композитные слои (composited layers). Этап composite размещает подготовленные слои, применяет к ним `transform` и `opacity` и собирает итоговую поверхность.

Поэтому анимация `transform` или `opacity` часто не требует нового layout и paint:

```css
.panel {
  transform: translateX(20px);
  opacity: 0.8;
}
```

Но отдельный слой не гарантирован. Решение о выделении слоя принимает браузер с учётом свойства, анимации, перекрытия элементов и доступных ресурсов. Слишком много слоёв расходует видеопамять, увеличивает объём растеризации и стоимость компоновки.

`will-change` является подсказкой, а не приказом. Его применяют точечно незадолго до изменения и убирают после него, если постоянный слой не нужен.

## Какие этапы обычно затрагиваются

| Изменение | Возможный путь |
| --- | --- |
| Размер или положение в потоке документа | style → layout → paint → composite |
| `color`, `background`, `box-shadow` | style → paint → composite |
| `transform`, `opacity` у композитного слоя | style → composite |
| Добавление большого DOM-поддерева | style → layout → paint → composite |

Таблица показывает распространённую модель, а не API-контракт. Реальный путь проверяют на панели Performance в DevTools: движок может оптимизировать изменение или, наоборот, затронуть большую область.

## Анимация и бюджет кадра

При частоте экрана 60 Гц новый кадр появляется примерно каждые 16,7 мс; на 120 Гц времени вдвое меньше. В этот интервал входят не только JavaScript, но и расчёт стилей, layout, paint и composite.

`requestAnimationFrame` запускает callback-функцию перед подготовкой следующего кадра, но не делает её быстрой автоматически. Тяжёлый JavaScript или layout внутри callback всё равно задержит кадр.

Для частого визуального движения обычно выбирают `transform`, избегают измерений после каждой записи и уменьшают область обновления. Для длинных списков основное улучшение часто даёт виртуализация — рендеринг только видимой части списка, а не микроправка CSS.

## Изоляция стоимости

CSS-свойство `contain` позволяет ограничить влияние элемента на layout, paint или расчёт размера. `content-visibility: auto` позволяет пропускать рендеринг невидимого содержимого. Эти свойства требуют проверки: неправильный `contain` меняет контекст раскладки, а неточная оценка внутреннего размера влияет на прокрутку.

Оптимизация начинается с измерения. Панель Performance показывает пересчёт стилей, layout, paint, растеризацию и composite; инструменты Rendering позволяют подсветить перерисованные области и границы слоёв.

## Ключевые уточнения

- Reflow — распространённое название повторного layout, а не отдельный браузерный API.
- Paint создаёт команды рисования, растеризация превращает их в пиксели, а composite собирает слои в кадр.
- `transform` и `opacity` обходят layout и paint только тогда, когда движок может обработать изменение на подходящем композитном слое.
- Чтение геометрии после изменения DOM способно принудительно запустить накопленный пересчёт layout.
- `will-change` и дополнительные слои расходуют память, а фактический путь изменения проверяется в DevTools.
