## Быстрый ответ

Пагинация (pagination), фильтрация (filtering) и сортировка (sorting) образуют единый контракт получения коллекции. Клиент передаёт размер и позицию страницы, фильтры и порядок; сервер применяет их к доступным пользователю данным и возвращает элементы вместе с метаданными продолжения.

Пагинация по смещению (offset pagination) проста и позволяет перейти к номеру страницы, но большое смещение может быть дорогим, а вставки и удаления между запросами создают дубли или пропуски. Пагинация по курсору (cursor pagination) кодирует позицию в стабильной сортировке и лучше подходит для бесконечной ленты, но не даёт произвольного перехода на страницу и не гарантирует неизменный снимок данных.

Для корректности нужен детерминированный порядок. Если `createdAt` не уникален, добавляют дополнительный критерий (tie-breaker), например `createdAt DESC, id DESC`. Все параметры, меняющие результат, входят в ключ запроса (query key) frontend-кеша; при их изменении текущая последовательность страниц сбрасывается.

## Контракт коллекции

```text
request:
  pagination + filters + search + sorting

response:
  items + next position + optional total/hasMore
```

API явно определяет:

- максимальный `limit` и значение по умолчанию;
- доступные поля и операторы фильтрации;
- допустимые поля и направление сортировки;
- порядок по умолчанию и tie-breaker;
- формат pagination и метаданных ответа;
- поведение для невалидного или устаревшего cursor;
- согласованность данных при параллельных изменениях.

Сервер применяет фильтрацию после проверки прав. Загрузка всех записей в браузер с последующим «скрытием» чужих данных не является контролем доступа.

## Offset и page pagination

```http
GET /users?offset=40&limit=20&sort=-createdAt,-id
```

или:

```http
GET /users?page=3&pageSize=20&sort=-createdAt,-id
```

Page обычно является удобной производной от offset: `(page - 1) * pageSize`. Подход подходит таблицам с номерами страниц, прямым переходом и относительно стабильным набором данных.

```json
{
  "items": [{ "id": "u_41", "name": "Ann" }],
  "page": 3,
  "pageSize": 20,
  "total": 143
}
```

Между запросами может появиться новый элемент в начале. Тогда прежний последний элемент первой страницы сдвинется на вторую и пользователь увидит его повторно. Удаление создаёт обратный эффект — запись может быть пропущена.

Высокий offset также способен заставить базу данных найти и отбросить много предыдущих строк. Точная стоимость зависит от запроса, индексов и СУБД, поэтому правило «offset всегда медленный» неверно, но масштаб нужно измерять.

## Cursor pagination

```http
GET /feed?limit=20&after=eyJjcmVhdGVkQXQiOiIuLi4iLCJpZCI6NzN9
```

Cursor представляет позицию в порядке выборки. Для сортировки `createdAt DESC, id DESC` сервер может логически продолжить запрос условием «меньше последней пары `createdAt`, `id`».

```json
{
  "items": [{ "id": "p_72", "createdAt": "2026-07-20T12:00:00Z" }],
  "pageInfo": {
    "hasNextPage": true,
    "endCursor": "eyJjcmVhdGVkQXQiOiIuLi4iLCJpZCI6NzJ9"
  }
}
```

Cursor является opaque value: клиент хранит и возвращает его без разбора. Backend может изменить внутреннее кодирование, подписать cursor от подмены или включить туда сортировку и версию фильтров.

Cursor pagination уменьшает сдвиги от вставок перед уже просмотренной позицией, но не создаёт автоматически консистентный snapshot. Обновление sort field, удаление записи или смена прав всё равно влияет на следующие страницы. Если требуется снимок на конкретный момент, API добавляет snapshot ID, timestamp или другой механизм согласованности.

## Стабильная сортировка

Порядок должен однозначно определять положение каждой записи:

```text
createdAt DESC, id DESC
```

`id` здесь является tie-breaker — дополнительным уникальным критерием для записей с одинаковым `createdAt`. Backend должен применять тот же порядок при создании cursor и следующем запросе.

Сортируемые поля ограничивают allowlist. Строка пользователя не подставляется напрямую в SQL. API нормализует направление и возвращает `400` для неподдерживаемого поля.

## Фильтры и поиск

Формат параметров является частью контракта:

```text
status=active
createdFrom=2026-01-01
tags=react&tags=typescript
sort=-createdAt,-id
```

Нужно определить разницу между отсутствующим параметром, пустой строкой и явным `null`. Для дат фиксируют timezone и включительность границ. Для массивов выбирают один способ сериализации и отражают его в OpenAPI.

Debounce уменьшает число запросов поиска, но не решает race condition. Старый ответ может прийти после нового. `AbortController` прекращает ожидание на клиенте и по возможности сетевую работу, а query library или request ID не позволяют устаревшему результату заменить актуальный.

Серверный поиск обычно имеет минимальную длину, нормализацию, ограничение сложности и отдельный rate limit. Иначе короткий ввод пользователя способен запустить дорогую полнотекстовую операцию на каждый символ.

## Состояние frontend

Query key включает все параметры, определяющие результат:

```ts
const usersQueryKey = [
  "users",
  {
    page,
    pageSize,
    search,
    status,
    sort,
  },
];
```

Объекты параметров сериализуют стабильно в соответствии с правилами query library. Два логически одинаковых набора filters не должны случайно создавать разные cache entries из-за порядка ключей или значений по умолчанию.

При изменении search, filters или sort:

1. отменяют или логически устаревают предыдущий запрос;
2. сбрасывают page или cursor;
3. сохраняют прежние данные только если это осознанный UX;
4. запрашивают новую первую страницу;
5. обновляют URL, если состояние должно пережить reload и быть доступным по ссылке.

Для infinite scroll различают первоначальную загрузку, дозагрузку, исчерпание страниц и ошибку следующей страницы. Новые элементы объединяют по устойчивому ID, чтобы повтор на границе не создал дубль. При этом бездумная дедупликация не должна скрывать серверную ошибку порядка.

## `total`, `hasMore` и доступность

Точный `total` нужен UI с номерами страниц, но его вычисление может быть дорогим или быстро устаревать. Infinite scroll часто достаточно `hasNextPage` и `endCursor`. API может возвращать приблизительное количество, если явно обозначает его семантику.

Кнопка «Загрузить ещё» часто доступнее бесконечной автоматической подгрузки: пользователь управляет изменением списка, а keyboard focus не теряется. Если используется IntersectionObserver, UI всё равно сообщает загрузку, ошибку и конец списка вспомогательным технологиям.

## Ключевые уточнения

- Offset позволяет перейти к номеру страницы, а cursor продолжает стабильную сортировку; выбор следует из UX и характера данных.
- Cursor уменьшает часть дублей и пропусков, но без snapshot-механизма не замораживает изменяемую коллекцию.
- Tie-breaker делает положение записи однозначным и должен участвовать и в сортировке, и в cursor.
- Debounce сокращает запросы, а защита от race condition определяет, какой ответ имеет право обновить UI.
- `total`, filters, sort и pagination являются частью API-контракта и cache key, а не только деталями компонента таблицы.
