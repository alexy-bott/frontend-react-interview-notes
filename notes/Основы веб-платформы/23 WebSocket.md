## Быстрый ответ

WebSocket — сетевой протокол и браузерный API для постоянного двустороннего обмена сообщениями между клиентом и сервером. После установки соединения (handshake) обе стороны могут независимо отправлять текстовые или бинарные сообщения без отдельной пары HTTP-запрос/ответ для каждого сообщения.

Он подходит для чата, совместного редактирования, multiplayer и других сценариев с частым обменом и низкой задержкой. Для обычного CRUD проще HTTP, а для однонаправленного потока сервер → клиент часто достаточно SSE.

WebSocket предоставляет канал, но не готовый прикладной протокол. Приложение само определяет аутентификацию, схему и проверку сообщений, подтверждения, проверку активности соединения (heartbeat), управление перегрузкой потока (backpressure), повторное подключение, восстановление подписок и совместимость версий.

## От HTTP handshake к постоянному каналу

Классическое соединение начинается с HTTP/1.1 handshake — обмена запросом и ответом для согласования протокола:

```http
GET /socket HTTP/1.1
Host: app.example.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: ...
Sec-WebSocket-Version: 13
Origin: https://app.example.com
```

При согласии сервер отвечает `101 Switching Protocols`, после чего стороны обмениваются WebSocket frames по тому же транспортному соединению. Современная инфраструктура может согласовать WebSocket и через механизм HTTP/2, но браузерный API остаётся тем же; приложение не должно строить бизнес-логику на конкретном варианте handshake.

URL `wss://` означает WebSocket поверх TLS и является аналогом HTTPS. На публичном сайте используют `wss://`: он шифрует трафик и проверяет сертификат сервера, но не подтверждает полномочия пользователя внутри приложения.

## Frames, сообщения и порядок

Протокол делит сообщения на кадры (frames) и умеет фрагментировать большое сообщение. Браузерное событие `message` отдаёт уже собранное текстовое или бинарное сообщение, поэтому прикладному коду обычно не нужно работать с frames.

Внутри одного живого соединения сообщения доставляются в порядке транспортного потока. Но WebSocket не хранит историю и не восстанавливает сообщения после разрыва. Если соединение оборвалось, прикладной протокол должен определить:

- какое сообщение было последним обработанным;
- потеряно ли подтверждение уже выполненной команды;
- какие subscriptions нужно открыть повторно;
- нужен ли новый снимок состояния вместо продолжения по курсору.

Поэтому упорядоченный транспорт не гарантирует однократное выполнение бизнес-операции.

## Browser API

```ts
const socket = new WebSocket("wss://app.example.com/socket", ["orders.v2"]);

socket.addEventListener("open", () => {
  socket.send(JSON.stringify({
    type: "orders.subscribe",
    requestId: crypto.randomUUID(),
  }));
});

socket.addEventListener("message", (event) => {
  const message = parseServerMessage(event.data);
  applyServerMessage(message);
});

socket.addEventListener("close", (event) => {
  handleDisconnect({ code: event.code, reason: event.reason });
});

socket.addEventListener("error", () => {
  // Browser намеренно не раскрывает все сетевые детали ошибки.
});
```

Конструктор принимает URL и необязательные подпротоколы. Он не позволяет приложению добавить произвольный HTTP-заголовок, например `Authorization`. `binaryType` определяет, получить бинарное сообщение как `Blob` или `ArrayBuffer`.

Событие `error` обычно не содержит причины, достаточной для диагностики. Полезные данные получают из кода закрытия, клиентской телеметрии и серверных логов, не записывая токен или сообщение с чувствительными данными.

## Прикладной протокол сообщений

JSON удобен для читаемости и эволюции schema, binary format — для размера и скорости. Выбор формата не отменяет versioning и validation.

```ts
type ClientMessage =
  | { type: "orders.subscribe"; requestId: string; after?: number }
  | { type: "order.cancel"; requestId: string; orderId: string };

type ServerMessage =
  | { type: "order.updated"; eventId: string; revision: number; payload: unknown }
  | { type: "command.accepted"; requestId: string }
  | { type: "command.rejected"; requestId: string; code: string };
```

TypeScript описывает данные после успешного разбора, но не проверяет сетевой ввод. На границе нужна runtime-схема или parser. Неизвестный `type`, слишком большой payload и несовместимую `version` обрабатывают явно, а не передают дальше в хранилище.

Подпротокол (`Sec-WebSocket-Protocol`) позволяет сторонам согласовать прикладной протокол из списка, предложенного клиентом. Его можно использовать для имени или версии протокола, но не стоит маскировать под него произвольный секрет без анализа утечек и инфраструктуры.

## Authentication и authorization

В браузере доступны несколько моделей:

- session cookie, автоматически подходящая handshake-запросу;
- короткоживущий одноразовый ticket в URL;
- аутентификация первым прикладным сообщением после открытия;
- согласованный framework-specific механизм через subprotocol.

Долгоживущий bearer token в query string рискован: URL может попасть в логи, monitoring и диагностические traces. Одноразовый ticket снижает этот риск, если быстро истекает и не может использоваться повторно.

При аутентификации через cookie сервер обязательно проверяет точный `Origin`. Браузер позволяет чужой странице вызвать `new WebSocket()` к вашему серверу, а CORS preflight для handshake не выполняется. Без проверки Origin и защиты протокола возможен Cross-Site WebSocket Hijacking: чужой site использует cookie жертвы.

Аутентификации при открытии недостаточно. Сервер проверяет авторизацию для каждой подписки и команды, потому что роль, владелец ресурса и сессия могут измениться во время соединения.

## Heartbeat и полумёртвое соединение

Протокол WebSocket содержит управляющие ping/pong frames, но JavaScript в браузере не предоставляет API для отправки protocol-level ping. Серверные библиотеки часто отправляют такой ping и проверяют pong автоматически.

Если приложению нужен собственный сигнал активности, вводят сообщения `ping`/`pong` или периодическое событие сервера. Heartbeat помогает обнаружить фактически потерянное соединение, которое ещё не получило `close` из-за NAT, proxy или внезапного отключения сети.

Интервал выбирают с учётом батареи мобильного устройства, proxy idle timeout и масштаба. Слишком частый heartbeat сам становится нагрузкой. Браузерная вкладка в фоне может сильно задерживать JavaScript timers, поэтому отсутствие прикладного pong не всегда означает одинаковую причину.

## Reconnect и восстановление

Закрытие может быть штатным, временным или окончательным. Например, code `1000` означает нормальное закрытие, а приложение может использовать документированный private range для причин вроде истекшей сессии. Неизвестное или аварийное закрытие не следует бесконечно повторять с фиксированной задержкой.

Повторное подключение использует exponential backoff, jitter и верхний предел задержки. После открытия клиент заново проходит аутентификацию, отправляет подписки и курсор последнего подтверждённого события. Сервер либо продолжает поток, либо сообщает, что нужен новый снимок состояния.

При logout, navigation или намеренном закрытии клиент отменяет запланированное повторное подключение. Иначе старый connection manager способен снова открыть соединение уже после выхода пользователя.

## Backpressure

Стабильный API `WebSocket` не предоставляет полноценный backpressure для входящих сообщений. Если сервер отправляет их быстрее, чем клиент обрабатывает события `message`, растут очередь и потребление памяти.

Для исходящих данных `socket.bufferedAmount` показывает число bytes, поставленных в очередь, но ещё не переданных сети:

```ts
const MAX_BUFFERED_BYTES = 1_000_000;

function sendDroppableUpdate(payload: string) {
  if (socket.readyState !== WebSocket.OPEN) return false;
  if (socket.bufferedAmount > MAX_BUFFERED_BYTES) return false;

  socket.send(payload);
  return true;
}
```

Это не универсальная защита. Нельзя просто отбросить платёжную команду или подтверждение. Для каждого типа сообщения определяют: поставить его в ограниченную очередь, объединить с новым значением, отказаться от операции или переподключиться и восстановить снимок состояния.

`WebSocketStream` использует Streams API и backpressure, но имеет ограниченную совместимость с браузерами. Его нельзя считать прямой заменой базового `WebSocket` без проверки целевых браузеров. Для более сложной транспортной семантики существует WebTransport, но это другой протокол/API и отдельное архитектурное решение.

## Масштабирование сервера

Каждое соединение живёт на конкретном экземпляре сервера. Если подписки и presence хранятся только в его памяти, load balancer должен сохранять routing или система должна вынести события и состояние в общий broker.

Типичная схема:

```text
клиенты
  -> load balancer
  -> WebSocket gateways
  <-> pub/sub or stream broker
  <-> application services
```

Sticky sessions упрощают routing, но не решают restart, deployment и broadcast между экземплярами. Нужны постепенное закрытие соединений перед остановкой server instance (connection draining), лимиты на подписки и сообщения, защита от медленных клиентов и стратегия массового reconnect после сбоя.

## Ключевые уточнения

- WebSocket — постоянный двусторонний транспорт; он не является базой данных, историей событий или готовым message broker.
- Порядок сообщений в одном соединении не даёт exactly-once semantics после повторного подключения.
- Browser constructor не принимает произвольные headers; authentication проектируют с учётом этой границы.
- При аутентификации через cookie сервер проверяет `Origin` и авторизацию каждого действия.
- Native ping/pong существует на уровне протокола, но JavaScript в браузере не отправляет ping frame напрямую.
- `bufferedAmount` помогает наблюдать исходящую очередь, но входной backpressure в классическом API отсутствует.

## Когда выбрать другой подход

- HTTP — CRUD, cacheable resources, file upload/download и редкие updates.
- SSE — уведомления, логи и прогресс в направлении сервер → клиент без активного двустороннего протокола.
- Polling — простое редкое обновление, когда несколько секунд задержки приемлемы.
- WebRTC data channel — peer-to-peer media/data сценарий с иной topology.
- WebTransport — когда нужны streams/datagrams и более низкоуровневые транспортные возможности при доступной инфраструктуре и поддержке браузеров.
