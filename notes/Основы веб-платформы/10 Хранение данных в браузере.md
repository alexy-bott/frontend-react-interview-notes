# Хранение данных в браузере

## Быстрый ответ

Браузер предоставляет хранилища с разными контрактами. Cookie нужна, когда небольшое значение должно участвовать в HTTP-запросах. `localStorage` и `sessionStorage` дают простой синхронный API «ключ — значение» для строк. IndexedDB хранит большие структурированные данные асинхронно. Cache Storage хранит пары `Request`/`Response`, а OPFS подходит для локальных файлов приложения.

Выбор начинается с владельца и жизненного цикла: должен ли сервер автоматически получать значение, переживает ли оно закрытие вкладки, нужен ли поиск по структуре, допустима ли потеря локальной копии и сколько данных ожидается.

Данные, доступные JavaScript того же origin, доступны и вредоносному скрипту при XSS. Поэтому браузерные хранилища не считают хранилищем секретов. `HttpOnly` cookie нельзя прочитать из JavaScript, но XSS всё ещё может выполнять действия от имени текущей сессии.

## Сравнение механизмов

| Механизм | Модель | Подходящие данные | Главные ограничения |
| --- | --- | --- | --- |
| Cookie | небольшая строка, автоматически участвует в HTTP | session ID, серверные flags | лимиты размера, сетевой overhead, CSRF и attributes |
| `localStorage` | синхронный `string -> string` на origin | theme, компактные несекретные настройки | блокирует main thread, нет транзакций и структурных queries |
| `sessionStorage` | Web Storage на origin и вкладку | временный draft, шаг локального flow | исчезает с browsing session, не общий между вкладками |
| IndexedDB | асинхронная transactional object database | offline entities, drafts, queues, blobs | schema/version migrations и более сложный API |
| Cache Storage | `Request -> Response` | offline resources и сетевые responses | invalidation и versioning проектирует приложение |
| OPFS | приватная файловая система origin | большие локальные файлы, задачи редакторов и локальных баз данных | поддержка браузеров, квота и собственный формат данных |
| `history.state` | состояние конкретной history entry | параметры UI при back/forward navigation | не долговременная база и зависит от истории вкладки |

React state и Redux store не являются постоянным браузерным хранилищем. Они живут в памяти JavaScript и обычно исчезают при перезагрузке, если приложение отдельно не сохраняет их между запусками.

## Cookie

Cookie хранит небольшое значение вместе с атрибутами, определяющими domain, path, срок и условия отправки. Браузер автоматически добавляет подходящие cookie к HTTP-запросу, поэтому они полезны для идентификатора сессии и состояния, которое должен читать сервер.

Цена — cookie отправляется с каждым подходящим запросом, даже если конкретному endpoint значение не нужно. Большие cookie увеличивают заголовки запроса и могут упереться в лимиты браузера или сервера.

`HttpOnly` делает cookie недоступной `document.cookie`, `Secure` ограничивает HTTPS, а `SameSite` управляет cross-site отправкой. Эти attributes влияют на безопасность и подробно разобраны в [Cookies и авторизация](<./11 Cookie и авторизация.md>).

## Web Storage

`localStorage` сохраняет строки для origin между browsing sessions:

```js
const SETTINGS_KEY = "settings:v2";

function saveSettings(settings) {
  localStorage.setItem(SETTINGS_KEY, JSON.stringify(settings));
}

function readSettings() {
  const rawValue = localStorage.getItem(SETTINGS_KEY);

  if (rawValue === null) {
    return null;
  }

  try {
    return JSON.parse(rawValue);
  } catch {
    localStorage.removeItem(SETTINGS_KEY);
    return null;
  }
}
```

Версия в key помогает отделить несовместимые форматы. `JSON.parse` всё равно возвращает непроверенные данные: schema старой версии или ручное изменение DevTools может нарушить ожидаемую форму, поэтому важную структуру валидируют.

API синхронный. Большая сериализация и запись выполняются на main thread, поэтому `localStorage` не подходит для частого persistence большого editor state.

`sessionStorage` имеет тот же строковый API, но разделяется по origin и top-level browsing context. Перезагрузка обычно сохраняет данные текущей вкладки, закрытие вкладки завершает сессию. Новая вкладка не должна использоваться как надёжный общий канал состояния; для обмена существуют `BroadcastChannel` и другие механизмы.

Событие `storage` уведомляет другие документы того же origin об изменении Web Storage. Документ, который выполнил `setItem`, не получает это событие для самого себя.

## IndexedDB

IndexedDB хранит JavaScript-compatible structured values через structured clone, поддерживает object stores, keys, indexes и transactions. API асинхронный и не блокирует main thread ожиданием диска.

Подходящие сценарии:

- offline-копии сущностей;
- локальные drafts и autosave;
- очередь операций до восстановления сети;
- большие collections с поиском по index;
- `Blob` и file metadata;
- кэш результата дорогого преобразования.

Версия базы открывается через `indexedDB.open(name, version)`. Изменение object stores и indexes выполняют в upgrade transaction. Миграция должна переживать старую вкладку, ошибку записи и данные от предыдущей версии приложения.

Несколько операций, которые должны примениться вместе, помещают в одну транзакцию. Ожидание произвольной сети внутри неё ненадёжно: транзакция может стать неактивной, пока event loop ждёт внешнюю работу. Сначала получают сетевые данные, затем открывают короткую локальную транзакцию.

## Cache Storage

Cache Storage хранит объекты `Request` и `Response`:

```js
const cache = await caches.open("static-v3");

await cache.add("/offline.html");

const response = await cache.match("/offline.html");
```

Cache API доступен из Service Worker и некоторых window/worker contexts. Service Worker делает его особенно полезным, потому что может перехватить `fetch` и выбрать network-first, cache-first или другую стратегию.

Cache Storage не соблюдает жизненный цикл HTTP-кеша автоматически. Приложение решает, когда добавить ответ, какое имя версии использовать и когда удалить старую запись. При этом сам `fetch`, результат которого кладётся в Cache Storage, может дополнительно использовать HTTP-кеш.

`Response` следует проверять перед сохранением: status, тип CORS-ответа, целостность и допустимость персональных данных. Неограниченный runtime-кеш способен занять квоту и долго хранить устаревшую информацию.

## OPFS

Origin Private File System является приватной для origin файловой системой в рамках File System API. Она полезна для больших локальных файлов, медиаредактора, SQLite/Wasm и задач, где object model IndexedDB менее удобна.

Пользователь не выбирает обычный файл на диске, а браузер управляет приватным пространством origin. OPFS не заменяет резервную копию и синхронизацию: очистка site data или eviction способна удалить локальные данные.

Поддержку и доступные sync APIs проверяют для целевых браузеров. Синхронные file handles предназначены для dedicated worker, чтобы не блокировать UI thread.

## Quota, eviction и persistence

Объём и правила очистки зависят от браузера, устройства, свободного диска, origin и режима просмотра. Значение quota не фиксируют одним числом в архитектуре.

```js
const estimate = await navigator.storage.estimate();

console.log({
  usage: estimate.usage,
  quota: estimate.quota,
});
```

По умолчанию данные часто хранятся в режиме без гарантии сохранности (best effort) и могут быть удалены при нехватке места. `navigator.storage.persist()` запрашивает постоянное хранилище, которое браузер очищает только при более явном действии пользователя, но запрос не обязан быть одобрен.

Приватный режим, настройки блокировки и partitioning могут менять доступность и время жизни данных. Любая операция с хранилищем способна завершиться ошибкой, поэтому приложение имеет запасной сценарий и не теряет критичные серверные данные из-за одной локальной записи.

## Безопасность и целостность

Хранилище разделяется по origin, но Same-Origin Policy не защищает от XSS внутри доверенного origin. Вредоносный скрипт может прочитать `localStorage`, IndexedDB и Cache Storage, изменить закешированный ответ или отправить данные наружу.

Локальное шифрование ключом, который тот же JavaScript получает автоматически, мало помогает против активного XSS: атакующий может украсть ключ или вызвать функцию расшифровки. Оно может защищать другой threat scenario, например экспорт файла, но не должно называться защитой от кода внутри origin без отдельной модели ключей.

На logout удаляют пользовательские query caches, IndexedDB records и Cache Storage entries, которые не должны перейти следующему пользователю на общем устройстве. Service Worker и вкладки координируют очистку, чтобы одна старая вкладка не записала данные обратно.

## Как выбрать

1. Данные должен автоматически получать сервер — cookie.
2. Небольшая несекретная настройка читается редко — Web Storage.
3. Нужны structured data, indexes, transactions или offline queue — IndexedDB.
4. Нужны сохранённые HTTP responses и offline fetch strategy — Cache Storage.
5. Нужна файловая модель или большой binary workload — OPFS после проверки поддержки.
6. Сервер является источником истины — любое локальное хранилище считается cache и имеет стратегию восстановления.

## Ключевые уточнения

- Web Storage синхронный и строковый, а IndexedDB асинхронный, структурированный и транзакционный.
- Cache Storage программно хранит `Request`/`Response` и не является тем же механизмом, что HTTP-кеш браузера.
- Данные одного origin доступны его JavaScript, поэтому XSS рассматривается как компрометация доступных скрипту хранилищ.
- Quota и eviction зависят от среды; локальная копия не становится гарантированно вечной базой.
- Механизм выбирают по владельцу, размеру, доступу и lifetime данных, а не по привычке сохранять всё в `localStorage`.
