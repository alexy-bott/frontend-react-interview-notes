## Быстрый ответ

Service Worker — событийный скрипт, который браузер запускает отдельно от страницы для определённого origin и области действия (scope). Он может перехватывать запросы контролируемой страницы, возвращать ответы из Cache Storage или сети, принимать push и выполнять некоторые фоновые события. Доступа к DOM у него нет.

PWA (Progressive Web App, прогрессивное веб-приложение) — веб-приложение, которое постепенно добавляет возможности, характерные для платформенных приложений: установку, отдельное окно, offline-сценарии, push и интеграцию с операционной системой. Web App Manifest описывает установленное приложение; Service Worker часто обеспечивает offline- и фоновое поведение, но это разные технологии.

Главная сложность Service Worker — не регистрация, а жизненный цикл и обновление. Старый worker может продолжать контролировать открытые вкладки, новый — ждать активации, а Cache Storage — содержать ресурсы нескольких версий. Непродуманное обновление создаёт несовместимую смесь старого HTML, нового JavaScript и удалённых chunks.

## Service Worker и другие workers

| Механизм | Основная задача | Жизненный цикл |
| --- | --- | --- |
| Web Worker | вычисления для страницы | обычно живёт вместе с создавшей его страницей или worker |
| Shared Worker | общий контекст выполнения для нескольких same-origin pages | живёт, пока есть подключённые контексты |
| Service Worker | сетевой proxy, offline, push и фоновые события для scope | событийный; браузер запускает и останавливает независимо от страниц |

Service Worker не является постоянным фоновым процессом. Браузер может завершить его между событиями и позже запустить снова. Поэтому нельзя хранить критичное состояние только в глобальных переменных; устойчивые данные размещают в Cache Storage или IndexedDB.

## Регистрация и scope

Страница регистрирует worker:

```ts
if ("serviceWorker" in navigator) {
  window.addEventListener("load", async () => {
    const registration = await navigator.serviceWorker.register("/sw.js", {
      scope: "/",
    });

    console.log(registration.scope);
  });
}
```

Service Worker доступен только в безопасном контексте (secure context): в production это HTTPS, а `localhost` разрешён для разработки. TLS нужен потому, что worker способен изменять сетевые ответы и сохраняется между переходами; подмена его по HTTP дала бы атакующему долгоживущий контроль над приложением.

Scope определяет URL клиентов, которые worker может контролировать. По умолчанию область связана с директорией скрипта worker: `/assets/sw.js` не должен неожиданно управлять всем origin. Обычно скрипт размещают ближе к корню приложения и задают scope осознанно.

Успешная регистрация ещё не означает, что текущая открытая страница уже контролируется. Первый worker обычно начнёт контролировать её после следующей navigation; `clients.claim()` может изменить этот момент, но требует совместимой стратегии ответов.

## Lifecycle: install → waiting → activate

```text
register/download
  -> install
  -> waiting, пока старый worker контролирует клиентов
  -> activate
  -> контролирует страницы в scope
  -> браузер отправляет fetch/push/message events
```

В `install` подготавливают ресурсы, обязательные для новой версии. `event.waitUntil(promise)` сообщает браузеру, что установка не завершена до выполнения promise. Если обязательное предварительное кеширование завершилось ошибкой и promise был отклонён, новый worker не активируется с неполным набором.

После `install` новая версия обычно переходит в `waiting`, пока открытые клиенты остаются под старой. Это сохраняет согласованность: одна страница не меняет сетевой controller посередине работы.

В `activate` удаляют только кеши, которыми действительно владеет приложение и которые несовместимы с новой версией. Cache Storage общий для origin, поэтому нельзя удалять всё подряд через `caches.keys()` без проверки префикса и владельца.

Worker не должен полагаться на переход строго с предыдущей версии: пользователь мог долго не открывать приложение и обновиться через несколько releases.

## `skipWaiting()` и `clients.claim()`

`self.skipWaiting()` разрешает новому worker не ждать закрытия старых клиентов. `clients.claim()` позволяет после активации начать контролировать уже открытые подходящие страницы.

Это не «правильные флаги для быстрого обновления». Они могут создать смешение версий:

```text
страница уже выполняет app-v1.js
  -> внезапно активируется service-worker-v2
  -> предположения API и кеша относятся к app-v2
  -> текущая страница получает несовместимый ответ
```

Их используют, только если протокол между страницей и worker обратно совместим либо приложение координирует перезагрузку. Частая стратегия: сообщить странице о waiting worker, показать «Доступна новая версия», по подтверждению активировать worker и перезагрузить все связанные вкладки.

## Событие `fetch`

Активный worker получает запросы контролируемых клиентов, включая navigation, скрипты, стили, изображения и явный `fetch`. `respondWith()` выбирает ответ:

```js
self.addEventListener("fetch", (event) => {
  const request = event.request;

  if (request.method !== "GET") return;

  if (request.destination === "image") {
    event.respondWith(cacheFirst(request));
  }
});

async function cacheFirst(request) {
  const cached = await caches.match(request);
  if (cached) return cached;

  const response = await fetch(request);

  if (response.ok) {
    const cache = await caches.open("shop-images-v3");
    await cache.put(request, response.clone());
  }

  return response;
}
```

Body объекта `Response` является потоком, который обычно нельзя прочитать дважды, поэтому для одновременного возврата и кеширования используют `response.clone()`.

Не нужно перехватывать каждый запрос. Если обработчик не вызывает `respondWith`, браузер использует обычный сетевой путь. Чем уже явные правила, тем проще избежать скрытых ошибок кеширования.

## Cache Storage и HTTP-кеш

Cache Storage — управляемое скриптом хранилище пар `Request`/`Response`. Приложение само решает, когда записывать, читать и удалять entries. HTTP-кеш управляется браузером по `Cache-Control`, validators и другим правилам HTTP.

Эти уровни могут работать одновременно:

```text
запрос страницы
  -> Service Worker logic / Cache Storage
  -> fetch(request)
  -> HTTP-кеш браузера
  -> сеть/CDN/сервер
```

Запись в Cache Storage не получает автоматический срок годности из `Cache-Control` как полноценную стратегию приложения. Worker должен определить версию, срок хранения и повторную проверку. И наоборот, `fetch()` внутри worker может использовать HTTP-кеш согласно `Request.cache` и HTTP-заголовкам.

Cache Storage хранится в хранилище origin, имеет квоту и может быть очищен браузером. Это слой производительности и offline-работы, а не база данных с гарантированной долговечностью.

## Стратегии caching

| Стратегия | Поведение | Подходящие данные |
| --- | --- | --- |
| Cache only | ответ только из Cache Storage | гарантированно заранее закешированные неизменяемые ресурсы |
| Cache first | кеш, при промахе — сеть и запись | статические assets с хешем в имени, изображения с допустимой устарелостью |
| Network first | сеть, при ошибке — кеш | navigation/document и данные, где свежесть важнее скорости |
| Stale-while-revalidate | сразу кеш, параллельно сетевое обновление | контент, где кратковременно допустим устаревший ответ |
| Network only | всегда сеть | критичные операции и запросы, которые нельзя обслужить устаревшими данными |

Стратегию выбирают для класса запросов, а не для всего приложения. `POST`, платежи, authentication и персональные ответы API нельзя бездумно пропускать через общий обработчик cache-first.

`stale-while-revalidate` ускоряет чтение, но пользователь сначала видит старые данные. Если это цена или permission, такая семантика может быть неприемлемой.

## Offline model

Offline не означает «закешировать всё». Нужно определить поведение каждого пользовательского действия:

- что доступно только для чтения;
- какие данные были получены именно этим пользователем;
- можно ли создать локальную mutation и отправить позже;
- как разрешаются конфликты после reconnect;
- как пользователь видит stale/offline status;
- какие данные удаляются при logout.

Для отложенных mutations нужны стабильный operation ID, идемпотентность на сервере и постоянный outbox, обычно в IndexedDB. Иначе повтор после неясного сетевого сбоя может создать дубликат.

Background Sync может попросить Service Worker повторить работу после восстановления сети, но API имеет ограниченную поддержку браузеров. Основной сценарий должен иметь запасной вариант: отправку outbox при следующем открытии или focus приложения.

## Обновление приложения и chunks

Типичный deployment выпускает:

```text
index.html
assets/app.ABC123.js
assets/chunk.XYZ789.js
```

После нового релиза HTML ссылается на новые assets с хешем в имени. Но часть пользователей остаётся со старой страницей или закешированным HTML и позже запрашивает старый lazy chunk. Если deployment сразу удалил этот файл с CDN, динамический `import` завершается ошибкой.

Надёжная стратегия сочетает:

- `no-cache` или короткую политику повторной проверки для HTML;
- долгий immutable HTTP-кеш для assets с хешем в имени;
- хранение assets нескольких releases на CDN в течение окна обновления;
- versioned Cache Storage names;
- явный сценарий обновления для waiting worker;
- обработку chunk-load failure с ограниченным reload, а не бесконечным циклом;
- проверку совместимости разных версий страницы, worker и API.

Service Worker способен и исправить, и усугубить эту проблему. Он должен возвращать HTML и assets согласованной версии либо безопасно переводить клиента на новый релиз.

## PWA и Web App Manifest

Web App Manifest — JSON metadata для установленного опыта:

```json
{
  "id": "/",
  "name": "Orders",
  "short_name": "Orders",
  "start_url": "/",
  "display": "standalone",
  "theme_color": "#ffffff",
  "background_color": "#ffffff",
  "icons": [
    { "src": "/icons/192.png", "sizes": "192x192", "type": "image/png" },
    { "src": "/icons/512.png", "sizes": "512x512", "type": "image/png" }
  ]
}
```

Manifest сообщает браузеру имя, icons, стартовый URL, идентификатор приложения и желаемый display mode. Он не кеширует assets и не создаёт offline-поведение.

Точные критерии установки и UI различаются между браузерами и платформами. Manifest и HTTPS являются общей основой; Service Worker часто добавляет offline-возможности, но не является универсальным техническим требованием установки во всех современных браузерах. `beforeinstallprompt` также не является кроссбраузерным стандартом, поэтому собственная кнопка установки должна быть progressive enhancement.

PWA остаётся обычным сайтом для браузера, который не поддерживает установку или конкретную возможность. Routing, deep links, accessibility и responsive layout должны работать без зависимости от install prompt.

## Push и notifications

Push-событие может запустить Service Worker, когда страница не открыта. Разрешение на уведомления запрашивают после понятного действия пользователя и объяснения ценности, а не сразу при первом посещении.

Payload push-сообщения и клик по уведомлению обрабатывают как внешние данные. Нельзя помещать секреты в уведомление: lock screen и история ОС могут быть видны другим людям. Обработчик клика проверяет и нормализует целевой URL, после чего фокусирует существующий клиент либо открывает новый.

Поддержка браузеров и платформ, а также гарантии доставки различаются. Push — канал уведомления, а не единственное хранилище события: после открытия приложение запрашивает актуальные данные у сервера.

## Безопасность и приватные данные

Service Worker действует в origin и имеет возможность изменять сетевой путь. Поэтому:

- скрипт и импортируемые зависимости защищают с помощью CSP и контроля цепочки поставки;
- ключи кеша учитывают пользователя и контекст авторизации;
- приватные ответы не складывают в общий кеш без явной модели;
- при logout удаляют кеши и данные, доступные предыдущему пользователю;
- нельзя считать Cache Storage секретным от XSS в том же origin;
- navigation fallback не должен возвращать app shell вместо API `404` или чужого файла.

Нельзя регистрировать worker из ненадёжного стороннего скрипта и нельзя отдавать `sw.js` с неожиданно долгим stale cache, который мешает браузеру проверять обновления.

## Ключевые уточнения

- Service Worker — событийный сетевой и фоновый worker, а Web Worker — контекст выполнения для вычислений страницы.
- Manifest описывает установленное приложение; Service Worker реализует сетевое и offline-поведение.
- Cache Storage управляется кодом и не равен HTTP-кешу.
- Новый worker обычно ждёт освобождения клиентов; принудительная активация безопасна только при совместимости версий.
- Service Worker может быть остановлен между событиями, поэтому постоянное состояние не держат только в глобальных переменных.
- Возможности PWA применяют как progressive enhancement с проверкой поддержки браузеров и платформ.

## Диагностика

В DevTools Application проверяют регистрацию, scope, текущий controller, состояния installing/waiting/active, Cache Storage и simulated offline. В Network проверяют, пришёл ответ от Service Worker, HTTP-кеша или сети.

Обязательные сценарии тестирования:

1. Первый visit без установленного worker.
2. Повторный visit online и offline.
3. Update при одной и нескольких открытых вкладках.
4. Переход сразу через несколько старых версий.
5. Отсутствующий old lazy chunk после deployment.
6. Logout/login другого пользователя на том же device.
7. Очистка по квоте и повреждённый или неполный кеш.
