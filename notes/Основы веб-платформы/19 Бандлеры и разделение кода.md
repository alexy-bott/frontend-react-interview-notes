## Быстрый ответ

Bundler, или сборщик модулей, начинает с точек входа (entry points), строит граф импортов и создаёт production-ресурсы: JavaScript chunks, CSS, изображения и runtime-код загрузки. По пути он преобразует TypeScript/JSX/SCSS, разрешает модули, удаляет доступный для анализа неиспользуемый код, минифицирует результат и добавляет хеш содержимого (content hash) в имена файлов.

Разделение кода (code splitting) делит граф на части, чтобы первый экран не загружал код редких маршрутов и функций. Статический `import` обычно включает модуль в текущую ветвь графа, а `import()` создаёт асинхронную границу и позволяет получить отдельный chunk.

Сборка — компромисс. Один большой начальный бандл задерживает загрузку и выполнение, а слишком много мелких chunks создаёт последовательные сетевые ожидания (waterfalls) и задерживает переходы. Решение проверяют анализатором бандла, панелями Network/Performance и метриками реальных пользователей.

## Основные понятия

| Понятие | Значение |
| --- | --- |
| Entry point | модуль, с которого начинается построение графа |
| Dependency graph | модули и связи статических и динамических imports |
| Bundle | один или несколько итоговых файлов сборки |
| Chunk | загружаемая часть графа; может быть initial или async |
| Runtime | небольшой код, который связывает modules и загружает chunks |
| Loader/transform | преобразование исходного формата в понятный сборщику модуль |
| Plugin | расширение более широких этапов сборки и вывода |
| Asset | JS, CSS, font, image и другой выходной ресурс |

Конкретные названия различаются между Webpack, Rollup, Rolldown, esbuild и другими инструментами. Общая модель графа и выходных assets полезнее запоминания одного config API.

## Этапы production build

```text
entry points
  -> module resolution
  -> dependency graph
  -> transforms
  -> tree shaking
  -> chunk graph
  -> minification
  -> content hashes и manifest
  -> output assets
```

**Module resolution** определяет, какой файл стоит за `import`: учитывает относительный путь, package exports, aliases, extensions и условия вроде `browser` или `import`.

**Transforms** превращают JSX, TypeScript и preprocessors в поддерживаемые форматы. Транспиляция TypeScript обычно удаляет типы, но не выполняет полноценный type checking. Поэтому `tsc --noEmit` или отдельная проверка остаётся частью CI.

**Minification** сокращает и переписывает код без изменения наблюдаемого поведения. Это не то же самое, что gzip/Brotli: минификация уменьшает исходные bytes, а HTTP compression сжимает файл при передаче.

**Content hash** меняет имя asset при изменении содержимого. Это позволяет долго кэшировать `app.8f3a1c.js`, пока HTML или manifest быстро получает ссылку на новую версию.

## Tree shaking

Tree shaking — удаление exports и ветвей модулей, которые сборщик может доказуемо не использовать. Лучше всего анализируются ES modules со статическими `import` и `export`.

```js
// math.js
export const sum = (left, right) => left + right;
export const multiply = (left, right) => left * right;

// app.js
import { sum } from "./math.js";

console.log(sum(2, 3));
```

При подходящей production-конфигурации `multiply` может не попасть в output. Слово «может» существенно: результат зависит от формата модуля, minifier и побочных эффектов.

```js
import "./register-global-listener.js";
```

Такой import нужен ради side effect — выполнения кода при загрузке. Сборщик не имеет права удалить его только потому, что exports не используются.

Tree shaking ограничивают:

- CommonJS и динамический доступ к exports;
- top-level side effects;
- неточное поле `sideEffects` в `package.json`;
- импорт большого namespace с последующим динамическим обращением;
- код, чистоту которого minifier не может доказать.

`sideEffects: false` является обещанием автора пакета, а не автоматическим анализом. Ошибочная настройка может удалить CSS import, polyfill или регистрацию, необходимые приложению.

## Code splitting

Статический import нужен до выполнения модуля:

```js
import { createEditor } from "./editor.js";
```

Dynamic import загружает модуль асинхронно:

```js
async function openEditor() {
  const { createEditor } = await import("./editor.js");
  return createEditor();
}
```

Сборщик создаёт границу chunk, а Promise выполняется после загрузки и выполнения модуля. Ошибка сети или несовпадение версии chunk отклоняет Promise, поэтому UI нужен error state и понятный recovery.

В React 18 route- или feature-level splitting часто строится через `lazy` и `Suspense`:

```tsx
const SettingsPage = lazy(() => import("./SettingsPage"));

function SettingsRoute() {
  return (
    <Suspense fallback={<PageSkeleton />}>
      <SettingsPage />
    </Suspense>
  );
}
```

Это переносит загрузку модуля до открытия маршрута, но не гарантирует хорошую скорость само по себе. Если `SettingsPage` сразу импортирует несколько тяжёлых chunks или начинает data fetch только после загрузки JS, получится waterfall.

## Как выбирать границы chunks

Естественные кандидаты:

- отдельные маршруты;
- editor, chart, map и другой крупный редкий widget;
- admin-функции, недоступные большинству пользователей;
- локали, feature flags и integrations;
- polyfills только для нужного окружения.

Код первого экрана, общий layout и маленькие часто используемые компоненты обычно не выигрывают от отдельного request. Shared vendor chunk может улучшить reuse между маршрутами, но слишком крупный vendor меняется из-за одной зависимости и заставляет снова загружать весь файл.

Границы выбирают по маршрутам пользователей и cache reuse, а не по правилу «один компонент — один chunk».

## Предзагрузка

Lazy chunk можно начать загружать до клика, когда есть сильный сигнал намерения: пользователь навёл курсор на ссылку, пункт появился рядом с viewport или сеть простаивает.

`preload` назначает высокий приоритет ресурсу текущей навигации. `prefetch` является подсказкой для вероятного будущего использования и обычно имеет меньший приоритет. Поддержка и фактическое планирование зависят от браузера и сборщика.

Избыточная предзагрузка конкурирует с LCP image, CSS и данными первого экрана. Поэтому нельзя preload-ить каждый lazy chunk.

## Development и production

Development server оптимизирует скорость запуска, обновления модулей и sourcemaps. Production build — размер, совместимость, hashing и стабильное исполнение.

Vite в development использует browser ESM и on-demand transforms, поэтому не обязан заранее собирать приложение в один bundle. Webpack обычно строит внутренний граф и incremental compilation. Конкретный production bundler Vite зависит от версии; эту деталь проверяют в карточке инструмента и документации проекта.

Поведение dev не доказывает production correctness. Перед release запускают реальный build и preview/e2e: ошибки появляются из-за base path, case-sensitive imports, env replacement, tree shaking, SSR boundaries и chunk URLs.

## Env, source maps и SSR

Переменная, подставленная сборщиком в frontend bundle, становится доступна пользователю. Префикс вроде `VITE_` или `NEXT_PUBLIC_` обозначает публичность, а не защищает secret.

Production source maps помогают error tracking восстановить исходный stack trace. Их можно загружать напрямую в monitoring и не публиковать как общедоступные files. Сокрытие source map не является защитой исходного алгоритма: выполненный JavaScript всё равно доставляется пользователю.

SSR-проект имеет как минимум server и client graphs. Модуль с `window` нельзя безусловно выполнить на сервере, а server-only secret не должен попасть в client graph. Dynamic import и условие runtime не всегда достаточны, если сборщик уже включил зависимость не в ту сторону границы.

## Deploy и старые chunks

При новой сборке content hashes меняются. Уже открытая вкладка или закэшированный HTML может запросить старый lazy chunk после deploy и получить `404`.

Надёжная схема сочетает:

1. Atomic deploy согласованного HTML и assets.
2. Долгое хранение предыдущих hashed assets.
3. Быстрое обновление HTML или его ревалидацию.
4. Обработку ошибки dynamic import с предложением обновить приложение.
5. Защиту несохранённых пользовательских данных перед reload.

Автоматический бесконечный reload опасен: если причина не исчезает, приложение попадёт в цикл.

## Как измерять

- bundle analyzer показывает, какие modules вошли в chunks;
- source-map explorer связывает minified output с исходными packages;
- Network показывает waterfall, transfer size, cache и timing;
- Coverage оценивает неиспользованный JS/CSS в конкретном сценарии;
- Performance показывает parse, compile и execution cost;
- size budget в CI замечает рост до merge.

Размер gzip не равен runtime cost. Два одинаково сжатых файла могут по-разному долго разбираться и выполняться на слабом устройстве.

## Ключевые уточнения

- Bundler строит граф и output assets, а transpiler и TypeScript type checker решают отдельные задачи.
- Tree shaking удаляет только код, который можно признать неиспользуемым без потери side effects.
- Code splitting переносит часть загрузки на более поздний момент, но не уменьшает общий объём кода автоматически.
- Полезная граница chunk следует пользовательскому маршруту и reuse; чрезмерное дробление создаёт дополнительные requests и waterfalls.
- Content hash, HTTP cache и стратегия deploy должны быть согласованы, иначе старый HTML или открытая вкладка запросит удалённый chunk.
