## Быстрый ответ

Код состояния HTTP (HTTP status code) сообщает общий результат обработки запроса на уровне протокола: успех, перенаправление, ошибку запроса или ошибку сервера. Тело ответа добавляет детали конкретного API: тип проблемы, поля формы, текущую версию ресурса, идентификатор запроса и безопасное пояснение.

Frontend использует оба уровня. Статус выбирает общий сценарий — показать данные, запросить вход, отобразить «не найдено», обработать конфликт или предложить повтор. Стабильный `type` или `code` в теле выбирает конкретное продуктовое поведение. Текст `message` для человека не используют как машинный идентификатор.

HTTP-ошибка существует только когда сервер или промежуточный узел вернул HTTP-ответ. Сетевой сбой, блокировка CORS и отмена запроса могут завершить `fetch` исключением без доступного статуса.

## Классы статусов

| Класс | Значение |
| --- | --- |
| `1xx` | промежуточная информация; браузер обычно обрабатывает её сам |
| `2xx` | запрос принят и обработан успешно |
| `3xx` | дальнейшее действие для получения результата: redirect, cache validation и другие варианты |
| `4xx` | сервер не выполняет запрос из-за его текущих условий или семантики |
| `5xx` | сервер или gateway не смог корректно завершить обработку |

`4xx` не означает автоматически «баг frontend-разработчика». Пользователь может не иметь доступа, ресурс мог быть удалён, версия устарела или сработал rate limit. `5xx` также не доказывает, что ошибка возникла именно в коде конечного backend: ответ мог вернуть proxy или gateway.

## Успешные ответы

| Статус | Когда используют | Что учитывает frontend |
| --- | --- | --- |
| `200 OK` | обычный успешный ответ | формат тела задаёт `Content-Type` |
| `201 Created` | создан новый ресурс | `Location` может указывать URI ресурса |
| `202 Accepted` | задача принята, но ещё не завершена | нужен job ID, status URL или канал прогресса |
| `204 No Content` | успех без тела | нельзя безусловно вызывать `response.json()` |
| `206 Partial Content` | возвращён диапазон ресурса | важны `Content-Range` и сборка частей |

`202` не означает, что операция обязательно завершится успешно. Он подтверждает только приём на обработку. Клиенту нужен отдельный контракт получения финального состояния.

## Redirect и кэш

Статусы `301`, `302`, `303`, `307` и `308` перенаправляют запрос, но по-разному сохраняют метод. `307` и `308` требуют повторить запрос с тем же методом и телом; поведение `301` и `302` исторически допускает преобразование `POST` в `GET`; `303` явно направляет клиента получить другой ресурс через `GET`.

`fetch` по умолчанию следует разрешённым redirect, поэтому JavaScript часто получает уже финальный ответ. Полная цепочка видна на панели Network, а `response.redirected` сообщает, что перенаправление произошло.

`304 Not Modified` относится не к переходу на другой URL, а к conditional request. Он сообщает HTTP-кэшу использовать сохранённое тело. При обычной загрузке через браузерный cache JavaScript часто видит собранный успешный response, а сам `304` — в Network panel.

## Authentication и доступ

`401 Unauthorized` означает, что у запроса нет подходящих authentication credentials. Несмотря на историческое имя статуса, речь идёт об аутентификации. Ответ должен содержать `WWW-Authenticate`, когда используется соответствующая HTTP-схема.

В cookie- или token-based приложении `401` может запустить один контролируемый refresh flow. Повторять refresh на каждый параллельный `401` нельзя: запросы объединяют вокруг одной попытки, ограничивают число повторов и завершают сессию, если refresh неуспешен.

`403 Forbidden` означает, что сервер понял запрос, но отказывается его выполнять. Часто пользователь уже аутентифицирован, но не имеет роли или права; это распространённый API-контракт, а не абсолютное требование наличия identity во всех случаях.

`404 Not Found` означает, что сервер не нашёл текущее представление ресурса или не хочет раскрывать его существование. Поэтому отсутствие ресурса и намеренное сокрытие доступа могут выглядеть одинаково.

## Ошибки данных и конфликты

| Статус | Типичный смысл |
| --- | --- |
| `400 Bad Request` | запрос нельзя корректно разобрать или он нарушает базовый контракт |
| `409 Conflict` | операция конфликтует с текущим состоянием ресурса |
| `412 Precondition Failed` | не выполнено условие вроде `If-Match` |
| `415 Unsupported Media Type` | сервер не поддерживает указанный `Content-Type` |
| `422 Unprocessable Content` | содержание синтаксически распознано, но выполнить инструкции невозможно |

Граница между `400`, `409` и `422` должна быть зафиксирована в API-контракте. Например, неверный JSON естественно даёт `400`, устаревший `ETag` — `412`, конкурентное изменение заказа — `409`, а field validation — часто `422`. Спецификация не превращает любое бизнес-правило в единственно возможный статус.

Для формы тело ошибки связывает правила с полями через стабильные коды. Сервер остаётся источником истины, а frontend решает, где показать сообщение и нужно ли сохранить введённые значения.

## Ограничение запросов и серверные сбои

`429 Too Many Requests` сообщает о превышении лимита. `Retry-After` может содержать число секунд или HTTP-date. Клиент не запускает немедленный бесконечный retry, а ждёт разрешённое время, добавляет ограниченный backoff и даёт пользователю понятное состояние.

`500 Internal Server Error` — общий непредвиденный серверный сбой. `502 Bad Gateway` означает некорректный ответ upstream-сервиса, `503 Service Unavailable` — временную недоступность, `504 Gateway Timeout` — истечение ожидания upstream.

Повтор допустим не для каждой операции. `GET` обычно можно повторить с ограничением попыток; `POST` заказа или платежа требует idempotency key либо проверки результата. Для `503` сервер также может вернуть `Retry-After`.

## Problem Details

RFC 9457 определяет media type `application/problem+json` для машиночитаемого описания HTTP-проблемы:

```json
{
  "type": "https://api.example.com/problems/validation-error",
  "title": "Request validation failed",
  "status": 422,
  "detail": "Two fields are invalid",
  "instance": "/orders/requests/abc-123",
  "traceId": "req_7f3",
  "errors": [
    {
      "field": "email",
      "code": "invalid_email",
      "message": "Email format is invalid"
    }
  ]
}
```

`type` — URI reference, идентифицирующий класс проблемы; `title` — краткое общее название; `status` повторяет HTTP-статус для удобства; `detail` описывает конкретный случай; `instance` идентифицирует конкретное возникновение. Поля `traceId` и `errors` являются расширениями конкретного API.

Problem Details не требует показывать `detail` пользователю без изменений. Текст может быть техническим, не локализованным или содержать лишние детали. UI выбирает безопасное сообщение по `type` или `code`, а `traceId` использует для обращения в поддержку и поиска серверных логов.

## HTTP-ошибка и ошибка сети в `fetch`

```js
async function readProblem(response) {
  const contentType = response.headers.get("content-type") ?? "";

  if (contentType.includes("json")) {
    return response.json();
  }

  return { title: await response.text() };
}

async function loadUser(id) {
  let response;

  try {
    response = await fetch(`/api/users/${id}`);
  } catch (cause) {
    return { kind: "network-error", cause };
  }

  if (response.status === 404) {
    return { kind: "not-found" };
  }

  if (!response.ok) {
    return {
      kind: "api-error",
      status: response.status,
      problem: await readProblem(response),
    };
  }

  return { kind: "success", data: await response.json() };
}
```

`fetch` отклоняет Promise при сетевой ошибке, блокировке ответа или отмене, но успешно разрешает его для `404` и `500`. Свойство `response.ok` равно `true` для диапазона `200–299`.

Production-обёртка дополнительно обрабатывает `204`, неожиданный `Content-Type`, невалидный JSON, `AbortError`, схему ответа и обновление auth. Эти обязанности не следует прятать в каждом UI-компоненте.

## Ключевые уточнения

- HTTP status задаёт общий протокольный результат, а стабильный `type` или `code` в теле — конкретную логику приложения.
- `fetch` различает сетевое отклонение Promise и HTTP-response с `response.ok === false`.
- `401` относится к отсутствующим или неподходящим credentials, а `403` — к сознательному отказу выполнить понятый запрос.
- `202` подтверждает приём, `204` исключает тело, а `304` обслуживает кэш; это разные успешные пути клиента.
- Retry учитывает идемпотентность и продуктовый контракт, а не запускается автоматически для любого `5xx`.
