## Быстрый ответ

HTTP-метод задаёт стандартную семантику запроса: получить представление, передать данные на обработку, заменить состояние ресурса, частично изменить или удалить его. Эта семантика нужна не только серверу и frontend-коду: на неё опираются браузеры, кэши, прокси и инструменты наблюдаемости.

Безопасный метод (safe method) предназначен только для чтения. Идемпотентный метод (idempotent method) можно повторить несколько раз с тем же предполагаемым итоговым эффектом на сервере. `GET`, `HEAD` и `OPTIONS` безопасны и идемпотентны; `PUT` и `DELETE` не безопасны, но идемпотентны; `POST` обычно не идемпотентен; свойства `PATCH` зависят от формата изменения.

Метод не обеспечивает поведение сам по себе. Сервер обязан соблюдать контракт, а клиент при retry учитывает не только название метода, но и тело операции, idempotency key, ответ сервера и продуктовые последствия повтора.

## Основные методы

| Метод | Стандартный смысл | Safe | Idempotent |
| --- | --- | --- | --- |
| `GET` | получить текущее представление ресурса | да | да |
| `HEAD` | получить метаданные, которые соответствуют `GET`, без тела ответа | да | да |
| `POST` | передать данные ресурсу для обработки | нет | нет по умолчанию |
| `PUT` | создать или полностью заменить состояние по известному URI | нет | да |
| `PATCH` | применить набор частичных изменений | нет | зависит от patch-документа |
| `DELETE` | удалить связь ресурса с указанным URI | нет | да |
| `OPTIONS` | узнать доступные параметры взаимодействия | да | да |

Safe и idempotent — свойства семантики, а не наблюдаемого количества внутренних действий. `GET` может записать access log или метрику, но клиент не запрашивает изменение бизнес-состояния. Повторный `DELETE` может вернуть другой статус, но предполагаемое конечное состояние остаётся тем же: ресурс больше не доступен по URI.

## `GET` и `HEAD`

`GET` получает представление ресурса. Его ответы естественно участвуют в HTTP-кэшировании, conditional requests и prefetch. Поэтому `GET /orders/42/cancel` не должен отменять заказ: crawler, preload или повторная навигация способны вызвать такой URL без намерения пользователя выполнить mutation.

`HEAD` запрашивает те же метаданные, что и `GET`, но сервер не отправляет тело ответа. Метод используют, например, чтобы проверить существование или свойства большого ресурса. Поддерживать отдельную несовместимую семантику `HEAD` не следует.

## `POST`, `PUT` и `PATCH`

`POST` просит целевой ресурс обработать переданное представление. Создание сущности — распространённый, но не единственный случай: `POST` может запускать поиск, отправку сообщения или бизнес-команду.

```http
POST /orders
Content-Type: application/json

{"productId":"p-42","quantity":1}
```

Повтор такого запроса способен создать второй заказ. Для операций, где клиент должен безопасно повторить неизвестный результат, API может принять idempotency key — уникальный идентификатор логической операции. Сервер сохраняет результат первого выполнения и возвращает его для повторного запроса с тем же ключом. Это прикладной контракт API, а не автоматическое свойство любого `POST`.

`PUT` адресует состояние по известному URI и создаёт или заменяет его целиком:

```http
PUT /users/42/preferences
Content-Type: application/json

{"theme":"dark","language":"ru"}
```

Повтор того же представления приводит к тому же целевому состоянию. Если API трактует пропущенные поля как сохранение старых значений, это уже ближе к частичному обновлению и должно быть явно описано.

`PATCH` передаёт документ изменений. Идемпотентность зависит от операции:

```json
{ "theme": "dark" }
```

Установка `theme` в конкретное значение может быть идемпотентной. Операция «увеличить balance на 10» при каждом повторе изменяет состояние заново и идемпотентной не является. Форматы JSON Merge Patch и JSON Patch задают изменения по-разному, поэтому клиент и сервер должны согласовать `Content-Type` и правила применения.

## `DELETE` и повторный запрос

Идемпотентность `DELETE` относится к целевому состоянию, а не к одинаковому ответу:

```text
первый DELETE /users/42  -> 204 No Content
второй DELETE /users/42 -> 404 Not Found
итог                         пользователь 42 отсутствует
```

Побочные бизнес-действия вроде повторной отправки уведомления должны быть устроены так, чтобы повтор запроса не создавал новый нежелательный эффект. Само слово `DELETE` в route этого не гарантирует.

## `OPTIONS` и CORS preflight

`OPTIONS` запрашивает возможности ресурса или сервера. Браузер использует его для CORS preflight: перед некоторыми межсайтовыми запросами проверяет, разрешены ли origin, метод и заголовки.

Frontend-код обычно не отправляет preflight вручную. Браузер создаёт его автоматически, а сервер должен ответить подходящими `Access-Control-Allow-*` headers. Успешный `OPTIONS` ещё не означает успех основного запроса: после проверки браузер отдельно отправит реальный метод.

## Повтор, кэш и UI

Идемпотентность делает повтор более предсказуемым, но не является полной политикой retry. После timeout клиент может не знать, получил ли сервер запрос. Перед повтором учитывают:

- можно ли повторно отправить тело;
- не истёк ли срок операции;
- есть ли idempotency key или версия ресурса;
- означает ли ошибка временный сбой;
- не создаст ли повтор конфликт с новым состоянием.

В интерфейсе mutation обычно имеет состояния pending, success и error. Optimistic update допустим, когда известен откат или повторная синхронизация. Метод помогает понять контракт, но не определяет UI-стратегию автоматически.

Кэшируемость также не сводится к правилу «только GET». `GET` и `HEAD` определены как кэшируемые, а ответ `POST` может быть кэшируемым при явных условиях, хотя такая схема поддерживается и используется реже. Фактическое поведение задают HTTP cache headers и кэш-реализация.

## Ключевые уточнения

- Safe означает намерение чтения без запрошенного изменения бизнес-состояния; технические логи и метрики этому не противоречат.
- Idempotent означает одинаковый предполагаемый итоговый эффект, а не одинаковый статус или байты каждого ответа.
- `POST` означает обработку представления и не ограничивается созданием сущности.
- `PUT` задаёт полное состояние по известному URI, а семантика `PATCH` определяется форматом переданных операций.
- Повтор запроса проектируется вместе с API-контрактом: HTTP-метод является основой решения, но не заменяет idempotency key, versioning и обработку конфликтов.
