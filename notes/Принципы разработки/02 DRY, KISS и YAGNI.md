## Быстрый ответ

DRY, KISS и YAGNI ограничивают разные источники сложности.

- **DRY (Don't Repeat Yourself):** одно знание или правило должно иметь одно авторитетное представление, чтобы его варианты не расходились.
- **KISS (Keep It Simple):** выбирать самое простое решение, которое понятно выполняет известные требования.
- **YAGNI (You Aren't Gonna Need It):** не реализовывать возможности и точки расширения до появления подтверждённой потребности.

DRY относится не к любому похожему коду. Одинаковая бизнес-валидация в трёх формах — дублирование знания, а похожая разметка двух доменных карточек может быть случайным совпадением. Перед выделением абстракции нужно проверить, одинаковы ли причина изменения и требуемый контракт. KISS и YAGNI защищают от ситуации, когда борьба с небольшим повторением создаёт более сложную общую систему.

## Базовая модель

| Вопрос | Принцип | Возможное действие |
| --- | --- | --- |
| Одно правило приходится синхронно менять в нескольких местах? | DRY | определить источник истины и переиспользовать правило |
| Решение трудно проследить из-за лишних слоёв и универсальности? | KISS | сократить модель и сделать поток явным |
| Код поддерживает только предполагаемый будущий сценарий? | YAGNI | отложить сценарий до подтверждённого требования |

```text
повторяется знание -> устранить расхождение
сложность не помогает текущей задаче -> упростить
требование только предполагается -> не реализовывать заранее
```

## DRY: не дублировать знание

Знанием может быть бизнес-правило, формат API, алгоритм преобразования данных, разрешение роли, формула цены или набор дизайн-токенов. Если оно скопировано, каждая копия становится отдельной версией правды.

Например, правило «пароль должен содержать не менее 12 символов» может жить в форме регистрации, смены пароля и восстановления доступа. После изменения требования одна форма легко останется со старым значением. Общая схема или функция делает правило единым и позволяет проверить его отдельно.

Совпадение строк ещё не означает общее знание. `ProductCard` и `OrderCard` могут временно иметь одинаковую сетку, но меняться по разным требованиям. Общий `UniversalCard` свяжет их и заставит добавлять флаги для каждого расхождения. В таком случае локальное повторение дешевле ложной абстракции.

Полезный критерий: части стоит объединять, если у них одно значение, одна причина изменения и один ожидаемый контракт. Если совпадает только текущая форма кода, объединение преждевременно.

## KISS: необходимая сложность без лишней

Простое решение не обязательно короткое. Явная функция из нескольких понятных шагов может быть проще однострочного выражения, которое требует знания редкого трюка. Отдельный API-слой может упростить приложение, если он убирает повторение обработки ошибок и преобразования DTO. DTO (Data Transfer Object) — структура данных транспортного контракта, например объект из ответа backend.

KISS оценивает сложность всей задачи поддержки:

- можно ли быстро проследить поток данных;
- соответствует ли название реальному поведению;
- есть ли у слоя самостоятельная ответственность;
- можно ли изменить типичный сценарий локально;
- нужна ли каждая настройка текущим требованиям.

Во frontend нарушение часто выглядит как компонент с десятками режимов, конфигурация для единственного использования или собственный мини-фреймворк поверх React. Упрощение может означать две явные реализации вместо одного универсального компонента.

## YAGNI: подтверждённая потребность вместо догадок

YAGNI учитывает стоимость преждевременной функциональности. Код «на будущее» нужно спроектировать, реализовать, протестировать, документировать и поддерживать уже сейчас, хотя реальные требования могут оказаться другими.

Если продукту нужен экспорт CSV, добавление одновременно PDF, XLSX, API плагинов и фоновой очереди без требования — лишняя работа. Реализованный CSV должен иметь ясную границу, чтобы его можно было изменить, но не обязан заранее содержать все предполагаемые расширения.

Известное ближайшее требование не является YAGNI. Если утверждённые сценарии уже включают несколько способов экспорта или таблиц, общий контракт решает текущую задачу. Отличие проходит между подтверждённой вариативностью и предположением разработчика.

## Как принципы работают вместе

DRY может подсказать выделить общую часть, а KISS и YAGNI — оставить повторение до прояснения модели. Решение удобно принимать последовательно:

1. Определить, что повторяется: знание, поведение, структура или только внешний вид.
2. Проверить, должны ли копии меняться вместе по одной причине.
3. Сформулировать минимальный общий контракт без флагов под частные случаи.
4. Сравнить стоимость локального повторения и новой зависимости между модулями.
5. Выделить абстракцию, если она уже упрощает реальные изменения.

«Правило трёх повторений» можно использовать как напоминание не спешить, но это не закон. Критичное правило безопасности или расчёта стоит централизовать сразу, а три визуально похожих компонента могут по-прежнему не иметь общей модели.

## Где применяется во frontend

| Ситуация | Анализ | Решение |
| --- | --- | --- |
| Правило валидации скопировано в нескольких формах | повторяется одно бизнес-знание | DRY: общая схема или функция в предметном слое |
| Компоненты сами преобразуют `created_at` и `full_name` | UI повторяет знание backend-контракта | DRY: преобразовать DTO в API-слое |
| Две карточки похожи внешне, но показывают разные сущности | причины изменения различаются | KISS: оставить отдельные компоненты; при необходимости вынести только визуальную оболочку |
| Таблица принимает множество флагов для отдельных страниц | общая абстракция скрывает разные сценарии | KISS: разделить ядро и предметные обёртки либо оставить отдельные таблицы |
| Предлагается добавить незаказанные форматы экспорта | потребность предполагается | YAGNI: реализовать подтверждённый формат и сохранить ясную границу |
| Несколько экранов уже используют одинаковую модель колонок и сортировки | устойчивый контракт подтверждён | DRY: выделить общее ядро таблицы |

## Пример

Предположим, цена со скидкой вычисляется и на карточке товара, и в корзине:

```ts
// ProductCard.tsx
const total = price - price * discountPercent / 100;

// CartItem.tsx
const total = Math.round(price * (100 - discountPercent)) / 100;
```

Это не просто похожие строки: обе формулы представляют одно правило цены, но уже по-разному округляют результат. Источник истины можно сделать явным:

```ts
type PriceInput = {
  priceInCents: number;
  discountPercent: number;
};

function calculateDiscountedPrice({
  priceInCents,
  discountPercent,
}: PriceInput): number {
  return Math.round(priceInCents * (100 - discountPercent) / 100);
}
```

Функция хранит правило в целых минимальных денежных единицах и не зависит от React. Компоненты отвечают только за отображение. Добавлять в неё заранее валютную конвертацию, налоги всех стран и несколько стратегий округления не нужно, пока такие требования не появились: это сохраняет KISS и YAGNI.

## Границы применения

- DRY снижает риск рассинхронизации знания, но создаёт зависимость от общего источника.
- KISS требует учитывать сложность изменения и эксплуатации, а не только число строк.
- YAGNI откладывает предполагаемые возможности, но не отменяет обязательные нефункциональные требования: безопасность, доступность, диагностику и согласованную архитектурную границу.
- Временное повторение допустимо, когда модель ещё исследуется; его полезно отметить и пересмотреть после появления устойчивого контракта.

## Ключевые уточнения

- DRY объединяет одно знание, а не весь синтаксически похожий код.
- Хорошая абстракция делает реальные изменения локальнее и не требует флагов для каждого потребителя.
- KISS допускает архитектурные слои, если каждый из них уменьшает общую сложность.
- YAGNI отделяет известные требования от предполагаемых будущих возможностей.
- Небольшое локальное повторение часто безопаснее общей зависимости с неверным контрактом.
