## Быстрый ответ

Composition over inheritance — принцип «предпочитать композицию наследованию». Вместо иерархии базовых и дочерних классов объект или компонент получает нужное поведение от небольших независимых частей и делегирует им работу.

В React композиция является основной моделью переиспользования. Интерфейс собирается вложением компонентов через `children`, передачей данных и функций через props, а повторяемая логика — через custom hooks. Context, render props и compound components нужны для более сложной координации частей.

Композиция не означает, что любой компонент должен быть максимально настраиваемым. Полезный контракт явно разделяет ответственность: что часть контролирует сама, что получает снаружи и какие гарантии сохраняет. Если API заполняется флагами, вложенными конфигурациями и функциями обратного вызова (callbacks) для несвязанных сценариев, отдельные компоненты могут быть проще.

## Композиция и наследование

| Подход | Связь | Как переиспользуется поведение | Основной риск |
| --- | --- | --- | --- |
| Наследование | «наследник является разновидностью базового типа» | переопределение и расширение методов базового класса | сильная связь с иерархией и внутренним состоянием родителя |
| Композиция | «часть использует другие части» | делегирование через явные входы и контракты | слишком широкий или запутанный композиционный API |

Наследование фиксирует связь во время определения класса. Изменение базового класса может повлиять на всех наследников, а сочетание независимых вариантов часто порождает новые уровни иерархии. Композиция связывает части в месте использования и позволяет заменить одну часть без изменения остальных, если контракт сохраняется.

Это предпочтение, а не абсолютный запрет. Наследование подходит для настоящей устойчивой связи типов и для расширения framework-класса по его документированному контракту. Но визуальные варианты интерфейса и сочетания поведений обычно не образуют стабильное дерево «является разновидностью».

## Как композиция работает в React

### `children`: вложенное содержимое

Контейнер управляет своей структурой, а конкретное содержимое передаёт родитель:

```tsx
<Panel title="Profile">
  <ProfileForm />
</Panel>
```

`Panel` отвечает за заголовок, отступы и рамку, но не знает о полях профиля. `ProfileForm` можно поместить в другую структуру страницы без наследования от `Panel`.

### Props и функции

Props передают данные и варианты поведения. Например, таблица может получить `columns` и функцию `renderCell`, а список — функцию `renderItem`. Функция как prop является стратегией: родитель задаёт изменяемую часть алгоритма, а компонент сохраняет общий поток.

Контракт должен быть ограниченным. Набор props `isUsersPage`, `isOrdersPage` и `specialAdminMode` выдаёт не композицию, а скрытое объединение разных компонентов.

### Custom hooks: композиция логики

Custom hook объединяет вызовы React Hooks и возвращает данные и операции для компонента. Он переиспользует логику работы с состоянием и жизненным циклом React, но сам по себе не делает состояние общим. Локальный state, созданный внутри hook через `useState` или `useReducer`, будет отдельным для каждого вызова. Состояние остаётся общим только тогда, когда hook явно обращается к одному context или внешнему store.

Например, `useDebouncedValue` может использоваться в разных полях поиска. Компоненты делят алгоритм задержки, но их значения независимы.

### Context и compound components

Context передаёт значение через поддерево без ручной передачи через каждый промежуточный компонент. Compound components — согласованный набор частей, например `Tabs.Root`, `Tabs.List`, `Tabs.Trigger` и `Tabs.Content`. Общий context связывает активную вкладку, идентификаторы и события, а пользователь собирает подходящую структуру из частей.

Такой API полезен, когда части должны координироваться и обычного `children` недостаточно. Он требует явных ограничений: какие части допустимы, где они должны находиться и какое доступное поведение гарантируется.

### Headless components

Headless-компонент управляет поведением и состояниями, но не навязывает готовое визуальное оформление. Например, Radix UI реализует для dialog управление фокусом, клавиатурой и ARIA-связями, а приложение компонует части и задаёт стили.

«Без готового оформления» не означает «без разметки и контракта»: структура частей необходима для корректной доступности и поведения.

## Где применяется во frontend

| Задача | Стабильная часть | Передаваемая часть |
| --- | --- | --- |
| Структура страницы | сетка, ограничения ширины | содержимое через `children` |
| Карточки сущностей | общая визуальная рамка | предметные данные и действия |
| Таблица | разметка, загрузка, пустое состояние | колонки, ячейки, действия строк |
| Форма | поля конкретного сценария | повторяемая логика через hook и UI-примитивы |
| Dialog | фокус, закрытие, модальный режим | заголовок, содержимое и действия |
| Tabs | активное значение и связь частей | состав и содержимое вкладок |
| API-сценарий | последовательность бизнес-действий | контракт доступа к данным или функция конкретной инфраструктуры |

Перед выделением общей части нужно определить её владение состоянием. Контролируемый компонент получает текущее значение и обработчик изменения снаружи. Неконтролируемый компонент хранит значение сам и обычно получает начальное состояние. Смешение этих моделей без явного правила создаёт трудно предсказуемый API.

## Пример

Композиционный контейнер ничего не знает о предметной сущности:

```tsx
import type { ReactNode } from "react";

type CardLayoutProps = {
  title: string;
  meta?: ReactNode;
  actions?: ReactNode;
  children: ReactNode;
};

function CardLayout({ title, meta, actions, children }: CardLayoutProps) {
  return (
    <article>
      <header>
        <h3>{title}</h3>
        {meta}
      </header>

      <div>{children}</div>
      {actions && <footer>{actions}</footer>}
    </article>
  );
}
```

Предметный компонент собирает из него нужный вариант:

```tsx
function UserCard({ user, onOpen }: UserCardProps) {
  return (
    <CardLayout
      title={user.name}
      meta={<UserRole role={user.role} />}
      actions={<button onClick={() => onOpen(user.id)}>Open</button>}
    >
      <UserAvatar name={user.name} src={user.avatarUrl} />
    </CardLayout>
  );
}
```

`CardLayout` переиспользует только устойчивую структуру. Он не получает весь `User`, не содержит условий для разных страниц и не знает, что делает кнопка. `UserCard` сохраняет предметный смысл и может изменяться независимо от карточек товара или заказа.

## Как выбрать механизм

| Потребность | Подход |
| --- | --- |
| Передать вложенное содержимое | `children` |
| Заменить небольшой участок поведения | функция или данные через props |
| Переиспользовать логику с Hooks | custom hook |
| Доставить общее значение связанному поддереву | context |
| Дать пользователю собрать координируемые части | compound components |
| Отделить доступное поведение от оформления | headless component |

Начинать стоит с простейшего подходящего контракта. Context или compound API добавляют только тогда, когда обычные props и `children` уже не выражают требуемую связь.

## Границы применения

- Композиция уменьшает связь с иерархией, но не исправляет неясную ответственность частей.
- Чрезмерное число callbacks и вариантов конфигурации может сделать поток данных скрытым.
- Custom hook извлекает логику, но его скрытые обращения к глобальному context или singleton по-прежнему создают зависимость.
- Headless-библиотеку используют в соответствии с её структурным и accessibility-контрактом; произвольная перестановка частей может нарушить поведение.
- Два самостоятельных предметных компонента лучше общей абстракции, если их сходство нестабильно.

## Ключевые уточнения

- Композиция собирает поведение из частей с явными входами, а наследование получает его через иерархию типов.
- `children` компонует UI, а custom hooks компонуют повторяемую логику.
- Локальный state внутри custom hook создаётся отдельно для каждого вызова; общий context или внешний store по-прежнему может быть одним источником состояния.
- Context помогает связанным частям обмениваться значением, но делает источник зависимости менее видимым.
- Хорошая композиция сохраняет небольшой контракт и понятное владение состоянием.
- Наследование остаётся допустимым при устойчивой связи типов и документированном контракте расширения.
