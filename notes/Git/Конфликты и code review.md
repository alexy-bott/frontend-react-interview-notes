## Быстрый ответ

Git-конфликт возникает, когда Git не может автоматически построить одно итоговое состояние из объединяемых изменений. Это бывает не только при редактировании одной строки: одна ветка могла удалить файл, который изменила другая, обе могли переименовать файл по-разному или изменить несовместимые участки структуры.

Разрешить конфликт — значит понять намерение обеих сторон, вручную собрать правильное итоговое состояние, пометить его через `git add` и продолжить прерванную операцию. После этого нужны проверка типов, тесты и запуск приложения: Git сравнивает данные и строки, но не понимает бизнес-логику.

Ревью кода (code review) дополняет эту проверку. Ревьюер оценивает соответствие задаче, корректность сценариев, безопасность, доступность, тесты и стоимость поддержки, а CI автоматически запускает воспроизводимые проверки. Ни ревью, ни зелёный пайплайн по отдельности не гарантируют отсутствие дефектов.

## Откуда возникает конфликт

При merge Git обычно находит общий предок двух веток — merge base — и сравнивает с ним обе стороны. Если изменения можно совместить однозначно, merge проходит автоматически. Если для одного участка существует несколько возможных итогов, Git останавливает операцию и просит разработчика выбрать результат.

```text
      C---D  feature
     /
A---B---E  main
    ^
 merge base
```

Основные виды конфликтов:

| Вид | Пример |
| --- | --- |
| Конфликт содержимого (content) | Обе стороны по-разному изменили пересекающиеся строки |
| Изменение/удаление (modify/delete) | Одна сторона изменила файл, другая его удалила |
| Переименование/переименование (rename/rename) | Стороны дали одному файлу разные имена |
| Добавление/добавление (add/add) | По одному пути независимо созданы разные файлы |
| Конфликт бинарных файлов | Обе стороны изменили бинарный файл, который Git не может объединить построчно |

Отдельно существует логический конфликт. Git может успешно объединить разные файлы или непересекающиеся строки, но вместе изменения нарушат API-контракт, порядок миграций, CSS cascade, типы или состояние интерфейса. Такой конфликт обнаруживают ревью, тесты и ручная проверка, а не маркеры Git.

## Как разрешать конфликт

1. Выполнить `git status` и определить, какая операция остановлена и какие файлы конфликтуют.
2. Посмотреть общий предок и обе версии, чтобы понять исходное поведение и цель каждого изменения.
3. Собрать финальное содержимое: иногда подходит одна сторона, иногда обе, иногда требуется третье решение.
4. Удалить служебные маркеры, проверить файл и выполнить `git add <file>`.
5. Запустить форматирование, проверку типов, тесты и проверить затронутый пользовательский сценарий.
6. Продолжить исходную операцию или отменить её, если выбран неверный путь.

| Операция | Продолжить | Отменить |
| --- | --- | --- |
| Merge | `git commit` или `git merge --continue` | `git merge --abort` |
| Rebase | `git rebase --continue` | `git rebase --abort` |
| Cherry-pick | `git cherry-pick --continue` | `git cherry-pick --abort` |

`git add` не проверяет правильность решения. Он записывает выбранное содержимое в index и сообщает Git, что файл больше не находится в состоянии неразрешённого конфликта (unresolved).

## Маркеры конфликта

```tsx
 <<<<<<< HEAD
return <Button disabled={isSaving}>Save</Button>;
 =======
return <Button loading={isPending}>Save changes</Button>;
 >>>>>>> feature/profile-copy
```

В обычном merge часть `HEAD` относится к текущей ветке, а нижняя часть — к интегрируемой. Но полагаться только на названия `ours` и `theirs` опасно: во время rebase смысл сторон для пользователя выглядит обратным, потому что Git воспроизводит коммит поверх нового основания.

Корректное решение определяется поведением, а не механическим объединением:

```tsx
return (
  <Button disabled={isPending} loading={isPending}>
    Save changes
  </Button>
);
```

Здесь сначала выясняется, означают ли `isSaving` и `isPending` одно состояние. Если да, сохраняют один источник истины. Если значения отражают разные процессы, условие строят из обоих и проверяют все переходы состояния.

Для сложного случая полезно посмотреть три версии через `git show`: общий предок, текущую и входящую стороны. Команда `git diff --cc` показывает объединённый diff незавершённого merge.

## Особенности frontend-проекта

Конфликт в lock-файле не следует решать случайным выбором половины текста. Сначала согласуют изменения манифеста зависимостей, затем восстанавливают lock-файл тем же пакетным менеджером и версией, которые использует проект, после чего проверяют diff и выполняют чистую установку зависимостей.

Сгенерированные файлы лучше пересоздать из их источника, если сборка воспроизводима. Для бинарных макетов и изображений Git обычно не умеет построить общий вариант: нужно выбрать нужный файл или подготовить объединённую версию внешним инструментом.

Частая синхронизация с базовой веткой уменьшает объём расхождения. Небольшие независимые изменения, короткоживущие ветки и понятные границы модулей уменьшают вероятность сложного конфликта, но полностью исключить его невозможно.

## Ревью кода

Цель ревью — уменьшить риск изменения и распределить знание о коде. Проверка начинается с вопроса, решает ли изменение нужную задачу, затем рассматриваются поведение, границы решения и реализация.

Автор помогает ревьюеру осмысленным размером MR и описанием:

- цель и ссылка на задачу;
- что изменилось и почему выбран этот подход;
- способ проверки и выполненные тесты;
- скриншоты или видео для визуального изменения;
- миграции, feature flags, влияние на API и способ отката;
- известные ограничения и намеренно вынесенная последующая работа.

Ревьюер в первую очередь проверяет последствия, которые трудно увидеть автоматикой:

| Область | Что проверить |
| --- | --- |
| Требования | Основной и пограничные сценарии, состояния загрузки, ошибки и отсутствия данных |
| Архитектура | Границы модулей, владение состоянием, понятность потока данных |
| API | Контракты, коды ответов, ошибки, повторные запросы, инвалидация кеша |
| Доступность | Семантика, клавиатурная навигация, управление фокусом, доступное имя (accessible name) |
| Безопасность | Пользовательский ввод, XSS, токены, секреты, права доступа |
| Производительность | Размер бандла, лишние рендеры, сетевые запросы, тяжёлые вычисления |
| Поддержка | Имена, сложность, диагностика, тестируемость |
| Доставка | CI, миграции, обратная совместимость, наблюдаемость и откат |

Комментарий ревью должен указывать риск или непонятное место, а не только предлагать личный стиль. Полезно отделять блокирующее замечание о корректности от необязательного улучшения. Автор отвечает на замечание и отмечает, что изменилось; обсуждение хранит контекст решения для команды.

CI проверяет формализуемые свойства: lint, типы, тесты, сборку и результаты сканирования безопасности. Ревью проверяет смысл и риски. Ручная проверка покрывает реальное взаимодействие, которое не вошло в автоматические сценарии. Эти уровни дополняют друг друга.

## Ключевые уточнения

- Git использует общий предок, чтобы определить изменения каждой стороны, и останавливается только там, где итог нельзя выбрать однозначно.
- Правильное разрешение сохраняет намерение изменений и корректное поведение, а не обязательно одну из готовых сторон.
- `git add` отмечает техническое завершение конфликта; качество решения подтверждают проверки.
- Автоматический merge может содержать логический конфликт без каких-либо маркеров.
- Lock-файл восстанавливают согласованным пакетным менеджером после проверки изменений манифеста.
- Ревью кода, CI и ручная проверка обнаруживают разные классы проблем.
