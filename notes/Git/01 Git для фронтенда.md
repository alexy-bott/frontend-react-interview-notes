## Быстрый ответ

Git — распределённая система контроля версий. Она хранит историю проекта в виде графа коммитов, позволяет независимо вести несколько изменений, сравнивать состояния проекта и объединять работу разработчиков. После `git clone` разработчик получает локальный репозиторий, поэтому создавать коммиты и просматривать уже загруженную историю можно без соединения с сервером.

В повседневной работе важно различать три локальные области: рабочую директорию с текущими файлами, область подготовленных изменений (staging area, или index) с содержимым следующего коммита и локальный репозиторий с зафиксированной историей. Удалённый репозиторий, например в GitLab, синхронизируется отдельно: `git fetch` получает изменения, а `git push` публикует локальные коммиты.

## Базовая модель

```text
рабочая директория --git add--> staging area --git commit--> локальный репозиторий
                                                                  |
                                                    git push / git fetch
                                                                  |
                                                        удалённый репозиторий
```

| Понятие | Что означает |
| --- | --- |
| Рабочая директория (working tree) | Файлы проекта в текущем состоянии на диске |
| Область подготовленных изменений (staging area, или index) | Версия файлов, из которой будет создан следующий коммит |
| Репозиторий | Объекты Git, ссылки и история коммитов внутри `.git` |
| Коммит | Зафиксированное состояние дерева файлов, метаданные и ссылка на родительский коммит |
| Ветка (branch) | Именованная подвижная ссылка на коммит |
| `HEAD` | Ссылка на текущую позицию; обычно указывает на выбранную ветку |
| Удалённый репозиторий (remote) | Сохранённые в локальном репозитории имя и адрес другого репозитория, например `origin` |
| Отслеживающая удалённая ветка (remote-tracking branch) | Последнее известное локально состояние ветки удалённого репозитория, например `origin/main` |

## Как Git хранит историю

Git представляет историю как направленный граф. Обычный коммит ссылается на одного родителя, merge-коммит — на нескольких, а первый коммит не имеет родителя. Поэтому история не обязана быть одной линейной цепочкой.

Коммит хранит ссылку на корень дерева файлов, автора изменений, автора коммита, сообщение и родителей. Содержимое файлов хранится в объектах Git и переиспользуется, если не изменилось. Учебная модель «коммит — снимок состояния проекта» верна для понимания поведения: при переходе на коммит Git восстанавливает зафиксированное дерево, а не последовательно применяет список патчей от начала проекта.

Ветка не содержит отдельную копию файлов. Это ссылка, которая обычно перемещается на новый коммит при `git commit`. `HEAD` чаще всего указывает на ветку, а ветка — на её последний коммит:

```text
A <- B <- C
          ^
        main
          ^
         HEAD
```

Если `HEAD` указывает непосредственно на коммит, возникает состояние detached `HEAD`. В нём можно изучать и запускать проект, но для нового коммита нужно создать ветку, иначе на него не останется удобной именованной ссылки.

## Состояния изменений

Новый файл сначала имеет состояние untracked: Git видит его, но ещё не отслеживает. Изменение отслеживаемого файла находится в рабочей директории. `git add` копирует выбранное содержимое в index, а `git commit` создаёт коммит именно из index.

Из-за этого один файл может одновременно иметь подготовленные (staged) и неподготовленные (unstaged) изменения: часть содержимого уже добавлена в index, а после этого файл снова отредактирован. Состояние показывают `git status`, `git diff` и `git diff --staged`.

```bash
git status
git diff             # рабочая директория относительно index
git diff --staged    # index относительно последнего коммита
```

Staging area позволяет включить в коммит только законченное логическое изменение. Для частичного добавления одного файла можно использовать `git add -p` и проверить подготовленный результат через `git diff --staged`.

## Локальная и удалённая история

`git clone` создаёт локальный репозиторий и настраивает удалённый репозиторий (remote), обычно с именем `origin`. Само имя `origin` не имеет особого сетевого поведения: это обычное локальное сокращение для адреса.

`git fetch origin` загружает отсутствующие объекты и обновляет отслеживающие удалённые ветки, но не меняет текущую ветку и рабочие файлы. После fetch можно сравнить `main` с `origin/main` и самостоятельно выбрать способ интеграции.

`git pull` выполняет fetch, а затем интегрирует полученную ветку через merge или rebase в зависимости от команды и конфигурации. Поэтому перед pull важно понимать выбранную стратегию. `git push` передаёт объекты и пытается передвинуть ветку в удалённом репозитории; сервер может отклонить push, если удалённая ветка содержит неизвестные локальной ветке коммиты или защищена правилами доступа.

## Рабочий цикл frontend-задачи

```bash
git switch main
git fetch origin
git pull --ff-only
git switch -c feature/ABC-123-profile-form

# работа над задачей
git status
git diff
git add -p
git diff --staged
git commit -m "ABC-123 add profile form validation"

git push -u origin feature/ABC-123-profile-form
```

После push обычно создают merge request: CI проверяет код, ревьюер оценивает изменение, а ветка интегрируется по правилам команды. `--ff-only` в примере запрещает `pull` автоматически создавать merge-коммит; это один из возможных командных вариантов, а не универсальное требование.

Логический коммит решает одну связанную задачу и оставляет проект в осмысленном состоянии. Такой коммит легче проверить, перенести через `cherry-pick` или отменить через `revert`. `git bisect` помогает найти коммит, в котором появился дефект: Git выполняет двоичный поиск по истории, а разработчик помечает проверяемые состояния как рабочие или дефектные.

## Файлы frontend-проекта

В репозитории обычно фиксируют исходный код, конфигурацию сборки, миграции и lock-файл пакетного менеджера. Lock-файл закрепляет точные версии зависимостей и должен обновляться тем же пакетным менеджером, который использует команда.

Секреты, локальные `.env` с реальными значениями, зависимости из `node_modules` и воспроизводимые артефакты сборки обычно исключают через `.gitignore`. Исключение зависит от проекта: например, статическая сборка может намеренно храниться в отдельной ветке для deployment.

`.gitignore` действует только на неотслеживаемые файлы. Если секрет уже попал в коммит, добавление имени файла в `.gitignore` не удалит его из истории. Секрет нужно немедленно отозвать или заменить, затем удалить из отслеживаемого состояния; при необходимости история очищается отдельно и согласованно со всей командой.

## Диагностика

| Задача | Команда |
| --- | --- |
| Увидеть текущее состояние | `git status` |
| Проверить неподготовленные изменения | `git diff` |
| Проверить содержимое будущего коммита | `git diff --staged` |
| Посмотреть граф истории | `git log --oneline --graph --decorate --all` |
| Обновить сведения об удалённом репозитории | `git fetch --prune origin` |
| Найти прежнее положение локальной ссылки | `git reflog` |
| Найти коммит, после которого появился дефект | `git bisect` |

`reflog` хранит локальную историю перемещений ссылок и часто помогает вернуть коммит после ошибочного rebase или reset. Это не резервная копия на сервере: reflog локален и его записи со временем удаляются.

## Ключевые уточнения

- Коммит фиксирует содержимое index, а не автоматически все изменения рабочей директории.
- Ветка — ссылка на коммит; параллельные ветки образуют граф общей истории.
- `HEAD` обозначает текущую позицию, а `origin/main` — последнее полученное локальное представление удалённой `main`.
- `fetch` получает историю без изменения рабочей ветки; `pull` дополнительно интегрирует её.
- Коммит остаётся локальным до успешного `push`.
- `.gitignore` предотвращает добавление новых неотслеживаемых файлов, но не очищает уже опубликованную историю.
