## Быстрый ответ

`merge`, `rebase` и `cherry-pick` интегрируют изменения, но формируют историю по-разному. `merge` соединяет линии истории, `rebase` пересоздаёт выбранные коммиты поверх нового основания, а `cherry-pick` применяет изменение из конкретного коммита как новый коммит в текущей ветке.

`revert` и `reset` решают разные задачи отмены. `revert` добавляет новый коммит с обратным изменением и сохраняет опубликованную историю. `reset` перемещает текущую ветку и в зависимости от режима меняет index и рабочую директорию, поэтому в основном используется для исправления локальной истории до публикации.

## Сравнение операций

| Операция | Результат | Меняет существующую историю | Основное применение |
| --- | --- | --- | --- |
| `merge` | Соединяет две линии истории; иногда создаёт merge-коммит | Нет | Интегрировать ветку с сохранением её истории |
| `rebase` | Пересоздаёт коммиты на новом основании | Да, меняются идентификаторы коммитов | Обновить и упорядочить собственную feature-ветку |
| `cherry-pick` | Создаёт новый коммит с изменением выбранного коммита | Нет, но добавляет копию изменения | Точечно перенести исправление |
| `revert` | Создаёт новый коммит с обратным изменением | Нет | Отменить опубликованное изменение |
| `reset` | Перемещает текущую ветку; может изменить index и рабочую директорию | Да | Исправить локальные коммиты или подготовленные изменения |

Выбор зависит не только от желаемой формы графа, но и от того, опубликована ли история и работают ли от неё другие разработчики.

## Merge

`git merge source` интегрирует историю `source` в текущую ветку. Если текущую ветку можно просто передвинуть вперёд без разветвления, Git выполняет fast-forward и отдельный merge-коммит не создаётся.

```text
до fast-forward:    A---B  main
                         \
                          C---D  feature

после:             A---B---C---D  main, feature
```

Если обе ветки получили собственные коммиты, обычный merge создаёт коммит с двумя родителями:

```text
      C---D  feature
     /     \
A---B---E---M  main
```

Merge сохраняет существующие идентификаторы коммитов и явный факт объединения. При `--squash` Git помещает итоговые изменения ветки в index, но не создаёт настоящий merge-коммит и не сохраняет связь графов; последующий коммит имеет одного родителя.

## Rebase

`git rebase new-base` находит коммиты текущей ветки, которых нет в новом основании, и последовательно воспроизводит их изменения поверх `new-base`. Каждый воспроизведённый коммит получает нового родителя и новый идентификатор, даже если итоговый код не изменился.

```text
до:          C---D  feature
            /
A---B---E  main

после:  A---B---E---C'---D'  feature
```

Rebase удобен для обновления собственной feature-ветки и получения линейной истории. Конфликт может возникать отдельно на каждом воспроизводимом коммите. После исправления конфликтов используют `git add` и `git rebase --continue`; `git rebase --abort` возвращает состояние до начала операции, а `--skip` пропускает текущий коммит и допустим только при осознанной ненужности его изменения.

```bash
git fetch origin
git switch feature/ABC-123
git rebase origin/main
```

Rebase опубликованной ветки меняет коммиты, которые уже могли получить другие разработчики. Повторная публикация требует обновления удалённой ссылки. Для собственной feature-ветки обычно применяют `git push --force-with-lease`: флаг откажется перезаписывать ветку, если её известное удалённое состояние изменилось. Он снижает риск, но не заменяет согласование работы в общей ветке.

## Cherry-pick

`git cherry-pick <commit>` берёт изменение, которое внёс указанный коммит относительно его родителя, и применяет его к текущей ветке. Результат фиксируется новым коммитом с другим родителем и идентификатором.

```bash
git switch release/1.8
git cherry-pick a1b2c3d
```

Операция подходит, когда небольшое срочное исправление (hotfix) нужно в release-ветке без интеграции всей исходной ветки. Она хуже подходит для переноса связанной серии изменений: можно пропустить зависимый коммит, нарушить порядок или позднее повторно получить то же изменение через merge.

## Revert

`git revert <commit>` вычисляет обратное изменение и создаёт новый коммит. Исходный коммит остаётся в графе, поэтому другие разработчики могут получить отмену обычным pull без восстановления переписанной истории.

```text
A---B---C---R
        ^   ^
     ошибка обратное изменение C
```

```bash
git revert a1b2c3d
```

Revert отменяет изменение, а не гарантирует возврат всего проекта к прежнему состоянию: последующие коммиты могли затронуть тот же код, поэтому возможны конфликты и обязательна проверка поведения. Для merge-коммита Git требует указать основного родителя через `-m`; такая отмена влияет и на дальнейшие merges, поэтому её выполняют только после проверки формы истории.

## Reset и restore

`git reset <target>` перемещает текущую ветку на `target`. Режим определяет, что произойдёт с index и рабочей директорией.

| Режим | Ветка/`HEAD` | Index | Рабочая директория |
| --- | --- | --- | --- |
| `--soft` | Перемещается | Сохраняется | Сохраняется |
| `--mixed` | Перемещается | Сбрасывается к `target` | Сохраняется |
| `--hard` | Перемещается | Сбрасывается к `target` | Сбрасывается к `target` |

`--mixed` используется по умолчанию. Например, `git reset HEAD^` уберёт последний локальный коммит из текущей ветки, но оставит его изменения в рабочей директории как неподготовленные. `--soft` оставит их подготовленными в index. `--hard` удалит отслеживаемые незакоммиченные изменения из рабочей директории, поэтому перед ним нужно точно проверить `git status`, target и возможность восстановления.

Для изменения состояния отдельных файлов понятнее применять `git restore`: `git restore file` возвращает файл в рабочей директории к содержимому index, а `git restore --staged file` убирает файл из staging area, сохраняя рабочие изменения. Эти команды не отменяют уже опубликованный коммит.

## Как выбрать операцию

| Ситуация | Подход |
| --- | --- |
| Влить готовую ветку и сохранить контекст объединения | `merge` |
| Обновить собственную feature-ветку перед MR | `rebase` или `merge` по правилам команды |
| Перенести одно независимое срочное исправление в release | `cherry-pick` |
| Отменить дефектный коммит в общей ветке | `revert` |
| Заменить последний локальный коммит | `git commit --amend` или `git reset` |
| Убрать файл из staging area | `restore --staged` |
| Вернуть потерянное положение локальной ветки | сначала найти коммит через `reflog`, затем создать на него ветку |

`git commit --amend` создаёт замену последнего коммита из текущего index и нового сообщения, поэтому его идентификатор меняется. Перед любой операцией над историей полезно проверить `git status` и граф через `git log --oneline --graph --decorate --all`. После интеграции или отмены запускают тесты: отсутствие Git-конфликта не доказывает корректность поведения приложения.

## Ключевые уточнения

- Fast-forward merge передвигает ветку без отдельного merge-коммита.
- Rebase создаёт новые коммиты и меняет их идентификаторы, потому что меняются родители.
- Cherry-pick переносит изменение выбранного коммита, а не связь с исходной веткой.
- Revert сохраняет общую историю и добавляет в неё явную отмену.
- Reset управляет веткой, index и рабочей директорией; режим определяет затронутые области.
- `--force-with-lease` проверяет известное состояние удалённой ветки, но общую ветку всё равно переписывают только по согласованному правилу.
