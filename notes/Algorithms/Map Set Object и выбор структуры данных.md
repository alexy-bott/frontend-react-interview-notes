## Быстрый ответ

Структуру данных выбирают по требуемым операциям и ограничениям хранения. `Array` представляет упорядоченную последовательность и подходит для рендера списка. `Set` хранит уникальные значения и удобен для частой проверки наличия. `Map` хранит пары ключ–значение с ключами любого типа. `Object` или `Record` естественны для структуры с известными полями и данных, которые должны без преобразования сериализоваться в JSON.

`Map` и `Set` обычно дают быстрые `get`/`has`/`set`, но ECMAScript требует лишь среднюю сублинейную скорость доступа, а не обязательную `O(1)` для каждого движка. Они расходуют дополнительную память и являются мутабельными, поэтому в React state создают новый экземпляр, а в Redux Toolkit state по умолчанию предпочитают сериализуемые массивы и объекты.

Частый frontend-сценарий: API возвращает массив для порядка отображения, а рядом строится индекс `Map<id, item>` для быстрых связей. Не нужно заменять индексом простой одноразовый поиск по маленькому списку: структура должна упрощать реальные операции.

## Как выбирать

| Требование | Структура | Причина |
| --- | --- | --- |
| Сохранить порядок и пройти элементы | `Array<T>` | индексы и методы последовательной обработки |
| Хранить уникальные значения | `Set<T>` | уникальность и `has` |
| Часто получать значение по динамическому ключу | `Map<K, V>` | явный API коллекции и ключи любого типа |
| Описать сущность с известными полями | object / interface | свойства имеют предметный смысл |
| Хранить строковый словарь в JSON или Redux state | `Record<string, T>` | естественная сериализация и DevTools |
| Привязать метаданные к объекту, не удерживая его в памяти | `WeakMap<object, T>` | слабая ссылка на ключ |

Порядок важен отдельно от поиска. Даже если сущности индексируются через `Map`, UI часто хранит `ids: string[]`, чтобы явно управлять сортировкой и рендером.

## Array

Массив допускает дубли, хранит порядок и предоставляет доступ по числовому индексу. Получение `array[i]` типично `O(1)`, а поиск значения через `find` или `includes` — `O(n)` в худшем случае.

Array остаётся лучшей моделью, когда нужно отобразить последовательность, сохранить сортировку, взять диапазон или выполнить один проход. Создание `Set` ради единственной проверки в массиве из пяти элементов добавит код и память без заметной пользы.

## Set

`Set` хранит каждое значение один раз и сохраняет порядок вставки при итерации. `has`, `add` и `delete` в обычной реализации считаются средними `O(1)`, но строгая гарантия спецификации — средняя сублинейная сложность.

Значения сравниваются по SameValueZero: `NaN` совпадает с `NaN`, а `0` и `-0` считаются одинаковыми. Объекты сравниваются по ссылке:

```ts
new Set([{ id: 1 }, { id: 1 }]).size; // 2
```

Для дедупликации объектов по смысловому ключу нужен `Map<id, object>` или отдельный `Set` уже встреченных ID.

## Map

`Map` принимает ключи любого типа, явно сообщает `size`, итерируется в порядке вставки и не смешивает данные с prototype. Это делает его удобным для динамического индекса, кеша внутри вычисления или группировки.

Ключи также сравниваются по SameValueZero, а объекты-ключи — по ссылке. Два равных по содержимому объекта являются разными ключами. Если ключ приходит из URL или JSON, он обычно строковый, и `Record<string, T>` может быть проще для сериализации.

`Map` не превращает построение индекса в бесплатную операцию. Создание из `n` элементов требует типично `O(n)` времени и памяти. Индекс выгоден при множественных поисках или когда он выражает основную модель доступа.

## Object и Record

Object подходит для сущности или конфигурации с известными именованными полями. Ключами свойств могут быть строки или symbols; числовая запись ключа преобразуется в строку.

При использовании объекта как словаря нужно отличать собственные свойства от унаследованных:

```ts
if (Object.hasOwn(userById, id)) {
  return userById[id];
}
```

Для словаря без prototype можно создать `Object.create(null)`, но TypeScript-типизация и сериализация должны быть осознанными. Неконтролируемые ключи нельзя без проверки смешивать с объектом конфигурации: специальные свойства и prototype pollution создают риск. `Map` естественнее отделяет динамические ключи от свойств объекта.

## WeakMap

`WeakMap` хранит значения по ключам, доступным для сборки мусора, так что сама запись не препятствует удалению ключа из памяти. Текущая спецификация разрешает объекты и незарегистрированные symbols; в практическом frontend-сценарии ключом почти всегда служит объект. WeakMap подходит для метаданных DOM-узлов, кеша вычисления по объекту или внутренних данных экземпляра.

WeakMap не итерируется и не имеет `size`: невозможно надёжно перечислить ключи, которые сборщик мусора может удалить в любой момент. Его выбирают по жизненному циклу, а не как «более быстрый Map».

## Ограничения React и Redux

`Map` и `Set` изменяются на месте. Такой код сохраняет ту же ссылку и не является корректным неизменяемым обновлением React state:

```ts
selectedIds.add(id);
setSelectedIds(selectedIds);
```

Создают новый экземпляр:

```ts
setSelectedIds(previous => {
  const next = new Set(previous);
  next.add(id);
  return next;
});
```

Redux Toolkit по умолчанию проверяет state и actions на сериализуемость. `Map`, `Set`, экземпляры классов и функции не сериализуются обычным JSON и затрудняют time-travel и отладку, поэтому нормализованное состояние сущностей обычно хранит `ids` и объект `entities`. Исключение требует явного архитектурного решения и настройки middleware, а не случайного помещения `Map` в store.

## Где применяется во frontend

| Ситуация | Подход | Стоимость и ограничение |
| --- | --- | --- |
| Выбранные строки таблицы | `Set<string>` | быстрый `has`, новый Set при обновлении state |
| Связать orders с users | `Map<userId, User>` | `O(u)` памяти ради типичного `O(1)` поиска |
| Нормализовать Redux state | `ids[]` + `Record<id, Entity>` | порядок отдельно, сериализуемый индекс отдельно |
| Сгруппировать товары | `Map<categoryId, Product[]>` | один проход, затем явное преобразование для JSON |
| Убрать дубли объектов по ID | `Map<id, object>` | при повторе остаётся последнее записанное значение |
| Метаданные для DOM-узлов | `WeakMap<Node, Metadata>` | ключи не удерживаются и не перечисляются |

## Пример

Дедупликация по ID с явной политикой «последняя версия побеждает»:

```ts
function uniqueUsersById(users: User[]): User[] {
  const userById = new Map<string, User>();

  for (const user of users) {
    userById.set(user.id, user);
  }

  return [...userById.values()];
}
```

Группировка:

```ts
function groupByCategory(products: Product[]) {
  const productsByCategory = new Map<string, Product[]>();

  for (const product of products) {
    const group = productsByCategory.get(product.categoryId);

    if (group) {
      group.push(product);
    } else {
      productsByCategory.set(product.categoryId, [product]);
    }
  }

  return productsByCategory;
}
```

Мутация массивов внутри локального нового `Map` безопасна: структура ещё не опубликована как React state. Функция проходит `n` товаров за типичное `O(n)` время и хранит `O(n)` ссылок в группах.

## Ключевые уточнения

- Array выражает последовательность, Set — уникальность, Map — динамическую связь ключ–значение, Object — именованную структуру данных.
- Map и Set сохраняют порядок вставки, но их ключевое преимущество — контракт коллекции, а не сортировка.
- Ключи Object приводятся к строкам или являются symbols; Map сохраняет тип ключа.
- Set и Map сравнивают объекты по ссылке, поэтому содержательная дедупликация требует ключа.
- WeakMap нужен для слабого жизненного цикла объектов или незарегистрированных symbols и не поддерживает перечисление.
- Map и Set требуют immutable-обновления в React и обычно не помещаются напрямую в Redux Toolkit state.
- Индекс ускоряет повторный поиск ценой времени построения и дополнительной памяти.
