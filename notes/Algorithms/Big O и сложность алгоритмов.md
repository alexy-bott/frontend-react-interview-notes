## Быстрый ответ

Big O, или «O-большое», показывает верхнюю асимптотическую границу роста затрат алгоритма при увеличении размера входа `n`. На практике им оценивают временную сложность (time complexity) — как растёт количество работы — и дополнительную пространственную сложность (space complexity) — как растёт используемая помимо входа память.

Big O не предсказывает точное время в миллисекундах и не учитывает напрямую язык, устройство и константы. Оно позволяет сравнить масштабируемость: один проход по массиву — `O(n)`, типичная сортировка сравнениями — `O(n log n)`, а сравнение каждого элемента с каждым — `O(n²)`.

Во frontend сложность важна при обработке API-данных, фильтрации таблиц, построении деревьев, проверке выбранных строк и вычислениях на каждом рендере. Частый приём — один раз построить `Map` или `Set`, потратить `O(n)` дополнительной памяти и убрать повторные линейные поиски.

## Классы роста

| Сложность | Название | Как растёт | Пример |
| --- | --- | --- | --- |
| `O(1)` | константная | оценка не зависит от `n` | чтение элемента массива по индексу |
| `O(log n)` | логарифмическая | вход на каждом шаге уменьшается в несколько раз | бинарный поиск в отсортированном массиве |
| `O(n)` | линейная | работа пропорциональна числу элементов | `map`, `filter`, подсчёт суммы |
| `O(n log n)` | линейно-логарифмическая | линейное число уровней с логарифмической глубиной | эффективная сортировка сравнениями |
| `O(n²)` | квадратичная | для каждого элемента обрабатывается порядка `n` элементов | полный перебор пар |
| `O(2^n)` | экспоненциальная | добавление элемента примерно удваивает число вариантов | перебор всех подмножеств |
| `O(n!)` | факториальная | перебираются перестановки | полный перебор порядка `n` элементов |

Последние два класса быстро становятся непрактичными и обычно встречаются в задачах перебора, а не в обычной обработке UI-списка.

```text
n = 100
O(n)   -> порядка 100 операций
O(n²)  -> порядка 10 000 пар

Это иллюстрация роста, а не измерение реального времени.
```

## Как выводить сложность

1. Определить размер входа: число строк, пользователей, символов или узлов.
2. Выбрать значимую операцию и посчитать, сколько раз она выполняется относительно входа.
3. Для последовательных этапов сложить стоимость и оставить доминирующий рост.
4. Для вложенных независимых проходов перемножить размеры.
5. Отдельно оценить дополнительную память.

```ts
for (const user of users) {
  renderUser(user);
}

for (const order of orders) {
  renderOrder(order);
}
```

Если считать `renderUser` и `renderOrder` операциями постоянной стоимости, два последовательных прохода стоят `O(u + o)`. Если обе коллекции считать одним входом размера `n`, это упрощается до `O(n)`, а не `O(n²)`.

```ts
for (const user of users) {
  for (const role of roles) {
    compare(user, role);
  }
}
```

Вложенные проходы стоят `O(u * r)`. Запись `O(n²)` верна только при сопоставимых размерах, обозначенных одной переменной `n`.

Константы и младшие члены отбрасывают: `3n + 10` относится к `O(n)`, а `n² + n` — к `O(n²)`. Для небольших данных константы всё равно влияют на реальное время, поэтому Big O не заменяет профилирование.

## Временная и пространственная сложность

Подсчёт суммы проходит все элементы за `O(n)` времени и использует `O(1)` дополнительной памяти: количество вспомогательных переменных не растёт с массивом.

Построение `Set` из массива занимает типично `O(n)` времени и `O(n)` дополнительной памяти. Проверки наличия после этого становятся быстрыми в среднем. Это обмен времени на память, а не бесплатная оптимизация.

При оценке space complexity обычно отдельно называют дополнительную память алгоритма. Сам входной массив уже существует и не считается новой памятью, если алгоритм его не копирует. Рекурсивный вызов также использует стек: глубина рекурсии входит в пространственную сложность.

## Случаи и амортизированная оценка

Best, average и worst case описывают лучший, средний и худший вход для выбранного алгоритма. `find` может завершиться на первом элементе, но в худшем случае просмотрит весь массив. Big O само по себе означает верхнюю границу и не равно автоматически worst case; при ответе нужно назвать, какой случай оценивается.

Амортизированная сложность усредняет стоимость последовательности операций. Добавление в конец динамического массива обычно `O(1)` амортизированно: отдельное расширение внутреннего хранилища может стоить `O(n)`, но происходит не при каждом `push`.

Для более точной математической записи существуют:

- `O(...)` — асимптотическая верхняя граница;
- `Ω(...)` — нижняя граница;
- `Θ(...)` — точная граница порядка роста сверху и снизу.

В обычном техническом разговоре Big O часто используют неформально как название порядка роста. Если точность важна, полезно отделять эту практику от строгого определения.

## Где применяется во frontend

| Ситуация | Стоимость | Улучшение |
| --- | --- | --- |
| Для каждого selected ID выполняется `items.find(...)` | `O(s * n)` | построить индекс `Map<id, item>` за `O(n)` |
| Каждая строка вызывает `selectedIds.includes(id)` | `O(rows * s)` | хранить выбранные ID в `Set` |
| Дерево строится через `filter` детей для каждого узла | до `O(n²)` | индексировать узлы или детей за один проход |
| Большой список фильтруется при каждом вводе | `O(n)` на каждое событие | debounce, серверный поиск, Web Worker или уменьшение входа по ситуации |
| Сортировка запускается на каждом рендере | типично `O(n log n)` каждый раз | считать только при изменении зависимостей и измерить стоимость |

Мемоизация помогает только при повторном вызове с неизменившимися зависимостями. Если массив или параметры меняются каждый раз, вычисление всё равно повторится, а кеш добавит собственную стоимость.

## Пример

Повторный поиск каждого выбранного элемента:

```ts
function getSelectedItems(items: Item[], selectedIds: string[]) {
  return selectedIds
    .map(id => items.find(item => item.id === id))
    .filter((item): item is Item => item !== undefined);
}
```

Для `n` элементов и `s` выбранных ID худшее время — `O(n * s)`, дополнительная память результата — `O(s)`.

Предварительный индекс:

```ts
function getSelectedItems(items: Item[], selectedIds: string[]) {
  const itemById = new Map(items.map(item => [item.id, item]));

  return selectedIds
    .map(id => itemById.get(id))
    .filter((item): item is Item => item !== undefined);
}
```

Построение индекса занимает `O(n)`, обход ID — типично `O(s)`, итого `O(n + s)` времени и `O(n + s)` дополнительной памяти с учётом индекса и результата. Оптимизация выгодна при достаточно больших данных или повторном использовании индекса; для маленького одноразового списка первый вариант может быть проще.

## Ключевые уточнения

- Big O описывает рост относительно размера входа, а измерение показывает время в конкретной среде.
- Временную и дополнительную пространственную сложность оценивают отдельно.
- Линейная, квадратичная и другие сложности называют по форме роста, а не по конкретному числу операций.
- Вложенные циклы перемножают размеры только когда внутренний объём действительно выполняется для каждого внешнего элемента.
- Best, average и worst case — характеристика выбранного случая; Big O — вид асимптотической границы.
- Амортизированная оценка объясняет редкие дорогие операции внутри дешёвой последовательности.
- `Map` и `Set` обычно ускоряют поиск ценой дополнительной памяти, но конкретные гарантии зависят от спецификации и реализации.
