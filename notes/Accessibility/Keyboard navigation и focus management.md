## Быстрый ответ

Клавиатурная навигация (keyboard navigation) означает, что все действия доступны без мыши и работают по ожидаемой для компонента модели. `Tab` перемещает фокус между обычными элементами управления, кнопка активируется через `Enter` или `Space`, ссылка — через `Enter`, а внутри составного компонента (widget), например tabs или menu, часто используются стрелки по правилам конкретного паттерна.

Управление фокусом (focus management) — осознанное перемещение фокуса после изменения интерфейса. Модальное диалоговое окно получает фокус при открытии и возвращает его на элемент открытия при закрытии; после удаления сфокусированного элемента фокус переводится на логичного соседа; после неуспешной отправки большой формы его можно перевести на сводку ошибок.

По умолчанию лучше сохранять нативный порядок DOM. `tabindex="0"` включает элемент в последовательность `Tab`, `tabindex="-1"` оставляет возможность программного фокуса, а положительные значения создают отдельный приоритетный порядок и обычно делают навигацию непредсказуемой.

## Базовая модель

```text
семантический элемент
-> нативная возможность получить фокус
-> ожидаемые клавиши управления
-> видимый focus indicator
-> осознанное перемещение после изменения UI
```

| Элемент или паттерн | Основные клавиши |
| --- | --- |
| Button | `Tab` для перехода, `Enter` или `Space` для активации |
| Link | `Tab` для перехода, `Enter` для открытия |
| Checkbox | `Tab` для перехода, `Space` для переключения |
| Radio group | `Tab` входит в группу, стрелки меняют выбранный вариант |
| Tabs | `Tab` входит в компонент, стрелки переходят между tabs по выбранной APG-модели |
| Menu | стрелки переходят между элементами, `Enter`/`Space` активируют, `Esc` закрывает |
| Modal dialog | `Tab` и `Shift+Tab` остаются внутри, `Esc` обычно закрывает |

Конкретные клавиши зависят от роли. Добавлять обработку стрелок каждому списку не нужно: обычные ссылки и кнопки уже перемещаются через `Tab`.

## Естественный порядок фокуса

Нативные ссылки, кнопки и поля формы участвуют в последовательной навигации автоматически. Порядок обычно следует DOM, поэтому DOM и визуальное расположение должны оставаться логически согласованными. CSS `order` или визуальное перемещение элемента не перестраивает последовательность фокуса.

| Значение `tabindex` | Поведение |
| --- | --- |
| отсутствует | используется нативная фокусируемость элемента |
| `0` | элемент включается в обычный DOM-порядок `Tab` |
| `-1` | `Tab` пропускает элемент, но на него можно вызвать `.focus()` |
| положительное | создаёт приоритет перед обычным порядком; почти всегда следует изменить DOM вместо этого |

`tabindex="0"` не превращает `div` в кнопку: он добавляет только возможность фокуса. Роль, обработка клавиш, состояния и доступное имя остаются ответственностью компонента.

Нативный `disabled` обычно убирает элемент управления из последовательности фокуса и блокирует активацию. `aria-disabled="true"` только сообщает состояние вспомогательным технологиям; обработчик и визуальное поведение разработчик блокирует сам. Выбор зависит от того, должен ли недоступный элемент оставаться доступным для чтения в порядке навигации.

## Навигация внутри сложного компонента

Menu, tabs, tree и grid считаются составными компонентами: `Tab` обычно входит в компонент один раз, а между внутренними элементами пользователь перемещается стрелками. Один распространённый способ реализации — roving `tabindex`: активный элемент получает `tabindex="0"`, остальные `-1`; при переходе значения и фокус перемещаются вместе.

```text
Tab -> [Tab A: tabindex=0] [Tab B: -1] [Tab C: -1]
Right Arrow
       [Tab A: -1] [Tab B: tabindex=0] [Tab C: -1]
```

Это сложное поведение должно соответствовать WAI-ARIA Authoring Practices, включая Home/End, ориентацию, недоступные элементы и связь с активной панелью. Для select, combobox, menu и dialog надёжнее использовать нативный элемент или проверенный headless-компонент, чем собирать частичную реализацию.

## Когда перемещать фокус

Фокус перемещают, когда без этого пользователь теряет контекст или остаётся на исчезнувшем элементе:

| Событие | Разумная цель |
| --- | --- |
| Открытие modal dialog | элемент внутри dialog согласно содержимому и риску действия |
| Закрытие dialog | элемент открытия или следующий логичный элемент, если первый исчез |
| Удаление строки | действие соседней строки, заголовок списка или кнопка добавления |
| Ошибки после submit | сводка ошибок или первое невалидное поле |
| Клиентская навигация SPA | заголовок или main по принятой политике навигации |

Фокус не следует перемещать после каждого обновления, сообщения или сетевого ответа. Неинтерактивное изменение можно объявить через живую область (live region), сохранив текущую позицию пользователя. При SPA-навигации учитывают источник перехода и восстановление позиции при Back/Forward; автоматический фокус на каждом рендере также будет мешать.

Для modal dialog initial focus зависит от содержимого. В коротком безопасном dialog это может быть первая кнопка. В длинном dialog фокус иногда ставят на статический заголовок с `tabindex="-1"`, чтобы пользователь сначала услышал контекст. В подтверждении разрушительного действия разумно сначала сфокусировать безопасную кнопку отмены.

## Видимый фокус

Пользователь должен всегда понимать, какой элемент управления активен. `:focus-visible` позволяет показывать выразительный индикатор преимущественно при клавиатурном способе взаимодействия:

```css
.button:focus-visible {
  outline: 3px solid #0b63ce;
  outline-offset: 3px;
}
```

Удаление стандартного outline браузера допустимо только при равноценной замене. Индикатор должен быть виден на разных фонах, не обрезаться `overflow` и отличаться не только небольшим изменением цвета.

## Пример

Сводка получает программный фокус только после неуспешной отправки, а не при каждой проверке поля:

```tsx
import { useEffect, useRef } from "react";

type ErrorSummaryProps = {
  errors: string[];
  submitAttempt: number;
};

function ErrorSummary({ errors, submitAttempt }: ErrorSummaryProps) {
  const summaryRef = useRef<HTMLElement>(null);

  useEffect(() => {
    if (submitAttempt > 0 && errors.length > 0) {
      summaryRef.current?.focus();
    }
  }, [errors.length, submitAttempt]);

  if (errors.length === 0) return null;

  return (
    <section ref={summaryRef} tabIndex={-1} aria-labelledby="error-title">
      <h2 id="error-title">Проверьте форму</h2>
      <ul>
        {errors.map(error => <li key={error}>{error}</li>)}
      </ul>
    </section>
  );
}
```

`tabIndex={-1}` позволяет сфокусировать section программно, но не добавляет его в обычную последовательность `Tab`. В рабочем коде для ключа ошибки нужен стабильный идентификатор, если одинаковые тексты могут повторяться.

## Проверка

1. Пройти сценарий только клавишами и не использовать мышь для «спасения».
2. Проверить логичный порядок `Tab` и `Shift+Tab` и отсутствие положительных `tabindex`.
3. Проверить ожидаемые стрелки, `Enter`, `Space`, `Esc`, Home и End для используемого паттерна.
4. Убедиться, что фокус видим, не попадает под перекрывающий слой и не остаётся на удалённом узле.
5. Проверить открытие, закрытие и повторное открытие overlays, а также Back/Forward в SPA.

## Ключевые уточнения

- Семантический HTML предоставляет нативную фокусируемость и клавиши; `tabindex` добавляет только участие в фокусе.
- Последовательность `Tab` следует DOM, поэтому визуальная перестановка не должна создавать другой смысловой порядок.
- Стрелки используются внутри определённых составных компонентов, а не как замена `Tab` для всей страницы.
- Программный фокус оправдан потерей контекста или началом нового явного взаимодействия.
- `aria-disabled` сообщает состояние, но самостоятельно не блокирует действие.
- `:focus-visible` помогает оформить фокус, но индикатор должен оставаться заметным и устойчивым.
