## Быстрый ответ

Доступность (accessibility, a11y) означает, что интерфейс остаётся воспринимаемым и управляемым для людей с разными возможностями зрения, слуха, движения и восприятия. Пользователь может работать с сайтом с клавиатуры, screen reader, увеличением, голосовым управлением или другими вспомогательными технологиями.

На уровне HTML основа доступности — правильные нативные элементы, понятные доступные имена, логичная структура заголовков и корректные связи между элементами формы. CSS и JavaScript дополняют эту основу: сохраняют видимый фокус, масштабирование, контраст, управление динамическими компонентами и понятные ошибки. ARIA используют, когда нативной семантики недостаточно, но она не заменяет встроенное поведение HTML.

## Карта темы

| Область | Что нужно обеспечить |
| --- | --- |
| Семантика | браузер и вспомогательные технологии понимают назначение элементов |
| Доступное имя | у элемента управления понятно, как он называется и для чего нужен |
| Клавиатура | пользователь может выполнить сценарий без мыши |
| Фокус | видно, где находится клавиатурный фокус, а его перемещение предсказуемо |
| Формы и ошибки | поля имеют подписи, а ошибки объясняют проблему и связаны с нужным полем |
| Визуальное представление | контент сохраняется при увеличении, не зависит только от цвета, фокус остаётся видимым |
| Медиа | содержательная информация имеет подходящую текстовую или синхронизированную альтернативу |
| Проверка | автоматические инструменты дополняются ручными проверками |

Эти области соответствуют практической реализации принципов WCAG: perceivable, operable, understandable и robust.

## Семантика, доступное имя и accessibility tree

Браузер использует семантику HTML, ARIA и текущее состояние страницы, чтобы сформировать представление интерфейса для accessibility API. В нём элемент управления может иметь роль, доступное имя, описание и состояние. Screen reader получает эту информацию через accessibility API и позволяет пользователю перемещаться по заголовкам, landmarks и элементам управления.

Доступное имя отвечает на вопрос «как называется этот элемент?». Источник имени зависит от элемента. Например:

- текст `<button>` обычно становится именем кнопки;
- связанный `<label>` задаёт имя полю формы;
- `aria-labelledby` может связать элемент с видимой подписью;
- `aria-label` может задать имя, когда подходящего видимого текста нет.

Placeholder внутри поля не является хорошей заменой постоянной подписи: он исчезает при вводе и выполняет другую функцию.

Нативный элемент обычно даёт и семантику, и ожидаемое поведение. У `<button>` уже есть роль кнопки, фокус и клавиатурная активация. Если сделать кнопку из `<div role="button">`, роль появится, но фокус, `Enter`, `Space` и disabled-поведение разработчику придётся реализовать самостоятельно.

## Клавиатура и фокус

Интерактивные элементы должны быть доступны с клавиатуры в понятном порядке. Обычно естественный порядок DOM даёт правильную последовательность `Tab`; положительный `tabindex` создаёт отдельный ручной порядок и поэтому редко является хорошим решением.

Клавиатурный пользователь должен видеть текущий фокус. Удалять `outline` без равноценной замены нельзя: если элемент получил фокус, пользователь должен понимать, где он находится.

Динамический интерфейс иногда требует управлять фокусом через JavaScript. Например, при открытии модального диалога фокус переводят внутрь него, клавиатурная навигация остаётся в пределах модального содержимого, а после закрытия фокус обычно возвращают к элементу, который открыл диалог. Подробные правила зависят от типа виджета и описаны в соответствующих WAI-ARIA patterns.

## Формы, визуальное представление и медиа

Поле формы, которому нужна пользовательская подпись, должно иметь понятное доступное имя, обычно через видимый `<label>`. Если значение недопустимо, `aria-invalid="true"` может передать состояние, а `aria-describedby` — связать поле с текстом ошибки или подсказки.

Информация не должна передаваться только цветом. Текст и элементы управления должны сохранять достаточный контраст, а увеличение текста и zoom не должны приводить к потере содержимого или функций.

Для изображений `alt` передаёт смысл или функцию изображения в текущем контексте; декоративный `<img>` получает `alt=""`. Для prerecorded video с аудиоконтентом нужны captions, если видео не является явно обозначенной альтернативой уже существующему тексту. Для prerecorded audio-only нужен эквивалентный способ получить ту же информацию, часто в виде transcript.

## Пример

```html
<label for="email">Email</label>
<input
  id="email"
  name="email"
  type="email"
  aria-invalid="true"
  aria-describedby="email-error"
>
<p id="email-error" role="alert">
  Введите адрес в формате name@example.com.
</p>
```

`label` задаёт доступное имя поля. `aria-invalid` сообщает, что текущее значение недопустимо, а `aria-describedby` связывает поле с объяснением ошибки.

`role="alert"` уместен, если сообщение появляется или обновляется динамически и его нужно сразу объявить пользователю screen reader. Если текст ошибки уже присутствует при первоначальной загрузке страницы, добавлять `role="alert"` только ради самого наличия ошибки не требуется.

## Как проверять доступность

Автоматический scanner полезен для части нарушений: отсутствующих имён, некоторых ошибок ARIA, контраста и структуры. Но он не знает весь пользовательский сценарий.

Поэтому автоматическую проверку дополняют вручную:

1. Пройти основной сценарий только клавиатурой.
2. Проверить порядок и видимость фокуса.
3. Увеличить страницу и убедиться, что содержимое и действия не теряются.
4. Проверить accessibility tree: роль, имя, описание и состояние ключевых элементов.
5. Для критичных сценариев выполнить целевой тест со screen reader.

## Где применяется во frontend

- При выборе HTML-элементов: нативная кнопка, ссылка, поле и заголовок дают браузеру правильную исходную семантику.
- При создании форм: `label`, описание ошибки и состояние поля должны быть связаны с соответствующим элементом управления.
- При разработке modal, menu и других динамических компонентов: требуется продуманное клавиатурное и focus-поведение.
- При стилизации: нельзя скрывать фокус, запрещать необходимое увеличение или передавать информацию только цветом.
- При работе с изображениями, аудио и видео: нужно определить, какая альтернатива передаст ту же содержательную функцию.
- При тестировании: автоматические проверки используются как часть процесса, а не как доказательство полной доступности.

## Ключевые уточнения

- Доступность — свойство полного пользовательского сценария, а не наличие отдельного ARIA-атрибута.
- Нативный HTML обычно даёт семантику и базовое поведение одновременно; ARIA в основном дополняет информацию для accessibility API.
- Доступное имя называет элемент управления, а дополнительное описание объясняет формат, ошибку или другой контекст.
- Клавиатурный фокус должен быть доступен и визуально заметен.
- Placeholder не заменяет постоянную подпись поля.
- Автоматическая проверка не подтверждает доступность целиком: важные сценарии нужно проходить вручную.
