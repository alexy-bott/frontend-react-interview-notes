## Быстрый ответ

Стратегия тестирования распределяет проверки по рискам, а не по обязательному проценту unit/integration/E2E. Чем выше вероятность и ущерб регрессии, тем сильнее должна быть проверка критичного contract. Быструю pure logic проверяют unit tests, пользовательское UI-поведение — integration tests, а небольшой набор сквозных business flows — E2E.

Уровень теста выбирают по риску. Чистую функцию, formatter или reducer проверяют unit-тестом. Компонент, форму, async state и взаимодействие с API проверяют integration-тестом через Testing Library и мок сети. Полный login, checkout, создание заказа, routing и права доступа закрывают E2E в реальном браузере. Цель - поведение пользователя и бизнес-инварианты, а не private functions, class names и внутренний state компонента.

Стратегия также включает test data, стабильные selectors, мокинг времени и сети, запуск в CI, покрытие критичных flows и борьбу с flaky. Coverage полезен как индикатор дыр, но сам по себе не доказывает качество: 90% строк могут не проверять ни одного важного пользовательского сценария.

## Ключевая схема

| Уровень | Что проверяет | Плюсы | Минусы |
| --- | --- | --- | --- |
| Unit | чистые функции, reducers, utils | быстро, дёшево | мало уверенности в интеграции |
| Integration | компонент + state + network mock | баланс скорости и уверенности | требует аккуратной среды |
| E2E | путь пользователя в браузере | высокая уверенность | медленнее и дороже |
| Contract | форма API между frontend/backend | ловит несовместимость | требует процесса |
| Visual | внешний вид и регрессии UI | ловит layout diff | шум от нестабильных снимков |

## Базовая модель

Стратегия тестирования начинается с рисков продукта. Сначала закрывают критичные пользовательские сценарии: авторизация, оплата, отправка формы, сохранение данных, права доступа, ошибки API и важные edge cases. Затем покрывают сложные функции и компоненты, где часто возникают регрессии.

Risk можно оценивать через вероятность × последствия: частота изменения, сложность state/async logic, число интеграций, финансовый/безопасностный ущерб и история bugs. Эта оценка определяет не только наличие теста, но и уровень, scenarios и частоту запуска.

## Развернутый ответ

Уровень теста выбирают по природе поведения. Чистая логика без DOM подходит для unit-теста. Поведение, видимое через интерфейс, проверяют integration-тестом: render компонента, действия пользователя, ожидание результата на экране. Полный путь через routing, backend contract, auth/storage и браузерное окружение закрывает E2E.

E2E не должен дублировать все unit и integration проверки. Его задача - доказать, что пользователь может пройти ценный flow целиком. Если каждую маленькую ветку UI перенести в E2E, pipeline станет медленным, дорогим и более flaky.

Coverage показывает, какие строки выполнились во время тестов, но не показывает качество assertions. Высокий процент покрытия может проверять слабые утверждения и не ловить критичный сценарий. Coverage полезен как сигнал дыр, но не как главная цель стратегии.

Mocks ставят на внешних нестабильных границах: network, timers, browser APIs, analytics, storage. Избыточный mocking отрывает тест от реального поведения приложения, поэтому важно сохранять баланс между контролем окружения и проверкой настоящей интеграции.

Contract, accessibility, visual и performance checks не являются дополнительными ступенями одной пирамиды. Они проверяют другие свойства: совместимость API schema, доступность, геометрию UI и budgets. Их добавляют там, где соответствующая регрессия имеет реальный риск.

После production bug определяют, на каком самом дешёвом уровне можно надёжно воспроизвести нарушенный contract, и добавляют regression test. Не каждый bug требует E2E: parser bug лучше закрыть unit test, mapping `422` — integration test, broken deployment route — smoke/E2E.

## Как выбрать уровень теста

| Нужно проверить | Уровень |
| --- | --- |
| Formatter, mapper, reducer, pure util | unit |
| Компонент реагирует на ввод и показывает ошибку | integration |
| Форма отправляет DTO и маппит `422` в поля | integration + MSW |
| Auth refresh повторяет исходный запрос | integration/API-client test |
| Пользователь проходит login/checkout целиком | E2E |
| API contract изменился несовместимо | contract/schema check |
| Верстка сложного компонента не съехала | visual regression при реальном риске |

## Ключевые уточнения

- Пирамида/trophy — эвристики распределения стоимости, а не обязательные числовые квоты.
- Приоритет задают product risk, частота изменений и цена пропущенной регрессии.
- Coverage показывает исполненные участки, но mutation/meaningful assertions определяют силу проверки.
- Contract test нужен только при понятном producer/consumer process; один fixture может сам устареть вместе с client.
- E2E не дублирует все component branches, а доказывает работоспособность критичного сквозного пути.
- Regression test добавляют на минимальном уровне, который воспроизводит причину, а не только внешний симптом.
