## Быстрый ответ

Big O, или «O-большое», показывает, как растут затраты алгоритма при увеличении размера входа `n`. Формально это верхняя асимптотическая граница: нас интересует порядок роста на больших входах, а не точное количество операций для конкретного `n`.

На практике через Big O оценивают временную сложность (time complexity) — как растёт количество работы — и дополнительную пространственную сложность (space complexity) — как растёт используемая помимо входа память.

Big O не предсказывает точное время в миллисекундах и не учитывает напрямую язык, устройство и константы. Оно позволяет сравнить масштабируемость: один проход по массиву — `O(n)`, эффективная сортировка сравнениями — обычно `O(n log n)`, а сравнение каждого элемента с каждым — `O(n²)`.

Во frontend сложность важна при обработке API-данных, фильтрации таблиц, построении деревьев, проверке выбранных строк и вычислениях на каждом рендере. Частый приём — один раз построить `Map` или `Set`, потратить `O(n)` дополнительной памяти и заменить повторные линейные поиски на обычно более дешёвые проверки по индексу.

## Классы роста

| Сложность    | Название                | Как растёт                                                       | Пример                                             |
| ------------ | ----------------------- | ---------------------------------------------------------------- | -------------------------------------------------- |
| `O(1)`       | константная             | оценка не зависит от `n`                                         | чтение элемента массива по индексу                 |
| `O(log n)`   | логарифмическая         | вход на каждом шаге уменьшается в несколько раз                  | бинарный поиск в отсортированном массиве           |
| `O(n)`       | линейная                | работа пропорциональна числу элементов                           | один проход, `map` или `filter` с дешёвым callback |
| `O(n log n)` | линейно-логарифмическая | примерно `log n` уровней работы, на каждом обрабатывается `O(n)` | эффективная сортировка сравнениями                 |
| `O(n²)`      | квадратичная            | для каждого элемента обрабатывается порядка `n` элементов        | полный перебор пар                                 |
| `O(2^n)`     | экспоненциальная        | добавление элемента примерно удваивает число вариантов           | перебор всех подмножеств                           |
| `O(n!)`      | факториальная           | перебираются перестановки                                        | полный перебор порядка `n` элементов               |

Для `map`, `filter` и других методов одного прохода запись `O(n)` предполагает, что callback сам выполняет `O(1)` работы. Если внутри него запускается поиск, сортировка или другой зависящий от размера входа алгоритм, его стоимость тоже нужно учитывать.

В `O(log n)` основание логарифма обычно не указывают. Логарифмы с разными постоянными основаниями отличаются только постоянным множителем, а такие множители в асимптотической записи отбрасываются.

Последние два класса быстро становятся непрактичными и обычно встречаются в задачах перебора, а не в обычной обработке UI-списка.

```text
n = 100

линейный рост:       условно ~100 единиц работы
квадратичный рост:   условно ~10 000 единиц работы

Это иллюстрация разницы в характере роста, а не утверждение,
что любой алгоритм O(n) выполняет ровно n операций.
```

## Как выводить сложность

1. Определить размер входа: число строк, пользователей, символов или узлов.
2. Определить значимые операции и посчитать, сколько раз они выполняются относительно входа.
3. Учесть стоимость вызываемых функций: вызов функции не является `O(1)`, если внутри неё выполняется работа, зависящая от размера данных.
4. Для последовательных этапов сложить стоимость и оставить доминирующий рост.
5. Для вложенных проходов перемножить размеры, если внутренний объём работы выполняется для каждого элемента внешнего прохода.
6. Для альтернативных веток определить, какая ветка выполняется в рассматриваемом случае; для worst case берут наиболее дорогую возможную ветку.
7. Отдельно оценить дополнительную память.

```ts
for (const user of users) {
  renderUser(user);
}

for (const order of orders) {
  renderOrder(order);
}
```

Если считать `renderUser` и `renderOrder` операциями постоянной стоимости, два последовательных прохода стоят `O(u + o)`. Если обе коллекции считать одним входом размера `n`, это упрощается до `O(n)`, а не `O(n²)`.

Важно, что предположение о постоянной стоимости здесь является частью анализа. Если `renderUser` внутри выполняет ещё один проход по коллекции размера `r`, его стоимость тоже должна войти в итоговую оценку.

```ts
for (const user of users) {
  for (const role of roles) {
    compare(user, role);
  }
}
```

Вложенные проходы стоят `O(u * r)`, потому что для каждого пользователя выполняется полный проход по ролям. Запись `O(n²)` верна только при сопоставимых размерах, обозначенных одной переменной `n`.

Константы и младшие члены отбрасывают: `3n + 10` относится к `O(n)`, а `n² + n` — к `O(n²)`. Для небольших данных константы всё равно влияют на реальное время, поэтому Big O не заменяет профилирование.

## Временная и пространственная сложность

Подсчёт суммы проходит все элементы за `O(n)` времени и использует `O(1)` дополнительной памяти: количество вспомогательных переменных не растёт с массивом.

Построение `Set` из массива занимает типично `O(n)` времени и `O(n)` дополнительной памяти. После построения проверки наличия в практических реализациях обычно имеют ожидаемую стоимость, близкую к `O(1)`, и потому могут быть значительно дешевле повторного линейного поиска. Это обмен времени на память, а не бесплатная оптимизация.

При оценке памяти важно заранее понимать соглашение. В этом материале под дополнительной памятью считаются новые структуры и результаты, созданные алгоритмом помимо уже существующего входа. Поэтому новый `Map`, промежуточный массив и возвращаемый массив входят в оценку.

Отдельно встречается термин auxiliary space — вспомогательная память. В такой оценке выходной результат нередко не учитывают и считают только память, необходимую алгоритму для самой работы. Поэтому на собеседовании полезно уточнять, включается ли результат в space complexity.

Сам входной массив уже существует и не считается новой памятью, если алгоритм его не копирует. Рекурсивный вызов также использует стек: глубина рекурсии входит в пространственную сложность.

## Случаи и амортизированная оценка

Best, average и worst case — лучший, средний и худший случай — описывают разные способы оценить один алгоритм на возможных входных данных.

Best case показывает наиболее дешёвый допустимый случай, worst case — наиболее дорогой. Average case — ожидаемая стоимость относительно выбранной модели или распределения входных данных, поэтому корректная средняя оценка требует понимания того, какие входы и с какой вероятностью рассматриваются.

Например, `find` может завершиться на первом элементе, но в худшем случае просмотрит весь массив.

Big O само по себе означает верхнюю асимптотическую границу и не равно автоматически worst case. Можно отдельно говорить, например, о `O(n)` для worst case или average case конкретного алгоритма. В обычных собеседованиях Big O действительно часто называют именно для худшего случая, поэтому рассматриваемый случай лучше проговаривать явно.

Амортизированная сложность отвечает на другой вопрос. Она описывает среднюю стоимость одной операции в последовательности операций, где иногда встречается редкая дорогая работа. Например, добавление в конец классического динамического массива имеет `O(1)` амортизированную стоимость: отдельное расширение внутреннего хранилища может стоить `O(n)`, но происходит не при каждом добавлении.

Для более точной математической записи существуют:

- `O(...)` — асимптотическая верхняя граница;
- `Ω(...)` — асимптотическая нижняя граница;
- `Θ(...)` — граница одного порядка роста сверху и снизу.

В обычном техническом разговоре Big O часто используют неформально как название порядка роста. Если точность важна, полезно отделять эту практику от строгого определения.

## Где применяется во frontend

| Ситуация                                              | Стоимость                       | Улучшение                                                              |
| ----------------------------------------------------- | ------------------------------- | ---------------------------------------------------------------------- |
| Для каждого selected ID выполняется `items.find(...)` | `O(s * n)`                      | построить индекс `Map<id, item>` за `O(n)`                             |
| Каждая строка вызывает `selectedIds.includes(id)`     | `O(rows * s)`                   | хранить выбранные ID в `Set`                                           |
| Дерево строится через `filter` детей для каждого узла | до `O(n²)`                      | индексировать узлы или детей за один проход                            |
| Большой список фильтруется при каждом вводе           | `O(n)` на каждое событие        | debounce, серверный поиск, Web Worker или уменьшение входа по ситуации |
| Сортировка запускается на каждом рендере              | типично `O(n log n)` каждый раз | считать только при изменении зависимостей и измерить стоимость         |

Не каждое улучшение меняет Big O самого алгоритма. Например, debounce уменьшает количество запусков фильтрации, а Web Worker переносит вычисление с основного потока, но сама фильтрация по-прежнему может занимать `O(n)`. Поэтому асимптотическую сложность и влияние на отзывчивость интерфейса нужно оценивать отдельно.

Мемоизация помогает только при повторном вызове с неизменившимися зависимостями. Если массив или параметры меняются каждый раз, вычисление всё равно повторится, а кеш добавит собственную стоимость.

## Пример

Повторный поиск каждого выбранного элемента:

```ts
function getSelectedItems(items: Item[], selectedIds: string[]) {
  return selectedIds
    .map(id => items.find(item => item.id === id))
    .filter((item): item is Item => item !== undefined);
}
```

Для `n` элементов и `s` выбранных ID худшее время — `O(n * s)`. Промежуточный массив после `map` и итоговый результат требуют `O(s)` дополнительной памяти.

Предварительный индекс:

```ts
function getSelectedItems(items: Item[], selectedIds: string[]) {
  const itemById = new Map(items.map(item => [item.id, item]));

  return selectedIds
    .map(id => itemById.get(id))
    .filter((item): item is Item => item !== undefined);
}
```

Построение индекса занимает `O(n)`. Если считать доступ к `Map` ожидаемо `O(1)`, обход `s` идентификаторов занимает `O(s)`, поэтому итоговое ожидаемое время — `O(n + s)`.

По принятому выше соглашению дополнительная память составляет `O(n + s)`: сюда входят индекс, временные массивы и итоговый результат.

Оптимизация выгодна при достаточно больших данных или повторном использовании индекса. Для маленького одноразового списка первый вариант может быть проще, поэтому более хорошая асимптотика не всегда означает более хороший практический выбор.

## Ключевые уточнения

- Big O описывает рост относительно размера входа, а измерение показывает время в конкретной среде.
- Асимптотическая оценка показывает поведение при росте входа и отбрасывает константы и младшие члены.
- `O(n)` для метода массива предполагает, что выполняемый на каждом элементе callback сам не добавляет зависимую от размера входа работу.
- Основание логарифма в `O(log n)` обычно не указывают, потому что смена постоянного основания меняет результат только на постоянный множитель.
- Временную и дополнительную пространственную сложность оценивают отдельно.
- При оценке памяти нужно явно понимать, считается ли возвращаемый результат или только auxiliary space.
- Линейная, квадратичная и другие сложности называют по форме роста, а не по конкретному числу операций.
- Сам факт вложенности циклов ещё не означает `O(n²)`: важно, сколько работы реально выполняется на каждой итерации.
- Best, average и worst case — характеристика выбранного случая; Big O — вид асимптотической границы.
- Average case требует модели или распределения входов, а амортизированная сложность описывает последовательность операций и является другим понятием.
- Амортизированная оценка объясняет редкие дорогие операции внутри дешёвой последовательности.
- `Map` и `Set` часто используют для ускорения поиска ценой дополнительной памяти, но точные характеристики зависят от структуры данных и реализации.
