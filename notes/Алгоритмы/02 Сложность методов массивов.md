## Быстрый ответ

Доступ к элементу массива по индексу обычно имеет `O(1)`. Методы, которые в худшем случае просматривают весь массив, — `map`, `filter`, `reduce`, `forEach`, `find`, `some`, `every`, `includes` — имеют `O(n)` без учёта работы функции обратного вызова (callback).

`push` имеет амортизированную `O(1)`, а `pop` — типичную `O(1)`. `shift`, `unshift` и изменение начала или середины через `splice` требуют перенумеровать хвост и обычно стоят `O(n)`. `sort` мутирует массив и обычно оценивается как `O(n log n)`, но ECMAScript не закрепляет конкретный алгоритм и Big O реализации.

Итоговая сложность определяется всей операцией. `orders.map(order => users.find(...))` — не `O(n)`, а `O(o * u)`. Цепочки методов дополнительно создают промежуточные массивы, а копирование перед `sort` добавляет линейное время и память.

## Типичные оценки

Спецификация ECMAScript задаёт наблюдаемое поведение, порядок вызовов и мутацию, но в основном не обещает конкретную сложность. Таблица отражает практическую модель обычного плотного массива в современных движках.

| Операция | Время | Дополнительная память результата | Причина |
| --- | --- | --- | --- |
| `array[i]`, `length` | `O(1)` | `O(1)` | прямой доступ |
| `map` | `O(n * C)` | `O(n)` | вызов callback для элементов и новый массив |
| `filter` | `O(n * C)` | до `O(n)` | проверка элементов и новый массив |
| `reduce`, `forEach` | `O(n * C)` | зависит от callback | один проход |
| `find`, `some`, `every` | best `O(1)`, worst `O(n * C)` | `O(1)` | возможна ранняя остановка |
| `includes`, `indexOf` | worst `O(n)` | `O(1)` | линейный поиск |
| `push` | амортизированно `O(1)` | обычно `O(1)` | добавление в конец, иногда расширение хранилища |
| `pop` | обычно `O(1)` | `O(1)` | удаление с конца |
| `shift`, `unshift` | обычно `O(n)` | зависит от движка | сдвиг индексов |
| `slice`, spread-копия | `O(k)` / `O(n)` | размер копии | создаётся новый массив |
| `splice` | до `O(n)` | зависит от удалённой части | сдвигается хвост, возвращаются удалённые элементы |
| `reverse` | `O(n)` | обычно `O(1)` | перестановка элементов на месте |
| `sort` | обычно `O(n log n)` сравнений | зависит от реализации | сортировка на месте |
| `toSorted` | обычно `O(n log n)` + копирование | `O(n)` | создаёт отсортированную копию |

`C` обозначает стоимость callback. Если эта функция выполняет линейный поиск по другой коллекции размера `m`, итог прохода становится `O(n * m)`.

## Последовательные и вложенные операции

```ts
const visibleNames = users
  .filter(user => user.visible)
  .map(user => user.name);
```

Это два последовательных линейных прохода: `O(n) + O(n) = O(n)` по классу роста. При этом создаются два массива, поэтому константы и дополнительная память больше, чем у одного цикла.

Объединять цепочку в `reduce` стоит только после измерения или при явной необходимости сократить аллокации. Два читаемых прохода часто лучше сложного аккумулятора для небольшого списка.

```ts
const rows = orders.map(order => ({
  ...order,
  user: users.find(user => user.id === order.userId),
}));
```

Внешний `map` выполняется `o` раз, а `find` в худшем случае просматривает `u` пользователей: итог `O(o * u)`.

## Скрытая стоимость callback-функции

Название метода не определяет сложность callback-функции. Особенно незаметна квадратичная стоимость при копировании аккумулятора:

```ts
const userById = users.reduce(
  (result, user) => ({ ...result, [user.id]: user }),
  {} as Record<string, User>,
);
```

Spread копирует растущий объект на каждом шаге, поэтому общий объём копирования может стать `O(n²)`. Изменять локальный аккумулятор внутри `reduce` безопасно, если он создан этой функцией и не является React state:

```ts
const userById = users.reduce<Record<string, User>>((result, user) => {
  result[user.id] = user;
  return result;
}, {});
```

Этот вариант типично `O(n)` по времени и `O(n)` по памяти результата.

## Мутация и React state

`sort`, `reverse`, `splice`, `push` и другие методы меняют исходный массив. Если массив хранится в React state или получен через props, мутация сохраняет прежнюю ссылку и нарушает модель неизменяемых обновлений. Это может скрыть изменение от сравнения ссылок, испортить мемоизацию и изменить данные другого потребителя.

```ts
const sortedItems = [...items].sort(compareItems);
// или в среде с поддержкой ES2023
const sortedItems = items.toSorted(compareItems);
```

Оба варианта создают новый массив. Spread добавляет `O(n)` копирования, а `toSorted` по контракту не меняет исходный массив. Поддержку нового метода определяют целевая версия JavaScript (`target`), TypeScript `lib` и набор поддерживаемых браузеров.

## Где применяется во frontend

| Ситуация | Анализ | Возможное решение |
| --- | --- | --- |
| `filter().map()` небольшого списка | два прохода, но ясный код | оставить без микрооптимизации |
| `find` внутри `map` больших коллекций | вложенный линейный поиск | заранее построить `Map` по ID |
| `includes` вызывается для каждой строки | `O(rows * selected)` | создать `Set` выбранных ID |
| Сортировка выполняется прямо над state | мутация общей ссылки | `toSorted` или копия перед `sort` |
| Поиск запускается на каждый ввод | линейная работа на событие | debounce, серверный поиск, уменьшение данных или worker по измерениям |
| `reduce` копирует аккумулятор через spread | возможная `O(n²)` | локально изменять новый аккумулятор или использовать `Map` |

`useMemo` не делает метод быстрее. Оно может повторно использовать прошлый результат, пока зависимости сохраняют ссылки; при новом массиве вычисление запускается снова.

## Пример

Индекс устраняет повторный `find`:

```ts
const userById = new Map(users.map(user => [user.id, user]));

const rows = orders.map(order => ({
  ...order,
  user: userById.get(order.userId),
}));
```

Для `u` пользователей и `o` заказов построение и обход занимают типично `O(u + o)` времени вместо `O(u * o)`. Индекс требует `O(u)` дополнительной памяти. Если обогащение выполняется многократно для одного массива users, индекс можно переиспользовать; если массив новый, его нужно перестроить.

## Ключевые уточнения

- Стоимость метода включает callback-функцию и операции, которые она запускает.
- Последовательные линейные проходы остаются `O(n)`, но отличаются аллокациями и константами.
- Ранняя остановка улучшает конкретный случай `find`/`some`/`every`, а худшая оценка остаётся линейной.
- `push` считается `O(1)` амортизированно, потому что редкое расширение массива дороже.
- `sort` и `reverse` мутируют исходный массив; `toSorted` и `toReversed` создают копии.
- ECMAScript не фиксирует универсальный Big O встроенных методов, поэтому таблица является практической моделью реализации.
