## Быстрый ответ

HTTP-кеширование позволяет повторно использовать сохранённый ответ в браузере, proxy или CDN. Политика ответа определяет, можно ли его хранить, кто может хранить, сколько времени он считается свежим и как проверить актуальность после истечения срока.

Свежий ответ используется без обращения к исходному серверу (origin server). Устаревший ответ можно повторно проверить: клиент отправляет `If-None-Match` с `ETag` или `If-Modified-Since` с датой, а сервер отвечает `304 Not Modified`, если тело не изменилось.

Для файлов с хешем содержимого (content hash) обычно используют долгий публичный кеш и `immutable`. HTML кешируют осторожно, чтобы он быстро получил ссылки на новую версию ресурсов. Персональные ответы не должны попадать в общий кеш без явно спроектированной политики.

## Где может находиться кэш

```text
application query cache
Service Worker Cache Storage
HTTP-кеш браузера
proxy / CDN shared cache
origin or backend cache
```

Это разные механизмы. HTTP-заголовки управляют HTTP-кешами, но не определяют автоматически срок данных в RTK Query и не удаляют запись из Cache Storage Service Worker. При проблеме «у пользователя старая версия» сначала выясняют владельца устаревшего ответа.

BFCache тоже не является HTTP-кэшем: он сохраняет целое живое состояние страницы для переходов назад и вперёд.

## Свежесть и ревалидация

```text
промах кеша -> запрос к серверу -> сохранить ответ

cache hit:
  fresh -> использовать без запроса
  stale -> проверить validator
           -> 304: использовать сохранённое тело
           -> 200: заменить ответ новым
```

`max-age=300` задаёт срок свежести в секундах относительно времени ответа. Shared cache может использовать отдельный `s-maxage`, который имеет приоритет над `max-age` для CDN и proxy.

```http
Cache-Control: public, max-age=300, s-maxage=3600
```

Браузер может считать ответ свежим пять минут, а CDN — час. Заголовок `Age` показывает, сколько секунд ответ провёл в общем кеше. Точный расчёт учитывает `Date`, задержки и правила RFC, поэтому это не просто локальный таймер JavaScript.

После истечения срока свежести ответ становится устаревшим (stale), но не обязан немедленно удаляться. Кеш может проверить его, временно использовать по разрешённой stale-политике или заменить после нового ответа.

## Директивы `Cache-Control`

| Директива | Значение |
| --- | --- |
| `max-age=N` | ответ свеж N секунд |
| `s-maxage=N` | отдельный срок для shared cache |
| `public` | ответ разрешено хранить общему кешу при соблюдении остальных правил |
| `private` | ответ предназначен для приватного кеша конкретного пользователя |
| `no-cache` | хранить можно, но перед каждым повторным использованием нужна успешная проверка |
| `no-store` | кеш не должен сохранять этот запрос и ответ |
| `must-revalidate` | устаревший ответ нельзя использовать без успешной проверки, когда обычные правила требуют ревалидацию |
| `immutable` | пока ответ свеж, клиенту не нужно проверять, изменился ли URL |
| `stale-while-revalidate=N` | разрешено временно отдать устаревший ответ и обновить его в фоне |
| `stale-if-error=N` | разрешено временно использовать устаревший ответ при ошибке исходного сервера |

`no-cache` не означает «не кэшировать». Для запрета хранения используется `no-store`. При этом новый `no-store` не обязан удалять копию, которая уже была сохранена раньше; смена политики требует учитывать существующие cache entries.

`private` разрешает хранение в приватном кеше браузера. Для особенно чувствительного ответа, который не должен оставаться на устройстве, используют `no-store` и дополняют его продуктовой моделью безопасности.

## Validators

`ETag` идентифицирует версию представления:

```http
ETag: "users-v42"
Cache-Control: no-cache
```

При следующем использовании клиент проверяет:

```http
If-None-Match: "users-v42"
```

Если представление не изменилось:

```http
HTTP/1.1 304 Not Modified
ETag: "users-v42"
```

`304` не содержит нового тела представления. Кеш объединяет подходящие метаданные с сохранённым ответом и отдаёт клиенту прежнее тело.

Strong ETag означает побайтово эквивалентное представление. Weak ETag с префиксом `W/` допускает семантическую эквивалентность при различиях байтов и не подходит для всех range- и concurrency-сценариев.

`Last-Modified` и `If-Modified-Since` используют время изменения. Дата имеет ограниченную точность и может быть менее надёжным validator, чем ETag, но остаётся полезным fallback.

## Cache key и `Vary`

HTTP-кеш выбирает запись по методу и целевому URI, а `Vary` добавляет значения указанных заголовков запроса в выбор варианта ответа.

```http
Vary: Accept-Encoding, Accept-Language
```

Без корректного `Vary` CDN может смешать сжатые форматы, языки или другое content negotiation. С другой стороны, `Vary` по высококардинальному значению вроде полного `User-Agent` создаёт слишком много cache variants и снижает hit rate.

Персонализированные ответы нельзя различать только по query key во frontend. Общий кеш видит HTTP-запрос, поэтому сервер должен задать `private`, `no-store`, корректный `Vary` или иной безопасный ключ кеша на CDN. Неверная политика общего кеша способна раскрыть данные другого пользователя.

## HTML и hashed assets

Production-сборка обычно создаёт immutable assets:

```text
app.8f3a1c.js
styles.17bd2e.css
```

Для них подходит:

```http
Cache-Control: public, max-age=31536000, immutable
```

Изменение содержимого создаёт новый URL, поэтому старый файл не нужно инвалидировать в браузерах. Это называют cache busting через content hash.

HTML содержит ссылки на актуальные assets и не получает такой долгий неизменяемый cache:

```http
Cache-Control: no-cache
ETag: "index-v42"
```

При deploy новый HTML начнёт ссылаться на новые hashed files. Старые assets не удаляют мгновенно: уже открытая вкладка или старый HTML могут запросить прежний lazy chunk. Надёжная схема использует atomic deploy, хранит предыдущие assets некоторое время и обрабатывает ошибку загрузки новой версии.

## API responses

Кэшировать API можно, если контракт определяет владельца, freshness и invalidation. Публичный каталог подходит shared cache лучше, чем профиль пользователя.

```http
Cache-Control: private, max-age=60
ETag: "profile-17"
```

HTTP-кеш и библиотека серверного состояния решают разные задачи. HTTP-кеш хранит представление согласно заголовкам. RTK Query или TanStack Query знает query key, подписчиков, refetch и optimistic update, но обычно не заменяет HTTP-кеш на уровне браузера или CDN.

Mutation не обязана автоматически удалить HTTP-cache entry. Сервер может использовать validators и cache-control, CDN — purge/surrogate keys, а frontend query cache — invalidation по собственным tags или keys. Эти механизмы проектируются согласованно.

## Диагностика старой версии

1. Проверить в Network фактический URL и колонку источника: memory cache, disk cache, Service Worker или сеть.
2. Посмотреть заголовки ответа `Cache-Control`, `Age`, `ETag`, `Vary` и цепочку перенаправлений.
3. Убедиться, что HTML ссылается на существующий hashed asset.
4. Отдельно проверить ключ кеша CDN, очистку и ответ исходного сервера.
5. Открыть Application → Service Workers/Cache Storage и проверить его стратегию.
6. Сравнить обычную навигацию, reload и новый чистый профиль, не считая disable cache постоянным исправлением.

Hard reload полезен для диагностики конкретного браузера, но не исправляет политику для всех пользователей. Изменение URL hashed asset надёжнее попытки заставить каждое устройство удалить старую копию.

## Ключевые уточнения

- Свежий ответ используется без запроса к исходному серверу, а устаревший требует ревалидации или явно разрешённого stale-поведения.
- `no-cache` требует проверки перед использованием, а `no-store` запрещает сохранение новой копии.
- `ETag` проверяет версию представления, а `304` позволяет повторно использовать уже сохранённое тело.
- Долгий cache безопасен для content-hashed assets, пока HTML быстро получает актуальные ссылки и старые chunks доступны во время перехода версий.
- Browser HTTP cache, CDN, Service Worker Cache Storage и frontend query cache имеют разных владельцев и правила invalidation.
