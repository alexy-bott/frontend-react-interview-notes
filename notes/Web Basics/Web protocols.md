## Быстрый ответ

Веб использует не один протокол, а несколько уровней. DNS помогает получить IP-адрес по доменному имени, IP доставляет пакеты между узлами, TCP или QUIC организует транспорт, TLS защищает соединение, а HTTP задаёт смысл запросов и ответов. Браузер скрывает большую часть этой работы за `fetch`, загрузкой документа и другими Web API.

Для страниц, ресурсов и большинства API базовым выбором остаётся HTTP(S). WebSocket добавляет постоянный двусторонний канал. Server-Sent Events (SSE) передаёт поток событий от сервера к браузеру поверх HTTP. WebRTC объединяет несколько протоколов и браузерных API для аудио, видео и передачи данных между участниками.

Frontend-код обычно не выбирает TCP, QUIC или версию HTTP напрямую. Браузер, сервер и сетевое окружение согласуют доступный вариант, а разработчик выбирает прикладную модель обмена и проектирует восстановление после ошибок.

## Уровни сетевого взаимодействия

```text
Прикладная модель:  HTTP, WebSocket, WebRTC
Защита:            TLS
Транспорт:         TCP, QUIC поверх UDP
Маршрутизация:     IP
Разрешение имени:  DNS
```

Схема намеренно упрощена. DNS сам является прикладным протоколом, а QUIC включает возможности транспорта и интегрирует TLS 1.3. Уровни нужны как модель ответственности, а не как утверждение, что каждый запрос всегда проходит отдельные шаги именно в таком порядке.

## HTTP/1.1, HTTP/2 и HTTP/3

Версии HTTP сохраняют общую семантику: методы, статусы, заголовки, URL и содержание сообщения. Отличается представление данных и работа соединения.

| Версия | Транспорт в браузерной практике | Главное отличие |
| --- | --- | --- |
| HTTP/1.1 | TCP, для HTTPS также TLS | запросы используют одно или несколько соединений; порядок ответов внутри соединения ограничивает параллелизм |
| HTTP/2 | один TCP-канал с TLS | несколько потоков запросов мультиплексируются в одном соединении, заголовки сжимаются |
| HTTP/3 | QUIC поверх UDP с TLS 1.3 | независимые QUIC streams уменьшают блокировку других HTTP-запросов при потере данных одного потока |

HTTP/2 не устраняет блокировку на уровне TCP: потерянный TCP-сегмент задерживает доставку последующих байтов соединения. В HTTP/3 потеря данных одного QUIC stream не обязана блокировать доставку данных остальных streams. При этом общая пропускная способность и congestion control соединения всё равно могут повлиять на все потоки.

Браузер и сервер согласуют поддерживаемый протокол. Для HTTP/2 используется ALPN во время TLS-соединения; поддержку HTTP/3 сервер может рекламировать, например, через `Alt-Svc`. Вызов `fetch()` не получает параметр «использовать HTTP/3».

## Как выбрать модель обмена

| Задача | Базовый выбор | Почему |
| --- | --- | --- |
| Загрузка страницы, CRUD, файлы | HTTP(S) | запрос-ответ, кэш, CDN и стандартная диагностика |
| Уведомления только от сервера | SSE | автоматическое переподключение и простой текстовый поток поверх HTTP |
| Чат или совместное редактирование | WebSocket | обе стороны отправляют сообщения независимо |
| Видеозвонок или P2P data channel | WebRTC | медиа, согласование соединения и передача между участниками |

Направление данных является только первым критерием. Дополнительно учитывают частоту сообщений, допустимую задержку, размер данных, прокси, авторизацию, возможность восстановить пропущенные события и стоимость постоянного соединения на сервере.

HTTP подходит и для периодического polling: клиент повторяет запрос через интервал. Для редких обновлений это часто проще постоянного соединения. При высокой частоте polling создаёт лишние запросы и задержку до следующего интервала, поэтому рассматривают SSE или WebSocket.

## Что меняется для frontend

**Кэш и CDN.** Обычные HTTP-ответы естественно участвуют в HTTP-кэшировании и доставке через CDN. Сообщения уже установленного WebSocket не обрабатываются HTTP-кэшем.

**Жизненный цикл.** Постоянный канал требует состояния `connecting`, `open`, `reconnecting`, `offline` и `closed`. После reconnect клиенту нужен способ получить snapshot или события после известной версии.

**Backpressure.** Если сообщения приходят быстрее, чем клиент обрабатывает их, очередь растёт. Нужно объединять промежуточные обновления, ограничивать буфер или запрашивать повторную синхронизацию. Сам выбор WebSocket эту проблему не решает.

**Безопасность.** В production используют защищённые схемы `https` и `wss`. TLS защищает канал, но права на подписку, типы сообщений и входные данные всё равно проверяет сервер.

**Наблюдаемость.** HTTP-запросы удобно видеть в Network panel. Для постоянного канала отдельно измеряют время подключения, reconnect, потерянные сообщения, размер очереди и задержку от серверного события до обновления UI.

## Ключевые уточнения

- Версии HTTP меняют транспортное представление и использование соединения, но сохраняют семантику методов, статусов и заголовков.
- HTTP/3 уменьшает блокировку между независимыми streams, но не делает сеть нечувствительной к потере пакетов и ограничению пропускной способности.
- SSE является потоком событий от сервера поверх HTTP, а WebSocket создаёт отдельный двусторонний протокол после установления соединения.
- WebRTC является набором протоколов и API для real-time communication, а не просто альтернативным способом выполнить CRUD-запрос.
- Браузер согласует низкоуровневый транспорт; frontend-разработчик выбирает прикладную модель, обработку ошибок и восстановление состояния.
