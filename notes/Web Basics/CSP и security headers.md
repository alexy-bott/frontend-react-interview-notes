## Быстрый ответ

CSP (Content Security Policy, политика безопасности контента) — набор правил, которые сервер передаёт браузеру в HTTP-заголовке. Правила определяют, какие скрипты, стили, изображения, сетевые подключения и другие ресурсы разрешены странице.

Основная задача CSP — уменьшить вероятность и последствия XSS. Даже если атакующий сумел вставить в HTML вредоносный код, строгая политика может запретить его выполнение: например, разрешить только скрипты с одноразовым `nonce`, запретить inline-обработчики и `eval()`.

CSP — дополнительный уровень защиты, а не замена безопасному выводу данных и очистке HTML (sanitization). Остальные заголовки безопасности решают другие задачи: HSTS требует HTTPS, `frame-ancestors` ограничивает встраивание страницы, `nosniff` запрещает браузеру угадывать MIME-тип, а `Referrer-Policy` управляет данными в `Referer`.

## Модель работы CSP

```text
сервер формирует HTML и заголовок CSP
  -> браузер разбирает политику
  -> страница пытается загрузить ресурс или выполнить код
  -> браузер находит подходящую директиву
  -> разрешает действие или блокирует его
  -> при настройке reporting отправляет отчёт о нарушении
```

Политика состоит из **директив (directives)** — отдельных правил для типов ресурсов или действий. Например, `script-src` управляет скриптами, `connect-src` — запросами `fetch`, WebSocket и EventSource, а `frame-ancestors` — тем, кто может встроить текущую страницу.

`default-src` служит запасным правилом для многих ресурсных директив, если более точная директива не задана. Но это не универсальная замена: например, `frame-ancestors`, `base-uri` и `form-action` нужно задавать отдельно.

## Основные директивы

| Директива | Что контролирует |
| --- | --- |
| `default-src` | запасной список источников для поддерживающих его ресурсных директив |
| `script-src` | загрузку и выполнение JavaScript, встроенные скрипты и компиляцию строки как кода |
| `style-src` | таблицы стилей и встроенные стили |
| `img-src`, `font-src` | источники изображений и шрифтов |
| `connect-src` | `fetch`, XHR, WebSocket, EventSource и другие соединения из скрипта |
| `frame-src` | страницы, которые текущее приложение может загрузить в `iframe` |
| `worker-src` | источники скриптов Worker и Service Worker |
| `object-src` | плагины через `object` и `embed`; обычно задают `'none'` |
| `base-uri` | допустимые значения `<base>`, влияющего на относительные URL |
| `form-action` | адреса, на которые разрешено отправлять HTML forms |
| `frame-ancestors` | origins, которым разрешено встроить текущую страницу |

`'self'` означает тот же origin, а не любой поддомен и не просто тот же site. `https:` разрешает любой HTTPS-origin и поэтому обычно шире, чем требуется. Звёздочка также не означает «безопасно разрешить всё»: выражение источника имеет точные правила и может открыть ненужные внешние адреса.

## Строгая политика для скриптов

Список разрешённых доменов сложно поддерживать безопасно: доверенный CDN может содержать JSONP endpoint, пользовательские файлы или скомпрометированный сторонний скрипт. Поэтому современная строгая CSP опирается прежде всего на `nonce` или хеш (hash).

**Nonce** — непредсказуемое значение, которое сервер генерирует заново для каждого HTML-ответа. Оно одновременно помещается в политику и в разрешённые `<script>`:

```http
Content-Security-Policy: script-src 'nonce-RANDOM_VALUE'; object-src 'none'; base-uri 'none'
```

```html
<script nonce="RANDOM_VALUE" src="/assets/app.js"></script>
```

Браузер выполнит скрипт, только если nonce совпадает. Значение должно быть криптографически случайным и уникальным для ответа. Нельзя подставлять один постоянный nonce во все страницы: после его утечки атакующий сможет пометить им свой скрипт. При кешировании HTML нужно убедиться, что политика и разметка получают согласованное значение и старый nonce не переиспользуется.

**Хеш (hash)** разрешает скрипт с конкретным содержимым. Он удобен для неизменяемого кода: изменение даже одного символа требует нового хеша. Хеш CSP подтверждает, что конкретный скрипт разрешён политикой; атрибут SRI `integrity` дополнительно проверяет содержимое загружаемого внешнего ресурса. Эти механизмы связаны, но решают не полностью одинаковые задачи.

`'strict-dynamic'` переносит доверие от скрипта с валидным nonce или хешем к скриптам, которые он динамически загружает. Это помогает приложениям с загрузчиком, но расширяет ответственность доверенного скрипта: если он создаёт `<script>` из данных атакующего, CSP уже не остановит эту цепочку.

## Что ослабляет CSP

`'unsafe-inline'` разрешает inline JavaScript, включая многие сценарии, которые CSP должна блокировать. `'unsafe-eval'` разрешает `eval()`, `new Function()` и другие способы компилировать строку как код. Их наличие не делает всю policy бесполезной, но существенно ослабляет защиту соответствующего контекста и требует понятной причины.

Разрешение широкого списка origins для скриптов тоже опасно. Любой разрешённый origin становится частью границы доверия: его компрометация или небезопасный endpoint могут привести к выполнению кода в origin приложения.

CSP не анализирует бизнес-логику скрипта и не делает доверенный код безопасным. Разрешённый бандл по-прежнему может передать пользовательскую строку в `innerHTML`, отправить данные не тому получателю или загрузить вредоносный скрипт через доверенный загрузчик.

## CSP в React и SSR

Для политики на основе nonce сервер должен создать nonce для каждого HTML-ответа и передать его:

1. В заголовок `Content-Security-Policy`.
2. В каждый разрешённый `<script>`, созданный при серверном рендеринге.
3. Во фреймворк или среду выполнения, если они сами создают загрузочные скрипты.

Это чаще относится к SSR и серверным шаблонам. У полностью статического SPA нет сервера, который меняет nonce для каждого ответа, поэтому для него удобнее CSP на основе хешей или архитектура без встроенных скриптов.

React экранирует обычные строковые значения JSX, но `dangerouslySetInnerHTML`, небезопасные URL и third-party widgets всё равно требуют собственной защиты. CSP страхует эти границы, а не исправляет их автоматически.

## Внедрение без поломки приложения

Сначала собирают фактические зависимости страницы: скрипты, origins API, изображения, шрифты, frames, Workers, аналитику и платёжные виджеты. Затем политику запускают через `Content-Security-Policy-Report-Only`: браузер сообщает о нарушениях, но не блокирует ресурсы.

Отчёт не означает, что источник нужно сразу добавить в список разрешённых. Сначала выясняют, нужен ли ресурс, можно ли убрать встроенный код, откуда появился неожиданный origin и не вызвано ли событие атакой или расширением браузера. Отчёты могут содержать URL и другие данные, поэтому их ограничивают, очищают и агрегируют как телеметрию безопасности.

После проверки ключевых пользовательских сценариев policy переводят в enforcing mode через `Content-Security-Policy`. Report-Only и enforcing policy можно временно использовать вместе: первая проверяет будущие ужесточения, вторая блокирует уже утверждённый набор нарушений.

## Другие заголовки безопасности

| Header | Какую угрозу уменьшает | Важная граница |
| --- | --- | --- |
| `Strict-Transport-Security` | переход с HTTPS на HTTP после того, как браузер узнал политику HSTS | длительный `max-age` и `includeSubDomains` включают только после готовности всех поддоменов и сертификатов |
| `X-Content-Type-Options: nosniff` | выполнение ресурса не в соответствии с объявленным MIME type | сервер всё равно обязан отправлять корректный `Content-Type` |
| `Referrer-Policy` | утечку path/query текущей страницы через `Referer` | не заменяет отказ от секретов и персональных данных в URL |
| `Permissions-Policy` | ненужный доступ страницы и вложенных frames к камере, микрофону и другим возможностям браузера | поддержка и синтаксис конкретных возможностей проверяются отдельно |
| CSP `frame-ancestors` | clickjacking — обманный клик по интерфейсу, скрытому внутри чужого frame | ограничивает, кто встраивает текущую страницу; `frame-src` решает обратную задачу |
| `Cross-Origin-Opener-Policy` / `Cross-Origin-Embedder-Policy` | часть cross-origin атак и изоляцию browsing context | нужны для cross-origin isolation, но могут сломать popup и third-party resources |

`X-Frame-Options` остаётся устаревающим заголовком для старых браузеров. В современных браузерах CSP `frame-ancestors` гибче: умеет перечислять разрешённые origins и проверяет всю цепочку родительских документов. Эта директива не наследуется из `default-src` и не работает при доставке CSP через `<meta>`.

Не каждый заголовок нужен в каждом ответе. Например, CSP почти не даёт пользы JSON API, ответ которого браузер не отображает как документ. Набор заголовков выбирают по типу ресурса, архитектуре и модели угроз (threat model), а не копируют без проверки.

## Ключевые уточнения

- CSP управляет тем, что странице разрешено загружать и выполнять; CORS управляет возможностью скрипта прочитать ответ с другого origin.
- Безопасный вывод и sanitization устраняют источник XSS, а CSP ограничивает выполнение кода, если первичная защита дала сбой.
- Nonce должен быть непредсказуемым и новым для каждого HTML-ответа; хеш привязан к точному содержимому скрипта.
- `frame-ancestors` защищает текущую страницу от чужого embedding, а `frame-src` ограничивает frames внутри текущей страницы.
- Report-Only нужен для наблюдения и настройки, но ничего не блокирует.
- Заголовки безопасности образуют несколько независимых границ защиты; один «большой» заголовок не заменяет остальные.

## Пример базовой политики

```http
Content-Security-Policy:
  default-src 'self';
  script-src 'nonce-{RANDOM_PER_RESPONSE}' 'strict-dynamic';
  style-src 'self';
  img-src 'self' data: https://images.example-cdn.com;
  font-src 'self';
  connect-src 'self' https://api.example.com;
  object-src 'none';
  base-uri 'none';
  form-action 'self';
  frame-ancestors 'none'
```

Это отправная точка, а не готовый заголовок для любого проекта. Например, `data:` для изображений, внешний CDN, `'strict-dynamic'` и запрет встраивания должны соответствовать реальному приложению.
