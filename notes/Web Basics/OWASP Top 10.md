## Быстрый ответ

OWASP Top 10 — регулярно обновляемый обзор наиболее критичных **категорий** рисков веб-приложений. Он помогает разработчикам замечать типовые классы проблем, но не является полным стандартом безопасности и не гарантирует защищённость после проверки десяти пунктов.

Актуальная редакция OWASP Top 10:2025 начинается с Broken Access Control, Security Misconfiguration и Software Supply Chain Failures. Для frontend-разработчика особенно важны разграничение UI и серверного контроля доступа, XSS и другие риски инъекций, безопасная аутентификация, настройки безопасности браузера, цепочка поставки npm, сторонние скрипты и отсутствие чувствительных данных в клиентском бандле и телеметрии.

Frontend может предотвратить часть уязвимостей и безопасно организовать интерфейс, но не является доверенной границей. Пользователь контролирует браузер, клиентский код и запросы, поэтому сервер обязан независимо проверять аутентификацию, авторизацию, входные данные и каждую критичную операцию.

## Как читать OWASP Top 10

OWASP объединяет множество конкретных слабостей в широкие категории. Например, Injection включает XSS и SQL injection, а Broken Access Control — доступ к чужому объекту по изменённому `id`, обход роли и отсутствие tenant isolation.

Позиция в Top 10 не означает точную вероятность конкретной атаки для любого продукта. Риск зависит от данных, ролей, integrations, deployment и возможного ущерба. Список используют как начальную карту для threat modeling, code review и security testing, а не вместо анализа архитектуры.

Версию списка нужно называть явно. Редакции 2021 и 2025 отличаются названиями и составом категорий, поэтому смешивание списков даёт неточный ответ.

## OWASP Top 10:2025

| Код и категория | Смысл | Типичная связь с frontend |
| --- | --- | --- |
| A01 Broken Access Control | пользователь получает доступ к чужим данным или действиям | UI скрывает кнопку, но API не проверяет роль, владельца ресурса или tenant |
| A02 Security Misconfiguration | небезопасные настройки приложения и инфраструктуры | чрезмерный CORS, слабые атрибуты cookie, CSP, заголовки, открытые sourcemaps или режим отладки |
| A03 Software Supply Chain Failures | компрометация зависимостей, сборки и цепочки доставки | вредоносный npm-пакет, `postinstall`-скрипт, CDN-зависимость или подменённый артефакт |
| A04 Cryptographic Failures | чувствительные данные недостаточно защищены при передаче или хранении | HTTP вместо HTTPS, секрет в bundle, токен или персональные данные в URL/storage без модели угроз |
| A05 Injection | данные интерпретируются как команда или код | XSS через HTML/URL/Markdown sink; на сервере также SQL-, command- и template injection |
| A06 Insecure Design | небезопасность заложена в сам сценарий и границы доверия | критичное действие без повторной проверки, неограниченное восстановление доступа, доверие цене из клиента |
| A07 Authentication Failures | система ошибается при установлении и поддержании личности пользователя | сломанный login/refresh/logout flow, session fixation, слабое восстановление доступа |
| A08 Software or Data Integrity Failures | код или данные принимаются без требуемой проверки целостности | неподписанная конфигурация, небезопасная десериализация, внешний скрипт без контроля источника и целостности |
| A09 Security Logging and Alerting Failures | атака не оставляет полезного сигнала или сигнал не приводит к реакции | ошибки не наблюдаются либо telemetry содержит секреты, но не содержит безопасного incident context |
| A10 Mishandling of Exceptional Conditions | исключительная ситуация приводит к fail-open, утечке или некорректному состоянию | UI разрешает действие при ошибке проверки, раскрывает stack/token или повторяет неидемпотентную операцию |

## A01: доступ проверяется на сервере

Скрытая кнопка, route guard и неактивный элемент управления улучшают UX, но не обеспечивают авторизацию. Пользователь может изменить JavaScript, состояние приложения и HTTP-запрос.

```text
GET /api/invoices/42
  -> authenticated user: user-7
  -> сервер проверяет право user-7 читать invoice-42
  -> только после проверки возвращает данные
```

Проверка нужна для каждого ресурса и действия, включая вложенные сущности, экспорт, массовые операции и admin API. Простое наличие валидной сессии не доказывает право на конкретный объект.

Frontend при этом не должен намеренно показывать недоступные действия и чужие данные. Но клиентская проверка прав используется для представления интерфейса, а серверная авторизация — как граница безопасности.

## A02: конфигурация является частью поведения

Security Misconfiguration — не только «ошибка DevOps». Frontend затрагивают:

- CORS allowlist и credentialed requests;
- `HttpOnly`, `Secure`, `SameSite`, `Path` и `Domain` у cookies;
- CSP и другие заголовки ответа;
- доступность sourcemaps, отладочных страниц и development endpoints;
- переменные окружения, которые попадают в public bundle;
- настройки CDN cache и публикации пользовательских файлов.

Переменная, доступная коду в браузере, уже не является секретом, даже если называется `API_SECRET` и пришла из CI environment. Инструменты сборки подставляют публичные переменные в бандл, который пользователь может скачать и исследовать.

## A03 и A08: supply chain и integrity

Цепочка поставки (supply chain) идёт от исходного кода и зависимостей до артефакта сборки и production. Риск возникает до запуска приложения: пакет, аккаунт сопровождающего, CI action, registry, CDN или хранилище артефактов могут быть скомпрометированы.

Базовые меры:

- хранить и проверять lockfile;
- устанавливать зависимости воспроизводимым способом, например `npm ci`;
- просматривать изменения прямых зависимостей и установочных скриптов;
- использовать SCA — анализ известных уязвимостей компонентов, но не считать его полной проверкой;
- минимизировать сторонние скрипты и их доступ к странице;
- защищать registry/CI credentials и release permissions;
- проверять происхождение и целостность build artifacts.

SRI (Subresource Integrity) позволяет браузеру сверить хеш внешнего скрипта или stylesheet с ожидаемым значением. Но SRI не проверяет бизнес-безопасность самого кода и неудобен для URL, содержимое которых меняется без обновления HTML.

A08 пересекается с рисками цепочки поставки, но сосредоточена на нарушенной границе доверия к конкретному артефакту кода или данных. Примеры: приложение принимает неподписанную конфигурацию, доверяет изменяемым данным в клиентском хранилище или выполняет код без требуемой проверки целостности.

## A04: браузер не хранит серверные секреты

HTTPS защищает данные в пути и подтверждает подлинность сервера через TLS-сертификат. Он не скрывает данные от JavaScript того же origin, расширений браузера с соответствующим доступом, логирования и уже скомпрометированного endpoint.

Нельзя помещать закрытые API-ключи, пароли и ключи подписи во frontend-бандл. Если браузер должен использовать значение, пользователь тоже может его получить. Публичные идентификаторы допустимы только тогда, когда backend или provider ограничивает их по origin, scope, quota и доступным операциям.

Чувствительные данные не помещают без необходимости в URL: они могут попасть в историю браузера, логи proxy и сервера, аналитику и `Referer`. Выбор cookie, памяти или Web Storage для токена зависит от модели угроз XSS/CSRF и архитектуры, а не от универсального правила «всегда хранить здесь».

## A05: данные не должны становиться кодом

Во frontend главный injection-риск — XSS. Цепочка возникает, когда данные из API, URL, CMS, storage или `postMessage` доходят до API, интерпретирующего строку как HTML, JavaScript или опасный URL.

```ts
// Данные интерпретируются как HTML.
container.innerHTML = comment;

// Данные остаются текстом.
container.textContent = comment;
```

Если продукт разрешает rich HTML, его очищают проверенным sanitizer с allowlist. CSP и Trusted Types добавляют границы, но не отменяют безопасный выбор DOM APIs. Server также обязан предотвращать SQL, command и другие injections на своей стороне: frontend validation не является security control для backend parser.

## A06: безопасный сценарий проектируют заранее

Insecure Design означает, что отдельные функции могут быть написаны без явных ошибок, но общий сценарий допускает злоупотребление. Например:

- цена заказа без проверки принимается из клиентского запроса;
- восстановление пароля позволяет неограниченно угадывать code;
- изменение платёжных реквизитов не требует повторного подтверждения;
- optimistic UI показывает успех до необратимой операции и скрывает критичный отказ;
- feature flag на клиенте считается защитой закрытой функции.

Здесь недостаточно sanitization или заголовка безопасности. До реализации нужно определить защищаемые ресурсы, участников, границы доверия, сценарии злоупотребления и безопасное поведение при отказе.

## A07: authentication — состояние с явными переходами

Authentication подтверждает, кто пользователь; authorization решает, что ему разрешено. Надёжный frontend flow различает как минимум неизвестное состояние session, authenticated и guest, а также корректно обрабатывает login, refresh, expiration и logout.

Refresh не должен превращать любой `401` в бесконечный повтор. Параллельные запросы координируют через single-flight, а неидемпотентный запрос повторяют только тогда, когда его body можно безопасно воспроизвести и протокол допускает повтор. При logout очищают клиентское состояние, но сервер также завершает сессию или отзывает refresh credential.

MFA и re-authentication особенно важны для изменения password, payout details, recovery factors и других критичных операций. Наличие уже открытого UI не доказывает свежесть authentication.

## A09: наблюдаемость без утечки данных

Security-relevant события должны позволять заметить атаку и начать расследование: repeated authentication failures, access denials, refresh reuse, аномальные permission changes и CSP violations. Сам по себе log без alert и ответственного процесса не даёт своевременной реакции.

Frontend-телеметрия не должна содержать пароли, access/refresh tokens, полные cookie, заголовки авторизации и лишние персональные данные. URL и тело запроса перед отправкой очищают. Для корреляции используют безопасные request/trace identifiers, версию релиза, route, тип ошибки и ограниченный технический контекст.

## A10: исключение не должно открывать доступ

Система должна переходить в определённое безопасное состояние, если зависимость недоступна, проверка прав завершилась ошибкой или ответ имеет неизвестный формат.

Например, если endpoint проверки прав не ответил, приложение не должно считать пользователя администратором «чтобы интерфейс продолжил работать». Это fail-open — отказ, при котором доступ становится шире. Безопаснее заблокировать защищённое действие, показать восстанавливаемое состояние и записать диагностический сигнал без секретов.

Повтор запроса также является частью обработки исключений. Автоматическое повторение `POST /payment` без контракта идемпотентности способно провести операцию дважды. UI должен различать «сервер не получил запрос», «операция выполняется» и «ответ потерян после успешной операции».

## Практическая проверка frontend-функции

Перед release полезно пройти по потоку данных и границам доверия:

1. Какие данные и операции являются чувствительными?
2. Кто проверяет authentication и authorization для каждого API action?
3. Откуда приходят недоверенные данные и в какие HTML/URL/code sinks они попадают?
4. Какие cookie, токены и персональные данные доступны скриптам, логам и аналитике?
5. Какие сторонние пакеты и скрипты выполняются и как контролируется их обновление?
6. Что произойдёт при timeout, ответе неверного формата, повторном запросе и частичном отказе?
7. Какие события позволят обнаружить атаку, не записывая секреты?

Для систематической проверки одного Top 10 недостаточно. OWASP ASVS даёт более подробные verification requirements, а threat modeling связывает требования с конкретной архитектурой продукта.

## Ключевые уточнения

- OWASP Top 10 перечисляет широкие категории рисков, а не десять конкретных багов и не полный security checklist.
- Название версии важно: карточка опирается на OWASP Top 10:2025.
- Клиентские проверки управляют UX; серверные проверки защищают ресурсы и операции.
- CORS не является контролем доступа, CSP не заменяет sanitization, а HTTPS не делает данные безопасными после доставки endpoint.
- Lockfile и dependency scanner снижают supply-chain risk, но не доказывают безопасность исполняемого пакета.
- Безопасная обработка ошибок сохраняет ограничения доступа и учитывает, можно ли повторять операцию.
