# Аудит и улучшение правил страниц конспекта

## Контекст

В `_templates/note-rules/` добавлен новый автономный комплект правил уровней 1–5. Он задаёт целевую модель для:

- постепенной переработки существующих 262 заметок;
- создания новых заметок по темам, которых сейчас не хватает;
- проверки и редактирования уже переведённых на новую модель страниц.

Новый комплект сравнивается с актуальным комплектом правил карточек из проекта `01-int-cards`. Старые правила используются только как источник проверенных уточнений процесса. Карточечная модель вопроса, основного ответа и дополнительных вопросов не переносится в конспект.

## Принятые решения

### Целевая содержательная модель

Целевая страница темы сохраняет новую структуру:

1. `Быстрый ответ`;
2. `Карта темы`;
3. один или несколько тематических H2 с необязательными H3;
4. необязательная `Мини-задача`;
5. обязательный блок `Где применяется во frontend`;
6. обязательный блок `Ключевые уточнения`;
7. `Связанные темы`;
8. `Источники`.

Свободное тематическое раскрытие заменяет карточечную модель главного и дополнительных вопросов. Примеры могут быть кодом, псевдокодом, схемой, таблицей, последовательностью или практическим сценарием.

### Репозиторная механика

Сохраняется действующее устройство `03-int-notes`:

- имена заметок не получают числовые префиксы;
- порядок заметок определяется списком ссылок в `notes/<Раздел>/README.md`;
- навигация использует маркеры `NOTE-NAV-TOP:*` и `NOTE-NAV-BOTTOM:*`;
- навигационные блоки обслуживает `scripts/generate_navigation.py`;
- репозиторные инварианты проверяет `scripts/check_notes.py`.

Правила страницы не должны вручную редактировать автоматически управляемую навигацию.

### Граница миграции

Новая структура является целевым стандартом, но не объявляет все текущие 262 заметки уже соответствующими ему.

Правила применяются полностью к:

- новой заметке перед её включением в репозиторий;
- существующей заметке, которую явно взяли в миграцию;
- заметке, уже переведённой на целевой стандарт.

Остальные существующие заметки продолжают проходить текущие репозиторные проверки до плановой миграции. Автоматическая проверка не должна начать требовать новые содержательные блоки сразу от всего корпуса.

## Результат сравнения со старыми правилами

### Уже присутствующие аспекты

Новые правила уже содержат следующие требования, поэтому они не добавляются повторно:

- единый цикл `1 → 2 → 3 → 4 → 5 → 1`;
- разделение `BUILD`, `VALIDATE`, `ANALYZE` и `EDIT`;
- работа с одной текущей версией;
- `NOT CHECKED`, `UNRESOLVED`, `REPO PASS` и `REPO FAIL`;
- пять критериев качества: техническая корректность, полнота, понятность, перегруженность и избыточность;
- приоритет первичных источников и запрет выдумывать данные;
- минимально достаточное редактирование;
- сохранение полезного смысла;
- финальная проверка на регрессии;
- создание первоначального содержательного черновика через уровень 3 `BUILD`.

### Новые сильные стороны

Новый комплект содержит полезные правила, отсутствующие в старом комплекте:

- приоритет интерпретации нормативных формулировок;
- инвариант ответственности уровней;
- минимальный цикл решения на каждом уровне;
- одного владельца для одной причины нарушения;
- запрет превращать примеры и рекомендации в скрытые механические нормы;
- явную границу между самодостаточностью правил и необходимостью внешней проверки фактов.

Эти положения сохраняются без ослабления.

### Полезные уточнения старого комплекта

В существующие разделы новых правил точечно адаптируются только уточнения, которые устраняют реальную неоднозначность:

1. Понятное и грамматически связное название темы с конкретным основанием для `FAIL`.
2. Ровно один структурный H1; H4–H6 запрещены для страницы темы; fenced code blocks не участвуют в проверке заголовков.
3. Однозначное разделение причин между уровнем 3, полнотой, понятностью и перегруженностью.
4. Доказательность `FAIL` понятности: конкретный фрагмент, недостающая связь, её значимость и создаваемое препятствие.
5. Фактическая проверка существенных изменяемых технических утверждений по применимому актуальному первичному источнику.
6. Блокирующий `NOT CHECKED`, если такое утверждение нельзя достоверно проверить.
7. Временная карта смысла для крупной правки, создающей риск потери самостоятельного полезного аспекта.
8. Различное представление результата для репозиторного файла и отдельно переданного Markdown-текста.

Уточнения встраиваются в существующие нормы. Дублирующие критерии и параллельные процессы не создаются.

## Исправляемые ошибки адаптации

В `01-file-structure.md` исправляются:

- обязательная двухзначная нумерация файлов;
- все остаточные маркеры `CARD-NAV-*`;
- упоминания номера файла как обязательной части структуры.

Дополнительно комплект согласуется с репозиторием:

- локальный минимум связанных тем устанавливается равным двум, как требует `scripts/check_notes.py`;
- входящая тематическая ссылка остаётся отдельным репозиторным инвариантом;
- запрет H4–H6 согласуется с действующей проверкой;
- команды обслуживания навигации и проверки указываются только в репозиторных правилах.

## Создание новой заметки и поиск пробелов

Канонический цикл уровней уже описывает первичную сборку после выбора темы. Ему добавляется отдельный предварительный маршрут, который не является шестым уровнем.

Маршрут поддерживает два явных входа:

1. пользователь задал конкретную тему;
2. пользователь поручил найти недостающие темы в определённой области репозитория.

До создания файла маршрут должен:

- проверить точные и содержательные дубли;
- определить пересечения и самостоятельную границу темы;
- выбрать раздел;
- определить место новой ссылки в `README.md` раздела;
- найти не менее двух обоснованных исходящих связей и кандидата для входящей связи;
- исследовать центральную модель и изменяемые утверждения по первичным источникам;
- сформировать временный смысловой план;
- передать первую заполненную версию каноническому циклу `00-workflow.md`.

Поиск тематических пробелов выполняется только в явно заданной пользователем области. Он не разрешает бесконечно расширять весь конспект и не создаёт заметку без подтверждённой самостоятельной учебной функции.

## Организация файлов правил

### Канонический комплект страницы

В `_templates/note-rules/` остаются каноническими:

- `00-workflow.md`;
- `01-file-structure.md`;
- `02-block-structure.md`;
- `03-content-distribution.md`;
- `04-content-quality.md`;
- `05-editing.md`.

Добавляются:

- `README.md` — короткие маршруты и ссылки без новых нормативных требований;
- `new-note-workflow.md` — предварительная проверка темы, поиск пробелов, исследование и первичная сборка.

### Репозиторные правила

Старый `_templates/GitHub Note Style.md` удаляется как конкурирующий содержательный шаблон.

Вместо него создаётся `_templates/repository-rules.md`, который определяет только:

- область ответственности `note-rules/`;
- границу постепенной миграции;
- правила главной страницы и страниц разделов;
- автоматически управляемую навигацию;
- репозиторные инварианты;
- команды `generate_navigation.py` и `check_notes.py`.

Он не дублирует целевую структуру страницы темы.

## Изменения автоматических проверок

На этом этапе `scripts/check_notes.py` не начинает требовать новую содержательную структуру от всех 262 файлов.

Проверка сохраняет текущие корпусные инварианты. Правила и скрипт согласуются по уже действующим требованиям:

- ровно один H1;
- отсутствие H4–H6;
- минимум две исходящие связанные темы;
- минимум одна входящая тематическая ссылка;
- существование локальных целей;
- корректность служебной навигации.

Отдельная массовая проверка целевой структуры будет добавляться вместе с планом миграции либо после появления явного признака, отличающего мигрированные заметки от старых.

## Проверка результата

После редактирования выполняются:

1. проверка всех внутренних ссылок комплекта правил;
2. поиск остаточных `CARD-NAV-*` и требований числовых префиксов;
3. поиск конфликтующих старых названий блоков вне исторического описания отличий;
4. проверка согласованности терминов `страница темы`, `заметка`, `уровень`, `REPO` и `NOT CHECKED`;
5. сопоставление требований с `generate_navigation.py` и `check_notes.py`;
6. `python scripts/generate_navigation.py --check`;
7. `python scripts/check_notes.py`;
8. `git diff --check`.

## Вне текущего объёма

В эту работу не входят:

- массовая переработка 262 заметок;
- выбор первой партии заметок для миграции;
- создание недостающих тематических страниц;
- изменение содержимого существующих заметок;
- включение целевой структуры в обязательную корпусную CI-проверку до определения миграционного признака.
